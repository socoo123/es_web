1. 先分清：索引不是一条景点

本课的索引叫 tut-f01-attractions，它组织一组景点文档及其字段规则。每条景点是一份 JSON 文档，用 _id 定位；settings 描述主分片/副本等索引配置，mappings 描述字段如何索引。可以把它理解为搜索数据的容器，但不要据此把它等同于关系数据库表。

旅游网站的业务数据库以后可以产生这些文档。现在使用固定文件样本即可把搜索学明白：索引先创建好，再写文档，然后让新搜索视图看到写入，最后执行查询。无需先搭数据库或网站。

请求作用
PUT /tut-f01-attractions创建索引，配置 settings / mappings
PUT /tut-f01-attractions/_doc/a-hz-xihu写入或完整覆盖这个 ID 的文档
POST /tut-f01-attractions/_refresh让此前写入对新搜索可见
POST /tut-f01-attractions/_search在该索引执行查询，返回命中

2. C01：启动自己的 ES 节点

准备 Docker Engine/Desktop、Compose v2+、Bash 和 curl 7.76+。Windows 可使用 WSL2；本课实际验收环境是 macOS arm64 + Docker。官方 Docker 指南要求 Docker Desktop 至少分配 4GB 内存。这里给单个教学容器 1GB 上限、512MB 堆，只用一条景点样本。

完整配置在 infra/single-node/compose.yaml。宿主端口 19200 映射到容器 HTTP 9200，不发布 transport 9300；Compose 项目和数据卷也与源码篇分离。

name: es-framework-single
services:
  es:
    image: docker.elastic.co/elasticsearch/elasticsearch:9.4.0
    environment:
      cluster.name: travel-search-lab
      node.name: travel-search-01
      discovery.type: single-node
      xpack.security.enabled: "false"
      xpack.ml.enabled: "false"
      ES_JAVA_OPTS: -Xms512m -Xmx512m
    ports:
      - "127.0.0.1:19200:9200"
    mem_limit: 1g
    volumes:
      - es-data:/usr/share/elasticsearch/data
volumes:
  es-data:

discovery.type=single-node 用于本课单节点；xpack.security.enabled=false 是显式选择，和官方默认的安全启动流程不同。端口只绑定本机，curl 不需要 CORS。es-data 挂在 ES 数据目录，停止/重启保留数据。ES 使用镜像自带 JVM，和 F02 的应用 JDK 25 是两回事。

cd projects/travel-search
docker compose -f infra/single-node/compose.yaml up -d
bash infra/single-node/wait.sh
export ES_URL=http://127.0.0.1:19200

后面的命令都在工程根目录执行。等待脚本最多探测 180 秒；它只确认 HTTP 入口可访问。首次拉镜像需要网络，失败时先区分拉取失败、容器退出与节点未就绪。

curl --fail-with-body -sS "$ES_URL/?pretty"
curl --fail-with-body -sS \
  "$ES_URL/_cat/nodes?format=json&h=name,ip,node.role,master"
curl --fail-with-body -sS "$ES_URL/_cluster/health?pretty"

GET / 返回版本与集群标识，不返回节点角色；角色由第二条 _cat/nodes 请求观察。第三条健康请求覆盖整个集群。

{
  "name": "travel-search-01",
  "cluster_name": "travel-search-lab",
  "version": {
    "number": "9.4.0"
  },
  "nodes": [
    {
      "name": "travel-search-01",
      "ip": "172.19.0.2",
      "node.role": "cdfhilmrstw",
      "master": "*"
    }
  ]
}

master: "*" 表示当前主节点，角色缩写不是业务字段。本实验没有单独配置角色列表。整个集群 green 只说明分配健康，不能证明景点已导入；集群还可能存在系统索引，主分片总数不等于本课景点索引的主分片数。后面把健康检查限定到本课索引。

端口连不上时看什么？

先看服务状态再看日志。若端口被占用，Compose 会报绑定失败；不要为本课停止已有业务服务。若容器退出 137，还需结合 OOMKilled / 日志判断是否内存不足。Linux 内核条件按日志和官方 Docker 运行要求核对。

docker info
docker compose -f infra/single-node/compose.yaml ps -a
docker compose -f infra/single-node/compose.yaml logs --tail=100 es

3. 创建索引：先声明字段如何搜索

下面的 index.json 是请求体。名称要参与全文检索，设为 text 并显式采用 standard；业务 ID 和城市编码设为 keyword；门票用整数分，0 是本课样本值，不是景区价格承诺。字段类型和中文分析链会在 F04 / F11–F14 继续对照。

{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 0
  },
  "mappings": {
    "properties": {
      "attraction_id": { "type": "keyword" },
      "name": { "type": "text", "analyzer": "standard" },
      "city_code": { "type": "keyword" },
      "ticket_price_fen": { "type": "integer" }
    }
  }
}

索引有一个主分片、零副本。单节点不能把同一主分片的副本放回自己，因此本课不要求副本；零副本也意味着没有另一份在线副本提供冗余。这里的配置只为小样本实验服务。

curl --fail-with-body -sS -X PUT \
  "$ES_URL/tut-f01-attractions?pretty" \
  -H 'Content-Type: application/json' \
  --data-binary @search/f01/index.json

curl --fail-with-body -sS \
  "$ES_URL/_cluster/health/tut-f01-attractions?wait_for_status=green&timeout=30s&pretty"

--data-binary @文件 把文件内容作为请求体发送；Content-Type 声明 JSON。--fail-with-body 让 HTTP 4xx/5xx 保留错误正文并返回非零退出码。URL 要加双引号，里面的 & 才不会被 shell 当作后台执行符。

{
  "create": {
    "acknowledged": true,
    "shards_acknowledged": true,
    "index": "tut-f01-attractions"
  },
  "index_health": {
    "status": "green",
    "timed_out": false,
    "active_primary_shards": 1,
    "active_shards": 1
  }
}

acknowledged 表示创建操作被确认；shards_acknowledged 表示等待的分片启动条件达成。随后请求显式等待本课索引 green，同时检查 timed_out=false、活动主分片和活动总分片均为 1。此时创建的是空索引，尚未写入西湖。

4. 写入景点：ID 放在 URL，字段放在 JSON

固定业务 ID 为 a-hz-xihu。JSON 中的 attraction_id 是普通字段；URL 最后一段才设置 ES 的 _id。两者保持相同是应用约定，ES 不会自动替你同步。

{
  "attraction_id": "a-hz-xihu",
  "name": "杭州西湖",
  "city_code": "HZ",
  "ticket_price_fen": 0
}
curl --fail-with-body -sS -X PUT \
  "$ES_URL/tut-f01-attractions/_doc/a-hz-xihu?pretty" \
  -H 'Content-Type: application/json' \
  --data-binary @data/f01/xihu.json
{
  "_index": "tut-f01-attractions",
  "_id": "a-hz-xihu",
  "_version": 1,
  "result": "created"
}

result=created 表示这个 ID 首次写入；_version=1 是文档版本。没有把响应中的成功理解成“已经可被 search 看见”：写入确认和搜索视图可见是两个条件。下面显式刷新，不依赖你复制命令时恰好跨过自动刷新周期。

5. 显式 refresh，然后按“西湖”搜索

查询 JSON 不是景点数据。它告诉 ES：对 name 使用 match 查询，搜索文本为“西湖”；operator=and 要求分析后形成的查询项共同满足。size=10 限制返回命中数；track_total_hits=true 要求准确统计本次匹配总数，两者职责不同。

{
  "size": 10,
  "track_total_hits": true,
  "query": {
    "match": {
      "name": {
        "query": "西湖",
        "operator": "and"
      }
    }
  }
}
curl --fail-with-body -sS -X POST \
  "$ES_URL/tut-f01-attractions/_refresh?pretty"

curl --fail-with-body -sS -X POST \
  "$ES_URL/tut-f01-attractions/_search?pretty" \
  -H 'Content-Type: application/json' \
  --data-binary @search/f01/search-xihu.json

第一条请求只刷新 tut-f01-attractions；第二条只在这个索引搜索。refresh API用于建立搜索可见性，本课为了观察明确调用一次；不要在实际批量写入时为每条文档强制刷新。它也不等同于数据备份。

{
  "took": 41,
  "timed_out": false,
  "_shards": {
    "total": 1,
    "successful": 1,
    "skipped": 0,
    "failed": 0
  },
  "hits": {
    "total": {
      "value": 1,
      "relation": "eq"
    },
    "max_score": 0.5753642,
    "hits": [
      {
        "_index": "tut-f01-attractions",
        "_id": "a-hz-xihu",
        "_score": 0.5753642,
        "_source": {
          "attraction_id": "a-hz-xihu",
          "name": "杭州西湖",
          "city_code": "HZ",
          "ticket_price_fen": 0
        }
      }
    ]
  }
}

先按三处核对：timed_out=false 且 _shards.failed=0；hits.total 是 value=1 / relation=eq；命中 ID 为 a-hz-xihu，_source 与固定样本一致。took 和 _score 是本次运行的测量结果，不作为跨环境固定断言。只有一个文档时，也不能用这个分数证明排序质量。

match会分析查询文本，再与字段中已索引的项匹配；它不是 SQL 的子串 LIKE。本课 standard 足以完成这条样本的命中，不代表它已具备中文词典、旅游别名或同义词能力。分词对照与评分调优在后续专题里用更多样本检验。

为什么不能用“等一秒”保证搜到？

自动 refresh 是调度行为，实际可见时间还受配置、索引是否被搜索和运行负载影响。第一课不测这个延迟，直接 refresh 消除观察竞态。F03 会关掉自动 refresh，严格对照 GET 已可见和 search 未可见，再刷新验证。

6. mapping、count、GET 分别回答什么？

curl --fail-with-body -sS "$ES_URL/tut-f01-attractions/_mapping?pretty"
curl --fail-with-body -sS "$ES_URL/tut-f01-attractions/_count?pretty"
curl --fail-with-body -sS "$ES_URL/tut-f01-attractions/_doc/a-hz-xihu?pretty"
请求核对点
GET /{index}/_mapping实际字段定义与 index.json 一致；不是景点内容
GET /{index}/_count刷新后搜索视图中有 1 条文档；不是请求次数
GET /{index}/_doc/a-hz-xihu按确定 ID 读文档，found=true，_source 为西湖样本

GET 按 ID 读取，search 按条件检索；即使返回同一景点，也不是同一条读取路径。本课已经刷新后核对，因此不借这里的结果推断未刷新时也相同。完整实际响应保存在验收记录。

7. C02 / C03：两个错误对照

C02：错误端口与未启动节点

先保留 C01 的索引。下面访问一个未监听的端口，再停止本工程 ES 访问正确端口。它们都在网络连接阶段失败，本次实测 curl exit=7，没有得到 ES 的 HTTP 404。若 19299 已有服务，选择另一空闲端口再做对照。

curl -sS --connect-timeout 2 --max-time 5 http://127.0.0.1:19299/
echo "$?"  # 本次连接拒绝为 7；只在上一条 curl 后立即查看

docker compose -f infra/single-node/compose.yaml stop es
curl -sS --connect-timeout 2 --max-time 5 "$ES_URL/"
echo "$?"

docker compose -f infra/single-node/compose.yaml start es
bash infra/single-node/wait.sh
curl --fail-with-body -sS --retry 30 --retry-all-errors --retry-delay 1 \
  --max-time 35 \
  "$ES_URL/_cluster/health/tut-f01-attractions?wait_for_status=green&timeout=30s&pretty"
bash labs/f01/04-search.sh

恢复后，数据卷保留了索引与景点。等待 HTTP 之后还要等待本课索引健康：本轮第一次实测中，HTTP 先可访问，紧接着刷新收到短暂的 index_not_found_exception，随后索引恢复；因此健康请求允许临时 404 重试。核对最终 timed_out=false / green 后，再搜索应仍命中同一 ID。

也可运行 bash labs/f01/08-connection-errors.sh，它额外用 EXIT trap 在中断时尝试恢复自己的 ES 服务。网络超时可能是 exit 28，HTTP 错误在启用 fail 选项后是 exit 22；按实际错误定位，不把所有失败都称“ES 没启动”。

C03：重复建索引 ≠ 在索引里写文档

再次发送相同创建请求。这个请求的资源还是索引，不会因为 JSON 相同就静默成功。

# 这里故意不加 --fail-with-body：保留预期 400 的正文供观察。
curl -sS -X PUT "$ES_URL/tut-f01-attractions?pretty" \
  -H 'Content-Type: application/json' \
  --data-binary @search/f01/index.json
{
  "error": {
    "type": "resource_already_exists_exception",
    "reason": "index [tut-f01-attractions/KpVFkwUSRf2sRbRCNEjLuw] already exists"
  },
  "status": 400
}

这里故意省略 fail 选项，好让你观察错误正文。curl 默认可能退出 0，但 HTTP 是 400，error.type=resource_already_exists_exception。不要只看 shell 退出码就判断请求成功。

现在重复发送 PUT /{index}/_doc/a-hz-xihu，再次写相同的完整文档：

# 相同索引、相同 _id、相同完整文档；不会多出第二条景点。
bash labs/f01/03-write.sh
curl --fail-with-body -sS -X POST "$ES_URL/tut-f01-attractions/_refresh?pretty"
curl --fail-with-body -sS "$ES_URL/tut-f01-attractions/_count?pretty"
curl --fail-with-body -sS "$ES_URL/tut-f01-attractions/_doc/a-hz-xihu?pretty"
{
  "write": {
    "_id": "a-hz-xihu",
    "_version": 2,
    "result": "updated"
  },
  "count_after_refresh": 1
}

同一个索引里的同一个 _id 被完整覆盖，result=updated、版本变为 2，刷新后文档数仍为 1。再次重复写，版本还会增长；改成另一个 ID 则是另一条文档。这个 PUT 不是局部字段更新，后续 F03 再看 update 和并发冲突。

下面只删除 tut-f01-attractions 及其文档，保留本工程容器和数据卷。不要用通配符删除索引。

# 只删除本课索引和里面的景点。不使用通配符，不删除数据卷。

练习：根据输出判断

1. 创建索引成功，能否说明“西湖”已经能被搜到？

不能。创建索引只建立配置和字段规则，还需写入景点文档；写入后要建立新搜索视图并执行查询。索引健康也不等于业务文档已导入。

2. 相同 JSON 写两次，一定只有一条文档吗？

要看索引与 _id。本课在同一索引使用相同 ID 完整覆盖，计数保持 1、版本增长。改用另一个 ID，即使 JSON 一样也会新增文档。JSON 中的 attraction_id 不自动决定 ES _id。

3. curl exit 7、HTTP 400、短暂 HTTP 404 应怎样区分？

exit 7 是连接阶段失败；本课重复建索引的 HTTP 400 是 ES 已收到请求并拒绝创建；重启后索引恢复前短暂 404 是 HTTP 已可访问但指定索引暂不可用。先读实际错误，再查端口/日志或等待对应资源。

本课陷阱

创建请求与写入请求都用 PUT，含义取决于路径。索引路径重复创建会失败；带 /_doc/{id} 的路径写入该 ID，重复写入会完整覆盖。
整个集群 green，不代表景点查询正确。本课用限定索引的健康、实际搜索 ID、mapping、count 和 GET 分别核对。
写入成功与 HTTP 恢复都不是“搜索一定可用”的充分条件。写后显式 refresh；停机恢复后等待本课索引，再搜索。
