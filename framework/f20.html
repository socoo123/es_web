1. 文本相关之后，还有“值得推荐吗”

F19给名称、短语与整名证据分配了权重，却没有区分两份同样写着“西湖 夜游”的资料。点评反映已体验者的评价，条数提供样本规模，访问热度表示近期注意力；三者不是同一件事。一次访问未必是购买，更不是好评。把它们直接当成同一种分数，会让大数量级的访问量吞掉文本证据。

Elasticsearch负责根据已索引的字段计算查询分数；它不会自动审核点评、识别刷量，也不会因为字段名叫quality就知道可信度。业务侧先形成口径明确的快照，再写入ES。这里将质量信号定义为经点评条数平滑后的均分，将热度信号定义为固定30天内去重访问量；二者都只是排序假设。城市、开放状态、币种和预算仍是必须满足的条件。

先分清两类问题：文本门槛决定谁能入场，数值奖励决定入场者怎样排。主输入“西湖 夜游”在简介中按OR匹配；只含“西湖”的展厅因此是弱相关候选，完全不含两词的山林则不是候选。提高奖励不会替游客补出未表达的活动意图。

3. 5分一条，为什么不等于稳定的满分质量

均分只回答已收到的点评平均多少分。若直接用R/5奖励，5分1评必然胜过4.8分千评，却没有表达我们对小样本不稳定的顾虑。本课先引入一份公开的先验：把每个景点视为先有20条平均4分的参考点评，再与真实有效点评合并，得到Q=(vR+20×4)/(v+20)。这叫收缩或平滑：样本少就更靠近4，样本多才更接近自己的均分。

因此5分1评得到85/21≈4.047619；4.8分1000评得到4880/1020≈4.784314；4.8分20评得到176/40=4.4。0条时分子80、分母20，Q=4，不需要伪造一个review_avg=0。m=20与C=4是本课指定假设，既不是ES默认，也不是从真实网站估计出的参数；Q不是置信区间或“有多大概率值得去”。相同均分下有更多点评会更靠近该均分，并非点评数越多质量必然越高。

Q在写入前计算一次，查询只读quality_score；review_count不会再直接加一次，避免把条数奖励叠两遍。ES没有因为看见两字段就自动运行这个公式。若审核后删掉点评，应由来源重新计算同版本Q与条数后一起更新，不能只减条数留下旧Q。本课用固定快照隔离评分机制，持续更新在后续数据链路学习。

6. f20-c02：热度的量纲会吞掉文本

执行02，依次看text、raw、quality、compressed、bounded与六次单份解释。raw把H直接加给文本；展厅H=10^18，超过游船的文本差距。它冲到第一，但无关山林即使H=10^20仍不进入，因为基底query没有匹配。数值奖励不会绕过closed、异城、超预算过滤。

bash labs/f20/02-popularity.sh

热度是访问次数，文本分和Q/5则在更小尺度。简单换一个weight可能适配今天的数据，却会被明天的极值再次突破。compressed使用自然对数ln(1+H)再乘0.15：0映射0，10映射约2.398，10^18映射约41.447。增长被压缩，却仍无有限上界，所以不能把“对数”称为封顶。

8. 缺值、已知0与非法函数要分别处理

field_value_factor先用实际字段值，缺失时才用missing，再乘factor，最后应用modifier；weight在外层。quality缺失用4，H缺失用0，因此missing与已知0热度得到同一奖励，但原文仍保留未知和已知的区别。missing不是补写文档，也不替换已有0。显式factor=0.1时热度函数是0.15ln(1+0.1H)，不是0.015ln(1+H)。03有真实公式核对。

ln(0)无效；本课用hz-zero单独触发ln的400，再切回ln1p恢复。删除missing参数后，对hz-missing评分同样400；恢复missing=0后成功。函数要求非负得分，不能依赖max_boost修好负数或非法对数，因为函数先计算。数值字段本身允许多值，field_value_factor只取其中第一个数值，本课来源契约只写单值，未演示用数组代表点评集合。

9. f20-c03：rank_feature是特征查询，也影响候选

另一种候选方案是把正向静态Q同时写入quality_rank，mapping为rank_feature。它要求单值、严格正数；普通double字段不能直接被rank_feature查询替代。03真实写入0、负数、多值均400，失败资料未留下。这个字段适合评分特征，不支持普通排序或聚合；需要原始数值展示、排序或统计时，保留quality_score等普通字段。它没有自动提供上游来源与审核。

rank模式把文本放must、特征放should，显式minimum_should_match=0。饱和函数设置pivot=4、boost=1，特征分=S/(S+4)，到S=4时为0.5，继续增大逐渐靠近1。本例七份候选保持不变，次序为steady/huge/fresh/small/zero/hot/missing。missing没有quality_rank，不获得特征奖励，但仍凭文本保留。

S是索引编码后的特征值，不保证等于_source的double。rank_feature保留9位有效精度，存在约0.4%的相对误差；例如山林原Q≈4.899820036，解释中S=4.890625，特征分≈0.55008787。断言用真实S核对公式，不能要求它与quality的double加分完全一致。这里显式pivot避免默认估计受语料影响；并未测试性能，track_total_hits=true也没有验证官方文档所述的跳过非竞争命中收益。

若去掉文本，只要求特征作must，即rank-only，山林因Q高排第一，missing因为没特征退出。它仍有城市/开放/预算过滤，但回答的已是“有质量特征的景点”，不再是“西湖夜游”。function_score只给基底query候选评分；rank_feature是一个查询子句，放在哪里会改变bool门槛。两者不能只按公式外观互换。

版本依据与目标源码入口

固定ES9.4.0源码：FieldValueFactorFunction → score核对缺值、factor与modifier顺序；FunctionScoreQuery → computeScore核对函数聚合；CombineFunction.SUM → combine/explain核对先封顶再加文本；RankFeatureFieldMapper与RankFeatureQueryBuilder核对字段/查询边界。另参阅官方函数文档、特征类型和特征查询；固定来源收据分列源码与当前文档。

10. REST语义先确定，再看关键Java

沿用Boot4.0.8、Temurin25.0.4.1+1、官方Java API与Rest5 Client9.4.8、Wrapper3.3.4/Maven3.9.11；服务连ES9.4.0，ES bundled JVM独立记录。服务端固定索引、字段、八种规则和可解释ID，浏览器不提交任意DSL。输入约束、完整规则构造如下；共同的服务样板见完整文件。

package dev.esweb.travel;

import jakarta.validation.constraints.*;

public record SignalInput(
        @NotBlank @Size(max = 60) String q,
        @NotNull @Pattern(regexp = "HZ|SZ") String cityCode,
        @NotNull @Min(0) @Max(100000000) Integer maxPriceFen,
        @NotNull @Pattern(regexp = "text|raw|average|quality|compressed|bounded|rank|rank-only") String mode,
        @NotNull @Pattern(regexp = "hz-(small|steady|fresh|zero|missing|huge|hot|noise|closed|expensive)|sz-steady") String explainId) {
}
    public SearchRequest request(SignalInput input) {
        Query text = Query.of(q -> q.match(m -> m.field("description").query(input.q()).operator(Operator.Or)));
        Query feature = Query.of(q -> q.rankFeature(r -> r.field("quality_rank")
                .saturation(v -> v.pivot(4.0f)).boost(1.0f)));
        var bool = new BoolQuery.Builder()
                .filter(f -> f.term(t -> t.field("status").value("open")))
                .filter(f -> f.term(t -> t.field("currency").value("CNY")))
                .filter(f -> f.range(r -> r.number(n -> n.field("ticket_price_fen")
                        .gte(0.0).lte(input.maxPriceFen().doubleValue()))))
                .filter(f -> f.term(t -> t.field("city_code").value(input.cityCode())));
        bool.must(input.mode().equals("rank-only") ? feature : text);
        if (input.mode().equals("rank")) bool.should(feature).minimumShouldMatch("0");
        Query base = Query.of(q -> q.bool(bool.build()));
        Query scored = base;
        if (!List.of("text", "rank", "rank-only").contains(input.mode())) {
            FunctionScore quality = FunctionScore.of(f -> f.weight(1.0)
                    .fieldValueFactor(v -> v.field("quality_score").factor(0.2)
                            .modifier(FieldValueFactorModifier.None).missing(4.0)));
            FunctionScore heat = FunctionScore.of(f -> f.weight(0.15)
                    .fieldValueFactor(v -> v.field("hot_30d").factor(1.0)
                            .modifier(FieldValueFactorModifier.Ln1p).missing(0.0)));
            List<FunctionScore> functions = switch (input.mode()) {
                case "raw" -> List.of(FunctionScore.of(f -> f.weight(1.0).fieldValueFactor(v ->
                        v.field("hot_30d").factor(1.0).modifier(FieldValueFactorModifier.None).missing(0.0))));
                case "average" -> List.of(FunctionScore.of(f -> f.weight(1.0).fieldValueFactor(v ->
                        v.field("review_avg").factor(0.2).modifier(FieldValueFactorModifier.None).missing(4.0))));
                case "quality" -> List.of(quality);
                default -> List.of(quality, heat);
            };
            double cap = input.mode().equals("bounded") ? 1.5 : 3.4028235e38;
            scored = Query.of(q -> q.functionScore(f -> f.query(base).functions(functions)
                    .scoreMode(FunctionScoreMode.Sum).boostMode(FunctionBoostMode.Sum).maxBoost(cap)));
        }
        Query finalQuery = scored;
        return SearchRequest.of(s -> s.index(INDEX).size(20)
                .trackTotalHits(t -> t.enabled(true)).explain(true)
                .query(finalQuery)
                .sort(srt -> srt.score(sco -> sco.order(SortOrder.Desc)))
                .sort(srt -> srt.field(f -> f.field("attraction_id").order(SortOrder.Asc))));
    }

所有卡片返回点评、Q、H与完整解释；缺失信号允许null，不把它当数据损坏。身份、名称、简介、硬条件、得分、sort与解释则必须完整。搜索超时/分片失败/字段不完整拒绝为502；输入400、ES拒绝502、连接不可用503，不把失败展示成空结果。搜索与单份解释复用整个query，包括过滤；两次独立请求不构成并发更新下的原子快照。

    public Result search(SignalInput input) throws IOException {
        var request = request(input);
        var response = client.search(request, SignalAttraction.class);
        if (response.timedOut() || response.shards().failed().longValue() != 0
                || response.hits().total() == null || !response.hits().total().relation().jsonValue().equals("eq"))
            throw new AttractionSearchService.IncompleteSearchException();
        var cards = response.hits().hits().stream().map(hit -> {
            var s = hit.source();
            if (s == null || !hit.id().equals(s.attractionId()) || s.name() == null
                    || s.description() == null || !input.cityCode().equals(s.cityCode())
                    || !"open".equals(s.status()) || !"CNY".equals(s.currency())
                    || s.ticketPriceFen() == null || s.ticketPriceFen() < 0
                    || s.ticketPriceFen() > input.maxPriceFen() || hit.score() == null
                    || hit.explanation() == null || hit.sort().size() != 2)
                throw new AttractionSearchService.IncompleteSearchException();
            return new Card(hit.id(), s.name(), s.description(), s.cityCode(), s.ticketPriceFen(),
                    s.currency(), s.status(), s.reviewAvg(), s.reviewCount(), s.qualityScore(), s.hot30d(), hit.score(), hit.sort().stream().map(v -> (Object) v._get()).toList(),
                    tree(hit.explanation()));
        }).toList();
        // Both calls use the same complete query, including filters. No writes occur in this observer.
        // They are separate requests, not one atomic snapshot under concurrent updates.
        var explainRequest = ExplainRequest.of(e -> e.index(INDEX).id(input.explainId()).query(request.query()));
        var explained = client.explain(explainRequest, SignalAttraction.class);
        if (!INDEX.equals(explained.index()) || !input.explainId().equals(explained.id())
                || explained.explanation() == null)
            throw new AttractionSearchService.IncompleteSearchException();
        return new Result(response.hits().total().value(), response.hits().total().relation().jsonValue(),
                response.took(), input, tree(request), tree(response),
                "/" + INDEX + "/_explain/" + input.explainId(), tree(explainRequest), tree(explained), cards);
    }

能力检查：先预测，再展开

把1条5分复制成1000条5分，Q会怎样？

从85/21约4.048靠近5，变为5080/1020约4.980；并不意味着允许复制真实点评。上游必须先去重。

为什么raw里山林没有因10^20热度进场？

function_score包住的基底query必须先匹配西湖或夜游，并满足硬条件。热度只给这些候选评分。rank-only去掉文本门槛才会让山林进入。

ln1p之后极值还会压倒文本吗？

会。本例compressed展厅仍第一；ln1p增长变慢但无有限上界，需要结合权重、封顶和真实查询集验证。

max_boost=1.5，为什么结果还能1.912？

它限制函数合并值F，boost_mode=sum再加文本B。最终B+min(F,1.5)，并未把最终分限制到1.5。

missing=4是否把文档中的0改为4？

不会。missing只在字段缺失时替代，之后还经过factor/modifier。它不写回_source，也不改变已存在0。已知零热度和缺失热度可同奖励而来源含义不同。

rank_feature的S为什么不是原Q，缺特征会不会被排除？

S经过特征编码，约0.4%相对精度误差；按解释中的S计算饱和。文本must、特征should时缺特征仅不加分；特征单独must则会被排除。

封顶后展厅仍高于无信号游船，是否说明参数已成功？

只能说明极值作用受限，不能据此宣布质量改善。它仍是已知坏案例；还要标注意图、评估不同输入和退步，不能靠一条结果选生产规则。

实际陷阱

信号叫质量，不代表已经可信。ES只读字段；审核、去重、窗口、缺失状态和同版本重算属于来源契约。平滑先验不能代替反作弊或统计评估。
压缩与封顶限制的对象不同。ln1p没有有限上界；max_boost限制合并函数值，不能修复非法函数，也不保证文本相关者全部在前。
替换查询类型可能已经换了候选问题。function_score给基底候选评分；rank_feature缺值不匹配该子句。必须明确must/should及文本门槛，不能只比较最终小数。
