映射系统

文档的 Schema · 约 17 分钟 · 前置:第 10 课 · 19 个实验

学习目标

  • 不写 mapping 放进一篇 JSON,从 GET _mapping 指出字符串推断成 text + fields.keyword(ignore_above: 256)、小数成 float、日期串成 date,并对上 DynamicFieldsBuilder.newDynamicStringField。
  • 预测 PUT _mapping 把已有 text 改成 keyword 的状态码与错误原文,指出这句话拼自 FieldMapper.checkIncomingMergeType。
  • 用 _analyze 加 term/match 对照同一字符串在两种词典里留下的 key,说出谁能被 match 命中、谁必须整串 term。

1. 心智模型:mapping 是索引的 schema

第 10 课把 GET /index/_doc/1 一路追到 Engine。写入这条路上还欠一个问题:JSON 里的 "title": "Elasticsearch Guide",凭什么变成倒排表里的某个词?答案就是 mapping——索引这一层的 schema。关系库先建表再插数;ES 默认让你先插数,但「表结构」同样存在,只不过第一篇文档替你写了。它决定每个字段写成哪种 Lucene 结构(切词的 text、整串的 keyword,还是 long/date),查询侧再按类型选 Query——它是「索引怎么建、查询怎么走」的分叉点,不是文档的注释。

运行时是三层(类名记在这,不画进方块):每个索引一份 MapperService,握着当前生效的 DocumentMapper;后者内含两个角色——给搜索的不可变 MappingLookup 和给写入的 DocumentParser。叶子是一个个 FieldMapper:title 可能是 TextFieldMapper,status 是 KeywordFieldMapper。_id/_source/_routing 这类元数据字段也是 mapper,走 MetadataFieldMapper,本课不展开。

3. text vs keyword:同一字符串的两条路

这是 mapping 里最贵的分叉。输入就用一个值:"Elasticsearch Guide"。text 默认走 standard 分析器,小写、按词切开,词典里躺两个 key;match 会对查询串做同一套分析,所以大小写不敏感地落到同一张 posting list 上。term 则故意不再分析:拿原始串去 term 一个 text 字段,词典里没有这个 key,安静地 0 hits。keyword 不走切词链,类 javadoc 第一句就是 indexes them as-is:整串一个 term,大小写、空格全保留。

Lucene FieldType 把这条分叉钉死。两边各看几行关键代码:

// TextFieldMapper.java
FieldType ft = new FieldType();
ft.setTokenized(true);                                          // IndexWriter 会跑分析器
ft.setIndexOptions(IndexOptions.DOCS_AND_FREQS_AND_POSITIONS);  // 短语、高亮要位置
ft.setOmitNorms(false);                                         // BM25 要字段长度
FIELD_TYPE = freezeAndDeduplicateFieldType(ft);

// KeywordFieldMapper.java
FieldType ft = new FieldType();
ft.setTokenized(false);                          // 整串当一个 term
ft.setIndexOptions(IndexOptions.DOCS);
ft.setOmitNorms(true);
ft.setDocValuesType(DocValuesType.SORTED_SET);   // 列存:排序/聚合走这里
textkeyword
tokenizedtrue,IndexWriter 里切词false,整串即 term
indexOptionsDOCS_AND_FREQS_AND_POSITIONSDOCS
norms开(BM25 字段长度)omitNorms
doc_values默认关SORTED_SET 列存
典型查询matchterm、terms 聚合、sort

写入侧两边都没有在 mapper 里手动调 analyzer.tokenStream:TextFieldMapper.parseCreateField 只是读出字符串、构造一个 Lucene Field 丢进文档;因为 FieldType 是 tokenized,真正切词发生在 IndexWriter。KeywordFieldMapper 把字符串收成 BytesRef,超长(UTF-8 超过 Lucene MAX_TERM_LENGTH = 32766)在进 Lucene 之前抛,避免半篇写入再标删;ignore_above 命中则整段不索引并记进 ignored。text 想聚合得开 fielddata: true,在堆上从倒排反建列存——贵、易熔断(第 25 课),MappedFieldType.fielddataBuilder 的默认实现干脆直接抛;keyword 天生 doc_values,不走这条路。

常见搭配是 fields 多字段:主字段 text 管全文,子字段 keyword 管精确与聚合。这不是两份 JSON,是同一份值写进两种 Lucene 字段——FieldMapper.parse 先 parseCreateField 写主字段,再把同一个 parser 位置交给子 mapper:

// FieldMapper.java
public void parse(DocumentParserContext context) throws IOException {
    parseCreateField(context);                       // 主字段先写
    if (builderParams.multiFields.mappers.length != 0) {
        doParseMultiFields(context);                 // 同一个值,再写一遍子字段
    }
}

代价是磁盘与索引时间都写两遍。status、error_code 这种永远不全文搜的字段,直接声明 keyword,别靠默认推断。

4. 动态映射:第一篇文档写死 schema

默认 dynamic: true:mapping 里没有的字段名,ES 按当前 JSON token 推断类型,把新 mapper 挂上,再按新类型把这个值索引进去。分叉点在 DocumentParser.parseValue:

// DocumentParser.java
Mapper mapper = getLeafMapper(context, currentFieldName);
if (mapper != null) {
    parseObjectOrField(context, mapper);           // 有叶子 mapper:按声明走
} else {
    parseDynamicValue(context, currentFieldName);  // 没有:动态推断
}

parseDynamicValue 先挡 STRICT/FALSE,再把 token 交给 DynamicFieldsBuilder.createDynamicFieldFromValue。字符串(VALUE_STRING)按这个顺序试:①能 Long.parseLong 且 numeric_detection 开 → long;②能 Double.parseDouble 且该开关开 → float;③不是纯数字且 date_detection 开、能按动态日期格式 parse 出毫秒 → date;④兜底 newDynamicStringField。默认值在 RootObjectMapper.Defaults:date_detection 开(IMPLICIT_TRUE)、numeric_detection 关(IMPLICIT_FALSE)。所以字符串 "42" 仍是 text + keyword,JSON 数字 42 才走 VALUE_NUMBER → long;而 "2024-01-15" 这种像日期的字符串,默认被收成 date。JSON 浮点是另一支:FLOAT/DOUBLE token 建成的是 float 不是 double——源码注释写明这是为了省空间,旧 Demo 里 29.99 显示 float 不是玄学。

字符串最终建成什么,看 DynamicFieldsBuilder.newDynamicStringField(普通对象这条路):

// DynamicFieldsBuilder.java
new TextFieldMapper.Builder(name, indexSettings, indexAnalyzers, false)
    .addMultiField(new KeywordFieldMapper.Builder("keyword", indexSettings, true)
        .ignoreAbove(256))          // 子字段名写死 "keyword",ignore_above 写死 256

两个例外:父对象带 time-series dimensions 时只建 keyword(维度要精确值);dynamic: runtime 走另一套策略,字段查询时从 _source 现算,不写倒排。文档解析结束后,新 mapper 也不只活在这一次 parse 里:createDynamicUpdate 把这批动态 builder 收成一份 mapping 源,由 MapperService.merge(..., MAPPING_AUTO_UPDATE) 合并进集群状态——这就是动画第 ⑥ 步。

dynamic遇到未知字段值还在 _source 吗能搜吗
true(默认)建成具体 mapper,写入 Lucene是能
runtime建成 runtime field,不写倒排是能,查询时现算
false不改 mapping;必要时记 ignored是否
strict立刻失败文档被拒—

STRICT/FALSE 根本拿不到 getDynamicFieldsBuilder()(调用会 UnsupportedOperationException),它们在 parseDynamicValue 里就被拦住。strict 的报错原文是 mapping set to strict, dynamic introduction of [字段名] within [_doc] is not allowed——根对象的 path 就是 _doc(MapperService.SINGLE_MAPPING_NAME)。

5. Mapping 合并:能加字段,不能改类型

用户 PUT /idx/_mapping 走 MergeReason.MAPPING_UPDATE。FieldMapper.checkIncomingMergeType 先比 mapper 的 Class,再比 contentType(),任一不同就抛同一句话:

// FieldMapper.java
if (Objects.equals(this.getClass(), mergeWith.getClass()) == false) {
    throw new IllegalArgumentException("mapper [" + fullPath() + "] cannot be changed from type ["
        + contentType() + "] to [" + mergeWith.contentType() + "]");
}
if (Objects.equals(contentType(), mergeWith.contentType()) == false) {
    throw new IllegalArgumentException(/* 同一句原文 */);
}

仓库测试把措辞钉死了(UpdateMappingTests 断言 mapper [foo] cannot be changed from type [long] to [double]),实验 4a 对的就是这句。注意 merge 看的是类型承诺,不看文档条数:零篇也改不了。读源码还要知道一条实验里看不到的分叉:FieldMapper.Builder.mergeWith 若发现 getMergeReason().isAutoUpdate(),类型冲突时 return this 不抛——动态更新保住已有 mapper,让那篇类型对不上的文档在 parseCreateField 里失败;用户显式 PUT 不是 auto-update,一定抛。换类型的正道只有一条:建新索引 + _reindex。

MergeReason谁用
MAPPING_UPDATE用户 PUT mapping,显式更新
MAPPING_AUTO_UPDATE索引文档时动态加字段
MAPPING_AUTO_UPDATE_PREFLIGHT动态更新送 master 前的预检,不改 this.mapper
INDEX_TEMPLATEcomposable template,同名字段允许后写覆盖
MAPPING_RECOVERY重启、搬 shard 时装回已有 mapping

doMerge 在非 preflight 路径上 synchronized:解析 incoming → 合并 builder → 换一个新的 DocumentMapper 引用。DocumentMapper 本身不可变,换 mapping 就是换引用;MappingLookup 的 javadoc 自述 mostly immutable snapshot——搜索线程拿着旧快照继续查,看不到半合并的树。最后是护栏(默认值以 9.4.0 MapperService 为准):

Setting默认说明
index.mapping.total_fields.limit1000字段总数(含 multi-field、object、runtime)
index.mapping.depth.limit20对象嵌套深度
index.mapping.nested_fields.limit100(老索引 50)nested 字段个数
index.mapping.dimension_fields.limit32768时序维度字段

超限时 merge / 动态更新失败——动态 mapping 不是无限加列,高基数字段很快逼近 1000。

6. 解析循环与查询侧的快照

写入一篇文档时,DocumentMapper.parse 把 SourceToParse 交给 DocumentParser.parseDocument:空 body 直接抛 document is empty;非空则先跑元数据 mapper 的 preParse(_id、_routing),再进 innerParseObject 的 token 循环,最后 postParse 与 createDynamicUpdate。循环里 FIELD_NAME 记名字,START_OBJECT / START_ARRAY / 标量 / VALUE_NULL 各走一条函数。两个要点:数组没有自己的类型,每个元素按同一字段 mapper 再 parse 一次("tags": ["search", "database"] 给 tags 留下两段 token 流);对象是扁平的,author.name 只是个带点的字段路径,同在一篇 Lucene 文档里——要「数组里每个对象独立成子文档」得用 nested,那是另一张文档,本课不碰。产物 ParsedDocument:若干 Lucene 文档、原始 _source、可能的动态 mapping 更新;Engine 怎么写 translog 是第 14 课。

查询侧不翻 FieldMapper 树:搜索、聚合、高亮拿 MappingLookup.getFieldType(name) 得到 MappedFieldType——能不能搜、用什么 analyzer、有没有 doc_values、termQuery/rangeQuery 怎么建。字段不存在时多数查询当 0 hits 而不是 400(那是 Query DSL 课的事)。动态推断实际会建成的类型就这几种:

类型何时出现可搜可聚合/排序
text普通字符串默认主字段match默认否(需 fielddata)
keyword字符串 multi-field,或显式声明term是(doc_values)
longJSON 整数range是
floatJSON 浮点(不是 double)range是
datedate_detection 命中的字符串range是
booleanJSON true / falseterm是

geo_point、dense_vector、nested 都要显式声明(或动态模板),不会从一句普通 JSON 里长出来。

清理

思考题

1. 写入 {"sku": "42"}(带引号)和 {"sku": 42}(不带),类型一样吗?再来 {"day": "2024-01-15"} 呢?

不一样,因为走的是不同 JSON token:字符串是 VALUE_STRING,数字是 VALUE_NUMBER。"42" 就算能 Long.parseLong,numeric_detection 默认关,仍是 text + keyword;42 与开关无关,直接 long。"2024-01-15" 默认成 date:date_detection 默认开,且它不是纯数字(源码特意拒绝纯数字当日期,免得 epoch/年份误伤)。

2. 索引里只有零篇文档,为什么 text 也改不成 keyword?自动更新遇冲突 return this 又是在保什么?

merge 比的是 mapper Class 和 contentType(),不看文档条数:mapping 一旦存在,就是对索引方式的承诺——倒排与 doc_values 都按那个 FieldType 建,改 type 等于宣布「用另一套结构读旧数据」,新旧文档没法用同一种 Query 解释。动态更新 return this 保的是集群:不让一篇类型不符的文档把 mapping 改坏,那篇文档在 parseCreateField 失败即可;显式 PUT 则必须让用户看见冲突。换类型只有新索引 + _reindex。

3. 什么时候接受默认 text+keyword,什么时候显式 keyword,什么时候 strict / runtime?

探索期、字段集合未知:默认 dynamic:true 换来「随便写就能 match 也能聚合」,代价是每个字符串写两份索引,高基数字段逼近 total_fields.limit(1000)。生产里身份类、状态类字段显式 keyword,确定全文搜的才 text(两者都要用 fields)。schema 稳定后 strict 把脏数据挡成 400,避免一次失误永久加列;runtime 适合偶尔查、不想撑 mapping 的字段——不占倒排,查询时扫 _source,延迟换空间。没有「又全文又聚合又零成本」的选项。

陷阱

🕳 第一篇文档定了终身:动态推断的类型一经写进 cluster state 就是 schema——price 第一次是数字,之后想全存字符串只能 400 或 reindex。生产索引先显式 PUT mapping 再放量写。
🕳 term 打在 text 上 0 hits,还不报错:term 不跑分析器,而 text 词典里的 key 是小写 token。要精确匹配就 term 打 keyword 子字段,且查询串与存储值一字不差;要大小写不敏感就用 match。
🕳 dynamic:false 是安静的丢失:写入 201、_source 里有,但字段不进倒排——搜不到、聚合不到。strict 才会 400 拦你;false 只能靠 GET _mapping / _field_caps 发现。
🕳 小数是 float、日期串是 date:动态映射把 JSON 浮点建成 float(不是 double),把日期样字符串建成 date。按 double 估精度与范围、按文本存日期的计划都会在这里翻车。
