JSON 里的值，怎样变成可查询的字段？mapping 决定写入结构与查询能力；未知字段先产生更新候选，经主节点合并后才成为索引的约定。理解这条边界，才能解释类型冲突、写入成功却查不到，以及 text / keyword 的差别。

学习目标

  • 通过 _mapping 对照字符串、数字、日期、数组与对象的动态推断；区分未知字段 detection 和已有数值字段 coercion。

11.1 本地解析候选，谁把它变成 mapping？

本课固定 Elasticsearch 9.4.0、Lucene 10.4.0，引用官方提交 2e8528e。主线限定新建普通 standard 索引、stored source、无匹配模板。mapping 是索引级字段约定，不是每篇 JSON 自带的类型标签。显式 properties 优先；未知字段是否可加入，取决于当前对象的 dynamic、动态模板与索引模式。第一篇文档可以促成新映射，后来的文档也可以增加尚未出现的字段。

MapperService 在节点本地管理该索引的 mapper；DocumentMapper 携带当前 MappingLookup 与解析器引用，解析时传入这份查找视图。叶子 FieldMapper 把 JSON 值变成 Lucene 字段，MappedFieldType 给查询侧提供能力与 Query 构造。不能从“每索引一份”推断整集群共享一个 Java 对象。构造与查找视图、parse

发现新字段后，DocumentParser.createDynamicUpdate 把本次新增 mapper / runtime 字段收成候选，放入 ParsedDocument。IndexShard 遇到非空 update，返回 MAPPING_UPDATE_REQUIRED，此时还没调用本次 Engine 写入。主分片预检 no-op / 合并冲突，向主节点请求更新；MetadataMappingService 合并并写入索引元数据，实际变化才增加 mappingVersion。主分片等待版本变化，再重解析并继续。createDynamicUpdate、IndexShard 的暂停边界、预检、等待与重试、主节点元数据写入

候选不是权威集群状态，本地 MapperService.merge 也不等于发布状态。并发更新可使候选成为 no-op；提交失败或等待超时会使本项失败。mapping 已更新也不能保证文档最终写入成功，更不能保证搜索已可见；映射变更和文档写入不是一起回滚的事务。实验用 refresh=true 固定后续搜索前提，不用响应猜内部更新次数。

11.2 未知值推断，与已知字段解析分开

DocumentParser.parseValue 先找已有 mapper；找到了就按它解析，找不到才进动态逻辑。下表是 dynamic:true、没有覆盖模板、普通父对象没有维度的默认推断。date_detection 默认 true、numeric_detection 默认 false，实验显式写出这些值。动态模板在匹配类型后可接管字段构建，不能把默认表当作所有索引的承诺。parseValue / parseDynamicValue、detection 默认、模板优先

未知 JSON 值普通 concrete 推断边界
42 / 29.99long / float数字 token 不靠 numeric_detection；精度需求可显式 double / scaled_float
"42"text + keywordnumeric_detection 关闭；开后可推断数值
"2024-01-15"date须匹配动态日期格式；纯数字字符串不走日期探测
其他字符串 / booleantext + keyword / booleankeyword 子字段 ignore_above=256；父维度对象可改为 keyword
null / 空数组通常不产生新 mapper已知字段的 null_value、动态策略等另判；strict 未知字段仍可拒绝
普通数组 / 对象按元素 / object 子字段不是独立 array 类型，也不会自动变 nested

字符串分支依次尝试数值、日期，再兜底文本；concrete 浮点策略返回 float，runtime 浮点策略返回 double。数组需逐元素判断兼容性，不能宣称任意混合值都可写。普通对象数组会丢失跨子字段的配对语义，需要独立对象匹配时应显式 nested。9.4.0 新建索引还有例外：新发现的 float 数组，元素数 128–4096、无模板覆盖、非 copy_to 目标等条件满足时可自动改为 dense_vector；因此“vector 永远要显式声明”不成立。token 与 detection、concrete 字符串与浮点、runtime 策略、vector 后处理、维度范围

11.3 同一字符串，两种字段结构

文档只给一份 title:"Elasticsearch Guide"。FieldMapper.parse 先解析主字段，再让 multi-field 解析同值；_source 不会增加 title.keyword。普通 text 使用 tokenized Field，让 Lucene 写入时执行分析；keyword 在本例没有 normalizer，形成一个完整词项。额外字段结构会增加写入与存储工作，成本由配置和内容决定，不能说固定“翻倍”。

本例字段写入结构查询与能力
title · textelasticsearch / guide；默认词频、位置与 normsmatch 分析后匹配；小写 term 也能命中；默认不聚合
title.keyword完整词项 Elasticsearch Guide；默认 doc_valuesterm 或 match 都可命中整串；doc_values 支撑聚合与排序

term 匹配字段类型提供的词项；term 不是只能查 keyword，match 也不是只能查 text。本例大写 term 打在 text 上为零命中，小写同词项则命中。match 按 search_analyzer 处理；默认与写入分析相符，但显式字段 / 请求配置可不同。keyword 的 match 可以走单词项快捷路径。term 查询主要匹配倒排词项，不能把它解释成“查询 doc_values”；keyword normalizer 可在写入和查询规范化，所以“term 永远原样比较”也应限定。termQuery、match 与 keyword 快捷路径、查询分析器选择、keyword 查询规范化

text 默认不提供普通聚合能力；显式 fielddata 等配置可以改变它，但会增加资源开销，聚合的是分析词项，不是原串。keyword 默认可聚合也有条件：动态子字段超过 ignore_above=256 时该字段不索引 / 不写 doc_values，原 source 和主 text 可仍存在。该阈值与 Lucene 的 UTF-8 term 字节上限不同。_analyze 只是分析本次输入；_field_caps 是类型与配置能力，二者都不是已有文档命中统计。text 默认结构、聚合能力判断、keyword 默认结构、ignore_above / normalizer

11.4 未知字段的四种去向

dynamic 可以在对象层设置，子对象可继承或覆盖；它控制未知字段，不会关闭已声明字段的解析。下面限定启用 stored source、没有 source excludes 的本课实验；源码还有 synthetic source、模板和索引模式分支。false / runtime / strict、source-only runtime 字段

dynamic未知字段值与查询
true推断具体 mapper，生成映射更新source 保留；按类型建结构，刷新后查询
strict未知字段使本项失败本篇未写入；失败更新不会删除旧同 ID 文档
false不建未知 mappersource 保留；普通字段查询看不到它
runtime建查询时字段，写进 runtime 区域本例字符串 keyword、小数 double；查询时从 source 计算

false 不是“安静丢失原值”。C7–C10 先刷新，再分别查 mapping、GET source 和 exists，才能把无结构与未刷新分开；必要时可用请求级 runtime_mappings 读取原值。runtime 也不是“不占 mapping”：字段进入 runtime 元数据并计入字段总数；它把部分工作移到查询时，成本取决于查询、数据和缓存，不能承诺一律全量扫描或固定更慢。C11–C13 对照其字段类型与查询结果；集群禁用昂贵查询时需按实际配置处理。

11.5 合并能增加什么，不能替换什么？

PUT /index/_mapping 执行合并，不是替换所有字段。已有 text 不能改为 keyword，FieldMapper.Builder.mergeWith 比较 builder 类与 contentType，零文档也不绕过该检查。新增字段或 multi-field 通常可以；ignore_above、coerce 等是否可更新按对应 mapper 参数规则判断，不能宣称“除了 type 都随便改”。builder 类型检查、本地合并与替换快照

自动更新遇到不同 builder 类型时可保留旧 builder，再按已有类型重解析；这不等于所有后续文档必然报错，仍看 coercion 等规则。新增映射不会给旧文档自动回填字段或新 multi-field；需要让相关文档重新经过写入解析。要保留同名字段并换索引类型，通常创建目标索引、声明映射，再 reindex；也可采用不同字段名、字段转换或 runtime 视图，须明确语义与代价。这里的冲突与“float 接受数值字符串”不是一回事。

index.mapping.total_fields.limit 默认 1000，统计具体字段、multi-field、object、alias 与映射 runtime 字段，不按值的基数计数。A3 顶层 6 个键，对应 7 个叶子、1 个 object 和 3 个 keyword multi-field，共 11 个计数字段；不是网页旧动画里的“8 个字段定稿”。根 _doc 不计。普通新 standard 索引的 ignore_dynamic_beyond_limit 默认为 false，超限可拒绝；启用后可跳过超限动态字段，但显式 mapping 更新仍受限。logsdb 的默认还看索引创建版本，不可泛化。限制及模式 / 版本默认、根计数含 runtime、对象递归计数、multi-field 计数、超限合并边界

实验：推断、查询与动态策略逐项对照

前提：自建 ES 9.4.0 / Lucene 10.4.0、单节点、默认 http://localhost:9200、安全关闭且本地 CORS 已配置。其他端点在连接设置选择；启用安全时需对应读写、管理与监控权限。四个本课资源首次不存在，没有匹配模板、默认摄取管道、外部写入 / 刷新任务或自定义分析器。实验显式 standard / stored source、1 主分片 / 0 副本、周期 refresh=-1、coerce=true；不会改集群设置。

本轮源码已核对，真实 API 未实测当前云端 9200 连接拒绝；既有 ES 9.4.0 启动记录显示运行时缺少 /proc/self/coredump_filter。首次及清理后完整重做均未运行。卡片为固定源码预期；浏览器验收验证操作和请求传递，不模拟 ES 响应。

完整顺序：A0 核对版本 → A1 创建 → A2 等待 → A3–A6 推断与 mapping → A7–A9 coercion。接着 B1–B7 对照分析 / 搜索；C1–C3 创建对照资源 → C4 等待 → C5–C13 分别验证 strict / false / runtime；最后 D1–D3 合并，E1 能力。只在需要搜索的写入加 refresh=true；GET source / mapping 不依赖搜索刷新。

思考题

1. "42" 为什么可被推成 text，而已有 float 又能接受 "29.99"？

前者没有 mapper，按 numeric_detection=false 的未知字符串推断；后者已经有 float，按数值 mapper 的 coerce=true 解析。索引类型保持 float，stored source 保留原字符串。任意无法解析的字符串仍会失败。

2. term 打在 text 上是否永远零命中？match 能查 keyword 吗？

都要看字段与输入。本例小写 term 命中 title 的 elasticsearch 词项；大写 term 没对上。keyword 无 normalizer 时 match 可以整串命中，但不会变成 text 的两个词项。不同 analyzer / normalizer、ignore_above 或参数可改变结果。

3. dynamic:false 写入成功、exists 无命中，原值去哪了？

本例 stored source 中仍有 note，但没有 mapper 或普通查询结构。C9 GET 可以取回；C10 已刷新仍无命中，排除了可见性原因。显式 runtime_mappings 可按 source 提供查询时视图，不能说原值只能永久丢失。

4. runtime 能避开 total_fields.limit 吗？高基数值与字段爆炸是否相同？

映射 runtime 仍占字段总数。高基数是同一字段很多不同值，字段爆炸是出现大量不同字段路径，两者影响不同资源。A3 只有 6 个顶层键却有 11 个计数字段，multi-field / object 也算；根 _doc 不算。

5. mapping 更新成功，是否证明文档已入库或历史数据已拥有新子字段？

都不能推出。主分片还要重解析并完成 Engine 写入，后续失败不会通用回滚已发布 mapping；搜索可见性另靠 refresh。新增 mapping 不会重索引历史文档，补齐新 multi-field 要让相关文档重新经过写入解析。

陷阱

🕳 把 JSON token 变化当作类型更新已有 mapper 按配置解析输入；数值 coercion 不改 float 类型。显式 PUT mapping 改 text→keyword 才是在试图更换既有类型。
🕳 把默认查询分析说成永远同一套本例 standard / 无 normalizer 决定词项。search_analyzer、请求 analyzer、keyword normalizer 都需另判；准确 text 词项也能被 term 命中。
🕳 source 里有值，就认为有字段结构false 的未知字段只保留原值；反过来，keyword 子字段有结构，却不是 source 内第二份 JSON。GET、mapping、搜索与 field_caps 分别回答不同问题。
🕳 用 runtime 替代字段治理runtime 仍在 mapping 内计数。未知 float 数组还可自动成为 vector；先确认索引创建版本 / 模式 / 模板，再按访问方式声明字段。
🕳 把更新候选或本地 merge 当作集群发布解析、主节点合并、节点应用、重试与文档写入分别有边界。并发 no-op、超限、解析失败及超时都要看实际响应；refresh 也不是 mapping 发布操作。
