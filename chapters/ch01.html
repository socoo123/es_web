Elasticsearch 是什么

学习目标

  • 用 _analyze 说清楚一段文本会被切成哪些 token,以及为什么搜 FOX 能命中 fox。
  • 看懂 _cat/shards 里的 primary / replica,并解释单节点集群为什么是 Yellow。
  • 解释「刚写入的文档,GET 拿得到、SEARCH 可能搜不到」背后的机制差异。

Elasticsearch 是基于 Lucene 的分布式搜索与分析引擎。你通过 REST API 写入 JSON 文档，再按文本、结构化字段或聚合条件查询。常见用途包括商品全文检索、日志排查和指标分析；本章用一段英文文本，把「写入 → 分词 → 倒排 → 搜索」串起来。

1. ES 快在哪:倒排,不是扫得快

在大量日志里找 OutOfMemoryError，逐篇扫描原文的工作量会随数据量增长。普通 B+Tree 通常难以直接加速前置通配符的 LIKE '%…%'，但关系数据库也可以使用专门的全文或其他索引，不能一概说它们只能全表扫描。倒排索引把查找方向从「文档 → 词」变成「词 → 文档」，先定位候选，再做查询所需的处理。耗时与倒排表长度、分片数、段数、评分和排序等有关，并不只取决于命中文档数。

评分、短语查询和高亮还会用到下面的信息。字段类型及 index_options 等配置决定哪些信息实际保存；默认 text 倒排记录位置，但不记录字符偏移。

挂的信息干什么用
词频 TF影响相关性评分；出现次数增加的收益通常会逐渐减小
文档频率 DF词出现在多少篇文档中；常见词通常区分度较低
位置 Position短语搜索:quick 和 brown 是否相邻
偏移 Offset定位高亮片段；可按需保存，也可在高亮时重新分析文本获取
先看业务需要:ES 提供单文档更新的原子性，但不提供关系数据库那样的跨文档 ACID 事务。它有特定条件下的关联能力，不能据此假定任意 JOIN 都适合。需要事务约束时，常由关系数据库保管主数据，再把数据同步到 ES 做搜索与分析。
关系数据库Elasticsearch说明
TableIndex一类文档的集合
RowDocument一条 JSON
ColumnField文档里的一个字段
SchemaMapping字段类型
Primary Key_id通常作为索引内的文档标识；使用自定义 routing 时还需一致的路由值
B+Tree 索引倒排索引优化目标不同:按列值找行 vs 按词找文档

2. 倒排表里存的是 token,不是原句

图 2 展示显式的 standard tokenizer + lowercase + stop，让 "The Quick Brown FOX" 变成小写、去掉停用词后的 token。实验 1a 只演示一次 _analyze 请求，不会更改字段配置；本章实验索引的 body 字段使用内置 standard，对应实验 1b。

字段可以另设 search_analyzer，写入和查询不保证配置完全相同。这里用 match 搜 FOX，查询分析后得到 fox，与索引中的 token 对齐。term 查询则不做这一步分析，直接给大写 FOX 通常不能命中这个小写词元。

陷阱:ES 内置 standard 默认停用词表是 CharArraySet.EMPTY_SET，所以 the 还在。当前 Lucene 10.4.0 的无参 StandardAnalyzer() 同样使用空停用词表；旧教材或显式传入停用词表的例子不能代表当前默认行为。实验 1a / 1b 对比的是「显式 stop」和「默认不去停用词」。

3. 六个核心概念与分片放置

概念定义源码里会见到的类
Cluster共享集群状态并协作的一组节点；仅集群名相同不会自动加入ClusterState.java
Node一个 ES 进程,可兼多种角色DiscoveryNode.java
Index一类文档的逻辑集合Index.java
Document一条 JSON,最小数据单元ParsedDocument.java
Shard索引的物理分片,每片是独立的 Lucene 索引IndexShard.java
Replica某一片的副本:故障可顶上,也能分担读ShardRouting.java

一个节点可以同时是 master-eligible、data、ingest,每个节点都能做 coordinating(路由请求、合并结果);生产上常把 master 和 data 分开,免得搜索把集群管理拖垮。现在记住:data 存数据、master 管状态。要分片,是为了三件事:单机放不下(水平扩展)、搜索各片并行(吞吐)、主分片挂了有副本(高可用)。

本章只有一个数据节点时，R0、R1 无处可放，副本为 UNASSIGNED。主分片已启动时，本索引状态为 yellow：能读写，但没有就绪的副本可接替，实验 2a / 2b 会展示这一点。

对本章在 9.4.0 新建的普通、非分区路由索引，IndexRouting.hashToShardId() 使用 floorMod(murmur3(routing), numberOfShards)，默认 routing 取 _id。旧创建版本的索引和分区路由还有不同分支，不能只看当前节点版本套公式。原索引的 number_of_shards 不能通过 _settings 直接改写；要调整布局，可在满足条件时用 _split / _shrink 创建目标索引，或新建索引后 _reindex。具体条件留到第 15 课。

4. ES 与 Lucene 的分工

一句话:Lucene 是单机搜索库,ES 把它变成分布式搜索系统。 ES 9.4.0 用的 Lucene 是 10.4.0(build-tools-internal/version.properties 与 GET / 的 lucene_version 一致)。

职责LuceneElasticsearch
倒排索引的构建与查询核心实现调用 Lucene
文本分词(Analysis)分析器框架包装并扩展
单机搜索IndexSearcher封装后再对外
分布式 / 分片 / 副本不支持负责
REST API不支持HTTP 接口
集群管理、选主不支持负责

写入:文档先到主分片,再复制到副本(怎么落盘是第 14 课)。搜索:先在各分片找候选,再取回真正要展示的文档(为什么分两阶段是第 16 课)。

5. 近实时:GET 和 SEARCH 不是同一件事

写入成功 ≠ 已经可被搜索。GET 默认是 realtime，按 _id 读取，通常不必等 refresh；SEARCH 使用可搜索视图，新写入的数据要等一次 refresh 才对它可见。refresh 不等于持久化提交，不能与 flush 混为一谈。

本章普通索引未显式设置 index.refresh_interval 时，默认间隔是 1 秒；进入 search idle 后，后台 refresh 可能暂停，下一次搜索可触发 refresh。这个间隔不是「最多晚 1 秒」的严格承诺，负载和调度也会影响可见性。写入的 ?refresh=true 主动刷新，?refresh=wait_for 等待一次刷新使本次写入可见；后者通常适合写后搜，但本章实验关闭了自动 refresh，必须手动刷新才能避免长时间等待。

核对本章关键结论：官方版本源码
  • 默认停用词：StandardAnalyzerProvider 与 Lucene 10.4.0 的 StandardAnalyzer() 都使用空表。
  • 本章路由公式：IndexRouting.hashToShardId() 按索引创建版本选择分支。
  • 主分片设置：IndexMetadata.INDEX_NUMBER_OF_SHARDS_SETTING 标记为 Final。
  • 默认记录哪些信息：TextFieldMapper 的默认字段设置 包含词频和位置，不包含 offsets。
  • search idle 与刷新：IndexShard 的周期性刷新判断。

思考题

1. 索引里已有数据，通过 _settings 把 number_of_shards 从 2 改成 3，会怎样？旧文档还能 GET 到吗？

设置变更会被拒绝，原索引仍为 2 个主分片，已有文档的 GET 不会因此受影响。调整分片布局要使用符合条件的 _split / _shrink，或新建索引并 _reindex，让数据与路由保持一致；并非所有目标分片数都符合 resize 条件。

2. 倒排擅长「词 → 文档」,那按 price 排序为什么别扭?ES 用什么结构补上?

排序需要的是「文档 → 字段值」,方向和倒排相反,倒着扫倒排表非常亏。ES 在索引时另建 Doc Values(按文档排列的列式存储),专门服务排序和聚合。

3. 为什么默认 1 秒 refresh 一次,而不是每条写入都 refresh?谁在为谁付出延迟?

refresh 要把刚写入的文档做成可搜索的新视图(segment),有 CPU 和文件成本。默认 1 秒是在写入吞吐和搜索可见性之间折中,而且只在分片没有进入 search idle 时按这个间隔走;若每写一条就 refresh,写入延迟会显著变差。?refresh=true 是把这笔成本转嫁给那一次写入的调用方。

陷阱

🕳 「标准分析器一定会去掉 the」:ES 内置 standard 默认停用词表为空,the 会留在 token 里。要停用词得显式拼 filter: ["lowercase", "stop"](实验 1 对比)。
🕳 单节点 Yellow 要看原因:本章主分片已启动，副本找不到第二个数据节点可放，索引因此为 yellow。可增加节点，或在接受无副本冗余的前提下设 number_of_replicas: 0。其他分配失败也会导致 yellow，排查时先看 UNASSIGNED 原因。
🕳 搜不到 ≠ 没写进去:先 GET 确认(realtime),再怀疑 refresh。别一搜不到就重复写入。

速记

一句话内容
快的原因倒排:查词典,不扫全集
分析链char filter → tokenizer → token filter;写入与查询的 token 要对齐，可配置不同的 search_analyzer
结构Index = N primary + 每片 M replica;同号 P/R 不同节点
路由本章新建普通索引用 floorMod(murmur3(routing), numberOfShards)，routing 默认取 _id；不能直接改写原索引主分片数
分工Lucene 管单机倒排;ES 管分布式、副本、REST、选主
近实时GET 默认 realtime；SEARCH 等 refresh。默认间隔 1s 是调度周期，不是延迟上限

排查顺序：先确认文档和字段，再检查分析后的 token 与查询类型，最后核对 refresh 和搜索条件。
