Elasticsearch 是什么

概念模型与使用场景 · 约 12 分钟 · 无前置 · 11 个实验 · 1 个动画

学习目标

  • 用 _analyze 说清楚一段文本会被切成哪些 token,以及为什么搜 FOX 能命中 fox。
  • 看懂 _cat/shards 里的 primary / replica,并解释单节点集群为什么是 Yellow。
  • 解释「刚写入的文档,GET 拿得到、SEARCH 可能搜不到」背后的机制差异。

1. ES 快在哪:倒排,不是扫得快

在大量日志里找 OutOfMemoryError:关系库的 LIKE '%…%' 和 grep 都是正向扫全集,耗时随数据量线性涨;倒排索引把查找方向反了过来,从「文档 → 词」变成「词 → 文档」,命中只取决于这个词的倒排表有多长。具体要几毫秒,取决于分片数、段数和查询本身,不能当成固定承诺。

真实倒排表里除了文档列表,还挂着统计信息,后面评分和短语搜索都会用到:

挂的信息干什么用
词频 TF一篇里出现越多,通常越相关
文档频率 DFthe 几乎每篇都有 → 权重低
位置 Position短语搜索:quick 和 brown 是否相邻
偏移 Offset高亮 <em>brown</em>
别当主库用:ES 没有传统事务、没有传统 JOIN。常见架构是 MySQL 做主存储与事务,ES 做搜索和分析——两者并存,不是替代。
关系数据库Elasticsearch说明
TableIndex一类文档的集合
RowDocument一条 JSON
ColumnField文档里的一个字段
SchemaMapping字段类型

B+Tree 索引倒排索引优化目标不同:按列值找行 vs 按词找文档

2. 倒排表里存的是 token,不是原句

下面这张图不是内置 standard 的默认行为,而是显式的 standard tokenizer + lowercase + stop:"The Quick Brown FOX" 变成小写、去掉停用词后的 token。字段可以另设 search_analyzer,写入和查询不保证配置完全相同,只要两边产出能对上的 token 就能命中——这里搜 FOX 命中,是因为两边最后比的都是 fox,不是原始字符串。

陷阱:ES 内置的 standard 分析器默认不去停用词。源码 StandardAnalyzerProvider.java 里默认停用词表是 CharArraySet.EMPTY_SET——所以只写 "analyzer": "standard" 时,the 还在。别把 Lucene 教科书里默认带停用词的 StandardAnalyzer 和它混为一谈。实验 2 会让你亲眼看到差别。

3. 六个核心概念与分片放置

概念定义源码里会见到的类
Cluster共用一个集群名、一起干活的一组节点ClusterState.java
Node一个 ES 进程,可兼多种角色DiscoveryNode.java
Index一类文档的逻辑集合Index.java
Document一条 JSON,最小数据单元ParsedDocument.java
Shard索引的物理分片,每片是独立的 Lucene 索引IndexShard.java
Replica某一片的副本:故障可顶上,也能分担读ShardRouting.java

一个节点可以同时是 master-eligible、data、ingest,每个节点都能做 coordinating(路由请求、合并结果);生产上常把 master 和 data 分开,免得搜索把集群管理拖垮。现在记住:data 存数据、master 管状态。要分片,是为了三件事:单机放不下(水平扩展)、搜索各片并行(吞吐)、主分片挂了有副本(高可用)。

只有一台机器时,R0、R1 无处可放,副本是 UNASSIGNED,集群状态 Yellow:主分片都在、能读写,但没有副本可切——实验 4 你会亲眼看到。另外,文档落在哪一片是创建时就定死的:源码 IndexRouting.java 里 hashToShardId() 用 murmur3 哈希后 floorMod(hash, numberOfShards) 取模,除数就是创建时的主分片数(_routing 默认取 _id)。所以主分片数不能事后改——hash % 2 和 hash % 3 不是同一个格子,旧文档会找错片;要改只能建新索引再 _reindex。

4. ES 与 Lucene 的分工

一句话:Lucene 是单机搜索库,ES 把它变成分布式搜索系统。 ES 9.4.0 用的 Lucene 是 10.4.0(build-tools-internal/version.properties 与 GET / 的 lucene_version 一致)。

职责LuceneElasticsearch
倒排索引的构建与查询核心实现调用 Lucene
文本分词(Analysis)分析器框架包装并扩展
单机搜索IndexSearcher封装后再对外
分布式 / 分片 / 副本不支持负责
REST API不支持HTTP 接口
集群管理、选主不支持负责

写入:文档先到主分片,再复制到副本(怎么落盘是第 14 课)。搜索:先在各分片找候选,再取回真正要展示的文档(为什么分两阶段是第 16 课)。

5. 近实时:GET 和 SEARCH 不是同一件事

写入成功 ≠ 已经可被搜索。GET 按 _id 取这一篇,写入成功后立刻能拿到(realtime,细节在第 10 课);SEARCH 走倒排表,而倒排表要等一次 refresh 才把新文档编进去。未改 index.refresh_interval 时默认是 1 秒(IndexSettings.DEFAULT_REFRESH_INTERVAL),但分片若长时间没有搜索会进入 search idle,不再按这个间隔后台 refresh,下一次搜索可能自己触发一次 refresh。所以「最多晚约 1 秒」只在分片仍被搜索、时钟还在走时成立。?refresh=true 能让这条写入立刻可搜,但那是拿写入延迟换可见性,生产路径别滥用。这就是「近实时(Near Real-Time)」的含义。

清理

思考题

1. 索引里已有数据,把 number_of_shards 从 2 改成 3,旧文档 _id=1 还能 GET 到吗?

不能(或不可预测)。路由公式 floorMod(hash, numberOfShards) 的除数是创建时定死的;即便设置项允许改,旧文档按 % 3 会算出另一片,GET 会去错误的 shard 上找。要改分片数只能新索引 + _reindex。

2. 倒排擅长「词 → 文档」,那按 price 排序为什么别扭?ES 用什么结构补上?

排序需要的是「文档 → 字段值」,方向和倒排相反,倒着扫倒排表非常亏。ES 在索引时另建 Doc Values(按文档排列的列式存储),专门服务排序和聚合。

3. 为什么默认 1 秒 refresh 一次,而不是每条写入都 refresh?谁在为谁付出延迟?

refresh 要把刚写入的文档做成可搜索的新视图(segment),有 CPU 和文件成本。默认 1 秒是在写入吞吐和搜索可见性之间折中,而且只在分片没有进入 search idle 时按这个间隔走;若每写一条就 refresh,写入延迟会显著变差。?refresh=true 是把这笔成本转嫁给那一次写入的调用方。

陷阱

🕳 「标准分析器一定会去掉 the」:ES 内置 standard 默认停用词表为空,the 会留在 token 里。要停用词得显式拼 filter: ["lowercase", "stop"](实验 1 对比)。
🕳 单节点 Yellow 不是故障:副本分片找不到第二台机器可放,UNASSIGNED 是正常现象;要么加节点,要么把 number_of_replicas 设为 0。
🕳 搜不到 ≠ 没写进去:先 GET 确认(realtime),再怀疑 refresh。别一搜不到就重复写入。

速记

一句话内容
快的原因倒排:查词典,不扫全集
分析链char filter → tokenizer → token filter;写入与查询同链
结构Index = N primary + 每片 M replica;同号 P/R 不同节点
路由floorMod(murmur3(_routing), numberOfShards),除数创建后不可变
分工Lucene 管单机倒排;ES 管分布式、副本、REST、选主
近实时GET 立即可见;SEARCH 等 refresh(默认 1s,search idle 时可能停表)

心法:凡是「搜」,先想倒排表里有没有这个 token;凡是「没有」,先想 refresh 过没过。
