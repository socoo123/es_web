聚合框架

搜索只返回一条商品，为什么分面仍能统计整家店？每片只送两个桶，为什么全局第二名会消失？聚合先在分片形成局部统计，再由协调角色归并；窗口限制、候选截断和执行期内存属于不同边界。沿着一棵聚合树，分别验证这三件事。

  • 计算两片 fruit 的全局排名，预测 shard_size=2、默认容量和 _key 排序的桶、sum_other 与误差上界，并用真实响应对照。
  • 沿 Builder → Factory → Aggregator → InternalAggregation → reduce 找到执行与结果边界；用加权 avg、bucket_sort 和 profile 验证归并、派生及策略差异。

19.1 返回一条 hit，聚合为什么仍有八篇？

本章限定 ES 9.4.0 / Lucene 10.4.0 的普通搜索，主例为单值 keyword 的 terms，默认按 _count:desc 排序，无采样、global、min_score、terminate_after 或分片失败。聚合在 Query 阶段统计主查询范围，不是对最终 hits 列表做一次 GROUP BY。A6 只返回一条最便宜的商品，三个 category 桶仍计数 3、3、2；A7 把 query 限定为 books，聚合输入才缩到三篇。

顶层 size 控制 hits 数，terms.size 控制最终桶数，是两个不同参数。size:0 不取 hits，普通桶/数值聚合仍执行。第 18 课的 post_filter 只约束 hits 收集，普通顶层聚合保留主 query 的范围；global、nested、filter 等聚合则各自定义范围，不能都称“所有命中文档”。

聚合类别读取什么本章例子
Bucket在当前范围按规则分组；文档可进入多个桶terms(category)、range(price)
Metric当前范围内合格字段值；缺失和多值按聚合规则处理avg(price)、sum、value_count
Pipeline普通聚合结果；不重新遍历原文档bucket_sort 重排已保留的桶

普通聚合结果随 QuerySearchResult 返回，之后还需全局 reduce。它不依赖主 hits 的 Fetch 来补齐统计；但“所有聚合绝不取字段”也过强：top_hits 聚合在分片构建自己的命中结果时会执行取字段工作。概念图省略这条专用路径。

Query 聚合注册；top_hits 自己取结果、专用 Fetch。

19.2 从描述到执行，跨节点返回的是哪层对象？

请求中的 by_fruit 是聚合名称，terms 的 field、size 等成为 TermsAggregationBuilder 的配置。分片上下文建立工厂树，Factory 按字段供应商、父桶条件和参数创建 Aggregator。Builder 描述要什么，Factory 装配实现，Aggregator 负责统计，InternalAggregation 携带可归并的结果；这是四种职责，不是同一对象换名字。

AggregationPhase.preProcess 注册 collector manager；newAggregatorCollector 创建顶层执行器并 preCollection。普通收集时，叶子 collector 遍历合格文档/字段值。收集结束由 AggregatorCollector.doPostCollection 调 buildTopLevel() 得到局部树，再释放执行器的相关状态；这不表示结果树也消失。顶层只有 owning bucket ordinal 0，子聚合由父聚合传入所需桶的 ordinals 构建结果。

收集后构建与释放、顶层结果入口。
字段与子聚合选择：没有一个固定的 keyword 执行器

bytes 供应商通常选择 global_ordinals；不支持序数时用 map。9.4.0 还有条件性的 filter-by-filter 适配、低基数、dense/remap 等路径，所以 profile 可能显示 StringTermsAggregatorFromFilters。数值/日期等使用 NumericTermsAggregator，并区分浮点和整数结果策略。选择实现的是工厂的供应商/创建逻辑；Builder 的 innerBuild 是构建 Factory。

bytes 选择、numeric 选择、global ordinals 优化分支

breadth_first 可推迟不参与排序的子聚合，只对入选父桶重放；depth_first 则在主收集时维护子聚合。不能说“avg 总是等父桶截完才开始算”。强制 depth_first 的条件包括子聚合需要分数且祖先为 nested，或按时间序列排序执行；不是满足任意一项就都强制。

强制模式条件、不延迟用于排序的子聚合

19.3 每片只送两桶，全局第二名为什么丢失？

B 组把词频放在两个单主分片索引上，避免 routing 改变分布。固定 ID、显式 refresh 后局部/全局响应如下。每文档一个 fruit；这里 doc_count 的求和才可以按一篇一次来读。

范围局部/全局词频cherry 名次
s0：11 篇apple6、banana3、cherry2本地第三
s1：11 篇apple4、date4、cherry3本地第三；apple/date 同 count 按 key 排
合计：22 篇apple10、cherry5、date4、banana3全局第二

六步演算：先计数，后选候选，再归并

默认候选容量在未显式选择 shard_size 且非 _key 排序时计算：min(Integer.MAX_VALUE, floor(size×1.5+10))；size=2 得13。然后 ensureValidity 把容量下限抬到 size。它约束的是容量，不是实际返回桶数：字段只有一个值、min_doc_count 或过滤条件，都可能让响应少于 size。

公式与取整、默认容量条件、参数有效性。

普通序数路径在构建局部结果时使用至多 shardSize 的优先队列；size 小不等于从一开始只统计两个值。s0 丢 cherry2，s1 丢 cherry3；协调角色只能合并收到的 apple、banana、date，最终保留 apple10、date4，没有补桶的第二阶段。

局部候选队列。
真实请求返回桶sum_other聚合误差上界
size2 / shard_size2apple10、date48：局部丢 cherry5 + 最终丢 banana37；桶内 apple0、date3
size2 / 默认13apple10、cherry57：date4 + banana30
size3 / shard_size2→3apple10、cherry5、date43：banana35；本例实际计数仍准确
size2 / _key:ascapple10、banana39：cherry5 + date40

sum_other_doc_count 是 terms 阶段因候选/最终窗口截断而未返回桶的计数总和，不是遗漏 key 数，也不是内存分配量；多值字段里一篇可计入多个桶。doc_count_error_upper_bound 则是计数误差的保守上界。聚合级7不表示 apple/date 实际都少7篇；本例date实际完整，上界仍为3。9.4.0 在 count 降序下可能用满队列的末尾返回计数估计缺失上界，显式3恰好满队列，因此全量正确计数仍可伴随上界5。

误差估计条件、累计与桶级误差。

增加 shard_size 通常改善 count 降序候选覆盖，但不构成任意数据的精度证明。_key 排序解决的是“按 key 选桶”，不是 count 排名；本章默认 min_doc_count=1 下无需这条过采样启发式。按 count 升序或某些子指标排序，误差可能不可界定而返回 -1。不能把 count 降序的上界解释直接套到所有 order。

19.4 reduce 如何合并指标，Pipeline 能补回谁？

协调入口 InternalAggregations.topLevelReduce 先归并普通聚合；内部按聚合名称选择 reducer，terms 再按相同 key 合并 doc_count 并递归归并子聚合。默认 count 降序的 partial reduce 保留供后续合并的候选，final reduce 才按 requiredSize 与 min_doc_count 做最终选取；并不是“所有 partial 都永不裁桶”，_key 与默认计数门槛满足特例时可以提前限制结果。

同 key 合并、key 特例与 final 选择。

单片也需要最终处理：InternalMultiBucketAggregation 的 mustReduceOnSingleInternalAgg() 返回 true，单份输入仍可进入 reducer。C4 的20个唯一值只返回2个，sum_other=18包含了局部与最终窗口的丢弃，不能简单说18个都在分片优先队列中被丢。

单份多桶仍归并、单份入口、slice 部分归并。

avg 不能直接平均各片均值。B15 只统计 apple：s0六个 price=1，s1四个 price=9，全局 sum42 / value_count10 = 4.2；(1+9)/2=5把两片误当同权。InternalAvg 在结果中携带 sum 与 count，合并后再除；多值/缺失时 count 是参与计算的数值个数，不一定等于 doc_count。

携带 sum/count、合并 sum/count。

只有最终普通聚合归并后才执行 Pipeline。B13 的 terms size2 先保留 apple/cherry，bucket_sort 按 key 降序取1桶，只能得到 cherry5；B14 先保留4桶，同样排序才得到 date4。这两卡的sum_other仍分别为7与0：bucket_sort移除的桶不会重新回记到terms的sum_other，因此不能用它反推Pipeline之后全部未显示桶的计数。bucket_sort读取并重建桶列表。Pipeline 没有向分片要新候选，所以也不能修复之前的漏桶。放大上游 size 只是扩大可见集合；若局部候选仍不足，仍不能保证完整。

最终 Pipeline 执行。

19.5 高基数的代价，不能由返回两桶推算

C 组用20个唯一 user_id 演示逻辑基数与返回桶数：size2返回两个桶、sum_other18；size20返回20桶、sum_other0。它证明的是结果截断，不是20个实际计数器，更不是百万级压力测试。执行状态可能按字段全局序数空间、命中后 remap 哈希、父桶与子聚合增长，也可能改写成 filters。C6 用 profile 查看本轮实际选择的执行器，本轮两次profile均见 StringTermsAggregatorFromFilters，delegate为 FilterByFilterAggregator；这是当前小数据的观测，不能推广成所有keyword请求的默认实现。

size、shard_size 会影响优先队列、候选序列化、协调内存和部分子聚合工作；不能说“缩小 size 完全不省内存”或“放大 shard_size 必定先撞某个 breaker”。高基数、命中比例、父桶数、收集策略、字段数据与节点并发一起决定消耗。min_doc_count 主要约束输出，不保证省去前期统计；cardinality 是近似去重指标，不能替代返回具体 key 的 terms。需要枚举大量 key 时应按需求考虑 composite 分页，而不是无界增大 size。

AggregatorBase.DEFAULT_WEIGHT=5120 是每个执行器的初始估计记账，后续另有状态分配；request、fielddata 与 parent 的保护边界不同。C7只读本地节点 breaker 状态，不改限额。tripped 为节点累计值，历史请求可非零；一张瞬时统计也不能恢复本次峰值。具体熔断机制留给第25课。

初始估计、请求 breaker 记账。
聚合怎样理解桶/结果
range请求列出区间；可以重叠，不是每篇只能进一桶
histogram / date_histogram字段值与数值/日历间隔产生 key；范围、空桶与 bounds 决定结果，不是请求预列全部 key
cardinality / percentiles近似指标；误差机制不同于 terms 候选截断
top_hits每桶选命中文档，含专用取字段工作

这些聚合不使用 terms 的 count Top-N 候选选择，不代表没有数值近似、桶数量限制、时区边界或资源成本。

思考题

1. hits size=1、terms size=2、query过滤，各限制什么？

顶层size只限返回hits；terms.size限最终桶，输入仍是当前聚合范围；query会缩小普通顶层聚合范围。post_filter另只门控hits，global/nested等范围需各自判断。

2. cherry为何丢失？size3/shard_size2抬底是否保证每片回三桶？

cherry两片都本地第三，容量2都没送，全局第二无从归并。容量抬到3在本例覆盖全部值；若合格值少于3，实际仍可少回。容量下限不是返回数量下限。

3. error_bound=7是否表示date实际少7篇？上界0是否意味着返回全部桶？

不是。聚合级与桶级不同，桶date上界3、本例真实count4仍完整；满队列会保守估计。默认13上界0但只回apple/cherry，sum_other7仍表示窗口丢弃date/banana。

4. 两片均值1与9，为何不是5？bucket_sort能找回date吗？

apple文档数6与4，应合并sum42/count10得4.2。terms先回apple/cherry时bucket_sort看不到date；扩大上游至本例四桶才能按key降序选到date。

5. sum_other18能证明20个计数器、min_doc_count能保证降低峰值吗？

不能。它是未返回桶计数总和，可能在局部和final两个阶段累积。具体状态由序数/哈希/filters与子聚合等策略决定；min_doc_count约束输出不保证跳过前期统计，须按实际负载测量。

陷阱

把两个size混在一起：顶层size0不关聚合；terms.size管最终桶，shard_size管局部候选容量，两者都不是内存字节限额。
误差字段当作修复或精确差值：sum_other不告诉遗漏key，上界不等于实际少计；非count降序不能照搬本例解释。
Pipeline替代全局补桶：它只访问普通归并结果；扩大上游size仍需确认分片候选覆盖。
桶规则等于预列所有key：range给区间，date_histogram按值、日历与时区算key；无terms截断不等于无边界或成本。

速记

边界结论
输入与hits普通顶层聚合统计query范围，不是最终hits；主hits Fetch不补统计，top_hits另取字段
执行与结果Builder描述 → Factory创建 → Aggregator统计 → InternalAggregation传递/归并
容量未指定且非_key：floor(size×1.5+10)，上限MAX；容量≥size，不保证实际桶数
默认count降序partial合并候选，final选size；_key有提前限制特例，排序条件必须说明

指标/Pipelineavg合sum/count；最终普通聚合后执行Pipeline，只看已保留结果
资源逻辑基数不等于计数器布局；5120B只是初始估计，需查策略与测量

心法：先分清统计范围，再看谁进入候选；归并只能使用收到的状态。
