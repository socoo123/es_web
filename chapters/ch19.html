聚合框架

分片先截桶,协调节点再合并 · 约 15 分钟 · 前置:第 16 课 · 17 个实验

学习目标

  • 用「size=2 的 terms、两份具体词频」说出:每 shard 若只回 2 桶,合并后谁会失踪、真正的全局第 2 名是哪个;并写出默认 shardSize 公式算出的数字。
  • 打开 Aggregator.buildTopLevel 和 InternalAggregations.reduce,指出 shard 上 build 出的是 InternalAggregation,协调节点 reduce 才按同名桶把 doc_count 加起来、再截 size。
  • 对高基数字段(每文档一个 user_id)的 terms 预测执行期要追踪多少桶;熔断的字节账留给第 25 课,本课只指到那条边界。

1. 心智模型:聚合跟 hits 走同一趟 Query,不走 Fetch

第 16 课把 SEARCH 钉死成 Query Then Fetch。hits 可以先比分再取正文;聚合不行——terms 要按字段值给所有命中文档分桶,没进全局 Top-10 的文档仍然可能是某个桶的主力。所以聚合在 Query 阶段就算完,塞进 QuerySearchResult.aggregations,和 (docId, score) 同一包回来;Fetch 只搬正文,碰不到这棵树。

聚合本身三类,一张表够,不要画成三列箭头网:

类型输入输出本课主例子
Bucket命中文档若干桶(每桶一组文档)terms 按 category / fruit
Metric一个桶里的文档一个数(或一组数)桶上的 avg(price)
Pipeline已经 reduce 完的聚合树再算出的新聚合bucket_sort、max_bucket,final reduce 之后才跑

Bucket 改变「文档怎么分组」,Metric 改变「这一组得出什么数」,嵌套时数据方向是父桶 → 子指标;Pipeline 不进这张对照——它吃的是别的聚合的结果,不是原始文档,所以看不到被 size 截掉的桶。

3. 三层对象:一份 JSON 怎样变成能收集文档的 Aggregator

{"aggs":{"by_fruit":{"terms":{"field":"fruit","size":2}}}} 在协调节点解析成 TermsAggregationBuilder(名字 by_fruit,requiredSize=2,shardSize 还是哨兵 -1),随 SearchRequest 发到每个数据节点。数据节点上要的不是 builder,是能进 Lucene collector 的 Aggregator:

// AggregatorFactories.build(节选)——SearchService 建 SearchContext 时跑
for (AggregationBuilder agg : aggregationBuilders) {
    aggFactories[i] = agg.build(context, parent);   // terms → TermsAggregatorFactory
}

keyword / IP 走 bytes 供应商(默认 ExecutionMode.GLOBAL_ORDINALS,没有序数才 MAP);numeric / date / boolean 走 NumericTermsAggregator(LongHash)。Query 开始前 AggregationPhase.preProcess → createTopLevelAggregators():每个 factory create(parent=null);顶层聚合的 owningBucketOrd 只有 0——「恰好一个父桶」,就是整次搜索的命中集。收集结束不在 Aggregator 自己的 close 里出结果,而在:

// AggregatorCollector.doPostCollection(节选)
for (Aggregator aggregator : aggregators) {
    internalAggregations.add(aggregator.buildTopLevel());
    aggregator.releaseAggregations();   // 立刻还字节——Aggregator 不再需要
}

// Aggregator.buildTopLevel:顶层专用,断言没有 parent
assert parent() == null;
return buildAggregations(newLongArray(1))[0];   // 对唯一的 owning ordinal 0 出结果

子聚合不能走这条:父聚合知道自己的优先队列留下了哪些桶,把那些桶的 ordinal 数组传进 buildAggregations(ordsToCollect)。这就是 size=2 的 terms 套 avg 时,avg 不会对「没进 shard 本地 top」的值再算一遍的原因——那些桶在父的 build 里已经被丢掉了。同一 shard 若切成多个 Lucene slice 并行搜,AggregatorCollectorManager.reduce 会先做一次分片内 partial reduce,再交给协调节点——主路径仍是:每个 shard 组交出一棵局部树。

4. 深潜:size=2 时,cherry 为什么会被挤掉

两个单分片索引合搜,{"size":0,"aggs":{"top":{"terms":{"field":"fruit","size":2}}}}。两片上的真实词频:

把这场挤掉连起来看:

默认策略是过采样,公式一行:

// BucketUtils.suggestShardSideQueueSize
final long shardSampleSize = (long) (finalSize * 1.5 + 10);   // 多要 50% + 给小 size 的常数垫
return (int) Math.min(Integer.MAX_VALUE, shardSampleSize);

谁在什么时候套:TermsAggregatorFactory.adjustBucketCountThresholds——只在哨兵 shardSize == -1(用户没写)且不是按 key 排序时。两条例外:① 用户显式写了 shard_size,启发式不跑(实验 9 故意写 2 制造挤掉);② 按 _key 排序不存在「按 count 排名被分布式计数弄错」的问题,不套,随后 ensureValidity 发现 -1 < requiredSize,把 shardSize 抬到至少等于 size。不变量:每个 shard 送回的桶数至少是 size,否则连填满全局 Top-size 都做不到。

shard 上的截断发生在 buildAggregations,不是收集时提前只记 2 个词。keyword 默认实现把优先队列长度设成 min(valueCount, shardSize):收集阶段仍给出现过的每个全局序数计数;出结果时只弹出队列里的 Top-shardSize,被挤出队列的桶 doc_count 累加进 sum_other_doc_count——所以 shard_size=2 的响应里常看到它 > 0;打开 show_term_doc_count_error 还能看到 doc_count_error_upper_bound:「没被送上来的桶最多可能有多少文档」的上界,不是精确误差。过采样把上界压小,但压不成理论 0——除非 shardSize 大到每片全量回传。

5. 协调节点 reduce:同名桶相加,再截 size

// InternalAggregations.reduce(节选)——QueryPhaseResultConsumer 收齐各 shard 后调
if (aggregationsList.size() == 1) {
    return reduce(aggregationsList.getFirst(), context);   // 单份仍可能 reduce,见下
}
try (AggregatorsReducer reducer = new AggregatorsReducer(...)) {
    for (InternalAggregations aggregations : aggregationsList) { reducer.accept(aggregations); }
    return reducer.get();
}

// AggregatorsReducer.accept:按「聚合名字」(请求 JSON 里那个 key)归组
AggregatorReducer reducer = aggByName.computeIfAbsent(
    aggregation.getName(), k -> aggregation.getReducer(context.forAgg(k), size));
reducer.accept(aggregation);

keyword terms 的 leader reducer 落在 StringTerms.getLeaderReducer → termsAggregationReducer(AbstractInternalTerms)。同 key 合并时 doc_count 加总、子聚合递归 reduce;final reduce(那一次 isFinalReduce() 为真)用 TopBucketBuilder 只留 requiredSize 个——这才是请求里的 size,不是 shardSize。partial reduce(slice 之间、batched_reduce_size 触发的中间合并不按 size 截到最终窗口,只是先加起来省内存;Pipeline 也在 final 之后才跑,看不到被 size 丢掉的桶。即使只有 1 个 shard,terms 仍会 mustReduceOnSingleInternalAgg() == true:单 shard 时 shardSize=13 带回 13 桶,协调节点还得截成 2、处理 min_doc_count 与 pipeline——「单 shard 跳过 reduce」不成立。

Query 阶段每 shard 回什么协调节点留下什么默认公式
hitsfrom+size 条 (docId,score)全局窗口 size 条,再 Fetch _sourcefrom+size(第 16 课,严格)
terms最多 shardSize 个桶(含 doc_count、子聚合)全局 size 个桶;没有第二阶段补桶size×1.5+10(未指定且非 key 序,近似)

hits 能严格保证,是因为排名键是可比较的 score:全局第 k 名一定落在某 shard 的本地前 k 名里。terms 按 count 加总:一个 key 的全局 count 依赖所有 shard 上该 key 的局部 count,本地第 3 仍可能合计成全局第 2——协调节点看不见的 key,reduce 永远加不回来。

6. 高基数与速查:执行期追踪的是全部值

size=2 只限制返回和跨节点传送。收集阶段 GlobalOrdinalsStringTermsAggregator 仍要给见过的每个全局序数记账:一百万个不同 user_id 就是一百万个计数器,哪怕只要 Top-10。这和 cherry 不是一件事——cherry 是「送少了排名错」,高基数是「还没上网,堆上已经胀了」。保护机制是 AggregatorBase 向 request circuit breaker 记账(每个聚合先挂约 5kb 的 DEFAULT_WEIGHT,数组扩张再 addEstimateBytesAndMaybeBreak);怎么撞、95% 水位,第 25 课拆。子聚合收集方式也有权衡:桶多时倾向 breadth_first(先建父桶、截完 Top-shardSize 再重放文档算子聚合),depth_first 单次扫描但子聚合跟着每个父桶走;嵌套在 nested 下或子聚合要分数时强制后者。

类型聚合这一课需要记住的
Buckettermssize vs shardSize;本课主路径
Bucketrange / histogram / date_histogram桶 key 事先知道,没有排名误差、没有过采样
Bucketfilters / nested过滤器分桶;进嵌套文档
Metricsum / avg / min / max / stats挂在桶下;reduce 时对同名桶再合并
Metriccardinality去重近似(HyperLogLog),不是 terms
Metricpercentiles / top_hits近似分位;每桶 Top-N 文档
Pipelinebucket_sort / max_bucket / cumulative_sumfinal reduce 之后才跑

清理

思考题

1. 仍用 s0+s1 词频:请求 size=3 且显式 shard_size=2,ensureValidity 会把 shardSize 抬到几?抬完之后三个桶是谁?cherry 在不在?

抬到 3——不变量是 shardSize ≥ size,不是「保持用户写的 2」。每片回本地 Top-3:s0 送 apple/banana/cherry,s1 送 date/apple/cherry;cherry 两边都在,合并 apple:10、cherry:5、date:4,cherry 在。若不抬,s0 只回 2 个,cherry 失踪,连全局第 3 都会错——这正是那条源码注释要防的(实验 11 验证)。

2. 为什么不能让每 shard 只回 size 个桶、指望协调节点凑出全局 Top-size?hits 的 from+size 为什么能严格保证、terms 不能?

shardSize = size 只保证「各片本地第 1」进得了候选,不保证全局第 size 名进得了:cherry 在两片都排第 3,各回 2 个就把真正的第 2 丢了。不变量是协调节点看不见的 key,reduce 无法凭空加回来。hits 的排名键是可比较的 score,全局第 k 名必在某片本地前 k;terms 的全局 count 依赖所有片上的局部 count,除非全量回传,只能过采样近似。

3. 默认 size×1.5+10、shard_size=size、极大 shard_size,各在付什么换什么?高基数字段上选「极大 shard_size」和选默认比,谁先撞第 25 课的 breaker?

默认:付每片多传约 50%+10 桶的网卡与协调内存,换小 size 时很难丢全局前几。shard_size=size:付排名可能错(date 顶替 cherry),换传输最少。极大 shard_size:付每片几乎全量序列化,换误差上界趋近 0——但收集期该胀的数组已经胀过了,高基数先撞的是数据节点上 Aggregator 的 request breaker,与 shard_size 写 13 还是极大关系不大。要降高基数内存:换 cardinality、加 include/min_doc_count、或别对 user_id 做 terms——把 size 写成 2 不省内存(实验 14 的 18 个 sum_other 就是证据)。

陷阱

🕳 把 size 当每 shard 的配额:size 是客户端要的全局桶数;每片默认送 size×1.5+10。以为「size=10 每片就只算 10 个值」和实验 14 的 18 个 sum_other 撞个正着——收集期跟基数走,不跟 size 走。
🕳 shard_size 写小了还信排名:shard_size=size 时全局第 2 可以在每片都只排第 3,cherry 就这么失踪。响应里的 sum_other_doc_count / doc_count_error_upper_bound 是「丢了的账」,不是修正;要的是过采样,不是读账。
🕳 以为单 shard 就跳过 reduce:terms 的 mustReduceOnSingleInternalAgg() == true——单 shard 时 shardSize=13 带回 13 桶,还得截成 size、跑 pipeline。reduce 不只是「跨节点相加」。
🕳 给 range/histogram 套过采样心智:它们的桶 key 在请求里就定了(区间、日历间隔),各 shard 回同一组 key,协调节点只加总——没有 cherry 问题,也没有 shardSize。
🕳 指望 pipeline 看到被截掉的桶:pipeline 吃的是 final reduce 之后的树,被 size 丢掉的桶它根本看不见。想对完整桶集做排序/统计,先放大 size。
