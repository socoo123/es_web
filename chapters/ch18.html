查询语法

JSON 怎样变成 Lucene Query · 约 15 分钟 · 前置:第 11、17 课 · 19 个实验

学习目标

  • 对同一个 text 字段发出 match: "quick brown" 和 term: "quick brown",先预测 hits 差异,再用 _analyze 对照词典里到底躺着哪些 token。
  • 打开 MatchQueryBuilder.doToQuery 与 MatchQueryParser.parse,说出默认 operator 如何把两个 token 收成 Boolean SHOULD;再用 _explain 在响应里指认这两条 should。
  • 打开 BoolQueryBuilder.doToQuery,对照 Occur.MUST 与 Occur.FILTER:filter 不算 BM25、命中集合可收成 bitset;must 要带 TF 的分数,同一份 bitset 替代不了。

1. 心智模型:DSL 不是 Lucene 能跑的东西

客户端写出的是 JSON。第 16 课协调节点扇出的 ShardSearchRequest 里,这份 JSON 已经是 SearchSourceBuilder.query() 指向的某个 QueryBuilder;第 17 课 parseSource 在分片上调 searchExecutionContext.toQuery(query),结果塞进 SearchContext.originalQuery。本课就是 toQuery 这一跳:Query DSL 的工作是「分析 + 组装 Lucene Query」,不是搜文档——搜文档是第 16 课 Query 阶段的事。

3. match:"quick brown" 怎样变成 SHOULD

REST 把 {"match":{"title":"quick brown"}} 解析成 MatchQueryBuilder("title", "quick brown")。真正造 Lucene Query 的是:

// MatchQueryBuilder.doToQuery(节选)
MatchQueryParser queryParser = new MatchQueryParser(context);
queryParser.setOccur(operator.toBooleanClauseOccur());   // 默认 OR → SHOULD
Query query = queryParser.parse(MatchQueryParser.Type.BOOLEAN, fieldName, value);
return Queries.maybeApplyMinimumShouldMatch(query, minimumShouldMatch);

Operator 的映射只有两行,不要画菱形分叉:

// Operator.toBooleanClauseOccur
case OR  -> BooleanClause.Occur.SHOULD;
case AND -> BooleanClause.Occur.MUST;

名字碰撞提醒:ES 的 index.query.MatchQueryBuilder 是 DSL Builder;MatchQueryParser 内部还有一个同名内部类(继承 Lucene 的 util.QueryBuilder),真正调 analyzer.tokenStream——读源码看 package,别当成同一个类。

分析器从哪来;keyword 会短路

未指定 analyzer 参数时,match 用字段的 search analyzer(text 默认 standard)。parse 里有一条短路:分析器是 KEYWORD_ANALYZER 且不是 PHRASE_PREFIX 时,直接 TermQuery(整串) 返回——所以对 keyword 字段发 match 不会切词(实验 15 验证)。text 字段继续 createBooleanQuery:

token 情况建成什么
0 个(停用词滤光)null,按 zero_terms_query(默认 none → 不匹配)
1 个单个 TermQuery(「单词 match 优化」就在这里,不是另一次 rewrite)
多个、跨多个 position("quick brown" 就是)analyzeMultiBoolean:每个 position 一个子句,occur 是 SHOULD/MUST
// MatchQueryParser 内部类 analyzeMultiBoolean(节选)
BooleanQuery.Builder q = newBooleanQuery();
while (stream.incrementToken()) {
    if (posIncrAtt.getPositionIncrement() != 0) {
        add(q, field, currentQuery, operator, false);   // operator = SHOULD(默认)
        currentQuery.clear();
    }
    currentQuery.add(new Term(field, termAtt.getBytesRef()));
}
// 产出: BooleanQuery(SHOULD: TermQuery("title","quick"), SHOULD: TermQuery("title","brown"))

它将成为第 17 课 originalQuery.query() 的那一份(还没加 alias FILTER,也还没 searcher.rewrite)。operator: and 只改 occur 为 MUST:两个词都要在,不是变成 phrase——短语要位置相邻,那是 match_phrase → Type.PHRASE → PhraseQuery(实验 16、17 用三档严格度对照)。

match 参数默认记住
operatoror多 token 之间 SHOULD 还是 MUST
analyzer字段 search analyzer覆盖字段默认;写错名字 QueryShardException
minimum_should_match无套在布尔上(至少中几个)

fuzziness无有它时 Builder rewrite 拒绝收成 TermQueryBuilder

4. term 不切词:和 match 对同一字段会怎样

第 11 课用 _analyze 看过索引侧:text 词典里是 token,keyword 词典里是整串。查询侧的对称命题:term 不会再跑 tokenStream。

// TermQueryBuilder.doToQuery(节选)
return mapper.termQuery(value, context);      // caseInsensitive 是另一分支

// TermBasedFieldType.termQuery —— 父类没有分析器
failIfNotIndexed();
return new TermQuery(new Term(name(), indexedValueForSearch(value)));
// indexedValueForSearch: BytesRefs.toBytesRef(value) —— 原样转,不 tokenStream
查询(text 字段)去词典找的 key文档索引后的 key命中?
match: "quick brown"quick、brown(SHOULD)the/quick/brown/fox是
term: "quick brown"整串 quick brown没有这个 term否
term: "quick"quick有是(碰巧已是 token)
term: "Quick"Quick(保留大写)只有小写否

term 在 text 上仍然跳过分析:整串、大小写不对,都会 0 hits。keyword 上的 term 对整串(天作之合);配了 normalizer 只 normalize 出恰好一个 token——不是 match 那种切多词,"Quick Brown" 经 lowercase normalizer 只是变成带空格的 quick brown 一整串。

5. bool:must 算分,filter 不算分、才谈得上缓存

子句必须命中?参与 BM25?Lucene Occur与缓存
must是是MUST要 TF/IDF,bitset 替代不了打分
filter是否FILTER只要在不在:可收成 BitDocIdSet / RoaringDocIdSet
should默认否;无 must/filter 时至少中一是SHOULD可选加分;minimum_should_match 可收紧
must_not必须不中否MUST_NOT同 filter,不算分
// BoolQueryBuilder.doToQuery(节选)
BooleanQuery.Builder builder = new BooleanQuery.Builder();
addBooleanClauses(context, builder, mustClauses,     BooleanClause.Occur.MUST);
addBooleanClauses(context, builder, mustNotClauses,  BooleanClause.Occur.MUST_NOT);
addBooleanClauses(context, builder, shouldClauses,   BooleanClause.Occur.SHOULD);
addBooleanClauses(context, builder, filterClauses,   BooleanClause.Occur.FILTER);
if (builder.build().clauses().isEmpty()) return Queries.ALL_DOCS_INSTANCE;  // 空 bool ≡ match_all

缓存的真名字要拆开记:① Occur.FILTER 是布尔子句类型,子 Weight 的 ScoreMode 不需要分数(缓存命中后 ConstantScoreScorerSupplier(..., COMPLETE_NO_SCORES));② 节点级 IndicesQueryCache → XLRUQueryCache 把「这个 Query 在这个 segment 命中哪些 doc」收成 DocIdSet——稠密(≥1%)进 FixedBitSet,稀疏进 RoaringDocIdSet;③ BitsetFilterCache 是另一份缓存,给 nested / join 这类必须一直物化 BitSet 的组件用,别把它说成 bool.filter 的实现。还有一条泼冷水:默认 UsageTrackingQueryCachingPolicy 会跳过太便宜的查询(单个 TermQuery 常不进缓存),所以「连打两次 term filter,hit_count 必 +1」不成立——选 filter 的第一理由是语义(不算分),缓存是有启发式的附加收益。

最后,post_filter 不是第五种子句:它是 SearchSourceBuilder 上另一份 QueryBuilder,在 hits 已按 query 排完、聚合也按 query 的文档集算完之后,再滤一层 hits——聚合桶不受它影响(实验 14)。侧边栏 facet 用它,不要和 bool.filter 混成一个开关。

6. 接到第 17 课:三层字段从这里填上

toQuery 不是 SearchContext 的方法,分片上的链是:SearchSourceBuilder.query → SearchExecutionContext.toQuery(Builder rewrite + doToQuery,收成 ParsedQuery)→ 写入 originalQuery → preProcess 加 alias FILTER → rewrittenQuery() 交给 QueryPhase。本课的 doToQuery 填第一层:

// SearchExecutionContext.toQuery(节选)
Query query = Rewriteable.rewrite(queryBuilder, this, true).toQuery(this);
if (query == null) query = Queries.newMatchNoDocsQuery("No query left after rewrite.");
return new ParsedQuery(query, copyNamedQueries());

// AbstractQueryBuilder.toQuery 是模板方法:子类 doToQuery 出 Lucene Query,
// 基类再套 boost(BoostQuery)与 _name(named queries → matched_queries)

第 16 课 Query 阶段每个 shard 回的 _score,就是这份查询(经后两层加工)在该 shard 的 EXTERNAL searcher 上跑出来的分数。

7. 其余查询:一张 8 行表够用

doToQuery 的模式都一样:看 MappedFieldType,让字段类型决定 Lucene Query。

清理

思考题

1. 只有一篇文档 title 为 "Elasticsearch in Action"(text)。A:term "elasticsearch";B:match "Elasticsearch Action";C:term "Elasticsearch in Action"。各几 hits?把 title 改成 keyword 再发 B、C 呢?

A:1 hit(查询串碰巧等于索引 token)。B:match 分析成 elasticsearch/action,SHOULD 都中 → 1 hit。C:整串 key 不在词典 → 0 hits。改成 keyword:B 的 match 走 KEYWORD_ANALYZER 短路成整串 "Elasticsearch Action" ≠ 存进去的整串 → 0 hits;C 整串精确相等 → 1 hit。同一套 JSON,字段类型一换,match/term 胜负对调。

2. 若 MatchQueryBuilder.doToQuery 直接把 alias FILTER 包进用户查询、只留一份查询,highlight / _explain 哪条不变量破?若执行时跳过 preProcess 的 buildFilteredQuery 又怎样?QueryBuilder.rewrite 能代替 searcher.rewrite 吗?

提前包进 doToQuery:_explain / highlight 会多出用户没写的 FILTER,对着「用户没写的查询」说话。跳过 buildFilteredQuery:别名过滤丢失,alias 索引会搜到不该看见的文档。都不能。QueryBuilder.rewrite 只在 Builder 上化简(缺字段→match_none、keyword match→TermQueryBuilder),它不跑分析器、也不做布尔展开——切词在 doToQuery,展开在 searcher.rewrite,三步各管一段。

3. status: published 和 date >= 2024-01-01 放 must 还是 filter?什么时候值得用 post_filter?query cache 不会无条件收下每个 Term filter,这怎么影响选择?

不参与「谁更相关」的条件放 filter:分数不被状态/日期拉动,FILTER 的无分 Weight 才允许 query cache 用 bitset 回放。post_filter 换的是「聚合看 query 那批文档、hits 再瘦身」——facet 场景;它不是更快的 filter,也吃不到 Query 阶段的缓存收益。单个 TermQuery 常被 UsageTrackingQueryCachingPolicy 当成太便宜而不缓存——所以选 filter 的第一理由是语义,缓存是附加的、有启发式的,别为了「一定命中 query_cache」把条件写复杂。

陷阱

🕳 对 text 用整串 term:词典里只有切开的小写 token,整串、大写全 miss——0 hits 不是 bug,是查询 key 和索引 key 不是同一种东西。_source 里看得见 ≠ 倒排里找得到。
🕳 把 operator: and 当成短语:AND 只改 occur(SHOULD→MUST),要求「都在」,不要求「相邻」;要相邻用 match_phrase(slop=0)。三档严格度:SHOULD < MUST < PHRASE。
🕳 「filter 更快,所以全写 filter」:filter 不算分是语义差异,不只是性能差异——放 must 的条件会拉动 _score(实验 12 vs 13)。反过来,「filter 一定命中 query_cache」也不成立:便宜的单 TermQuery 常被策略跳过。
🕳 match 不是「永远切词」:它用字段的 search analyzer:keyword 字段上 match 走 KEYWORD_ANALYZER 短路、整串不切(实验 15)。切不切由 mapping 决定,不由查询名决定。

速记

一句话内容

心法:进倒排之前变没变——match 变(token 是钥匙),term 不变(整串是钥匙);算不算分,是 must 和 filter 的分界线。
