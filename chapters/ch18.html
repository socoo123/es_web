查询翻译与过滤边界

查询语法

同样写着 “quick brown”，为什么 match 有结果、term 没结果？JSON 先成为查询描述，字段分析器与字段类型再决定 Lucene 查询的形状；bool 决定哪些条件算分，收集器决定过滤影响 hits 还是聚合。沿这三条边界读源码，才能解释零命中与分数变化。

学习目标

  • 在同一个显式 standard 的 text 字段上，预测 match、整串 term 和大写 term 的命中集合，并用分析输出、保存的词向量解释差别。
  • 用同一数据对照默认 OR、显式 AND 与默认短语查询，说清词项、位置、词序和零词项如何影响 Lucene 查询构造。
  • 用分数、过滤别名 Explain 和两个聚合响应，区分 must、filter、post_filter 的语义及查询缓存的适用条件。

18.1 JSON 到 Lucene Query，中间改写了什么？

DSL 是构造查询的描述。REST 解析出 QueryBuilder，分片的 SearchExecutionContext.toQuery 先调用 Rewriteable.rewrite，再调用 Builder 的 toQuery。子类的 doToQuery 根据字段类型生成 Lucene Query，基类处理 boost 与命名查询，结果包装为 ParsedQuery。此时还没有遍历倒排或返回 hits。toQuery、模板方法。

层次输入与输出负责什么
Builder rewriteQueryBuilder → QueryBuilder按可用上下文化简；可在多个阶段提前发生
doToQueryQueryBuilder → Lucene Query本例在这里分析 title 并组装子句
Lucene rewriteLucene Query → 改写后的 Query执行前按 reader 与查询实现改写

不能把这张表读成所有查询固定三次分配新对象。默认 keyword 的 match 在 doIndexMetadataRewrite 中可提前变成 TermQueryBuilder；有 fuzziness 或 lenient 时该优化会跳过。显式分析器、normalizer 和字段类型都会影响结果。图 01 刻意只展开 本课 title=text、standard、默认 OR、无同义词与模糊参数的两条转换路径。keyword 的 Builder 改写。

第 17 课的三个查询字段接在这之后：parsedQuery 同时保存 originalQuery 与 query；preProcess 根据 alias、nested、slice 等条件补充 FILTER；rewrittenQuery() 懒加载 searcher.rewrite(query())。没有额外约束时 query 可以就是原查询。默认高亮可取原 ParsedQuery；Explain 则取执行查询。默认高亮来源。保存原查询、前处理过滤、执行改写。

18.2 match 用分析器，term 用字段查询工厂

match 未指定 analyzer 时使用字段的 search analyzer。本课显式将索引与搜索分析器都设为 standard：StandardTokenizer 按词边界切分，LowerCaseFilter 小写化，默认停用词表为空，因而保留 the。它不是简单的空白切分器。Quick, BROWN! 的两个输出也为 quick、brown。选择搜索分析器；Lucene 10.4.0 分析链、默认空停用词表。

term 则委托 MappedFieldType.termQuery。本课默认 text 的继承实现直接把值转成 BytesRef，再建 TermQuery，不运行全文 tokenStream。因此关键问题是“查询值与已索引的 term 是否一致”，不能只看 _source 中有没有那句话。term 字段委托、默认词项查询。

title 查询本例用来匹配的 term命中 ID
match quick brownquick / brown，默认 SHOULD1、2
term quick brown带空格的一个整串无
term quick小写 quick1、2
term Quick大写 Quick无

_analyze 展示分析结果，不是直接读取整个倒排词典。本课额外保存了 title 的词向量，A5 对文档 1 读出 the/quick/brown/fox，位置为 0/1/2/3。词向量带 offsets 是本课 term_vector=with_positions_offsets 的显式设置，不代表默认 text 总保存字符偏移。A4、A5、A6 与搜索对照共同构成证据。

keyword 的边界 默认 keyword 分析器保留整串，match 可提前 Builder 改写，parser 内另有关键词短路。配了 normalizer 的 keyword 仍会归一化单词项：本课 status_fold 的大写 PUBLISHED 经 lowercase 可被 term 命中。显式 analyzer 也可覆盖本次 match，不能把“term 不分词”概括成“所有字段都原样比较”。parser 短路、单词项归一化。

18.3 两个词都在，不等于同一个短语

MatchQueryBuilder 默认 operator 为 OR，映射为 Occur.SHOULD；AND 映射为 MUST。parser 取得 tokenStream 后先检查词项数、位置和词图，本例两个独立位置进入 analyzeMultiBoolean，每个位置生成一个 TermQuery 子句。不要将“任意多 token 的 match”都简写为两个普通 TermQuery：同位置同义词、词图、模糊与前缀都有其他构造。默认 OR、Occur 映射、词流分类、多位置 Boolean 构造。

相同数据上的请求条件实测 ID
match quick fox，默认 OR至少一个 term1、2
match quick fox，AND两个 term 都在1
match brown quick，AND词序不约束1、2
match_phrase quick brown默认 slop=0，分析后词序与相对位置一致1、2
match_phrase brown quick / quick fox分别词序反向 / 中间有间隔无 / 无

只看 quick brown 的 match 命中 1、2 无法证明默认 OR，因为两篇刚好都含两个词。B1 换成 quick fox，只有一个词的文档 2 仍然入选，才与 B2 的 AND 构成有效对照。同一文档的多个匹配子句可累加评分贡献，但跨文档不能仅用“命中更多词”保证名次，词频、文档长度等也影响分数。

零词项也要与缺字段、零命中分开。本课 standard 不移除 the；B7 明确在本次 match设置 analyzer=stop，分析 the 得零词项。zero_terms_query=none 返回无匹配，改成 all 则选择 match_all；这不修改 mapping，也不把词加回分析输出。实际外层 bool 或别名过滤仍然适用。零词项处理。

六步快照保留 JSON、参数、词流、子句、term 对照与 SearchContext 连接，便于暂停逐步读。它解释本例构造，不承诺每种字段或查询都走相同路径。窄屏可以在快照内部横向滑动。

18.4 bool 的分界是评分语义，缓存另有条件

子句匹配要求普通评分上下文中的贡献Occur
must必须命中有MUST
filter必须命中无FILTER
should按门槛决定有SHOULD
must_not必须不命中无MUST_NOT

映射由 BoolQueryBuilder.doToQuery 完成，filter 与 must_not 还走去重添加路径，空 bool 返回 match_all。这里的“must 算分”指普通评分上下文；外层若把整个 bool 放进 filter 或根本不需要分数，不能据子句名字断言一定执行评分。单层 bool 有 should 且无 must/filter 时，默认门槛为 1；已有 must 或 filter 则为 0，显式 minimum_should_match 可以收紧。嵌套 bool 各层分别判断。真实四子句构造；官方门槛说明。

C5 与 C6 命中同一篇文档 4，但把 status 从 filter 移入 must 后分数上升；本例 keyword 的 TermQuery 也使用相似度评分，不是固定常数分。C7 只有 filter，三篇分数为 0。C8 加一个 should quick，在同层已有 filter 的条件下它默认可选，文档 3、4 仍留下；C9 显式门槛为 1 才只剩文档 1。把过滤条件误放进 should，可能直接改变返回集合。

无分命中集合可以缓存，但 FILTER 不等于必定缓存。节点级 IndicesQueryCache → XLRUQueryCache 按 query 与 segment 保存 DocIdSet，仍需 Weight 可缓存、segment 合适、策略与容量允许；本章四篇数据不验证缓存命中。使用跟踪策略会跳过单个 TermQuery 等便宜查询。BitsetFilterCache 是另一套服务 nested 等场景的缓存，不能作为 bool.filter 的同义词。优先按是否需要评分选 filter，再讨论性能。缓存资格与策略；Lucene 策略。

源码细节：集合表示不是一句“命中率 ≥1%”

cacheImpl 用 scorer.cost() * 100 >= maxDoc 选择 BitDocIdSet/FixedBitSet，否则用 RoaringDocIdSet；依据是 scorer 的 cost 估计，不是事后精确命中文档占比。两种表示都存命中集合，不能替代原查询的评分计算。缓存集合选择。

18.5 post_filter 是另一条收集门槛

若希望列表只展示 published，但状态分面仍显示 draft 的数量，应该在哪里过滤？把 published 放进 query 的 bool.filter，会先缩小主查询候选集，普通顶层聚合也只看到 published。独立的 post_filter 则限制 hits，保持该聚合的主查询范围。图 02 对应 C10 的四篇文档实验。

QueryPhase 对 post_filter 创建 COMPLETE_NO_SCORES Weight，再传给查询阶段收集器。CompositeLeafCollector.collect 只在 TopDocs 路径调用 shouldCollectTopDocs 检查 postFilterBits，聚合路径独立收集。因此不能解释成“取出 size 条并排好序后再删 hits”：否则过滤后可能凑不齐应有的匹配结果。它也不是第五种 Occur。无分 Weight 与收集、hits 门槛、两路收集。

18.6 Explain 观察的是执行查询

单篇 _explain 和搜索体里的 explain:true 是不同入口，普通主查询评分都解释 rewrittenQuery，还可能叠加 rescore 等处理。单篇入口会先 parsedQuery → preProcess，所以别名过滤也参与判断。C4 对 published 别名解释文档 2：虽然 quick、brown 都中，但 status=draft，返回 200、matched=false，并能看到 status:published 的失败条件。不能说 Explain 只对用户 originalQuery 说话。单篇解释、搜索命中解释。

Explain 里可找 title:quick/title:brown 的贡献，却不保证文字包含 SHOULD。B9 的 validate 查询表示、Occur 源码和 OR/AND 命中对照一起解释构造。网页对带查询体的 Explain 使用 POST；底层 ES 也有 GET 路由，但本浏览器客户端不发送 GET body，旧卡实测会得到 400 缺 query 验证错误。

思考题

1. 文档 4 的 title 若换成默认 keyword，match “Elasticsearch Action” 与 term “Elasticsearch in Action” 各如何？

默认 keyword 保留整串，前者整串不等于字段值，零命中；后者精确相等，命中。若给 keyword 配 normalizer 或给 match 显式 analyzer，要按新条件重算。mapping 类型不能在已建字段上直接切换，本题是假设重建字段后的对照。

2. 为何 AND “brown quick” 命中，而 match_phrase “brown quick” 不命中？

AND 只要求两个 term 都在，不检查词序；默认 slop=0 的短语按分析后的相对位置与词序匹配。原文 quick brown 两词相邻却顺序相反。quick fox 是另一个不匹配原因：同序但相隔一个词。

3. published 放 filter，再放 should quick，不设门槛会排除 lazy dog 吗？

不会。同层已有 filter，should 默认门槛 0；published 的 lazy dog 保留、分数为 0。显式 minimum_should_match=1 才要求 quick 命中。嵌套 bool 的门槛要按层判断。

4. 想让分面显示 draft、列表只显示 published，为什么不能先取 size 条再过滤？

先截断可能丢掉排在窗口外但满足 published 的文档。post_filter 是 Query 阶段 hits 收集门槛，聚合继续看主 query 集合。放在 bool.filter 则同时缩小两路；是否缓存不能改变这项语义选择。

5. 别名 Explain 会解释过滤后的查询，为什么还保留 originalQuery？

两者服务不同观察需求。默认高亮可以取原 ParsedQuery，执行 Explain 则先 preProcess 并取 rewrittenQuery，必须尊重别名过滤。不能为了让解释“干净”跳过 buildFilteredQuery；过滤别名的范围约束会丢失。

陷阱

_source 有整句，不代表 text 有这个整串 term先看 mapping 与分析输出，再核对本例保存的词向量。默认 text 上的 term 不做全文分析；normalizer、case_insensitive 等显式条件需另判断。
AND 不是短语，命中更多词也不保证跨文档排名更高AND 管词项条件，match_phrase 管分析后的相对位置与词序；评分还取决于其他统计。
filter 的意义是无分条件，不是无条件缓存纯 filter 本例分数为 0；加入评分子句可改变分数。四篇数据、两次重复请求均不能证明缓存 hit_count 必增。
post_filter 不是排序结束后再删 Top-N它在 Query 阶段只门控 hits 收集，不影响本课普通聚合。Explain 也解释执行查询；带 body 的网页请求使用 POST。

速记

机制可检验的结论
转换链Builder rewrite → doToQuery → Lucene rewrite；可复用对象，不是每步都分配
match / termmatch 用搜索分析器；term 委托字段工厂，不做全文分词，但可单词项归一化
本例词流standard：词边界 + lowercase，保留 the；无同义词的两位置 OR 构造 SHOULD
AND / phraseAND 都在；默认短语检查词序与相对位置；zero_terms_query 控制零词项行为
bool普通评分上下文 must/should 贡献分；filter/must_not 无分；should 门槛按同层判断
收集范围query 约束两路；post_filter 只门控 hits；Explain 观察 rewrittenQuery
缓存与重做缓存依赖策略/segment；点名清理 → 创建 → green → 固定 ID 写入并 refresh → 对照

心法：先看词项怎样生成，再看谁参与评分，最后看过滤约束哪条收集路径。
