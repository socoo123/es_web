25.1 资源不足，应该检查哪一道入口？

第 19 课的 terms 可以只返回两个桶，却在收集、候选排序和结果合并中使用更多内存。第 8 课的线程池可以只排有限任务，却无法单靠任务数约束每个任务的字节量。ES 因而保留几种保护机制：内存熔断器检查估算与堆占用，IndexingPressure 跟踪在途写入字节，线程池限制执行与排队。三者都可能造成 429，处理方式不能只由 HTTP 状态码决定。

熔断器也不是跳过一次就锁住节点的开关。调用方提交一笔估计；子账决定能否记入，随后 Parent 检查总压力。通过后请求继续，失败后调用链释放相应资源。tripped 是累计拒绝计数，不参与下一次准入判断。这是一套降低内存风险的检查，不是覆盖全部分配的硬配额，也不保证节点绝无 OOM。父级复核、未跟踪内存及并发都会影响结果。

保护机制看什么拒绝时先查什么
子 breaker / Parent跟踪估算；默认 Parent 用真实堆加本笔预留circuit_breaking_exception、名称、label、bytes_wanted / bytes_limit
IndexingPressure节点上在途 coordinating / primary / replica 字节es_rejected_execution_exception 的写入阶段与字节原因
线程池执行线程、排队任务、执行器状态es_rejected_execution_exception 的执行器原因与对应池统计

本课图解是固定版本的机制概括，省略插件的自定义 breaker、部分调用方细节和 GC 内部过程。A、B 组只验证 request 的低限额分支；C 组观察正常写入计数，没有以小 Bulk 证明写入拒绝或分块水位实际触发。

25.3 子账拒绝在 CAS 前，Parent 拒绝要回滚

以正数增量 bytes、正子限额为例，子账先读当前 used，计算 (used + bytes) × overhead。严格大于限额才拒绝；拒绝时增加该子账的 tripped，尚未 CAS，本笔没有进入底层 used。没有超限才尝试 CAS；并发修改使 CAS 失败时，循环重读并重新检查。正常加账入口是 addEstimateBytesAndMaybeBreak。

CAS 成功后，Child 调用 checkParentLimit((long)(bytes × overhead), label)。若 Parent 抛出熔断异常，Child 用 addWithoutBreaking(-bytes) 撤销本笔，再把原异常向上传递。回滚使用原始字节；直接调整不乘 overhead，也不再次检查 Parent。账额被扣除和实际堆立即被 GC 回收是两个过程。源码：Parent 失败回滚

两个特殊值还要分开：限额 0 让该子账的检查入口立即拒绝，包括增量为 0 的调用；-1 只跳过子账自身限额检查，仍会检查 Parent，不能解释成整条路径永不熔断。调用方可用 addWithoutBreaking 释放、回滚或直接调整，它本身不作准入检查。源码：0 / -1 分支

25.4 Parent 默认看真实堆，首次超限还要复核

默认 indices.breaker.total.use_real_memory=true，Parent 比较量是 HeapMemoryUsage.getUsed() + newBytesReserved。Parent 不是可单独 add/subtract 的第四本子账；它在检查时计算总量。开关为 false 才汇总全部注册子账的 used × overhead，该汇总已包含 Child 刚记入的增量，不再额外加预留。Parent 默认限额随模式分别为 95% / 70%；实际配置必须读取覆盖与运行时字节值。源码：模式与真实堆采样

常见子账（并非全部）默认限额 / overhead记账类别
request堆 60% / 1.0请求内存，TRANSIENT
fielddata堆 40% / 1.03字段数据与全局序数相关缓存，PERMANENT
inflight_requests堆 100% / 2.0传入请求占用估算，TRANSIENT

这些百分比是默认分类限制，不是预先划好的互斥内存分区；之和可以超过 Parent 限额，不能由此推断同一时刻各账必不顶满。overhead 是估算修正系数；子账统计 estimated_size_in_bytes 输出原始 used，比较限额时才乘该系数。durability 是跟踪内存类别的提示，不是“PERMANENT 只能手动清缓存、TRANSIENT 必定立即释放”的承诺。源码：限额与 overhead 默认值

在 checkParentLimit 中，第一次测量超限后会调用 overLimitStrategy，策略结果仍超限才增加 Parent 的 tripped 并抛异常。真实堆与 G1 条件满足时可尝试 GC 后复测；其他条件可使用恒等策略。复核不承诺回收成功。Parent 异常的 durability 由所有子账 transient / permanent 估算占比决定，不只看本次调用使用 request。源码：复核与 durability

Parent 的 stats 使用 memoryUsed(0)：默认是当前真实堆采样，false 模式是所有子账的加权和。不能把节点 JVM 所有内存都当成 Java 堆，也不要求 Parent 值必大于几本子账的裸 used。采样时刻、预留估算、GC 和其他活动都会改变数值。实验前提 4、5 先辨认口径，再谈大小。源码：统计口径

25.5 聚合的 6KB 预留与 5KB 重量怎样相遇？

单个普通聚合 builder 的默认预留是 6KB = 6144 字节，聚合树会累计各 builder 的预留。上下文先用 preallocate[aggregations] label 向底层 request 账申请这笔，再把 Aggregator 与 BigArrays 接到 PreallocatedCircuitBreaker 包装器。AggregatorBase 的默认重量是 5KB = 5120 字节，这笔会先消耗已有缓冲，不是底层额外再加 5KB。

举例：先预留 6KB，内部消耗 5KB，底层仍记 6KB；后续累计内部消耗达到 8KB，仅向底层再记 2KB，并进入满缓冲直通状态。后续释放跟随相应路径；Aggregator 关闭退自己的 requestBytesUsed，包装器最后关闭时处理尚未用满的预留。这是预留覆盖与补差，不能画成“6KB + 5KB + 数组”。源码：覆盖、补差与关闭

三次 terms 对照都显式带 request_cache=false，排除分片请求缓存对重复查询执行路径的干扰。此参数只控制本次请求，不改变索引的缓存配置。同一请求 body 不等于一定重新执行相同收集过程，因此要把缓存条件也写入实验前提。

B 组将底层 request 限额降到 1KB。在默认 memory 类型、overhead=1、普通 terms 和堆有余量的前提下，单 agg 的 6KB 初始预留已经超过 1024 字节，预期在子账 CAS 前拒绝，还没有以本次结果验证高基数收集内存。错误可能包装在搜索异常中，要继续读 root_cause 或 failed_shards 的 reason。异常中的 bytes_wanted 可以含此前 used，不必精确等于 6144。

BigArrays 的部分扩容在分配前检查，也有已创建小数组再核算、失败后释放的路径，不能一概说“调用方从不先分配”。标签 <reused_arrays> 指这类记账；Aggregator 的零字节周期检查会给 Parent 再检查真实堆的机会，协调端归并也可记录 <reduce_aggs>。请求结束后的低 used 不能反推峰值内存。源码：分配前与分配后核算

size、shard_size 会影响响应与候选窗口及相关内存，但不能限定全部收集状态。高基数风险还受查询范围、执行方式、子聚合与并发影响；min_doc_count 不是对收集内存的普遍上限。需要桶列表就继续使用合适的桶查询；只有业务要近似去重计数时才考虑 cardinality，两者不能等价替换。源码：收集后的候选窗口

25.6 写入压力与队列各有一套账

IndexingPressure 不是 CircuitBreaker 实现。在普通非 forceExecution 路径中，coordinating / primary 先把增量记入共享 combined 账，再加当前 replica 字节，与该阶段限额比较；超限撤销刚加入的增量并增加相应 rejections。replica 则对自己的当前字节与 replicaLimit 比较。释放句柄扣除当前占用。它们都可能通过 EsRejectedExecutionException 对外表现为 429。源码：primary / replica 判断

默认项9.4.0 条件
coordinating / primary 限额分别默认继承 indexing_pressure.memory.limit（堆 10%）；可显式不同
replica 限额默认 1.5 × primary 配置；默认组合下相当于堆 15%
增量 Bulk 高水位分块当前 combined + replica ≥ 堆 7.5%，且当前块操作字节 ≥ 1MiB
增量 Bulk 低水位分块高水位分支未命中；当前用量 ≥ 堆 5%，且当前块操作字节 ≥ 4MiB

分块水位属于调用 Incremental.maybeSplit() 的增量 Bulk 处理路径，不是“任何 HTTP Bulk 原始包超过 1MB / 4MB 就必拆”。比较的是两项同时满足的 ≥ 条件，高水位先判断。这些默认量可由节点配置改变，本章不修改它们。C 组只观察正常写入的 current 与 total；线程池 queue 计任务，不能和写入字节相加。源码：水位与块字节的 ≥ 条件

25.7 从一次 429 到可重复的恢复

先读取完整错误链。[request] 与 [parent] 表示不同拒绝位置；内存异常带 bytes_wanted、bytes_limit、durability，写入或执行器拒绝则看阶段、池名与 reason。再对照同一节点、同一时间附近的统计，比较当前量与计数增量。不能把旧 tripped ≥1 当作本次证据，也不能断言一次 REST 请求只增加一次计数。

恢复限额只改变后续检查条件。null 删除指定层的设置覆盖，生效值可能回到 persistent、节点配置或默认值；并不自动恢复你先前覆盖掉的 transient 原值。B 组因此只允许原先无相关集群覆盖的专用节点，显式清理并核对实际限额，不把单节点重启当清理方法，也不把 transient 当生产配置建议。源码：删除的是指定覆盖

图下的七步机制保留 Parent 拒绝示例：H=1000MiB，request 已记 50MiB、增量 500MiB，子限额 600MiB；堆采样 900MiB，Parent 限额 950MiB。假定复核后仍超限，Child 撤销 500MiB，再传递标明 [parent] 的异常。示意使用清楚的算术，不是把 1GiB 的 95% 写成 950MiB；实际百分比字节值以 API 为准。

一次拒绝可以帮助节点继续服务，但不保证下一次请求成功、堆占用不变或集群一直 Green。健康色描述分片可用性。优化时先缩小查询与聚合范围、控制并发，写入客户端检查 item 错误并采用有界退避重试；不要无限立即重试同一个失败请求。此处是处理建议，未在本章实现自动重试器。

实验：基线 → 低限额 → 恢复 → 清理重做

实验前提与实测状态ES 9.4.0 / Lucene 10.4.0，专用单节点、无并发客户端，默认 memory 型 request 与 overhead=1，堆有余量。默认教程端点是 http://localhost:9200、匿名；启用安全的节点先在控制台选择有效认证。本轮云端官方容器因缺少 /proc/self/coredump_filter 启动失败，以下全部为源码核对后的待实测预期，未执行 API、清理或重做。

思考题

1. request 限额设为 -1，Parent 还会拒绝吗？

会。-1 只选择子账的 noLimit 加账路径，之后仍执行 checkParentLimit；0 则在子入口立即拒绝。直接 addWithoutBreaking 只作调整，不等同于正常准入。

2. 6KB 预留后消耗 5KB，再消耗到 8KB，底层记了多少？

先 6KB，消耗 5KB 时仍为 6KB，累计消耗到 8KB 时再补 2KB。包装器用预留覆盖内部记账，不能写成 6+5+8KB。其他内存仍可能另行记账，不能拿这三个数字当总峰值。

3. Parent 初次测到真实堆加预留超过 95%，一定马上 429 吗？

不一定。先执行超限策略，策略结果仍超过实际限额才抛。G1 条件满足时可能尝试 GC 并复测，但不保证回收或通过；显式配置也可能使限额并非 95%。

4. null 恢复以后，limit 不是原值却返回 acknowledged=true，算恢复成功吗？

不算。null 只删除该层覆盖，不还原被覆盖掉的旧值。本章用原先无覆盖的前提避免这个问题，并同时核对设置与运行时限额；tripped 可以保留累计，它不会锁住新请求。

5. 返回两个 terms 桶与只需要去重数量，能用同一种优化吗？

不能直接等价。size 控制桶窗口，但不约束全部收集内存；cardinality 给近似计数，不给同样的桶和每桶文档数。先确认结果语义，再缩小数据范围、候选与并发，不把 min_doc_count 当通用内存上限。

陷阱

把 429 都当内存熔断内存、写入压力、执行器拒绝可同为 429。看完整错误链、名称与对应指标，再决定处理方式。
把预留与消费重复相加6KB 预留覆盖缓冲内的 5KB；超出部分才再交到底层。limit=1KB 实验验证初始预留拒绝，没有测量高基数峰值。
认为 -1 禁用了整套熔断器该值只跳过子限额，Parent 仍检查；0 会立即拒绝子账检查入口。
把首次超限、释放账额当立即拒绝或 GCParent 超限还需策略复核；账额释放与 JVM 堆回收分开。熔断器没有覆盖所有内存分配。
用 null 或重启代替原值恢复null 删除覆盖，不还原被覆盖掉的旧 transient。只能按本组无原覆盖前提执行，并复查实际限额。
把当前统计与历史计数混看tripped、rejections、total 是累计；used、current、queue 有各自口径。删索引不使节点计数归零；健康色也不是内存准入指示。
