熔断器与背压

先记账,超限 429,节点还活着 · 约 15 分钟 · 前置:第 8、19 课 · 14 个实验 + 熔断水位旗舰动画

学习目标

  • 用 GET /_nodes/stats/breaker 指出 parent / request / fielddata 的 limit_size_in_bytes、estimated_size_in_bytes、tripped;并解释默认 Parent 的 estimated 为什么接近真实堆、常大于三本子账之和——不是三本相加。
  • 打开 ChildMemoryCircuitBreaker:说出子熔断器超限时在 CAS 之前就 circuitBreak(账上还没这笔);Parent 超限时账已加上,必须 addWithoutBreaking(-bytes) 回滚再抛。
  • 把 indices.breaker.request.limit 用 transient 调到 1kb,对 tut-l25-card 发一次 terms,观察到 circuit_breaking_exception(label preallocate[aggregations],HTTP 429);再用 null 恢复——可逆,只在本地教程集群做。

1. 心智模型:一本运行中的字节账

熔断器不是保险丝烧断后整机停电。它是一本运行中的字节账:每次分配先告诉账本「我打算再用 N 字节」,账本看限额,要么放行并记下,要么拒绝这次分配——请求失败,节点还活着。假想一台 1GB 堆 的节点:默认 Parent 限额是堆的 95% = 950MB;子账 request 默认 60% = 600MB,fielddata 默认 40% = 400MB。此刻 request 账上已有 50MB,JVM 真实堆已用 900MB。一次高基数 terms(第 19 课的那种)估计还要 +500MB:先加进 request → 550 ≤ 600,过;再问 Parent:真实堆 900 + 这笔预留 500 = 1400 > 950,破 → 把刚加的 500MB 扣回去,抛 CircuitBreakingException,REST 映射成 HTTP 429。三件事同时成立:限额可以叠(子过了还要过 Parent);默认 Parent 看的是真实堆 + 这一笔预留,不是三本子账相加;拒绝发生在加账之后——所以必须回滚,否则账比真实占用还高,后面每笔都更冤。

账本加之前这一笔加之后限额过?
request50MB+500MB550MB600MB过
真实堆(Parent)900MB+500MB 预留1400MB950MB破
fielddata未动0同前400MB过

回滚后 request 回到 50MB;客户端拿到 429;那 500MB 从没真正分配——节点没有被撑爆。写入侧还有另一本账(IndexingPressure,§6),拒绝时抛的是 EsRejectedExecutionException(第 8 课线程池那种),不是熔断器。

3. 子熔断器:CAS 之前就拒绝

调用方从不先 new 一块堆再回头问「能不能用」——它把估计值交给账本,label 会进异常文案,所以实验里你会看见 preallocate[aggregations] 或 <agg [users]>,不是一个泛泛的 "memory"。负数走另一条:addWithoutBreaking,不乘 overhead、不问 Parent、不熔断——专门用来释放或回滚。真正干活的是 ChildMemoryCircuitBreaker:

// common/breaker/ChildMemoryCircuitBreaker.java(节选)
if (memoryBytesLimit > 0 && newUsedWithOverhead > memoryBytesLimit) {
    logger.warn("[{}] New used memory {} [{}] for data of [{}] would be larger ...",
        this.name, newUsedWithOverhead, ByteSizeValue.ofBytes(newUsedWithOverhead), label, ...);
    circuitBreak(label, newUsedWithOverhead);   // 还没有 compareAndSet!
}
// Attempt to set the new used value, but make sure it hasn't changed
// underneath us, if it has, keep trying until we are able to set it
} while (this.used.compareAndSet(currentUsed, newUsed) == false);

子账自己跳的时候,账上还没有这一笔——失败则账面不变,这和 Parent 跳的路径正好相反(§4)。circuitBreak 把文案拼成 [request] Data too large, data for [label] would be [X/Y], which is larger than the limit of [L/M] 然后抛异常;HTTP 状态码不在熔断器里写死,在异常上:

// common/breaker/CircuitBreakingException.java(节选)
@Override public RestStatus status() { return RestStatus.TOO_MANY_REQUESTS; }   // 429
@Override protected void metadataToXContent(XContentBuilder builder, Params params) {
    builder.field("bytes_wanted", bytesWanted);
    builder.field("bytes_limit", byteLimit);
    builder.field("durability", durability);   // request=TRANSIENT / fielddata=PERMANENT
}
子账setting默认限额overheaddurability
requestindices.breaker.request.limit60% 堆1.0TRANSIENT(请求结束就释放)
fielddataindices.breaker.fielddata.limit40% 堆1.03PERMANENT(要清缓存/改查询)

fielddata 多乘 1.03,因为从 doc values 加载到堆的真实占用常略高于估算;request 默认乘 1.0,聚合这边大量走 BigArrays、按页精确加减。限额 0 会立刻 circuitBreak(所以破坏实验用 1kb 不用 0b);-1 表示只记账永不跳。

4. Parent:不是第四本账,默认看真实堆

CircuitBreaker.PARENT 的 javadoc 写得很直:Parent 是孩子们的合计上限,自己不能被 add/subtract。每次孩子 CAS 成功之后才问它:

// ChildMemoryCircuitBreaker.addEstimateBytesAndMaybeBreak 末尾(节选)
try {
    parent.checkParentLimit((long) (bytes * overheadConstant), label);
} catch (CircuitBreakingException e) {
    // If the parent breaker is tripped, this breaker has to be adjusted
    // back down because the allocation is "blocked" but the breaker has
    // already been incremented
    this.addWithoutBreaking(-bytes);   // 回滚用原始 bytes,不再乘 overhead
    throw e;
}

这就是「先加会计再拒绝」:孩子账已加上,Parent 说不行,必须减回去。若漏掉回滚,图 1 的 request 会永远顶着 550MB,之后再来 51MB 的合法聚合就会撞 600MB 孩子限额——而那 500MB 根本没分配成功。Parent 的 setting 是 indices.breaker.total.limit,默认值跟着 indices.breaker.total.use_real_memory(默认 true)走:

// indices/breaker/HierarchyCircuitBreakerService.java(节选)
public static final Setting<Boolean> USE_REAL_MEMORY_USAGE_SETTING = Setting.boolSetting(
    "indices.breaker.total.use_real_memory", true, Property.Dynamic, Property.NodeScope);

public static final Setting<ByteSizeValue> TOTAL_CIRCUIT_BREAKER_LIMIT_SETTING = new Setting<>(
    "indices.breaker.total.limit",
    settings -> USE_REAL_MEMORY_USAGE_SETTING.get(settings) ? "95%" : "70%",
    ...);

checkParentLimit 拿什么和 95% 比,也由这个开关决定:trackRealMemoryUsage=true 时 totalUsage = currentMemoryUsage() + newBytesReserved,前者接 MEMORY_MX_BEAN.getHeapMemoryUsage().getUsed()——图 1 的 900+500=1400 就是这条;false 时才退化成「各孩子估算之和」,限额默认也变 70%(集成测试常关这个开关,所以测试里看到 70% 别抄进生产笔记)。孩子的 used×overhead 仍会汇总成 transient/permanent 两列,但那只用来挑 Parent 异常的 durability(瞬时多 → TRANSIENT),不是默认限额的比较项。`GET /_nodes/stats/breaker` 里 parent 那行的 estimated_size_in_bytes 同源:默认模式下约等于此刻真实堆——所以常常大于 request+fielddata+inflight 的 estimated 之和,堆上还有倒排、segment、线程这些没挂账本的东西。实验 0 就要你先预测这一点。

5. 第 19 课的高基数 terms,字节怎么进 request 账

第 19 课钉死过:size=2 只限制返回的桶,收集期仍要给见过的每个全局序数记账。本课补账本这一侧。聚合上下文一建立,先按所有 agg 的 bytesToPreallocate() 之和在 request 上扣一笔——单个 agg 默认 DEFAULT_PREALLOCATION = 6kb,标签 preallocate[aggregations]。把限额调到 1kb 时往往在这里就 429 了,还没走到收集文档、更没走到 shardSize(实验 4-7 验证;集成测试 CircuitBreakerServiceIT.testAggTookTooMuch 把限额设 100b,断言文案含这个 label)。每个 Aggregator 构造时再挂 5kb:

// search/aggregations/AggregatorBase.java(节选)
public static final int DEFAULT_WEIGHT = 1024 * 5;   // 5kb
// 构造器末尾:
addRequestCircuitBreakerBytes(DEFAULT_WEIGHT);

protected long addRequestCircuitBreakerBytes(long bytes) {
    if (bytes >= 0) {
        context.breaker().addEstimateBytesAndMaybeBreak(bytes, "<agg [" + name + "]>");
    } else {
        context.breaker().addWithoutBreaking(bytes);   // 释放走这条
    }
    this.requestBytesUsed += bytes;
    return requestBytesUsed;
}

BigArrays 扩页时标签是 <reused_arrays>;收集过程每 1024 次还会 addEstimateBytesAndMaybeBreak(0, label)——加 0 字节,专门给 Parent 一个「用真实堆再看一眼」的机会。所以高基数 terms 的内存曲线是:先 6kb 预留 → 再 5kb 重量 → 计数数组随基数涨,每涨一次就可能 MaybeBreak;把 size 写成 2 几乎不改变这条曲线。要降内存,换 cardinality、加 include / min_doc_count、或干脆别对 user_id 做 terms——breaker 是安全网,不是配额系统。协调节点合并聚合树时 QueryPhaseResultConsumer 还会记 <reduce_aggs> 一笔,那是数据节点 build 完之后的另一跳;单分片实验里通常先炸在数据节点这一跳。

6. 写入另一条账:IndexingPressure,不是 CircuitBreaker

Bulk 背压和熔断不是同一张决策网。IndexingPressure 不实现 CircuitBreaker,超限抛 EsRejectedExecutionException(第 8 课的老朋友):

角色setting默认
coordinating / primary 上限indexing_pressure.memory.limit(coordinating/primary 各自跟随)10% 堆
replica 上限indexing_pressure.memory.replica.limit1.5× primary = 15% 堆
低水位拆 Bulkindexing_pressure.memory.split_bulk.watermark.low5%;超过则 >4MB 的 Bulk 拆
高水位拆 Bulkindexing_pressure.memory.split_bulk.watermark.high7.5%;超过则 >1MB 的 Bulk 拆

coordinating 真正比较的是「当前 coordinating+primary 字节 + replica 字节」对 coordinatingLimit:超了先把刚 addAndGet 的字节减回去再抛——和 Parent 那条「加了再回滚」是同一类不变量,只是账本不同、异常类型不同。GET /_nodes/stats/indexing_pressure 能看 coordinating_in_bytes / primary_in_bytes / replica_in_bytes 和 *_rejections(本课不把它调爆:写入背压和聚合熔断别缠在一次破坏实验里)。另外,集群健康色不是熔断:Green/Yellow/Red 说的是分片是否 STARTED(第 1、23 课);熔断是单次请求的 429,集群仍可以是 Green。整本账走一遍:

清理

思考题

1. 恢复限额之后 request.tripped 仍 ≥1。此时再发一次不带 aggs 的 match_all(size=0),会因 tripped>0 继续被拒吗?若当初把限额设成 0b 而不是 1kb,不带 aggs 的搜索还能过吗?

tripped 只是计数器,不是锁:恢复 60% 后不带 aggs 的 match_all 照过——它几乎不加 request 账。限额 0b 完全不同:memoryBytesLimit == 0 时任何一次 addEstimateBytesAndMaybeBreak(包括加 0 探 Parent、聚合预留)都立刻 circuitBreak,「简单搜索还能用」指望不上。所以破坏实验用 1kb 这种极小但非 0 的可逆值,并且必须 null 恢复。

2. 为什么孩子必须先 CAS 加上账、再问 Parent,而不是先问 Parent 再加?Parent 跳了却漏掉 addWithoutBreaking(-bytes),哪条不变量破了?子账自己跳时为什么不能先 CAS?

Parent 默认看的是真实堆 + 这一笔预留,不是孩子账本本身;孩子必须先把自己的估算加上,其它并发分配看到的 used 才含这一笔,避免大家同时对同一块空档乐观加。Parent 拒绝说明分配没发生、估算却已入账——不变量是「used = 此刻仍被允许占着的估算」,所以必须回滚。漏回滚的话,图 1 的 request 停在 550MB:再来 51MB 的合法聚合就撞 600MB,而那 500MB 从没分配成功。子账自己跳若先 CAS,失败路径同样要回滚,还会把 used 瞬时抬过限额让别的线程误读——所以它在 CAS 前 circuitBreak,失败则账面干净。

3. 生产上要挡住高基数 terms,三条路:(a) 把 request.limit 从 60% 降得很小;(b) 保持 60%,把 total.limit 从 95% 往下压、继续 use_real_memory=true;(c) 不改 breaker,禁止对 user_id 做 terms / 改用 cardinality。各付什么、换什么?哪条会误伤「聚合很小但节点堆已经很高」的请求?

(a) 专挡聚合/请求内存这一类,但误伤所有稍大的合法聚合——像实验里 6kb 预留都过不了;fielddata 膨胀和「堆被别的东西占满」它不一定挡得住。(b) 挡的是整机:不论字节进没进 request 账,真实堆逼近就拒;误伤的正是「聚合很小但堆已 94%」的请求——包括不带 aggs 的搜索,因为 checkParentLimit 看的是真实堆。(c) 从根上不让一百万基数进收集期,breaker 留给真正的异常尖峰。高基数 terms 优先 (c);breaker 是安全网不是配额系统——第 19 课已经证明极大 shard_size 救不了收集期数组,先撞的就是本课这本 request 账。

陷阱

🕳 把 Parent 当「三本子账之和 ≤ 95%」:那只在 use_real_memory=false 时成立,而且那条路径默认是 70%。当前默认 true:Parent 拿真实堆(HeapMemoryUsage.getUsed())+ 这一笔预留去比 95%,stats 里 parent.estimated ≈ 真实堆,常大于三子之和。
🕳 以为 size=2 就只占两个桶的内存:收集期按基数记账:先 preallocate[aggregations] 6kb、再 agg 5kb、再随基数扩 BigArrays;size/shard_size 只管返回窗口。限额 1kb 时连 6kb 预留都过不了,根本轮不到收集。
🕳 混淆两种拒绝:聚合熔断是 CircuitBreakingException(HTTP 429,带 bytes_wanted/bytes_limit/durability);IndexingPressure / 线程池队列满是 EsRejectedExecutionException(第 8 课)。账本不同、异常类型不同,别在一张图里搅。
🕳 以为 tripped>0 就熔断锁死:tripped 是计数器,恢复限额后不清零也不拦新请求。也别把限额设 0b——那会让任何一次记账(包括加 0 探 Parent)立刻拒绝;破坏实验用 1kb + transient + 课末 null。
🕳 把健康色当熔断指示:Green/Yellow/Red 说的是分片是否 STARTED;熔断是单次请求的 429,集群完全可以 Green 时疯狂 429——反之 Yellow(第 23 课)和内存毫无关系。
