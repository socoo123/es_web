21.1 多个读者怎样共享控制信息？

搜索要知道目标分片在哪，写入要知道索引 mapping，管理操作要检查 block。它们读取的是 ClusterState 的控制信息；文档内容仍存放在分片引擎中。请求协调节点与数据节点可以是同一台机器，但这些职责仍要分清。

逻辑状态采用快照语义：更新构造新对象，旧引用继续看到旧逻辑状态。Builder 可以复用未变化的子对象，不要求每次深拷贝整份树。读取某一份快照避免读到该对象的字段被原地改动，但不意味着所有节点已同时应用，也不意味着一次跨节点请求取得全局事务快照。

职责本课关心的内容恢复边界
Metadata索引定义、mapping/settings、cluster UUID、协调 term 与投票配置；索引表在 ProjectMetadata持久化部分帮助重启恢复；具体受角色、序列化上下文和写入路径约束
GlobalRoutingTable按 project 组织路由表，记录分片状态、主副角色、节点位置集群状态中的路由表不作为这份持久化元数据保存；全重启后重新恢复与分配
DiscoveryNodes当前成员、主节点 ID、本地节点 ID 与角色视图全重启重新发现成员；滚动重启中仍有存活节点保持协调状态
ClusterBlocks全局与 project/索引级操作阻断部分由已保存的设置或恢复流程重建，不能全归为永久配置

“不可变”是概念契约。9.4.0 中 routingNodes 是按需生成的 volatile 缓存，构造过程还会派生 minVersions，但 minVersions 字段本身是 final。不要由缓存推断逻辑状态可原地修改，也不要承诺所有读方法都无锁：构建 RoutingNodes 的慢路径使用同步。

21.3 API 看见的是哪些段？

先选择 metric，再用 filter_path 裁剪输出。metadata,routing_table 只选择这两类状态段；即便 filter 写了 version，也不会创造顶层版本。增加 version metric，才输出 version 和 state_uuid。master_node 是另一项 metric；顶层 cluster_uuid 是状态头信息，cluster_name 由 REST 包装层提供。A4/A5 的差别可以直接验证。

本章索引限定写在 /_cluster/state/{metric}/tut-l21-docs。它限制索引元数据与路由范围，不能把整个 cluster 的 term/version 变成本索引的计数器。A8 读 term 时不带索引限定，因为该路径的元数据过滤分支会只保留索引与必要信息。REST 默认使用本节点已应用的状态；9.4.0 已消费废弃的 local 参数，不要套用旧版“默认一定转主节点”的解释。

位置能说明什么
metadata.indices.tut-l21-docs.settings.index索引的 1 主 0 副等定义；mapping 同在 metadata 的索引条目中
routing_table.indices.tut-l21-docs.shards["0"]当前分片拷贝的 STARTED/primary/node，异步初始化时状态可能不同
metadata.cluster_coordinationterm、last_committed_config、last_accepted_config、voting_config_exclusions；没有名为 config 的投票字段
nodes 与 master_node角色是资格，主节点 ID 是当前当选身份；term 随选举历史变化，不固定为 1
blocks本例无阻断时为空；green 只描述分片健康，不能保证没有只读等 block
观察范围：集群状态 API 用于理解与诊断控制信息，不是稳定的业务查询数据模型。本课请求限制必要 metric/索引；pending_tasks 仍是集群级列表，可能包含其他索引任务。

21.4 一次请求，可能换几份快照？

MasterService.patchVersions 比较新旧对象身份：若 executor 返回原对象，任务可成功而不发布；换了状态对象才递增顶层版本，若 Metadata 身份也变了，再递增内部元数据版本。incrementVersion() 使 UUID 回到未知占位，随后 build() 生成新 UUID。版本与 UUID 重置、构造与子对象复用 是两个不同动作。

身份或版本用途怎样观察
ClusterState.version标识已提交状态的顺序；特殊本地未提交状态另有边界顶层 version；一次索引创建可有创建、分配、STARTED 等多个更新
stateUUID标识具体状态，也是 Diff 的基准锚点version metric 同时输出 state_uuid；它不是索引 UUID 或 cluster UUID
Metadata.version元数据变化时递增的内部版本；等待请求的门槛API 不输出 metadata.version，与顶层不是同一计数器，也不能假设总是严格小于它
文档 _version单篇文档更新的版本GET 文档；已有字段普通写入无需换集群状态

B 组先等待两个索引主分片稳定，再比较 V2 与写文档后的 V3。strict mapping 和显式 keyword 排除了本例的动态字段新增；refresh=true 确保搜索读者刷新，不负责递增集群版本。没有其他任务时 V3 可等于 V2；写入未知字段会被 strict 拒绝，而允许动态 mapping 的另一种配置可触发状态更新。若版本变了，UUID 只能确认状态身份变化，不能单凭它归因到这篇文档。

C 组把本索引 refresh_interval 从 1s 改到 5s，再重交同样的值，对照“值发生变化”与“成功 no-op”。源码上的“每份新状态递增一次”，不能改写成“每个管理 API 只加一”。本章通过本索引设置演示元数据变化，操作末尾显式恢复，再点名删除资源。

wait_for_metadata_version 比较内部版本是否达到门槛（≥），不是等待顶层版本，也不会修改状态。C5 用已满足的 1，C6 用最大 long 和 wait_for_timeout=1ms 做有界超时；超时响应仍 HTTP 200，wait_for_timed_out=true，不附带状态快照。内部版本谓词与超时分支、REST 超时输出 可对照。门槛必须 ≥1，传 0 会返回 400；请求参数检查明确拒绝 0。等待参数不能保证整个 HTTP 请求在 1ms 内结束。

21.5 两条单线程队列，各守哪条边界？

不可变保证旧读者继续读取旧逻辑状态，更新仍要按序组合。如果两个任务都从同一份 N 出发，一份增加索引，一份修改设置，各自输出一份“下一状态”，它们不能由简单覆盖完成正确合成。MasterService 批处理相关任务、基于当前状态计算；发布完成或失败的回调后，再取下一批。

MasterService 的更新池 core=0、max=1；发布可以异步运行，主更新线程等待完成回调，并非忙循环。每个节点的 ClusterApplierService 使用 core=max=1 的优先级执行器。主更新池、发布完成回到更新线程、本地单线程执行器 分别证明计算并发度、批次接续与本地应用并发度。

协调层通常发送 Diff，等待足够有主资格的节点持久接受，再通知 commit 和应用；接受条件来自投票配置，不能偷换成所有数据节点过半。发布接口把主节点自己的应用放在通知应用之后，但不能由此推断所有故障或落后节点都先完成，也不能把“提交成功”理解成所有节点在同一瞬间生效。

本地步骤此时 state() 与回调的约束
连接节点、按条件应用集群设置在引用更新前；需允许持久化且 Metadata 变化，才跑 clusterSettings.applySettings；并非所有索引设置都走这个 consumer
ClusterStateApplier.applyClusterState新状态已提交、尚未更新本地公开引用；用 event.state()，不能把旧 state() 当新状态
state.set(newClusterState)原子换引用，ClusterService.state() 从此返回新快照；旧引用仍有效
ClusterStateListener.clusterChanged引用已更新；通常捕获异常并记录，但同步回调仍占用同一应用线程，慢回调会挡后续状态

Applier 要能处理已提交状态，异常会中断本轮后续应用；Listener 较晚并不等于允许任意重活。两个接口都要求快，适合的重活应异步派发，同时遵守应用组件自身的可见性要求。Applier 契约、Listener 契约、实际回调与异常分支 应一起读。

A10 的 pending_tasks 包含队列待处理项，也可包含当前 executing=true 的任务；同一批次可对应多条任务。持续增长的等待时间值得诊断，但一次空数组只是一次观察，无法证明全程未堵塞，也不能据此测出多节点发布耗时。

21.6 Diff 为什么必须对上上一份 UUID？

一个变化集只在正确基准上才有意义。ClusterStateDiff.apply 先判断当前 UUID 已等于目标 UUID 时可直接返回；否则要求当前 UUID 等于 fromUuid。不匹配就抛 IncompatibleClusterStateVersionException，发布方退回全量；新节点也可直接收到全量。发送分支、不兼容时重传全量 是实际回退入口。

这里省略 wire 编码、压缩、超时与重试。Diff 是传输优化，不改变最终状态的正确性要求；全量也能正确表达下一份状态，成本随元数据规模、节点数与更新频率变化。本章单节点 API 只能观察版本/字段，不验证远程 Diff、投票容错或不同节点的应用延迟，这些需要多节点实验。

动手实验：3 组，29 张操作卡

前提：运行 ES 9.4.0 / Lucene 10.4.0 的单节点学习集群，默认匿名端点 http://localhost:9200；有认证时在连接/控制台配置具备所需权限的凭据。本课只创建 tut-l21-docs 与 tut-l21-ver，不得已有同名数据或适用的外部 mapping 模板。显式 1 主 0 副、auto_expand=false、strict keyword、stored source、refresh=1s、无 default/final 管道。节点变化、后台管理任务和其他索引均可能影响集群版本与队列。

思考题

1. filter_path 点名 version 和 metadata.version，为什么仍可能两个都没有？

顶层 version 需要 version metric；内部 Metadata.version 在 9.4.0 API 上下文本来就不序列化。filter_path 只能裁剪输出，不能越过任一边界。wait_for_metadata_version 能检查内部门槛，不等于响应会输出它。

2. 建索引后 version 增加 3，是否违反“每次新状态加一”？acknowledged=true 又一定会加吗？

一个 API 可以触发创建、分配、分片启动等多个批次；每份改变的状态按源码递增，合起来可超过一次。相同设置重交可以返回原对象，成功但不发布。比较还需排除主任期变化和其他任务；不要仅用总差值猜某个内部批次数。

3. 已声明字段的文档写入后 V3=V2，文档 _version=1。这两个版本冲突吗？

不冲突。文档版本属于那篇文档；集群版本属于控制状态。strict mapping 的既有字段普通写入不需要新增映射。动态 mapping、自动创建索引或同窗口的其他任务会使观察不同；refresh 与集群版本也不是同一机制。

4. 把重活挪到 Listener，就一定不会堵状态应用吗？Applier 应读哪个新状态？

Listener 发生在 state.set 之后，已经不妨碍本轮引用发布，但同步回调仍占用应用线程，下一份状态要等它结束。两个接口都应快速完成，适合的工作派发到后台。Applier 读 event.state()，本地公开 state() 此时仍是旧引用。

5. 接收节点错过一份状态，可以把 Diff 尽力贴上去吗？单节点实验能验证回退吗？

不能。fromUuid 是所需基准，贴到另一份可能组合出主节点从未发布的混合状态；不兼容就退全量。单节点的字段/版本观察没有证明跨节点传输；本章对 Diff 和投票边界提供固定源码证据，实际容错需额外多节点实验。

陷阱

🕳 把序列化当作全部字段：term 来自 CoordinationMetadata，routingTable 的字段类型是 GlobalRoutingTable，minVersions 是 final；API 的扁平索引视图和隐藏的 metadata.version 不等于 Java 的完整对象形状。
🕳 成功请求等于一次版本增加：创建可触发多批次，no-op 可以不发布；版本变化不能单独定位原因。稳定分片后比较同窗口，另核对 mapping、设置和任务。
🕳 不可变等于同步生效或所有读取无锁：节点可落后、旧引用仍读旧状态，惰性派生可有同步慢路径。应用时还要维护各组件，原子换引用不覆盖整个组件更新过程。
🕳 Listener 允许慢，pending 只有未执行项：同步 Listener 会挡后续状态；pending_tasks 也可列正在执行项。读空一次不代表整个期间没有等待。
