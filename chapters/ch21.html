LESSON 21 · 第五篇 · 分布式机制

集群状态

一份不可变快照,集群的「真理之源」 · 约 15 分钟 · 前置:第 5、16 课 · 16 个实验

学习目标

  • 用 GET /_cluster/state/metadata,routing_table 指认 Metadata 里的分片设置与 RoutingTable 里的分片放置;并解释为什么 filter_path 里写了 version,顶层 version 还是不会出现。
  • 列出 ClusterState 真正的 private final 字段;说出 term() 不是字段、Java 字段 routingTable 的类型是 GlobalRoutingTable。
  • 用一次建索引对照顶层 version 从 N 到 N+1、state_uuid 换成新串;再写出 MasterService 与 ClusterApplierService 各自怎么把更新钉成单线程。

1. 心智模型:更新 = 换一份快照,不是在黑板上改字

每个节点内存里都躺着一份当前的 ClusterState,而搜索线程、写入线程、Master 任务线程会同时读它:这个请求该打哪个 shard(第 16 课的路由表)、这个索引还在不在、集群是不是只读(第 5 课的动态设置)。要是这份对象可以原地改字段,读的一方就得加锁,否则随时看见半新半旧的状态。ES 的选择是相反的方向:旧对象永远不改。Master 基于 version N 算出一份全新的 N+1,发布、提交,各节点把引用换成新快照;还攥着 N 的线程继续安全地读——那份快照在被造出来的瞬间就冻结了。

一份快照里,读者这课先记住四块——后文 §4 会把每一块钉到能在 REST JSON 里指认的位置:

组成管什么重启还在吗
Metadata索引定义、Mapping、Settings、cluster UUID、选举用的 term每次更新落盘;全集群重启后仍在
RoutingTable每个分片现在在哪个节点、是 primary 还是 replica只在内存;全重启按 Metadata 重建
Nodes(DiscoveryNodes)集群有哪些节点、谁是 Master、本节点是谁只在内存;滚动重启靠节点间复制保住
Blocks(ClusterBlocks)集群级 / 索引级阻断(只读、恢复中)随状态走;部分由 Metadata 里的设置推导

3. 真正的字段:别背旧图,打开文件核对

ClusterState 类注释把不变量写在最前:概念上不可变;Metadata 落盘、其余内存;更新都提交给 MasterService;同一 ClusterStateTaskExecutor 的任务打成一批,每批产出一份新 ClusterState;发布通常走 Diff。实例字段是这些——除按需缓存的 routingNodes 和派生的 minVersions,全部 private final:

// cluster/ClusterState.java(节选)
private final long version;
private final String stateUUID;
private final GlobalRoutingTable routingTable;   // 不是 RoutingTable
private final DiscoveryNodes nodes;
private final Metadata metadata;
private final ClusterBlocks blocks;
private final Map<String, Custom> customs;
private final ClusterName clusterName;
private final boolean wasReadFromDiff;
// built on demand —— 唯二的非 final
private volatile RoutingNodes routingNodes;

4. 四块逐个钉到 JSON

Metadata。四块里唯一落盘的(XContent 持久化,GATEWAY 上下文必须忠实还原)。集群级字段有 clusterUUID、coordinationMetadata(term、投票配置)、persistentSettings / transientSettings(第 5 课的动态设置就写在这);索引、模板、别名在 ProjectMetadata 里。单 project 的 GET /_cluster/state/metadata 输出:metadata.cluster_uuid、metadata.cluster_coordination.term、metadata.indices.<index>.settings.index.number_of_shards、metadata.indices.<index>.mappings。第 5 课的动态更新在节点侧的挂点也在这:应用时看到 metadataChanged() 才跑 clusterSettings.applySettings,而「变了没有」比的是对象身份(state.metadata() != previousState.metadata()),不是逐字段 equals——「改就换新对象」的后果渗到了每一处判断。

RoutingTable。一张图:ImmutableOpenMap<String, IndexRoutingTable>。JSON 是 routing_table.indices.<index>.shards["0"][],数组元素带 state(STARTED)、primary、node、relocating_node。第 16 课 SEARCH 扇出之前协调节点问的就是它。不落盘:全集群同时断电后,Master 从 Metadata 的索引定义重新分配(第 23 课)。

Nodes。DiscoveryNodes 持有节点 map、masterNodeId / localNodeId 和按角色切好的视图;REST 上 nodes metric 还附带 nodes_versions、nodes_features。master_node 是单独 metric——路径里写它,就只回 Master 的 node id,不必拖整份 nodes map。

Blocks。一份集群级 Set<ClusterBlock> 加按 project 的索引级 block。只读集群(cluster.blocks.read_only)、恢复未完成都走这里。健康空闲的集群上 GET /_cluster/state/blocks 多半是 {}——空也是证据:没有全局阻断。四块之外还有 customs(插件挂的集群级扩展)和按需构建的 RoutingNodes(「按节点看分片」的派生视图,贵,所以惰性)。

5. version 从 N 到 N+1:只有 Master 能加一

任务自己算出的对象,版本号还是旧的;真正加一发生在 MasterService.patchVersions——状态对象变了才 incrementVersion;若 Metadata 的对象身份也变了,再给 Metadata 自己的 version 加一。两套计数器别混:

// cluster/service/MasterService.java(节选)
private ClusterState patchVersions(ClusterState prev, ClusterState next) {
    if (prev != next) {                       // 对象没换 = 没有更新,不发布
        Builder builder = incrementVersion(next);  // version+1,UUID 打回 "_na_"
        if (prev.metadata() != next.metadata()) {  // 身份比较,不是 equals
            builder.metadata(next.metadata().withIncrementedVersion());
        }
        next = builder.build();               // build() 时生成全新 stateUUID
    }
    return next;
}
计数器谁加一REST 上哪里看见
ClusterState.versionMaster 的 incrementVersion顶层 version(metric 必须包含 version)
Metadata.versionmetadata.withIncrementedVersion()metadata 段里;wait_for_metadata_version 等的是它

节点侧换成新引用,靠 ClusterApplierService 里那条 AtomicReference<ClusterState>;ClusterService.state() 只是转调。读到的永远是已经应用完的那一份——不是 Master 正在算、还没 commit 的那份。所以一次成功的建索引:顶层 version 加一、state_uuid 换成另一个字符串(不是旧串改字符);攥着旧引用的线程毫无感觉——旧对象的 version 字段是 final 的 42,没有人能改它。

6. 更新必须单线程:Master 上一条线程算,每个节点一条线程应用

「单线程」不是口号,是两个线程池都把并发度钉成 1,外加一条「算完一批必须等发布结束才接下一批」。

Master 这边。更新线程名 masterService#updateTask,线程池是 scaling 但 max=1;队列从 0 变 1 时才 fork 处理器,然后一直抽到抽干。一批的入口 executeAndPublishBatch:读当前 state() 当输入,跑 executor,再 patchVersions;对象身份没变就不发布,变了就交给 ClusterStatePublisher.publish。发布完成的 listener 被 fork 回同一条 Master 线程——发布期间这条线程闲着,下一批必须等这一批 commit(或失败)才开始。同一 executor 上 Master 忙时涌进来的任务会并成一批、只产出一份新状态:这是吞吐阀门,不是并行授权。类注释自己都承认:cluster state updates run in sequence, one-by-one, so they can be a performance bottleneck——单线程不是因为更新高频要抢 CPU(它相对搜索/写入是低频的),是因为必须全局有序。优先级队列允许紧急任务插队,但洪水般的 HIGH 会饿死 NORMAL,注释劝生产代码尽量用 NORMAL。GET /_cluster/pending_tasks 看的就是这支还没算的队列,空闲集群上是 [],不是坏了。提交任务的现代入口是 ClusterService.createTaskQueue,别再用已废弃的 submitUnbatchedStateUpdateTask。

节点这边。ClusterApplierService 更直接:EsExecutors.newSinglePrioritizing,core=1、max=1。应用顺序写在 applyChanges 里:

// cluster/service/ClusterApplierService.applyChanges(节选)
callClusterStateAppliers(clusterChangedEvent, stopWatch);
nodeConnectionsService.disconnectFromNodesExcept(newClusterState.nodes());
logger.debug("set locally applied cluster state to version {}", newClusterState.version());
state.set(newClusterState);
callClusterStateListeners(clusterChangedEvent, stopWatch);

第 5 课的 applySettings 嵌在 Applier 之前(Metadata 变了才跑)、state.set 之前。Applier 与 Listener 的分工是源码级事实,不是风格建议:

ClusterStateApplierClusterStateListener
调用点state.set 之前之后(此时 state() 已是新快照)
接口方法applyClusterStateclusterChanged
用途内部结构先跟上(如 IndicesService 为新索引建服务)已可见之后的反应(日志、轻量触发)
抛异常非常坏:拦住后面的 Applier,节点可能反复应用同一份状态直到被踢出集群被 catch 后 WARN 一条,不回滚已 set 的快照

发布协议收成四步:发给所有节点(通常是 Diff)→ 等足够多有 Master 资格的节点 accept(写入持久存储)→ 通知大家 commit 并 applyClusterState → 最后 Master 自己 apply。所以 Master 上跑着两个单线程角色:「算出下一份」和「应用到本节点」;非 Master 节点只跑后者。若两个线程同时从 42 算出两份 43,后发布的那份会覆盖先发布的,先那份里的索引或 setting 直接丢失;接收节点的 Diff 也对不上 fromUuid。这就是本课的核心不变量:后一份必须是前一份的函数,所以算和应用都只能一条队列。

Diff:已有节点只收变化

发布通常不传整份 N+1。ClusterState 实现 Diffable,ClusterStateDiff.apply 第一件事就是核对 UUID:

// cluster/ClusterState.java · ClusterStateDiff.apply(节选)
if (toUuid.equals(state.stateUUID)) { return state; }   // 没变,原样奉还
if (fromUuid.equals(state.stateUUID) == false) {
    throw new IncompatibleClusterStateVersionException(...);  // 对不上 → 全量重发
}

不变量:Diff 只能贴在 fromUuid 那一份上。新节点、或中间丢过一份状态的节点对不上 UUID,发布方退回全量——类注释原话:fall back to sending the full state if the receiving node is new or it has missed out on an intermediate state。stateUUID 因此不是装饰品:它让「只传变化」变得安全。wasReadFromDiff 标记这份是不是 Diff 拼出来的,排障时在 toString() 里能看到 from_diff: true。

清理

思考题

1. GET /_cluster/state/metadata,routing_table?filter_path=version 的响应里会有 version 字段吗?同一请求改成 filter_path=metadata.cluster_coordination,term 能看到吗?PUT 一篇 mapping 已声明的文档后再看 version metric,数字涨吗?

不会出现 version。metric 只有 metadata、routing_table 时 toXContentChunked 根本不写顶层 version 段;filter_path=version 裁的是不存在的字段,变不出东西——它只是 REST 层对已写出 JSON 的裁剪。term 可以看到:它住在 metadata.cluster_coordination.term,是 Metadata 的内容,不是 ClusterState 的顶层字段。写文档不涨:文档走 Engine/Translog 的数据平面(第 10、14 课),不提交 ClusterState;若数字真的动了,是别的集群任务在同一窗口发生了——看 state_uuid 是不是也换过,换了才算一次状态更新。

2. 若 Master 用 8 个线程并行从同一份 version 42 算更新,哪条不变量先破——「读不用锁」、「N+1 是 N 的函数」,还是 Diff 的 fromUuid?

破的是后两条,「读不用锁」反而安然无恙。两个任务一个建索引、一个改 max_shards_per_node,都拿 42 当输入、各产出一份 43:后写入的 43 会丢掉前一份里的变更——「每一份已提交状态都是上一份的函数」没了。同时接收节点无法对两份 Diff 都满足 fromUuid == 当前 stateUUID,第二条 Diff 直接 IncompatibleClusterStateVersionException。不可变只让读者免锁,从不授权并行写:MasterService 和 ClusterApplierService 把池子钉成 1,守的就是这条合成顺序。

3. 已有节点传 Diff、新节点传全量:永远传全量破什么?允许「尽力 merge 对不上 UUID 的 Diff」又破什么?把同步逻辑放进 Applier(失败即挡后续应用)而不是 Listener,换来什么、付出什么?

永远全量:正确,但每次改个副本数都要序列化并搬运整份 Metadata + 路由表,大集群的带宽和 CPU 顶不住。乱 merge 对不上 UUID 的 Diff:可能在缺了中间版本的节点上拼出一份 Master 从未提交过的混合状态——共识碎了,这比慢严重得多。放 Applier:换来「对外可见的那份快照,内部结构一定已经跟上」——搜索不会打到一个 IndicesService 还不认识的索引;付出的是 Applier 成了单线程瓶颈,实现必须短、必须消化任何状态且禁止抛异常,慢了就卡住整条应用队列。Listener 允许慢、允许抛,因为它已经不挡 state.set。

陷阱

🕳 把 filter_path 当 metric 选择器:它只能裁剪已经序列化出来的 JSON。metric 不含 version,filter_path 写了也变不出 version;想看就得把 version 写进 URL 的 metric 列表。
🕳 拿旧 classDiagram 背字段:9.4.0 里 term 不是 ClusterState 字段(住在 Metadata 的 CoordinationMetadata);routingTable 字段类型是 GlobalRoutingTable;索引 Map 在 ProjectMetadata.indices——REST 扁平输出只是单 project 的兼容视图。
🕳 以为写文档会涨 version:文档写入走 Engine/Translog 的数据平面,不提交 ClusterState。看到 +1 时先看 state_uuid 换没换——换了才是又一次状态更新(可能是 ILM、健康检查等后台任务)。
🕳 不可变 = 可以并行算再 merge:没有三路 merge 这回事。合成函数是 f: State_N → State_{N+1},单线程守的是写的顺序;不可变只让读免锁。两个 max=1 的线程池不是巧合,是协议的一部分。
🕳 在 ClusterStateApplier 里抛异常:会拦住后面的 Applier,节点可能反复应用同一份状态直到被踢出集群。重活放 Listener——它晚于 state.set,慢一点、抛一下都不影响新快照生效。
🕳 pending_tasks 返回 [] 以为出事了:它列的是 Master 队列里还没算的批,空闲集群就是空数组。真正要警惕的反而是它持续非空——那是状态更新堵了。
