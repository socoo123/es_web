搜索服务与搜索上下文

约 22 分钟 · 前置：第 16 课 · 3 组 / 32 张操作卡（含清理） · 2 幅交互图 / 2 条路径动画 · 1 个六步机制动画

一个分片怎样把查询跑完，又怎样让下一页继续读取同一份数据？SearchService 管执行，SearchContext 装本次状态，ReaderContext 保留读者引用。理解这三者，就能分清查询改写、超时与 PIT 分页各自控制的边界。

学习目标

  • 用 PIT 的上下文统计与第二页结果，解释为什么关闭本次 SearchContext 不会关闭保留的 ReaderContext。
  • 用分词、查询校验、过滤别名的 Profile/Explain/高亮，区分用户查询、补充过滤与 Lucene rewrite。
  • 分别识别 400 脚本保护、200 部分超时、429 严格超时；传最新 pit_id 和完整 sort，完成一次可清理重做的分页。

1. SearchContext 关闭了，下一页怎么继续？

第 16 课解释协调侧如何选出全局命中，本课进入一个目标分片。SearchService 获取读者、准备查询、执行 Query/Fetch 并管理清理。SearchContext 保存本次执行的 query、from/size、排序、聚合、超时与结果；ReaderContext 保存取得 searcher 所需的供应者及引用。两者的区别是职责与所有权，不能只记成“一个短、一个长”。

普通多分片查询在 Query 结束后也可能保留 ReaderContext，供稍后的 Fetch 使用；若没有需要获取的命中，可提前释放。普通 Fetch 完成后释放单会话读者。PIT/scroll 则跨请求保留。SearchContext.close() 通知 closeFuture，释放注册在它上的本次 searcher、结果和查询构造内存等资源，并不等于销毁所有底层 IndexReader。

这一区别可以直接测：本章一主零副 PIT 索引，先记录本索引 open_contexts=N；打开 PIT 后变为 N+1；先后搜两次仍保留这个读者；显式关闭后回 N。本轮两次都是 0→1→0。统计的是保留上下文数，不是独占物理 reader 数；多片 PIT、同索引其他请求及副本选择会改变账本。源码：Query 的创建与关闭、普通 Fetch 释放、Reader 引用清理。

2. void + listener，意味着结果在什么时候交付？

indices:data/read/search[phase/query] 的 handler 接到公开入口 executeQueryPhase(ShardSearchRequest, CancellableTask, ActionListener<SearchPhaseResult>)。它返回 void，结果通过 listener 交付。正常路径先进行请求改写，再经 executeQueryPhaseAsync 提交执行；普通索引用 search executor，系统索引由选择器决定。某些 can-match 分支可提前回空结果，因此不能概括为“每次一定创建上下文”或“handler 一定立即返回”。

// 9.4.0 正常执行分支的简化；省略改写、等待、追踪与失败包装
executeQueryPhaseAsync(...):
  ensureAfterSeqNoRefreshed(..., () -> {
    reader = createOrGetReaderContext(request);
    mark = reader.markAsUsed(getKeepAlive(request));
    return executeQueryPhase(request, task, reader);
  }, listener);

private executeQueryPhase(request, task, reader):
  try (SearchContext context = createContext(reader, request, task, QUERY, true)) {
    loadOrExecuteQueryPhase(request, context);
    // 单目标分片、无 rankBuilder 的普通 QTF 可在此接着 Fetch
    return result; // 结果引用需保留到上下文清理之后
  } // 先关闭本次 context，执行包装再通知 listener

createContext 先检查取消，构造 DefaultSearchContext，从 reader 取得 searcher；随后 parseSource 写入查询、排序、聚合、timeout 等，未给 from/size 时落为 0/10，再 preProcess 校验窗口、补过滤并注册取消回调。解析或前处理失败会关闭本次 context 后抛出。可缓存只是资格，缓存命中才跳过 QueryPhase，未命中仍执行。普通 QTF 单目标分片且无 rankBuilder 可复用本次 context 做 Fetch；kNN/DFS 等入口条件另论，不把这一优化当成新 SearchType。

源码：handler 注册、公开入口与异步调度、executor 选择、createContext、缓存资格与执行。下面保留六步动画，用手动步进对照正常执行分支。

3. 三个查询层，不能靠 Profile 猜全部中间态

请求中的 DSL 先是 QueryBuilder，再转换为 Lucene Query。DefaultSearchContext 保存 originalQuery（ParsedQuery），同时把 query 设为其中的 Lucene 查询；前处理只在有需要时加入别名、非 nested 根文档或 slice 过滤。rewrittenQuery() 第一次调用再执行 searcher.rewrite(query())，缓存这份执行改写。没有额外过滤时 query 可以就是原查询，rewrite 也可能返回同一对象。

字段 / 方法谁写入与谁读取
originalQuery / parsedQuery()parseSource 的 toQuery 结果；默认高亮取这份查询。显式 highlight_query 可覆盖。
query()起初等于原查询，preProcess 通过 buildFilteredQuery 按需补 MUST/FILTER。
rewrittenQuery()懒加载 searcher.rewrite；QueryPhase 使用，ExplainPhase 也拿它调用 searcher.explain。

本例 title 显式使用 standard，match: "quick brown" 默认 OR，分析出 quick、brown 后构造 SHOULD；不是等 Lucene rewrite 才分词。前置的 QueryBuilder rewrite 与此处 Lucene rewrite 也是两层。A5 的 _analyze 只证明 token，A6 的 _validate/query 展示改写后的查询表示，二者不能直接读取三个私有字段。字段的写入顺序要靠固定源码确定。

A7 给原索引加 n=1 的过滤别名，A8 同时开 Profile、Explain 和高亮：仅文档 1 命中，高亮 quick/brown，而 profile 查询树和 explanation 都能看到 n 过滤。旧文“Profile/Explain 都对 originalQuery 说话”不成立。默认高亮的查询来源与执行过滤分开，仍不能推断高亮片段严格代表所有布尔条件。别名过滤也不应被当作直接按 ID 访问的安全边界。

源码：字段写入、过滤的条件分支、懒加载 rewrite、match 转 Lucene Query、Explain 使用执行查询、默认高亮来源。

4. timeout 控制查询检查点，不是整个请求的截止线

请求体 timeout 覆盖本次 context 的默认查询超时；未配置时 search.default_search_timeout=-1，不装这条检查。QueryPhase 为非 scroll 查询注册回调，取相对时钟，发现 time > startTime + timeout 才抛 TimeExceededException。检查可发生在叶子开始、分批评分等位置，小数据并不等于“一次检查也没有”。9.4.0 ThreadPool 默认相对时钟每 200ms 更新缓存；检查间隔与时钟更新共同影响观测。

本轮 33 篇 × 两万次合法计算，took 超过 1ms 仍 timed_out=false；把固定数据扩到 3003 篇后，两轮都触发了短超时。这些是本机观测，不是工作量阈值承诺。不要按 took 反推每个检查点看到的时间。请求改写、等待、Fetch、网络与客户端处理也不由这条 1ms 保证包住；合并的单片路径在 Query 后会清掉查询超时检查再做 Fetch。

发生的事情本例响应与解释
查询超时，显式允许部分结果200 + timed_out=true；hits/total 可能不完整，不能当全集。
查询超时，显式禁止部分结果本例一片全失败，429；顶层 search_phase_execution_exception，内层 search_timeout_exception。
五百万次 Painless 循环400 + script_exception/painless_error：先撞循环语句计数保护，不是查询超时。
任务取消 / 等 checkpoint 超时各有取消或等待路径，不能把所有失败改称 timed_out。

默认允许部分结果来自 search.default_allow_partial_results=true，可被配置覆盖；本章两卡显式切换，避免默认值干扰。Scroll 的这个 getTimeoutCheck 不安装，PIT 搜索仍可使用。Painless 默认循环语句计数上限为一百万，不能靠不断扩大单次循环造超时。本章保留旧脚本作为预期错误，再用两万次、结果实际参与评分的有界脚本先跑 30s 基线，后跑 1ms 对照；此实验要求允许昂贵查询与 inline score script。

源码：查询计时与 scroll 条件、叶子与分批检查、分批检查、200ms 默认缓存间隔、相对时钟读取、429 与部分结果出口。

5. PIT 保留视图，search_after 保存进度

PIT 不是搜索结果缓存：每次仍按本次查询执行，但从保留的分片读者视图读取。C 组打开 PIT 后，第一页 quick 返回 1、2；随后写 new 并显式 refresh，旧 PIT 第二页仍只有 4，重搜旧视图仍是 1、2、4；普通搜索已经是 1、2、4、new。同一 PIT 换查 lazy 又返回 3，进一步说明缓存的不是 quick 结果。多片 PIT 保留各片视图，不提供跨片同一事务时刻的承诺。

分页需要同时传递两样东西：每次响应的最新 pit_id，以及上一页末条命中的完整 sort 数组。PIT 自动追加 _shard_doc，本例虽只显式按 ts 排序，sort 仍是两个值：本轮末项为 [2, 1]；第二项随当前 PIT/分片文档布局决定，必须复制响应，不能写死。分页保持 query/sort，from 保持默认 0；C11 换查询是新的搜索，不接续 quick 的游标。

边界ScrollPIT + search_after
跨请求保存LegacyReaderContext 与 ScrollContext，包括 lastEmittedDoc 等分页状态。ReaderContext 保留视图；客户端传完整 sort 表示进度。
下一次执行新 SearchContext，更新分页状态；不是只做 from += size。新 SearchContext，同视图可执行不同查询；同一条分页链保持 query/sort。
本节查询 timeout不装 getTimeoutCheck。可以装；不等于客户端全程 deadline。
释放清 scroll、后台过期清理等；普通/scroll 执行失败会释放读者。关 PIT、过期清理等；单次搜索失败一般不主动释放 PIT，但不能保证所有故障可恢复。

深分页采用 PIT + search_after；Scroll 仍适用于某些批处理路径，不能从 isRetryable 断言推出所有并发/重试保证。PIT 缺失时仅在供应者能取得相同 searcher ID 等条件下尝试重建，不承诺节点丢失后旧视图一定恢复。keep_alive 只需覆盖到下一次操作；在用请求有 markAsUsed 引用保护，过期由后台 reaper 检查，默认检查周期 1m。用完以最新 ID 关闭。本轮 succeeded=true、num_freed=1，随后旧 ID 搜索返回404；先释放上下文所有者引用，底层资源是否归零还取决于其他持有者。

参考 官方分页步骤与完整 sort / 最新 PIT ID 规则、PIT 的保留与资源条件；源码：重建的相同 searcher 条件、保活与过期检查、失败释放的范围。

思考题

1. 多分片 Query 后 SearchContext 已关闭，Fetch 怎么读取相同文档号？

ReaderContext 可跨 Query/Fetch 暂存同一读者引用，Fetch 另建本次上下文。SearchContext 与 reader 的所有权不同；普通 reader 在完成或不需Fetch时释放，PIT跨请求保留。

2. Profile/Explain 能否证明 originalQuery 不含别名过滤？

不能。它们可反映执行查询及过滤；Explain 调 rewrittenQuery。默认高亮才以 parsedQuery 为查询来源。字段写入与 buildFilteredQuery 分支需要源码证明；接口与过滤别名实验提供外部行为证据。

3. took=7ms、timeout=1ms 却 timed_out=false，是否必定是漏洞？

不是。超时依赖检查点与相对时钟，默认缓存间隔200ms；took与这条查询计时的覆盖范围也不同。本轮33篇合法计算未触发，3003篇触发；不能保证每台机器同样结果，更不能无限加循环绕过脚本保护。

4. 只按 ts 排序，为什么 search_after 仍要传两个值？

PIT追加_shard_doc作为稳定决胜值。复制上一页末项完整sort，使用最新pit_id，保持query/sort；本轮[2,1]只是实际例子。去掉第二值或重开PIT沿用旧游标会破坏分页前提。

5. 关闭 PIT 返回 num_freed=1，能否说一个物理 reader 已立即销毁？

不能。它表示释放了上下文；其他在用请求与读者还可能持引用。markAsUsed保护执行，最终资源释放受引用归零条件约束。open_contexts回N也不是所有句柄/内存的总账。

陷阱

把两个 Context 合并：普通搜索也有临时上下文，PIT保留reader，SearchContext装本次执行；并非所有入口每次都创建它。
把400当超时：旧五百万循环触发脚本保护；查询超时的部分结果200与严格429要核对具体reason，不只看状态。
漏传ID与排序值：filter_path可能删掉pit_id，PIT还隐式加_shard_doc。每次拿最新ID和末项完整sort，用完显式关闭。
重开污染快照：仅覆写最初五篇不会删new。点名清理重建才能恢复C组3→4的前提；过期PIT也不能无条件恢复旧视图。
