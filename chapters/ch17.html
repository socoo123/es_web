搜索服务与搜索上下文

学习目标

  • 打开 SearchService.executeQueryPhase,说出对外那条签名(参数、返回值),以及结果什么时候交给 listener——不是「方法 return 时 Lucene 已经跑完」。
  • 沿 SearchContext 的生命周期指出 originalQuery、query、rewrittenQuery() 各是谁写入、给谁用;对照一次 match: "quick brown" 的中间态。
  • 用很小的 timeout 观察 timed_out: true(并说清为什么数据太少时看不到),再对照 getTimeoutCheck → handleTimeout 这条源码路径;用 PIT 证明 Reader 快照在写入之后仍不变。

1. 心智模型:第 16 课的「每个 shard 回 10 条」在这里执行

第 16 课停在协调节点:Query Then Fetch 已经把请求扇出去了。本课只看其中一个 shard:它必须在本地 Lucene 上找出自己的 Top-N,把 (docId, score) 送回去——完整 _source 还轮不到它(单分片捷径除外)。运输层动作名 indices:data/read/search[phase/query],handler 直接调 searchService.executeQueryPhase。

3. SearchContext 生命周期:create → execute → close

对外入口:void + listener

SearchTransportService 把 QUERY_ACTION_NAME 接到这条 public 方法。读签名时抓三件事:

// SearchService.executeQueryPhase — Transport handler 那条:签名是 void + listener
public void executeQueryPhase(ShardSearchRequest request, CancellableTask task,
                              ActionListener<SearchPhaseResult> listener) {
    // rewriteAndFetchShardRequest → ensureAfterSeqNoRefreshed(
    //     shard, orig, () -> executeQueryPhase(orig, task), l)   ← private 重载丢进 search 池
}
  1. 返回类型是 void,结果走 ActionListener——第 8 课不变量:handler 线程不能同步卡在 Lucene 上。
  2. 真正跑 Lucene 的是 private 重载 SearchPhaseResult executeQueryPhase(ShardSearchRequest, CancellableTask);普通搜索(waitForCheckpoint 未设)里 ensureAfterSeqNoRefreshed 立刻 runAsync(search 池, …)。
  3. listener 何时收到值:search 池里那次 private 调用 return 之后。单分片且无 rankBuilder 时它接着 executeFetchPhase,listener 拿到 QueryFetchSearchResult;否则是 QuerySearchResult。
同名重载(简化)谁来调给 listener 的类型
(ShardSearchRequest, CancellableTask, ActionListener)[phase/query]:QTF 的 Query 相位QuerySearchResult 或 QueryFetchSearchResult
(QuerySearchRequest, SearchShardTask, …)DFS 之后的 Query(QUERY_ID_ACTION_NAME)QuerySearchResult
(InternalScrollSearchRequest, SearchShardTask, …)Scroll 翻页ScrollQuerySearchResult

create → execute → close,全写在一条 try-with-resources 里

// SearchService — private SearchPhaseResult executeQueryPhase(...)
final ReaderContext readerContext = createOrGetReaderContext(request);
try (
    Releasable ignored = readerContext.markAsUsed(getKeepAlive(request));
    SearchContext context = createContext(readerContext, request, task, ResultsType.QUERY, true)
) {
    loadOrExecuteQueryPhase(request, context);   // 能缓存就缓存,否则 QueryPhase.execute
    if (request.numberOfShards() == 1 && (request.source() == null || request.source().rankBuilder() == null)) {
        return executeFetchPhase(readerContext, context, afterQueryTime);   // 单分片:顺手 Fetch
    }
    context.queryResult().incRef();
    return context.queryResult();
} // SearchContext.close() 在这里发生

createContext 的顺序:① checkCancelled(task),能早取消就不去开 reader;② 构造 DefaultSearchContext:从 ReaderContext 拿 Engine.Searcher 包成 ContextIndexSearcher,默认超时来自 search.default_search_timeout(默认 NO_TIMEOUT = 「不装检查」);③ parseSource:from / size / query / sort / aggs / 请求级 timeout;④ from/size 仍是 -1 就落 DEFAULT_FROM=0、DEFAULT_SIZE=10——第 16 课「每个 shard 回 10 条」的同一个默认值;⑤ preProcess():校验 from+size 不超 index.max_result_window,并改写 query 字段(下一节);⑥ 任一步抛错,先 close() 再往外抛,避免 searcher 泄漏。SearchContext.close() 只做一件事:closeFuture.onResponse(null)——这一趟的 searcher 视图被放掉;PIT / Scroll 的 ReaderContext 另外活在 activeReaders 里。

4. 三个查询字段:originalQuery、query、rewrittenQuery

旧课把 query 说成「rewrite 之后的 Lucene Query」,与当前代码不一致。现在是三层:

字段 / 方法类型谁写入含义
originalQuery(getter parsedQuery())ParsedQueryparseSource 里 toQuery(...)用户查询转成的 Lucene Query,不含 alias / nested / slice filter。javadoc:塞进这里的东西会漏进 highlighting
query(getter query())Lucene Query先等于 originalQuery.query(),再被 preProcess() 换成 buildFilteredQuery(query)真正要执行的查询,尚未 Lucene rewrite
rewriteQuery(getter rewrittenQuery())Lucene Query第一次调用时 searcher().rewrite(query())(懒加载)QueryPhase 交给 searcher.search 的那一份
// DefaultSearchContext
public SearchContext parsedQuery(ParsedQuery query) {
    this.originalQuery = query;   // 用户侧 ParsedQuery,留给 highlight / explain
    this.query = query.query();   // 先等于同一份 Lucene Query
    return this;
}
// preProcess() 末尾:改的是 query,不是 originalQuery
this.query = buildFilteredQuery(query);   // 有 filter 则 BooleanQuery(MUST: 原 query, FILTER: alias/nested/slice)

「为什么必须留两份」的不变量:Profile / Highlight / Explain 要对着用户写的查询说话;Lucene 收集文档必须把别名过滤算进去。只留 rewrite 后那份,高亮会对着带 FILTER 的 BooleanQuery 说话、和用户 DSL 对不上;只留用户那份去 search,alias 索引会搜到不该看见的文档。另外别混两种 rewrite:parseSource 之前 ShardSearchRequest 已经跑过一轮 Rewriteable.rewrite(QueryBuilder → QueryBuilder,如某些 range 收成 match_all);本课说的是 searcher.rewrite(QueryBuilder 产物 → 可执行 Query)。第 18 课接着挖前者。

用户 DSL大致对应的 Lucene Query(originalQuery.query() 这层)
match: {title: "hello"}TermQuery("title", "hello")(标准分析器、单 token)
match: {title: "hello world"}BooleanQuery(SHOULD: hello, SHOULD: world)
match_phrase: {title: "hello world"}PhraseQuery
term: {status: "active"}TermQuery(不分析)
range: {age: {gte: 18}}PointRangeQuery
bool: {must: […], filter: […]} BooleanQuery(MUST / FILTER)

5. 超时:检查点上标 timed_out,不是立刻杀线程

请求体里的 "timeout": "1ms" 在 parseSource 写成 context.timeout(...)。超时走的是 Lucene 收集过程中的 cancellation 回调,不是墙上时钟一到就 Thread.interrupt:

// QueryPhase.getTimeoutCheck(节选)
boolean timeoutSet = searchContext.scrollContext() == null          // Scroll 不装这条超时
    && searchContext.timeout() != null
    && searchContext.timeout().equals(SearchService.NO_TIMEOUT) == false;
if (timeoutSet) {
    final long maxTime = startTime + searchContext.timeout().millis();
    return () -> { if (searchContext.getRelativeTimeInMillis() > maxTime) {
        searchContext.searcher().throwTimeExceededException(); } };
}

所以本地 3 篇文档的 match_all 经常在第一次检查之前就结束,timed_out 仍是 false——不是 bug,是检查粒度。ContextIndexSearcher 接到 TimeExceededException 后记下 timeExceeded=true,尽量带着已收集的部分结果返回,然后:

// SearchTimeoutException.handleTimeout
if (allowPartialSearchResults == false) {
    throw new SearchTimeoutException(target, "Time exceeded");   // → HTTP 429
}
querySearchResult.searchTimedOut(true);   // 继续,部分结果 → 顶层 timed_out: true

取消(用户 abort、task 取消)走另一条:lowLevelCancellation 默认 true,preProcess 里 addQueryCancellation(() -> task.ensureNotCancelled()),取消抛 TaskCancelledException,不会伪装成 timed_out: true。wait_for_checkpoints 那种「等 refresh 等到超时」走 ensureAfterSeqNoRefreshed,和查询收集超时也不是一回事。

6. Scroll vs Point-in-Time:一张表

不要把 Scroll 当成「现在做分页的默认办法」。PIT 是跨请求钉死 Reader 的推荐方式;Scroll 仍存在(LegacyReaderContext + ScrollContext.lastEmittedDoc),但是旧路径。现代组合是 PIT + search_after:

ScrollPoint-in-Time(推荐)
怎么开_search?scroll=1m → LegacyReaderContext,受 search.max_open_scroll_context(默认 500)限制POST /idx/_pit?keep_alive=1m → openReaderContext,singleSession=false
跨请求活着的是什么LegacyReaderContext + ScrollContext(lastEmittedDoc / totalHits)同一份 Engine.SearcherSupplier(IndexReader 视图冻结)
每一次翻页仍 createContext + 执行 + close;processScroll 只做 from += size仍短命 SearchContext;进度靠请求里的 search_after
超时检查getTimeoutCheck 要求 scrollContext() == null:不装普通 _search + PIT 可以设 timeout
重试 / 并发context id 不可 retry(isRetryable() == false 断言);同一 scroll_id 不能并发PIT id 找不到目标节点时可按同一份 commit 重建;同一 PIT 上可并发搜
怎么关DELETE /_search/scroll;keep-alive 到期;失败即 freeReaderContextDELETE /_pit;keep-alive 到期;单次搜索失败不丢 PIT

search_after 本身不是 PIT:没有 PIT 时,两次 _search 各自打开当时的 EXTERNAL searcher,中间 refresh 进新文档,第二页可能看到第一页看不到的行、或漏行。PIT 把 Reader 钉住,两页之间「这一份索引视图」不变——代价是 IndexReader 占着文件句柄与内存,直到 keep-alive 到期或显式 DELETE /_pit,所以 keep_alive 要设短、用完要关(实验 8-15 走一遍完整闭环)。

清理

思考题

1. 索引里只有 1 篇文档,timeout=1ms、match_all、允许部分结果:timed_out 是 true 还是 false?为什么实验 4 里 33 篇 + 忙循环就反过来?

1 篇时更常见 false:timeout 只在收集过程的检查点上看相对时钟,不是一进 executeQueryPhase 就判负——1 个 doc 往往在第一次检查之前就结束。实验 4 用 script_score 给每个命中挂忙循环,把收集拉长,检查点才有机会抛 TimeExceededException。「设了 1ms 就一定超时」不成立,这是检查粒度,不是 bug。

2. 为什么必须同时留 originalQuery 和 query/rewrittenQuery?只留其中一份,哪两条不变量会破?

只留 rewrite 后那份:高亮对着加了 alias FILTER 的 BooleanQuery 说话,和用户 DSL 对不上(annotate 位置偏移也会差)。只留用户那份直接 search:别名/nested/slice 过滤丢失,alias 索引会搜到不该看见的文档。所以分字段:originalQuery 给 highlight / explain / profile,query(preProcess 加 FILTER、未 rewrite)是执行计划,rewrittenQuery() 才是 searcher.search 收到的那份。

3. 深分页为什么推荐 PIT + search_after,而不是 Scroll 当默认、也不是无限加大 from?PIT 钉 Reader 的代价是什么?

from+size 受 max_result_window 限制,且每 shard 要先收集 from+size 再丢弃 from(第 16 课的窗口论点在深分页上更糟)。Scroll 用服务端 lastEmittedDoc + from += size 换「客户端省事」,但 context 不可重试、不能并发、超时检查被关、失败就 freeReaderContext。PIT 把视图冻在 Reader 上、进度放客户端 search_after,可重试可并发;代价是 IndexReader 占文件句柄/内存直到 keep-alive 或 DELETE /_pit——keep_alive 必须设短、用完显式关。

陷阱

🕳 把 SearchContext 和 ReaderContext 当一个:Scroll/PIT 跨请求活的是 ReaderContext;SearchContext 每一趟都 create → close。「SearchContext 活 1 分钟」是旧口径,别再这么记。
🕳 「设了 timeout=1ms 就一定 timed_out」:超时是收集检查点上的相对时钟,数据太少时一次检查都不会跑。要稳定观察它,得先把工作量造上去(实验 4 的忙循环);别用 ?scroll= 去凑——Scroll 根本不装这条检查。
🕳 timed_out: true 和 HTTP 429 是两码事:同一个 TimeExceededException,allow_partial_search_results 默认 true 时带部分结果返回 200 + timed_out: true;false 时抛 SearchTimeoutException 变 429。排查「偶发 429」先查是不是禁了部分结果。
🕳 PIT 忘了关:每个 PIT 占一份 IndexReader(句柄 + 内存),open_contexts 就是它的账本。keep-alive 到期会兜底,但「等过期」期间一直占着——用完 DELETE /_pit。
