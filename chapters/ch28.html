索引生命周期管理

日志持续写入时，谁决定换一份索引接写，旧索引又何时进入下一阶段？ILM 把策略拆成步骤，为每条索引保存执行状态与当前相定义，再分别检查 rollover 条件和阶段年龄。理解这两个判断，就能读懂等待、策略更新与模板接力。

学习目标

  • 从 explain 找到 phase/action/step 与 phase_execution，对照活策略，辨认当前相缓存及等待原因。
  • 通过受控 rollover 验证旧文档留在000001、alias接写000002、模板注入新代托管设置，并区分创建年龄与阶段年龄。
  • 分别实测“当前 Hot 加 forcemerge”和“只改 max_age”，用 StepKey 集合解释缓存保留或刷新，完成点名清理与重做。

1. 索引带着状态，策略定义下一步

ILM 策略由 Phase 组成：阶段名、min_age 与 actions。hot、warm、cold、frozen、delete 是有序的合法阶段名；策略可以省略部分阶段。每个 action 再展开为步骤，执行位置用 StepKey=(phase, action, step) 表示。阶段名不等于独立执行类，也不等于数据已经迁到某个节点。

选出的 master 上，IndexLifecycleService 安排周期检查，并响应集群状态变化。两种触发调用不同的 runner 入口，不能说“每次状态变化都会检查 rollover”。周期入口处理 AsyncWaitStep 等条件，状态变化入口推进相应动作。默认 indices.lifecycle.poll_interval=10m，下限1s；本课临时15s，仅缩短调度间隔，不承诺动作在一个 poll 内完成。异步操作、分片等待和重试均会影响时间。服务触发分工。

先用 GET /{index}/_ilm/explain 看“这条索引在做什么”：managed 是否托管；phase/action/step 当前执行位置；step_info 等待或错误原因；phase_execution 当前相的缓存策略版本与定义。刚创建时可能看到 new，也可能已推进到 hot；以目标步骤作为等待条件。请求活策略用 GET /_ilm/policy/{name}，两份响应应对照读取。

2. rollover 与阶段切换，用的是哪一个时钟？

rollover 为持续写入创建下一代，并翻转写目标。它要求至少一个 max_*，达到任意一项 max 且全部 min 才放行。max_age 看索引创建年龄，不按自定义 origination date 改算；max_primary_shard_size 看最大的主分片，不能把它当全部主片大小之和。下面用 alias 路径解释本课的1m与显式文档门槛。

判断计时与条件如何验证
写索引是否 rollovermax_age从创建算；本课额外min_docs=2单篇保持等待；dry-run看conditions，第二篇refresh后放行
旧索引是否进warm本课无origination_date，零点取rollover时刻，年龄≥2h；前相步骤已完成旧索引hot/complete，查看lifecycle_date_millis与age
旧索引是否进delete同一个零点年龄≥24h，且之前相完成不是进入warm后再加24h；本课不等待真实长时动作

WaitForRolloverReadyStep 用 dryRun(true) 检查；通过后，RolloverStep 发起实际 rollover。随后等待新分片、更新旧索引生命周期日期、设置 index.lifecycle.indexing_complete=true。indexing_complete不是写入阻止开关，不能把“alias停止向旧索引写”说成“旧索引从此不可写”。本课一直经write alias写；旧文档留在旧索引，没有随rollover搬迁。五步链。

阶段年龄的条件可写成 now ≥ 起算时刻 + 目标相min_age。没有origination date时，本课旧索引的起算时刻经rollover更新；index.creation_date 本身不被改写。若显式配置或解析 index.lifecycle.origination_date，runner会优先使用它，不能把本课简化零点外推到所有索引。目标相min_age从活策略读取，门槛达到后还要完成前相动作。起算日期与年龄判断。

空索引保护与显式实验门槛ILM默认only_if_has_documents=true；没有显式min_docs或min_primary_shard_docs时补min_docs=1。本课显式min_docs=2让第一篇成为观察屏障，与默认空索引保护分开。min_docs=0可显式允许空索引；ILM还有200,000,000主分片文档数的隐式max条件。直接调用Rollover API的局部conditions不改策略，也不能当作ILM默认条件的完整镜像。dry-run与默认条件。

alias方式的接力由模板完成。匹配的index template给每一代注入 index.lifecycle.name 与 index.lifecycle.rollover_alias；首索引手动配置 is_write_index:true。模板只在创建时应用，不回改已有索引。不要在模板的 aliases 中重复声明这个rollover alias本体，否则下一代创建会触发duplicated alias检查；其他用途的别名不在此禁令内。重复rollover alias检查。rollover本身不会复制旧索引的lifecycle settings；无接力模板或显式新索引配置，新代可能不受ILM管理。创建请求与alias翻转。

本课显式write alias便于观察翻转。源码还允许只有单目标、未设置is_write_index的经典alias作为写目标，不能说“缺true必定ERROR”。data stream自动组织backing indices与写索引，省去手写rollover_alias及bootstrap write alias；使用ILM时仍需匹配模板中的策略配置。不要混同ILM与另一套Data Stream Lifecycle。

3. 改活策略，当前相会立刻改道吗？

索引元数据中的 phaseDefinition 缓存当前相。PolicyStepsRegistry 把缓存相覆盖到活策略的phaseMap，再生成执行步骤；TransportExplainLifecycleAction 展示同一份相定义。缓存保护当前执行路径，避免并发PUT把正在执行的步骤抽掉；它不表示策略永远不能修改。

修改与状态机制本课证据
当前相添加forcemerge当前相StepKey集合变；缓存不刷新A组活策略v2、000001当前相仍v1，只含rollover
只改rollover.max_age当前步骤仍在、相步骤集合相同，可安全刷新B组缓存跟着变v2、max_age=10m
改未来相的min_age或actions门槛读活策略；换相时装入该相定义固定源码核对，本课不等待2h/24h动作
缓存缺失、ERROR或解析失败不满足安全刷新检查，先诊断状态不套用“只改条件就一定刷新”的简化表述

决定安全性的不是action名称数量，而是完整的 StepKey 集合。当前step必须仍在新策略中，旧/新相定义须能解析，当前相集合相同才安全。加删action常改变集合，具体仍看步骤展开；已到terminal不是“再PUT就从hot重新开始”。内容与保存的安全headers相同时，PUT可以是no-op；真正更新才递增策略version。刷新资格、集合判定、no-op更新。

5. 两组可重做实验

环境为ES9.4.0/Lucene10.4.0、匿名单节点 http://localhost:9200 的专用学习集群；开启认证时使用控制台当前凭据。先确认ILM RUNNING、全局poll无自定义覆盖，记录实际配置；本课临时修改poll会影响所有ILM托管索引，因此只在专用学习集群执行。确认 action.destructive_requires_name=true 后才做通配符错误卡。

资源仅用 tut-l28-*：A组模板、策略、alias与两代logs索引；B组独立safe策略、alias与空索引。初始这些资源必须不存在；若存在，先确认属于本课并完成下面点名清理。索引显式1P0R、strict keyword mapping、refresh_interval=-1，固定ID写入时 refresh=true。rollover后不要再重复首代写卡；否则会写入当前代并可能继续滚。

顺序：前置3卡 → A1–A14（只写一篇，稳定观察并确认max_age=true）→ A15写第二篇放行 → A16–A23（等待实际新代、alias及explain）→ B1–B7 → 清理7卡。等待卡按目标响应重复查询；出现ERROR先读step_info，不凭“约80秒”继续。默认策略warm2h/delete24h未在本课长时运行。

清理与重做（7卡）

B6/B7已经清掉safe资源；中断时也先补这两步。然后明确删除000001、000002，再删模板和A策略，恢复前置记录的poll，逐个核对索引不存在。重复删除的404需按资源含义确认；不能把404当成第一次成功删除。若产生第三代，先查询本章索引名称，逐个明确删除，不使用通配符清理。清完后从前置重新运行，策略版本重新从1开始。

思考题

1. 000001已经创建10小时，刚刚rollover。warm=2h，delete=24h，最早何时进入这两相？

本课无origination_date：阶段起算日期更新为rollover时刻。warm最早rollover后2h，delete最早rollover后24h，还需前相完成与调度推进；不是出生后2h，也不是warm后24h。显式origination_date会改变阶段计时口径。

2. 活策略v2有forcemerge，explain却仍是v1：这是更新失败吗？只改max_age会怎样？

A组添加动作改变Hot步骤集合，故老索引保留缓存v1，活策略已更新成功。B组只改max_age且当前步骤仍在、集合相同、缓存可解析，安全刷新到v2；下一次条件评估用10m。ERROR或其他资格失败不能套用这条结果。

3. 用data stream后，可以删掉模板中的ILM策略配置吗？

不能以data stream自动管理写索引为理由省掉ILM配置。它省去手写rollover_alias和首代write alias，ILM仍需从匹配模板获得策略名。若采用Data Stream Lifecycle，那是另一套管理方式，不是这个ILM实验的等价配置。

4. 相同固定ID重复写能重做整个实验吗？indexing_complete=true能拦直接写旧索引吗？

rollover前重复固定ID只是updated，不增加文档数；rollover后同样的alias请求会落在新代。完整重做须点名清理全部资源并恢复poll，再从前置开始。indexing_complete标识ILM索引阶段处理，不等同index.blocks.write；只能按实际写入阻止设置判断是否只读。

陷阱

把调度周期当完成上限15s是poll间隔。初始化、异步动作和分片等待可能跨多次检查；以step、alias及资源存在为准，不靠动作够快或固定等待80秒。
混同默认保护与实验门槛默认只在未显式给文档min条件时补min_docs1；本课显式min_docs2。直接dry-run的局部conditions不修改策略。
漏掉下一代托管模板注入lifecycle设置；只给首代绑定策略可能只滚一代。模板不得重复定义这个rollover alias本体；data stream仍要配置ILM模板。
把缓存与活策略读成一份explain只展示当前缓存相。安全刷新比较实际步骤集合，还看资格、当前步骤及解析；未来相年龄门槛另读活策略。
清理顺序与原配置丢失点名删索引再删策略。策略被引用和通配符保护均可返回400；poll=null只去掉该层覆盖，有原transient值时应恢复原值。
