LESSON 28 · 第六篇 · 高级专题

索引生命周期管理

Hot→Warm→Delete 是触发器,不是五个类 · 约 15 分钟 · 前置:第 5、23 课 · 20 个实验 + 一分钟 rollover 动画

学习目标

  • 对 tut-l28-logs-000001 画出「满 1 分钟 → rollover(000002 接写)→ 滚走后再满 2h → warm → 再满 24h → delete」这条触发链,把 rollover.max_age 对上 WaitForRolloverReadyStep 的 dry_run、把 min_age 对上 isReadyToTransitionToThisPhase——两种时钟,两次判断。
  • 用 GET /{index}/_ilm/explain 读出 phase/action/step/phase_execution,说出当前 step 是从索引 metadata 里缓存的 phaseDefinition 解析的(PolicyStepsRegistry.getStep),explain 展示的是「这条索引正在执行的那一相」,不是策略全文。
  • 预测 PUT _ilm/policy 改策略会不会立刻作用在已有索引上,用 PhaseCacheManagement.isIndexPhaseDefinitionUpdatable 对照:当前相的 StepKey 集合变了就不刷新(实测:活策略 version=2 带 forcemerge,索引缓存仍 version=1 只有 rollover);并说出 rollover 新索引的托管身份靠模板接力(rollover 本身不复制 lifecycle settings)。

1. 心智模型:阶段是触发器,不是五个类

忘掉「Hot 类把索引交给 Warm 类」。仓库里阶段只有一种数据结构:Phase = 名字 + min_age + 一组 LifecycleAction。合法名字写在 TimeseriesLifecycleType.ORDERED_VALID_PHASES 里:hot、warm、cold、frozen、delete——五个名字,一个类。触发器有两种时钟:

谁在等条件写在哪源码里谁判定
还在写的那份要不要 rolloverHot 里 rollover 的 max_age / max_primary_shard_size / max_docs(至少一个 max_*)WaitForRolloverReadyStep:对 Rollover API 做 dry_run,满足才迈到 attempt-rollover
已经滚走的那份要不要 进下一阶段下一阶段的 min_ageIndexLifecycleRunner.isReadyToTransitionToThisPhase:now ≥ lifecycleDate + min_age

min_age 的零点值得单独记。InitializePolicyContextStep 先把 lifecycleDate 设成索引创建时间;rollover 成功后,UpdateRolloverLifecycleDateStep 把被滚走的那份的 lifecycleDate 改成 rollover 时刻——所以「再满 2h」是从停止写入起算,不是从创建再加 2h;_ilm/explain 里的 age 看同一个零点。Rollover 也不是「索引改个名」:它要求一个 write alias(index.lifecycle.rollover_alias 指到 tut-l28-logs 且 is_write_index: true),条件满足后写指针翻到 000002。还有一个实测出来的关键事实(实验 3、11):rollover 不会把 index.lifecycle.name 复制给新索引——无模板时 000002 的 settings 里根本没有 lifecycle 键,managed=false,链条滚一代就断。生产正解是配一个 index template 接力:模板只带 lifecycle settings(不要把 rollover alias 写进模板,否则 rollover 直接 ERROR:found duplicated alias in index template),首索引手动带 write alias。Data stream 免手写这些,本课用 alias 就为了把每条 setting 看清。

3. 轮询读的是这份索引上的 Step,不是「五个阶段对象」

Master 上的 IndexLifecycleService 做两件事:集群状态一变就 triggerPolicies 一遍;另外用 SchedulerEngine 按 poll 间隔再跑一遍。旧课把间隔写成「每 10 秒」——错的,默认在这:

// x-pack/plugin/core/.../ilm/LifecycleSettings.java(节选)
public static final Setting<TimeValue> LIFECYCLE_POLL_INTERVAL_SETTING = Setting.timeSetting(
    LIFECYCLE_POLL_INTERVAL,
    TimeValue.timeValueMinutes(10),      // 默认 10 分钟
    TimeValue.timeValueSeconds(1),       // 下限 1s
    Setting.Property.Dynamic, Setting.Property.NodeScope);

一轮周期对每个托管索引取出 LifecycleExecutionState 里的当前 StepKey((phase, action, step_name) 三元组,不是类)交给 runner;一个索引失败不挡后面的。Hot 里一次 rollover 实际是一串 step,由 RolloverAction.toSteps 排好:

step_name类干什么
check-rollover-readyWaitForRolloverReadyStepdry_run,等 max_*(外加默认注入的 min_docs: 1)
attempt-rolloverRolloverStep真的调 Rollover API(新索引按模板创建)
wait-for-active-shardsWaitForActiveShardsStep等新索引分片起来
update-rollover-lifecycle-dateUpdateRolloverLifecycleDateStep把旧索引 lifecycleDate 写成 rollover 时刻

当前 step 从哪来是本课要钉死的第一件事。PolicyStepsRegistry.getStep 不按策略名去读集群上那份最新策略,而是解析索引 metadata 里缓存的当前相 JSON:

// x-pack/plugin/ilm/.../PolicyStepsRegistry.java(节选)
final String phaseJson = Objects.requireNonNullElse(
    indexMetadata.getLifecycleExecutionState().phaseDefinition(),
    InitializePolicyContextStep.INITIALIZATION_PHASE);   // 还没进相 → 初始化
final List<Step> phaseSteps = parseStepsFromPhase(policyName, phase, phaseJson);
final Step s = phaseSteps.stream().filter(step -> step.getKey().equals(stepKey)).findFirst().orElse(null);

parseStepsFromPhase 把缓存的当前相覆盖进活策略的 phaseMap 再 toSteps()——执行 Hot 用的 max_age 是这份索引 metadata 里那份 JSON 的 max_age,除非缓存被刷新(下一节)。_ilm/explain 读同一份状态:TransportExplainLifecycleAction 把 lifecycleState.phaseDefinition() 解析成 PhaseExecutionInfo 填进 phase_execution(policy/version/phase_definition)。所以 explain 不是「策略现在长什么样」,是「这条索引正在执行的那一相长什么样」。把实验那份数据走一遍:

4. 改策略,已有索引不一定立刻改道

PUT /_ilm/policy/{name} 给策略 version+1,然后 PutLifecycleMetadataService 调 PhaseCacheManagement.updateIndicesForPolicy。类注释把「为什么要缓存」说死了:We cache the currently executing ILM phase in the index metadata so the ILM execution for managed indices is not irrecoverably interrupted by a concurrent update policy——不是策略不可变,是正在跑的这一相不能被并发 PUT 抽掉当前 step。能不能安全重读由 isIndexPhaseDefinitionUpdatable 决定:

// x-pack/plugin/core/.../ilm/PhaseCacheManagement.java(节选)
if (newStepKeys.contains(currentStepKey) == false) {
    return false;   // 新策略里已经没有当前 StepKey:不能刷新
}
if (newPhaseStepKeys.equals(oldPhaseStepKeys)) {
    return true;    // 当前相的 StepKey 集合没变(例如只改 max_age):可以刷新
} else {
    return false;   // 当前相加/删了 action:不刷新
}
你改了什么已有索引会怎样
当前相的 StepKey 集合变了(加/删 action)不刷新缓存;把旧相跑完,explain 仍是旧 phase_definition
当前相的条件变了、StepKey 没变(只改 max_age)会刷新;下一轮 poll 的 dry_run 用新条件
未来相的 min_age / actions当前相继续;进入那一相时从活策略加载
索引已经 TerminalPolicyStep / 策略跑完再改策略也没有效果

常见 action 用表收尾:Hot 里 forcemerge / shrink 在 TimeseriesLifecycleType.HOT_ACTIONS_THAT_REQUIRE_ROLLOVER 中——必须先 rollover 再执行,所以它们出现在 Hot 时也是 rollover 之后的 step,不是另一种触发器。

hot / warmforcemerge、shrink、allocate、readonly合并段、减分片、迁节点、关写入
cold / frozensearchable_snapshot本课不展开;仍是 Phase 上的一个 action

思考题

1. 实验 8 不加 action、只把 Hot 的 rollover.max_age 从 1m 改成 10m(StepKey 集合不变)。000001 若仍停在 check-rollover-ready,explain 里的 max_age 会立刻变成 10m 吗?本来 1 分钟该发生的 rollover 还会发生吗?

会立刻变:newPhaseStepKeys.equals(oldPhaseStepKeys) 为 true,updateIndicesForPolicy 刷新缓存,explain 的 phase_definition 变 10m、version=2;下一轮 poll 从刷新后的 JSON 构造 WaitForRolloverReadyStep,带着新条件 dry_run——1 分钟时不再满足,要再等约 9 分钟。与实验 8 的加 forcemerge 相反:加法改 StepKey 集合,缓存不动;只改条件则缓存跟着动。「改 Hot 不影响正在跑的 Hot」在这条路径上不成立。

2. 为什么把当前 phase JSON 缓存在索引 metadata 里,而不是每次 poll 都读集群上的活策略?若并发 PUT 把正在执行的 action 整段删掉,哪条不变量会破?

缓存保的是「当前这一相的执行计划不能被抽掉」。getStep 只认缓存 JSON 里的 StepKey;若每次读活策略,并发 PUT 删掉 rollover 或整个 Hot,runner 会在 check-rollover-ready 上找不到下一步,索引掉进 error,而且没有一份「当时正在执行的相」可用来把动作做完。不变量:一份索引一旦开始跑某一相,这一相的 steps 必须能跑完(或明确进 error/手动 retry),不能在两次 poll 之间变成「策略里没这个 step」。未来相不在缓存里,进入时再读活策略——所以改 Delete 的 min_age 仍然有效。

3. 生产上「日志 7 天热、30 天删」:(a) poll 调到几秒、策略也写很短,好在测试里立刻看见;(b) 保持默认 10 分钟、策略用天为单位。各付什么换什么?data stream 相比手写模板 + rollover_alias,省掉和藏掉的各是什么?

(a) 教程和集成测试能在一分钟内看见 000002,但每个 poll 都要扫全部托管索引并可能提交集群状态任务,master 会被 ILM 拖住;过短 min_age 还会让 shrink/forcemerge 在数据仍热时跑。(b) rollover 最多迟到一个 poll 槽,对按天的日志可接受,换来 master 空闲。data stream 把写索引和 rollover 目标绑在流名字上:省掉模板接力 + rollover_alias + is_write_index 这整面出错墙(以及本课实测的「不复制 lifecycle.name」陷阱);藏掉的正是实验 3-4 必须看清的那几条 setting——出错时你少一个可以指认的旋钮。

陷阱

🕳 以为 rollover 会把策略带给新索引:实测 alias 方式 rollover 不复制 index.lifecycle.name——无模板时 000002 的 settings 没有 lifecycle 键,managed=false,链条滚一代就断。必须配 index template 接力;且模板里不能带 rollover alias 本体(否则 duplicated alias → ERROR step)。
🕳 把 explain 当策略全文读:phase_execution.phase_definition 是这条索引正在执行的缓存相(PolicyStepsRegistry.getStep 读同一份 JSON),只有当前相的 actions——想看全文用 GET _ilm/policy。改策略后的分叉(活策略 v2 vs 缓存 v1)正靠这两份对照。
🕳 「改策略不影响已有索引」记成绝对:门闩是 StepKey 集合:加/删当前相 action → 不刷(跑完旧相);只改 max_age → 刷(立刻生效);改未来相 → 进相时生效;索引已 Terminal → 无效。别背简化口诀,背这四行。
🕳 忘了 min_docs 暗门和 min_age 零点:only_if_has_documents 默认 true 给 dry_run 注入 min_docs:1,空索引到点不滚;被滚走那份的 lifecycleDate 已改成 rollover 时刻,「再满 2h」从停止写入起算——拿创建时间手算会差出一大截。
🕳 清理乱了顺序或用通配符:先删索引(去引用)再删策略,否则 400 in use;且 DELETE /tut-l28-* 默认被拒(action.destructive_requires_name=true)——显式点名删;poll 记得 null 回默认 10 分钟。
