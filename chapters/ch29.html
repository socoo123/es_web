安全机制

约 25 分钟 · 前置：第 6、7、28 课 · 5 组实验 / 32 张操作卡 · 2 幅交互图（2 条路径动画）· 1 个七步机制动画

同一个 alice，为什么能搜索日志，却连 GET / 都得到 403？本课沿着普通 HTTP 请求追踪凭据、Authentication 和 Action 权限，把「没有被认证」与「已认证但未获准」分开，并用两个独立节点与可重做实验逐项对照。

学习目标

  • 在 9201 对照缺凭据、错密码、伪造 ApiKey 的三种 401，说明 reason、token 抽取与回退条件分别能证明什么。
  • 用固定版本源码定位 Basic 在 Realms 的入口，区分认证器顺序、Realm 默认列表和成功缓存调整后的实际校验顺序。
  • 创建 reader 与 alice，验证日志读取/搜索 200、集群/监控/写入 403及自查 200；清理本课资源后完整重做。

29.1 一次普通请求在哪两处可能被拒绝？

认证回答「这个凭据代表谁」，产出 Authentication；授权回答「这个主体能否执行该 Action、访问该资源」。对本课普通 HTTP 请求，头部认证在业务 REST Handler 执行前完成，随后内部 Action 的安全过滤器读取身份并调用授权服务。因此，无凭据 GET / 的响应没有集群信息，不能据此认为主节点没有启动。

本课锚定 Elasticsearch 9.4.0 / Lucene 10.4.0。图中箭头表示调用推进与结果分支，完整静态图一直保留；省略 OPTIONS/CORS 预检、内部系统请求、远程传输、run-as、附加认证和插件细节。它解释普通路径，不把所有 HTTP 请求都概括为相同的两道检查。

可选插件认证器之后，Service Account 与 OAuth2 都识别 Bearer，API Key 识别 ApiKey，最后的 Realms 才抽取 Basic。这个顺序由 AuthenticationService 构造函数 确定；HTTP 入口的「填充上下文 → authenticate」见 Security 的头部认证回调。客户端传的是凭据，Action 授权接收的是已经构造好的身份。

29.3 CONTINUE 不等于失败，更不承诺密码后备

每个认证器先抽取认识的凭据，再尝试校验。抽不到时返回 notHandled()；抽到了却未成功、且允许继续时，也可返回 CONTINUE。迭代只在 CONTINUE 时继续；SUCCESS 进入身份完成流程，TERMINATE 或异常结束。格式损坏、后端不可用等错误不能一概归成「换下一家试试」。

结果下一步本课对照
CONTINUE尝试下一个；可带未成功校验的信息Basic 跳过前三类；伪造 ApiKey 的信息可累积
SUCCESS停止后续认证器，完成 Authenticationelastic / alice 在 Realms 校验成功
TERMINATE 或异常停止，返回对应失败或处理错误本课不制造全部终止分支；以源码条件为准

Realms 里有两件不同的事：先调用各 Realm 的 token() 抽取一种凭据，再让支持这种 token 的 Realm 依次校验。本课未自定义 Realm 配置，默认列表为 reserved → file → native；但 lastSuccessfulAuthCache 可将该用户名上次成功的 Realm 提前。实验显示 elastic 来自 reserved、alice 来自 native，不能用这两条身份响应证明每次实际遍历都从 reserved 开始。

LDAP/Active Directory 等用户名密码 Realm 也可支持 Basic；SAML/OIDC 则有自己的认证流程。Basic 留在 Realms，让多种用户名密码后端共享凭据抽取；这里只解释结构和分工，不声称任何一种排列一定更快。

🕳 一次请求同时发 ApiKey 与 Basic 会怎样？本机 9.4.0 实测发送两个 Authorization 请求头值返回 400：multiple values for single-valued header [Authorization].，不会演示“API Key 赢、Basic 备用”。本课普通认证得到一份 Authentication；run-as 或附加认证需另读对应流程，不能套用“任何请求只能有一个主体”。

29.4 三种 401：方法名不能替代分支条件

本课 9201 未配置匿名用户。缺凭据时链没有产生身份，进入 handleNullToken，没有可用回退后返回 missing credentials；若显式配置匿名角色，结果可以不同。错密码时 Basic 已在 Realms 抽出，setHandleNullToken(false) 禁止这个回退；全部支持的 Realm 都没有有效用户，consumeNullUser → authenticationFailed 返回 unable to authenticate user。不要将错密码说成“Realms 最后返回 CONTINUE 再由链统一生成”——本版本有明确的 Realm 失败回调。

请求本课响应 reason机制证据
无 Authorizationmissing authentication credentials for REST request [/]没有有效身份；本课无匿名回退
Basic 错密码 / 已删用户unable to authenticate user [用户名] for REST request [/]Basic 已被 Realms 抽取，用户校验未成功
ApiKey：编码为 xxx:yyyunable to authenticate with provided credentials and anonymous access is not allowed for this requestAPI Key 已抽取却无有效 key；错误附带缺失 id 的信息

第三行也可以经过 handleNullToken，虽然前面的 ApiKey 已经被抽取。因此不能把方法名翻译成“从未抽出任何 token”。状态、reason 和 additional_unsuccessful_credentials 一起才是证据；格式错误或后端故障还可能产生其他响应，本课不把所有认证阶段错误都概括为 401。

这三次 401 在本课都是 security_exception，携带 Basic 与 ApiKey 双挑战。挑战列表取决于 Realm、TokenService 与 API Key 服务配置，不是 9.4.0 的恒定两项。准备卡显示本课 token_service.enabled=false、api_key_service.enabled=true；因 HTTP TLS 显式关闭，token service 默认关闭，其他配置可能出现 Bearer。

curl -i http://localhost:9201/
curl -i -u elastic:wrong-password http://localhost:9201/

29.5 身份相同，为何一次 200、一次 403？

alice 在本课只有 tut-l29-reader 角色：cluster 权限为空，只对 tut-l29-* 授予 read。先用管理员显式创建并写入 tut-l29-logs，再让 alice 请求同一数据：文档 GET 和搜索 200；GET / 的 cluster:monitor/main、CAT 的监控动作、写入和创建索引都拒绝为 403。

索引授权不只做 Role.checkIndicesAction(action)：它还解析请求里的索引/别名、限制可访问资源并构造 IndicesAccessControl。本课单一普通索引可以用「名字范围 + 动作权限」理解；通配符、受限索引、复合子请求和远程索引还有不同分支。明确请求范围以外的名字返回 403，也不能据此承诺任意通配符请求都返回 403。

GET /_security/_authenticate 也经过授权判断。RBAC 的 checkSameUserPermissions 对这类自查授予权限，因此 alice 200，不需要 manage_security；无凭据时仍是 401。查询自己的 _has_privileges 同理：请求可成功返回 200，而结果里 read=true、write=false、monitor=false。它回答权限问题，200 不代表这些权限都为 true。

普通多角色授权是允许权限的组合，新增角色通常扩展允许范围，不会把另一个角色的允许“减掉”。FLS/DLS 属于索引访问控制，也受相应许可和配置约束，不是新的认证器；同一资源多份 DLS 限制组合也不是逐个 AND，存在不受限授权时可取消限制。本课采用一个无 FLS/DLS 的 read 角色，未实测字段/文档安全、真实 API Key、run-as 或自定义授权引擎。

29.6 先确认端点，再解释状态码

端点本课配置已指定的请求
localhost:9200单节点，安全关闭，匿名请求GET / 200；两个已测试 _security 路由 400 no handler
localhost:9201独立单节点，安全开启，HTTP TLS 关闭，无匿名无凭据 GET / 401；管理员 200；alice 的 GET / 403

9200 关闭安全时没有这套认证授权，也不会给每个请求构造一个“匿名 superuser”。这与安全开启后配置匿名用户是两种机制。available=true 表示该功能在当前许可下可用，enabled=false 表示开关关闭。Security 不注册其普通安全 REST Handler，本课两个具体路由因而返回 400 no handler；任意 URL / 方法仍可能碰到其他路由规则，不能一概承诺 400。

🕹 本课环境分别运行 bash docker/start.sh 与 bash docker/start-secure.sh。9201 使用教学账号 elastic / elastic-password；两座集群不共享数据、角色和用户。HTTP 与固定口令是本机教程的显式配置，不代表生产部署的 TLS/凭据方案。卡片锁定端点和认证，不随全局连接设置漂移。

七步回放：把概念与证据接起来

先看完整图，再用机制播放器逐步检查：请求边界 → 认证器顺序 → Realm → RBAC → 三种 401 → 自查 → 端点与重做。支持暂停、上一步、下一步和重置；系统减少动态效果时不自动播放。

动手实验：5 组 / 32 张操作卡

初始条件：两个 9.4.0 单节点已启动；9201 无本课 tut-l29-logs、tut-l29-denied、用户和角色。若以前做过，先按清理组点名清理并核对，再从 A 开始。实验卡的数字保留原 ID，执行顺序以页面从上到下为准：A 认证 → B 准备 → C 授权 → D 端点 → E 清理。本轮真实两遍结果和原始响应记录在本章验收记录。

准备采用 1 主片 / 0 副本、严格 keyword mapping、固定 ID 与显式刷新，避免旧文档和自动 refresh 让对照失效。重复建索引会 400；重复更新角色/用户的 created 为 false；同 ID 重复写入为 updated，文档数仍 1。清理索引重复运行会 404，删除用户/角色重复为 404 found=false；这些不等于清理失败。

A · 认证失败与成功（6 卡）

B · 管理员核对配置、准备数据与身份（5 卡）

C · 同一 alice 的允许、拒绝与自查（9 卡）

先完成 B。建索引拒绝卡使用另一个不存在的本课名字；范围外搜索只发送明确名称请求，不创建或删除范围外资源。看见 403 后，比较 action、资源名与角色，不只比较路径是否“像读请求”。

D · 9200 的独立端点对照（4 卡）

E · 点名清理与重做确认（8 卡）

使用管理员删除用户 → 角色；验证旧密码 401，再删除数据索引并逐项核对资源不存在。清理只删除本课创建的对象；不要用通配符 DELETE。确认后从 A → B → C → D → E 完整重做，不沿用上一轮的 created / updated 预期。

可选收起本课节点：docker compose -f docker/docker-compose-secure.yml down，数据卷保留。重启不会等价于删除数据、用户和角色，重做仍应按本课清理流程恢复前提。

思考题

1. 缺凭据、错密码、伪造 ApiKey 都是 401，为什么不能只看状态码推断经过哪个方法？

缺凭据无身份且本课无匿名回退；错密码在 Realms 已抽出 Basic，关闭 null-token 回退，由 consumeNullUser 的失败回调生成用户文案。伪造 ApiKey 已抽出却未通过，仍可能经过 handleNullToken，并带 additional_unsuccessful_credentials。结合 reason、配置与源码条件；401 本身不能证明“没抽过 token”。

2. alice 的 GET / 403，为什么文档 GET、搜索、自查却都能 200？

认证成功只是给出身份。GET / 需要 cluster:monitor/main，reader 没有集群权限；匹配日志索引的 GET 和搜索在 read 范围。自查由同用户授权分支授予，不需要 manage_security。_has_privileges 返回 200 时，权限结果仍可为 false。

3. 默认列表 reserved → file → native，能据此说每次密码校验都按这个顺序吗？

不能。配置影响默认 Realm 列表，lastSuccessfulAuthCache 还可将某用户名上次成功的 Realm 提前；各 Realm 是否支持该 token 也决定是否校验。_authenticate 证明实际认证 Realm，不提供完整遍历轨迹。

4. 角色 names 命中 tut-l29-*，为何 PUT 新索引、写入和 CAT 仍 403？

names 是资源范围，privileges 才授予动作；read 不包括 create_index、write 和 CAT 所需的监控动作。实际资源解析与访问控制共同判断。应逐项读 action 与资源，而不是把名称匹配当作全部权限。

陷阱

🕳 把所有 401 都叫“没权限”本课 401 是没有有效认证结果，403 是已有身份但此动作被拒绝；还要看 reason。头部格式、后端错误、匿名与其他安全路径会影响响应，不能对整个系统写成绝对二分。
🕳 把 _authenticate 叫“免授权”它经过 RBAC，由同用户分支授予；无凭据仍 401。自查成功不授予所有安全管理动作。
🕳 把两种顺序写成永远不变认证器顺序由构造函数决定，Realms 内的默认列表与实际校验顺序要分开。成功缓存可重排；同时发送两个 Authorization 值也不是后备凭据配置。
🕳 关闭安全等于匿名 superuser关闭安全不会构造匿名 superuser，也不等同于启用匿名角色。先核对端点和 enabled，再解释该路径上的具体响应。
