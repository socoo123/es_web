LESSON 29 · 第六篇 · 高级专题

安全机制

先认证再授权,链上第一个成功即停 · 约 15 分钟 · 前置:第 6、7、28 课 · 19 个实验 + 认证链动画

学习目标

  • 对安全节点(localhost:9201)发一次不带凭据的 GET /,预测并对照 401 + missing authentication credentials + 双 WWW-Authenticate 挑战;再带 elastic:elastic-password 对照 200;用错密码拿到另一种 401(unable to authenticate user)——同码不同因,文案就是链走到哪一步的指纹。
  • 打开 AuthenticationService 构造函数,按源码背出认证链顺序:(可选 Pluggable)→ Service Account → OAuth2 token → API Key → Realms;说出 curl -u 为什么前三环全 CONTINUE、Basic 落在最后一环 Realms 的 UsernamePasswordToken.extractToken。
  • 亲手造一个 403:建只有 tut-l29-* read 权限的角色和用户 alice,让 alice 打 GET / 拿 action [cluster:monitor/main] is unauthorized … with effective roles;再让 alice 打 _security/_authenticate 靠 checkSameUserPermissions 拿 200——认证失败 401、授权失败 403、问自己是谁免授权不免认证。
🕹 本课需要两座集群:9200 一直用的「安全关闭」学习节点照旧;9201 是本课新开的「安全开启」节点——终端跑 bash docker/start-secure.sh(账号 elastic / elastic-password),本课实验已固定指明各自端点,互不干扰。安全关闭时 _security 整组路由不存在,所以这套实验必须在 9201 上做。

1. 心智模型:先问「你是谁」,再问「你能不能」

安全开启时,HTTP 请求进节点有两道闸。第一道是认证(authentication):从 Authorization 头里抽出一种凭据,按固定名单依次尝试,谁先 SUCCESS 谁赢,后面不再试。第二道是授权(authorization):已经知道你是谁,再用角色(RBAC)判断这个 action 能不能做。认证发生在 handler 跑起来之前(Security.java:先把凭据填进 ThreadContext,再 authenticationService.authenticate)——所以实验 1 的 401 响应体里连 cluster_name 都没有,RestMainAction 根本没跑。用一次具体请求走链:

这张图证明三件事:认证在授权前面;链是 first-match(黄色级的 CONTINUE 不是失败);Basic 不在链的最前面——它藏在最后一环 RealmsAuthenticator 里。旧课把顺序画成 Token → API Key → LDAP → SAML,漏了 Service Account,也把 Realms 里的 Basic 和 SAML 摆成了同一层海报;SAML/OIDC 也是 Realm,只是认的凭据不是 Basic 用户名密码,本课不展开。

3. 认证链 first-match,顺序以构造函数为准

每个 Authenticator 做两件事:extractCredentials 看头里有没有自己认识的凭据;有则 authenticate 校验。抽不到返回 null,链把它当成 notHandled()。三种结局写在 AuthenticationResult.Status:

状态含义链怎么办
SUCCESS这环认出并校验通过停。写出 Authentication,后面的不再跑
CONTINUE没抽到凭据,或抽到了但校验失败且允许别人再试试下一个
TERMINATE这环认定整条链必须停(凭据坏到不可恢复)停,失败

真实顺序不是背出来的,是构造函数的参数顺序:

// x-pack/plugin/security/.../authc/AuthenticationService.java(节选)
this.authenticatorChain = new AuthenticatorChain(settings, operatorPrivilegesService, anonymousUser,
    new AuthenticationContextSerializer(),
    pluggableAuthenticatorChain,                                        // 有插件自定义认证器时插在最前
    new ServiceAccountAuthenticator(serviceAccountService, nodeName, meterRegistry),
    new OAuth2TokenAuthenticator(tokenService, meterRegistry),
    new ApiKeyAuthenticator(apiKeyService, nodeName, meterRegistry),
    new RealmsAuthenticator(numInvalidation, lastSuccessfulAuthCache, meterRegistry)
);

迭代停不停,看的就是 CONTINUE 这个谓词——SUCCESS 不满足谓词,迭代结束;四环都 CONTINUE 且从未抽出 token,才进 handleNullToken。链按头前缀分流:

顺序Authenticator认的头curl -u 时
0(可选)PluggableAuthenticatorChain插件自己说了算教程集群通常没有
1ServiceAccountAuthenticatorBearer 且能解析成 service account token头是 Basic → CONTINUE
2OAuth2TokenAuthenticator同样看 Bearer(access token)同样抽不到 → CONTINUE
3ApiKeyAuthenticatorApiKey + Base64(id:key)前缀不对 → CONTINUE
4RealmsAuthenticator各 Realm 的 token();用户名密码 Realm 认 Basic在这里命中

Service Account 和 OAuth2 共用 Bearer 前缀:前者先 tryParseToken,解析不成再让 OAuth2 拿同一段 Bearer 去 TokenService。Basic 更靠后的原因在 UsernamePasswordToken.extractToken:头不是 Basic 前缀就返回 null——注释写得很直白,maybe it is valid for another realm。Realms 内部按 getDefaultOrderedRealmList() 再 first-match 一次:reserved 永远第一(实验 4 实测 elastic 走的就是 reserved realm),然后是默认 file、native。curl -u 因此几乎总是:前三环抽不到 → Realms 抽出 UsernamePasswordToken → 某个用户名密码 Realm SUCCESS。若同时塞了 ApiKey 和 Basic,API Key 在前,Basic 根本不会被问到——first-match 的不变量:一次请求只有一个身份。

4. 两种 401:缺凭据走 handleNullToken,错密码走 authenticationError

无凭据的请求每一环都抽不到 token,链走尽仍是 CONTINUE,且 shouldHandleNullToken() 仍为 true(Realms 只有抽出过 token 才会把它打成 false):

// x-pack/plugin/core/.../authc/DefaultAuthenticationFailureHandler.java(节选)
public ElasticsearchSecurityException missingToken(HttpPreRequest request, ThreadContext context) {
    return createAuthenticationError("missing authentication credentials for REST request [{}]", null, request.uri());
}
// createAuthenticationError 保证 RestStatus.UNAUTHORIZED(401),并加 WWW-Authenticate

错密码走另一条:Realms 已抽出 token、setHandleNullToken(false),迭代结束后 CONTINUE 但不再 handleNullToken,而是 authenticationError("failed to authenticate", …)。同样 401,文案不同——实验 1 与实验 5 的实测对照:

无凭据(实验 1)错密码 / 用户不存在(实验 5、19)
token 抽出过?没有(没有任何一环认领)有(Basic 头被 extractToken 解码)
走的工厂missingTokenauthenticationError
实测 reasonmissing authentication credentials for REST request [/]unable to authenticate user [elastic] for REST request [/]
响应头相同:WWW-Authenticate: Basic realm="security", charset="UTF-8" + ApiKey(双挑战,9.4.0 实测)

5. 有了 Authentication 才做 RBAC:401 与 403 分家

认证成功后 Authentication 写进 ThreadContext;授权是另一次调用 AuthorizationService.authorize(authentication, action, request, listener)——它不再看 Authorization 头。默认引擎 RBACEngine 先向 CompositeRolesStore 要角色,包成 RBACAuthorizationInfo,随后按 action 名分叉:cluster 动作 → Role.checkClusterAction;index 动作 → Role.checkIndicesAction;都不是 → deny。GET / 是 cluster:monitor/main。拒绝时走 Exceptions.authorizationError,状态是 403 FORBIDDEN:

// x-pack/plugin/core/.../support/Exceptions.java(节选)
public static ElasticsearchSecurityException authenticationError(String msg, Object... args) {
    ElasticsearchSecurityException e = new ElasticsearchSecurityException(msg, RestStatus.UNAUTHORIZED, args);   // 401
    e.addBodyHeader("WWW-Authenticate", "Basic realm=\"" + XPackField.SECURITY + "\", charset=\"UTF-8\"");
    return e;
}
public static ElasticsearchSecurityException authorizationError(String msg, Object... args) {
    return new ElasticsearchSecurityException(msg, RestStatus.FORBIDDEN, null, args);                            // 403
}
认证失败授权失败
发生点链还没交出 Authentication已经有用户,Role.check* 为 false
HTTP401 UNAUTHORIZED403 FORBIDDEN
头带 WWW-Authenticate(挑战:请给凭据)不挑战,你已表明身份
实测文案missing credentials / unable to authenticate useraction [cluster:monitor/main] is unauthorized for user [tut-l29-alice] with effective roles [tut-l29-reader]

有一个例外:checkSameUserPermissions——「问自己是谁」这类动作(GET _security/_authenticate)只要认证过就授予。实验 10 里 alice 连 GET / 都是 403,却能在 _authenticate 拿 200,靠的就是这条,不是 superuser 特供。多角色用户(旧课 alice 挂 log_reader + metric_writer)在授权侧是权限并集——RBAC 的加法,和认证链的 first-match 相反:认证只能有一个身份,授权可以把多个角色叠在这个身份上。字段级/文档级安全(FLS/DLS)也在这之后:index privilege 先允许你搜 logs-*,field_security(grant/except)与 query(文档过滤,自动 AND 进查询)再削一刀——它们不是认证链的一环,是 IndicesAccessControl 包进查询的。

思考题

1. 无凭据请求与错密码请求,HTTP 状态相同吗?reason 相同吗?哪一次会经过 UsernamePasswordToken.extractToken?哪一次会调用 handleNullToken?

都是 401,reason 不同。无凭据:没有任何 Authenticator 抽出 token,链全 CONTINUE,shouldHandleNullToken 仍 true → handleNullToken → missing authentication credentials。错密码:Basic 头被 UsernamePasswordToken.extractToken 解码出用户与错密码,Realms 校验失败后 CONTINUE,但已 setHandleNullToken(false) → authenticationError → unable to authenticate user。两次都带 WWW-Authenticate,都还没进 RBAC。实验 19 补第三种:用户被删,文案与错密码同款——token 抽出过,只是查无此人。

2. 为什么认证必须 first-match,不能「API Key 验一下、Basic 再验一下,两个都过才放行」或「两个都过就权限取并集」?若改成并集,哪条不变量破了?

first-match 保证一次请求只有一个主体。API Key 在链上先于 Realms:同时出现时以 API Key 为准,Basic 根本不会被问到。改成「都要过」,合法的只用 -u 的请求会被 API Key 环拖死;改成「都过则并集」,同一请求可能同时是「受限 API Key」和「superuser 密码」,审计里的 Authentication、API Key 自己的 role_descriptors、run-as 全部失去「这是谁」的唯一答案。授权侧角色可以叠加(并集),认证侧身份不能——两个方向的规则相反,这不是不一致,是分工。

3. API Key 做成链上独立的 ApiKeyAuthenticator(排在 Realms 前),Basic 只作为 Realms 里的一种 token()。另一种设计是把 Basic 也提成平级 Authenticator。各付什么换什么?几乎只用 -u 的集群,每请求先过前三环,划算吗?

API Key 独立且靠前:校验走 ApiKeyService(id+key、过期、自带 role_descriptors),不必先解析成某个 Realm 用户。Basic 留在 Realms:与 reserved/file/native(及启用的 LDAP 等)共用「用户名密码 → User → 角色」这条路,避免再复制一套密码校验,也让「file 与 native 谁先」继续复用 Realm 顺序。代价是每次 Basic 请求前三环各做一次前缀判断——见不到 Bearer / ApiKey 就返回 null,比一次磁盘/网络 Realm 查询便宜得多,教程集群付得起。把 Basic 提成平级可以让纯密码集群少绕 Realms 列表,但拆开 UsernamePasswordRealm 的共用抽取,得不偿失。

陷阱

🕳 把 401 当「没权限」:没权限是 403(身份就位、角色不过,文案带 effective roles);401 是「我还不承认你是谁」。两种 401 还要再分:missing credentials(token 没抽出过)与 unable to authenticate user(抽出过、校验失败)——排障时文案就是链走到哪一步的指纹。
🕳 背旧课那张 Token→API Key→LDAP→SAML 海报:漏了 Service Account,层级也错了。9.4.0 链:(可选 Pluggable)→ Service Account → OAuth2 → API Key → Realms;Basic 不是链上第五个兄弟,是 Realms 里 UsernamePasswordToken.extractToken 认的头;SAML/OIDC 是 Realm,不是链环。
🕳 以为主管账号失败是连接问题:端口听着呢——401 + WWW-Authenticate 挑战就是它在说话。也别把「安全关闭」当成「路由还在但放行」:_security 整组 handler 不注册,GET /_security/_authenticate 在 9200 是 400 no handler(第 7 课口径)。
🕳 以为 _authenticate 免认证:它免的是授权(checkSameUserPermissions:认证过即可问自己是谁),不免认证——无凭据时照样 401(实验 2)。alice 能 200 而 GET / 403,正是这两层分开的证据。
🕳 混淆认证并集/角色并集:多角色在授权侧是权限并集(RBAC 的加法);认证侧一次请求只能有一个身份(first-match)。同时塞 ApiKey 和 Basic,API Key 赢,Basic 不会被问到。
