学习目标

  • 区分源码区域、运行时 modules / plugins 目录与 Classic / Stable API，避免把 X-Pack 当作第三种加载协议。
  • 解释独立插件的默认隔离，并指出 extended.plugins、SPI 暴露层和 JarHell 如何改变判断。
  • 从 ReindexPlugin 或 MapperSizePlugin 找到“实现对象进入核心注册表”的具体调用点，结合 API 的响应正文验证自己的推断。

1. 先分清：源码在哪里、怎么安装、用什么 API

“模块”“插件”“X-Pack”容易被放在一张三分表里，其实它们回答不同的问题。modules / plugins 是发行目录与安装方式；x-pack 是源码区域；Classic / Stable 是扩展 API 与描述文件协议。一个功能可以同时属于几条分类轴。

分类轴本课例子如何确认
源码区域modules/reindex、plugins/mapper-size、x-pack/plugin固定 tag 的构建文件与实现类
运行时目录内置 modules；另外安装的 plugins发行目录及 _nodes/plugins 的两组数组
扩展 APIClassic 的 Plugin / ActionPlugin；Stable 分析组件 API描述文件类型、入口类或命名组件
功能许可X-Pack 包含 Basic 可用和更高许可等级功能具体功能的许可判断，不能由目录名推断

标准发行版通常把 reindex 作为内置 module 提供；mapper-size 是需要另外安装的 Classic plugin。许多 x-pack/plugin 项目也作为模块随发行版打包。运行时加载的是发行产物中的目录，不能把源码目录直接当成已加载功能清单。插件安装、移除或升级后需要按对应版本要求重启节点；本课实验只观察现有节点，不修改安装状态。

加载目录的入口见 loadModulesBundles / loadPluginsBundles；X-Pack 的许可等级区分见 XPackLicenseState 许可等级。不要为了验证路由归属手动删除内置 modules 目录：其他模块可能声明依赖它，发行版完整性和可启动性不能由这一幅概念图保证。

2. 隔离的是类可见性，不是所有风险

普通独立插件不会把所有 JAR 摊平放进一个 classpath。PluginsLoader 为每个 bundle 建立自己的实现加载器或 Java 模块层；它可以沿父路径访问核心的可见类，默认无法直接加载另一个无关插件的私有实现与第三方库。模块化 bundle、非模块化 Classic 和 Stable 走不同分支，因此“所有插件都是一个 URLClassLoader”也不准确。

图中的 A、B、E 是机制角色。A、B 未声明扩展时，二者可以携带各自的第三方依赖版本；但这不保证插件一定能启动或运行。本插件内部、核心可见类、显式扩展依赖仍要接受重复类与重复 codebase 检查；模块可见性、版本兼容、构造器和插件代码本身也可能失败。ClassLoader 隔离不能替代权限约束或错误处理。

若 E 的 Classic 描述文件声明 extended.plugins=B，父路径会合并核心和 B 的可暴露层：B 有单独 SPI 时使用 SPI；没有单独 SPI 时可使用实现层。它不是任意互通开关：B 的插件实例还必须实现 ExtensiblePlugin。全部实例创建后，PluginsService 才调用扩展加载回调，把声明扩展者的 SPI 实现交给被扩展插件。

可见性、JarHell 与扩展的源码依据

PluginsLoader：父路径、SPI 与加载分支；checkBundleJarHell：核心与传递扩展依赖；loadPluginBundles / loadExtensions；被扩展插件的接口检查。图省略中间父加载器、模块层及 Lucene SPI 刷新；箭头表示可访问关系，不表示先后调用，也不承诺绕过 Java 模块导出限制。

3. 从加载到生效：核心只认扩展接口

第三章看到的启动过程可以再切细一点。Bootstrap 读取 modules / plugins 的 bundle 描述，按扩展依赖排序，检查 JarHell 与版本兼容并建立加载层；Node 构造时创建 PluginsService，Classic 分支通过 classname 找到入口类并反射创建实例。建立加载层与创建插件实例属于不同步骤。

ReindexPlugin 实现 ActionPlugin。NodeConstruction 调用 filterPlugins(ActionPlugin.class)，把匹配实例交给 ActionModule。ActionModule 既收集 getActions() 的 Action / Transport 处理类，也在初始化 REST 时调用 getRestHandlers()；ReindexPlugin 返回 RestReindexAction，其 routes() 声明 POST /_reindex，随后注册到 RestController。注册发生在 Node 构造期，HTTP 开放在 Node.start 后段。

这解释了第二章的编译依赖方向：核心定义接口，模块实现接口；核心装配时接收这些实例，而不需要直接引用 ReindexPlugin。图里的动画展示启动装配路径，实际请求到达后还有参数解析、Action 执行等步骤，第 6、7 课再追。REST 扩展还可过滤 handler 并注册占位处理器，图示限定正常允许的 Reindex 注册路径。

从启动入口到 POST 路由的源码导航

initPhase2：扫描与创建加载器 → Node 构造 PluginsService → Classic 反射入口；唯一构造器 → filterPlugins → ActionModule 接收 ActionPlugin → ReindexPlugin 的 Action 与 REST 扩展 → initRestHandlers 收集插件处理器；REST 过滤与注册 → RestReindexAction.routes。

扩展目标Classic 接口交给核心的内容
REST / ActionActionPluginREST handlers、Action 与 Transport 类
分析AnalysisPlugin分析器、分词器与过滤器工厂
字段与元数据字段MapperPlugin类型解析器与 metadata mapper
查询 / 聚合SearchPlugin命名的查询与聚合扩展
摄取 / 脚本 / 仓库IngestPlugin / ScriptPlugin / RepositoryPlugin处理器工厂、脚本引擎、仓库实现

Plugin 抽象基类还提供 getSettings()、getNamedWriteables()、getNamedXContent()、getExecutorBuilders()、getBootstrapChecks() 与 onIndexModule() 等钩子。createComponents(PluginServices) 可用 Node 提供的服务创建组件；9.4.0 也接受待注入的组件类和 PluginComponentBinding，返回值不能一概解释为“全按对象自身类型绑定”。其中实际实现 LifecycleComponent 的组件会被 Node 收集管理。依据见 createComponents 与注入装配、LifecycleComponent 收集 与 Plugin 基类钩子。

Classic 入口构造器：必须有且只有一个 public 构造器，签名为 ()、(Settings) 或 (Settings, Path)。加载器不会按三种签名的优先级逐个尝试；这条规则不用于 Stable 命名组件的入口。

4. 用 mapper-size 把注册追到副作用

源码中先看 plugins/mapper-size/build.gradle 的 esplugin 配置：classname 指向 org.elasticsearch.plugin.mapper.MapperSizePlugin。打包任务使用模板生成 Classic 的 plugin-descriptor.properties；因此在源码目录找不到同名文件，不能据此判断插件没有描述文件。

// MapperSizePlugin 的核心注册方法
@Override
public Map<String, MetadataFieldMapper.TypeParser> getMetadataMappers() {
    return Collections.singletonMap(SizeFieldMapper.NAME, SizeFieldMapper.PARSER);
}

它把 _size 对应的解析器交给 MapperPlugin 扩展点。NodeConstruction 收集 MapperPlugin 后，IndicesModule 合并 metadata mapper 注册表；与已有名称冲突会失败。这里先建立“能解析 _size 的能力”，并不会自动给所有索引启用该字段。

在已安装 mapper-size 的节点上，索引 mapping 中显式设置 "_size": {"enabled": true} 才启用记录。SizeFieldMapper.postParse 取本次解析的源字节长度写入整数数值字段，可用于相应字段查询与排序。它表示文档源的字节大小，不是字符数，也不是 Lucene 压缩后的磁盘占用。本节通过源码验证机制；动手演示 _size 需要先安装匹配版本的 mapper-size。

构建、注册与写入依据

esplugin.classname → 生成描述文件任务 → getMetadataMappers → Node 收集 MapperPlugin → 合并 metadata mapper 注册表 → postParse 源字节长度。

5. Classic 与 Stable：兼容范围与扩展能力一起看

Classic 使用 plugin-descriptor.properties，要求 classname，并继承 Plugin。对正常语义版本构建，加载兼容性检查要求描述中的 ES 版本与当前构建版本一致，同时检查 Java 版本。内部接口可能变化，插件发布者需要提供匹配版本的产物。

Stable 使用 stable-plugin-descriptor.properties，不声明 Classic 入口 classname；PluginsService 扫描命名组件注册到 StablePluginsRegistry，并放入 StablePluginPlaceHolder 表示插件已加载。命名组件通过稳定扩展接口提供分析能力，不是把 Classic 的 createComponents 或 REST 钩子原样搬过来。

9.4.0 的比较ClassicStable
入口classname → Plugin 实例命名组件扫描，无 Classic 入口类
主要能力REST、字段、查询、服务等扩展接口稳定分析组件 API
ES 版本检查描述版本与当前构建版本相同同一 major，构建目标版本不得高于当前版本
仍要检查Java 要求、JarHell、产物与运行配置；版本检查通过不能证明任意插件代码正确

所以“升级友好”有明确边界：Stable 不能跨 major 自动兼容，也不能把面向未来 ES 版本构建的产物装到更早节点。这些版本规则以正常 ES 9.4.0 语义版本构建为前提；不把开发构建的例外当成发布兼容承诺。依据见 verifyCompatibility、描述文件类型与入口约束、Stable 组件扫描与占位 与 命名组件注册表。

实验：先观察清单，再验证路由

前提：使用控制台连接到已运行的 ES 9.4.0，并设置该端点需要的认证。先执行实验 1，再执行实验 2。多节点逐个核对返回的节点 ID 与名称；权限不足的 401 / 403 不能用于判断插件是否存在。两个操作均不创建索引或文档，无需清理，可重复执行；第二张是故意无效的 POST 请求，应保留空对象 {}，不要填入真实 reindex 参数。

实验 1：节点分别加载了什么

标准发行版通常能在 modules 数组中找到 reindex、analysis-common、lang-painless 等；plugins 是否为空取决于节点安装状态，不是固定预期。请求额外保留节点名称和失败数量，避免把过滤后的空响应直接解释为“没有模块”。GET /_cat/plugins?v 只遍历 plugins，不列 modules，见 CAT 只遍历 pluginInfos；默认发行版模块存在也可能没有 CAT 插件行。

实验 2：空对象到达 Reindex 后会发生什么

在 Reindex 正常加载、权限允许且请求进入处理器的前提下，{} 可以解析为 ReindexRequest，随后因缺少源索引上下文和目标索引而验证失败，预期 400。对照错误正文里的 action_request_validation_exception 与具体原因，例如 index must be specified；它比状态码更能证明经过了 Reindex 的参数检查。参数验证依据见 ReindexRequest.validate；fromXContent。

400 本身无法证明路由已加载。9.4.0 的无 handler 分支也返回 400；如果路径又命中别的路由但 HTTP 方法不支持，还可能返回 405。404 常用于命中 handler 后资源不存在等情况。结合实验 1、错误类型与 reason 判断，不通过删除模块重做实验。无 handler 的源码见 handleBadRequest 返回 BAD_REQUEST。

思考题

1. A、B 带不同版本的同名第三方库，是否一定 JarHell？

未声明扩展的独立 bundle 不把所有私有库放到同一个 classpath；它们可以隔离各自版本。仍要检查本插件、核心可见类以及显式扩展的传递依赖，不能只凭两个版本不同就断言能启动或必失败。

2. E 声明 extended.plugins=B 后，能否访问 B 的所有实现？

要看 B 的暴露层：有独立 SPI 时使用 SPI，没有时使用实现层；Java 模块导出也影响可见性。B 还必须实现 ExtensiblePlugin，相关依赖仍接受 JarHell 检查。描述项不是随意绕过边界的开关。

3. server 看不见 ReindexPlugin 的编译类名，为何还能注册路由？

核心定义 Plugin / ActionPlugin，模块提供实现；Classic 加载器按描述文件反射创建实例。Node 筛选 ActionPlugin，ActionModule 调用接口取得 RestReindexAction，再注册其 routes。这是启动装配路径；实际请求执行另追 Action 链。

4. plugins 数组有 mapper-size，但某索引读不到 _size，应该先查什么？

核对相关节点的安装状态和索引 mapping 是否显式启用 _size，再核对写入时机及字段取回方式。插件存在提供解析能力，不会自动启用所有索引；_size 也不是压缩后的磁盘统计值。

5. 为 ES 9.5 构建的 Stable 插件，能直接装到 ES 9.4 吗？

不能按兼容规则这样推断。9.4.0 对正常语义版本要求 major 相同，插件构建目标不能高于运行版本；Classic 则要求描述中的 ES 版本与当前构建版本相同。Java 和其他加载检查依然适用。

陷阱

🕳 把不同分类轴混为三类插件：X-Pack 是源码区域与功能集合，包含不同许可等级；它不是与 Classic / Stable 并列的加载协议。
🕳 只看清单或状态码：_cat/plugins 不列 modules；plugins 不保证为空；无 handler 也可返回 400。核对节点清单、错误正文和源码归属。
🕳 通过删模块来证明“可插拔”：发布模块可能有依赖关系。用清单和注册点验证归属，不把移除目录后必能启动写成通用结论。
🕳 装好了就等于功能已启用：加载插件提供能力；索引 mapping、功能配置与权限仍决定具体行为。_size 必须显式启用。
