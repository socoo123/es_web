插件体系

核心精简,功能外挂 · 约 14 分钟 · 前置:第 2、3 课 · 2 个实验

学习目标

  • 说出插件体系的隔离不变量,并解释 A 插件的第三方依赖为什么砸不到 B。
  • 解释 server 编译时看不见 ReindexPlugin,运行时却能提供 POST /_reindex 的机制。
  • 对照 mapper-size 说出描述文件 classname 是怎么来的、指向谁。

1. 心智模型:默认看不见彼此

插件体系要记的不是 12 个接口名,是这条隔离不变量:每个插件一块独立 ClassLoader;A 的第三方库,B 默认加载不到。

第 2 课的依赖箭头在编译期,这一课的 ClassLoader 在运行期。两条合起来:server 既不能 api project(':modules:reindex'),也不会把所有插件 JAR 倒进同一个 classpath。

2. Plugin 基类:先挂钩,再选接口

Plugin 是抽象类,提供每个插件都有的生命周期钩子;想加 REST、分词器、字段类型,再 implements 对应接口(完整列表在 Plugin.java 文件头 javadoc,打开就能数):

你想加的实现
REST 端点 / ActionActionPlugin
分析器 / 分词器AnalysisPlugin
字段类型 / _size 这类元数据字段MapperPlugin
查询 / 聚合SearchPlugin
写入前处理器IngestPlugin
脚本引擎ScriptPlugin
快照仓库RepositoryPlugin
基类常用钩子干什么
createComponents(PluginServices)创建自己的服务;返回 LifecycleComponent 的会被 Node 托管生命周期
getSettings()声明插件自己的 Setting,让 ES 识别并校验
getNamedWriteables() / getNamedXContent()注册节点间序列化类型 / 请求体命名 JSON 解析器
getExecutorBuilders()要独立线程池时用(ML 这类)
getBootstrapChecks()给第 3 课的生产检查加一条
onIndexModule(IndexModule)索引创建时挂钩(自定义 Engine 走这里)

精读一个钩子就能看懂「插件不是挂在旁边的 JAR,而是把对象交进 Node」——ReindexPlugin 覆盖 createComponents,用 Node 借来的 PluginServices(Environment、指标注册表…)造出自己的组件,返回的对象被 Guice 绑到自身类型:

public Collection<?> createComponents(PluginServices services) {
    return List.of(
        new ReindexSslConfig(services.environment().settings(), services.environment(),
            services.resourceWatcherService()),
        new ReindexMetrics(services.telemetryProvider().getMeterRegistry()));
}
构造器只能有一个,签名三选一:(Settings, Path) / (Settings) / ()。PluginsService.loadPlugin 发现多个 public 构造器直接抛 IllegalStateException——不是「按优先级依次尝试」。

3. 加载顺序:发现 → 实例化 → 注入

注入分两层:① 接口方法——Node 装配时按接口收集插件交给对应模块,ActionModule 吃到的就是 pluginsService.filterPlugins(ActionPlugin.class) 的结果;② 插件扩展插件——全部实例化后调 loadExtensions(),实现了 ExtensiblePlugin 的插件(如 x-pack security)通过 SPI 收到声明了 extended.plugins=<我> 的那些实现(自定义 Realm 就是这么挂上的)。

5. 描述文件与最小插件

每个插件运行时目录必须有 plugin-descriptor.properties,但源码树里通常没有——它是 esplugin{} Gradle 插件打包时从模板生成的:

esplugin {
  description = 'The Mapper Size plugin allows document to record their uncompressed size at index time.'
  classname ='org.elasticsearch.plugin.mapper.MapperSizePlugin'
}
// plugins/mapper-size/ 入口类的全部有效逻辑:
public class MapperSizePlugin extends Plugin implements MapperPlugin {
    @Override
    public Map<String, MetadataFieldMapper.TypeParser> getMetadataMappers() {
        return Collections.singletonMap(SizeFieldMapper.NAME, SizeFieldMapper.PARSER); // "_size"
    }
}

mapping 里 "_size": { "enabled": true } 时,索引时把未压缩文档大小记成整数,之后可取回可排序。Classic 插件描述文件必须写 classname;Stable 插件走 stable-plugin-descriptor.properties,classname 为空,靠稳定 SPI 注册(权衡见思考题 3)。

思考题(含原课仓库实验)

1. 插件 A、B 各带不同版本 Guava,节点能启动吗?A 的代码 new ImmutableList 会用到 B 那份吗?

能启动(只要没和 server 的 classpath 撞车)。JarHell 查的是「插件 vs server、插件 vs 它声明扩展的插件」,不是两两互比;A 加载类只问自己的 loader 和 parent(server),问不到 B。以为「两个 Guava 必 JarHell」的错觉来自把所有 JAR 当成扁平 classpath。

2. server 编译期看不见 ReindexPlugin,运行期却能提供 POST /_reindex,怎么做到的?

接口(Plugin/ActionPlugin/RestHandler)定义在 server,实现在 module 里,启动时反射加载再 filterPlugins 注入——依赖倒置:核心稳定,功能外挂。把 ReindexPlugin 塞进 server/src,server 就编译依赖 reindex 的一切,没装这功能的发行版连核心都编译不了,第 2 课的不变量就破了。

3. Classic Plugin 与 Stable Plugin 各在换什么?

Classic 换来能力(createComponents、自定义 REST、碰内部 API),代价是内部 API 一变就得改、和 ES 版本绑死。Stable 只依赖 plugin-api、无入口类(server 放 StablePluginPlaceHolder 占位),换来升级友好,代价是暂时没有那套生命周期钩子。引入它是让第三方插件不必每个小版本重新编译。

陷阱

🕳 _cat/plugins 判断不了 module:它只列 plugin;start-local 上经常是空的。判断 module 用 _nodes/plugins 的 modules 数组(实验 1)。
🕳 源码树里找不到 plugin-descriptor.properties:它是打包产物,由 esplugin{} 从模板生成;别把运行时目录和源码目录当同一个。
🕳 「内置」≠「编译进 server」:拿掉 modules/reindex 目录,节点照常启动,只是 POST /_reindex 变 404——路由来自插件的 getRestHandlers,不在 server 核心路由表里。

速记

一句话内容
隔离每插件独立 ClassLoader,默认互相看不见
挂钩Plugin 基类给钩子;REST/分词/字段是按需 implements 的接口
加载发现 descriptor → 反射实例化 → filterPlugins/loadExtensions 注入
三类modules 随发行版 / plugins 手动装 / x-pack 商业;代码形态相同
构造器必须唯一,签名三选一

心法:核心定义接口,功能自带实现;互相看不见,除非显式声明。
