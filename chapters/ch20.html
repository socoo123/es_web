20.1 谁决定窗口，谁加载与解释？

默认普通搜索按相关性选结果，但“Query 就定了全部名次”仍省掉了一层：每片只交局部候选，协调节点再合并并选取全局 from/size 窗口。单词、双词查询改变候选分；function_score 组合查询分和函数分；字段 sort 改变比较键。可选 rescore 在分片 Query 末尾重打一段候选，随后才交协调节点。

在本课两篇干净语料中，默认双词搜索返回 a/b；字段 views desc 返回 b/a。track_scores=true 可以同时显示“a 的相关性更高”，却仍按 views 排。这不是 Fetch 给命中项加了一个装饰顺序，而是收集和全局合并使用了不同比较键。Fetch 除 _source 外还可取 stored fields、Doc Values、高亮等；说明树由 Fetch 的 Explain 子阶段按已选 hit 生成。

20.3 两篇文档，先算一遍胜负

新建普通索引 tut-l20-bm25，1 主 0 副，title 显式 standard、内置 BM25、norms，保存词向量；views 为 integer Doc Values。默认 standard 不去停用词，这两个输入恰好各产生两个 token。默认 query_then_fetch 用分片局部词项/字段统计；这里仅搜索一个片，避免把跨片差异混进手算。

ID title 与 TF dl views
a elasticsearch tutorial：1 / 1 2 10
b elasticsearch elasticsearch：2 / 0 2 100

字段统计为 N=2（含 title 词项的文档数）、n(es)=2、n(tutorial)=1，avgdl=4/2=2。对这个默认 OR 双词 match，没有额外业务 boost，分数是匹配词贡献之和。手算使用 ES Legacy 的经典形式：

IDF = ln(1 + (N - n + 0.5) / (n + 0.5))
L   = 1 - b + b × dl / avgdl
tf_sat = freq × (k1 + 1) / (freq + k1 × L)
score  = Σ 查询词boost × IDF × tf_sat
k1=1.2，b=0.75；本例 L=1。

IDF(es)=ln(1.2)≈0.18232156，IDF(tutorial)=ln(2)≈0.69314718；tf_sat(1)=1，tf_sat(2)=1.375。单词时 b≈0.25069216 胜过 a≈0.18232156；双词时 a 多一个 tutorial 贡献，变≈0.8754687，b仍≈0.25069216。A5–A9 将词向量、分数和树里的参数一一对齐。

查询 a b 次序
elasticsearch ≈0.1823 ≈0.2507 b → a
elasticsearch tutorial ≈0.8755 ≈0.2507 a → b

七步机制：集合统计 → 公式 → 胜负

饱和比较固定 dl/avgdl=1：TF 1→2 的因子从1到1.375，20→21从≈2.075到≈2.081，边际增益明显变小，但仍增长。实际往文档堆词可能同时增加长度，不能从这条曲线推导“堆词绝对买不到排名”。k1=0 时匹配词的词频不影响此因子；b=0 去掉长度影响，b=1 使用完整长度比。调整参数仍需对具体语料验证。

20.4 Explain 为什么显示 boost=2.2？统计为何会变？

Lucene 的实现把 tf 写成不含 k1+1 的分式；ES 9.4.0 默认 provider 仍包装 LegacyBM25Similarity，把这个倍数放入传给 Lucene 的 boost。因此查询没写 boost，解释树仍显示2.2，乘以 IDF 和原始 tf 后就对上手算。统一倍数在同参数的纯 BM25 比较中不改变顺序；和其他函数、不同字段参数、阈值混用时，绝对尺度仍可能影响结果。@Deprecated 是代码提示，不是已经切换默认的证据。

默认 discount_overlaps=true，位置增量为0的重叠 token 不计入 norm 长度；长度存储/解码有量化，较长字段的 Explain 可标 approximate。本例长度2可精确对照。字段 N 不是索引总篇数；avgdl 使用该字段总词频 / docCount，而 norm 的重叠折扣不等于所有集合统计都按同一规则扣除。

C1 新增长度2、含 title 但不含查询词的 c，刷新后 N=3、n(es)=2、avgdl仍2，IDF=ln(1.6)≈0.4700036，a/b分数变≈0.4700/0.6463。C4再加缺 title 的d，本例 N仍3，a分数不变。未刷新、落在其他片、字段缺失或长度变化，都可能改变结论；更新/删除旧版本还可能在 merge 前留在统计里。完整重做须删除本课索引再创建，不靠把 c 删除或 a/b 重写来恢复精确 N=2。

20.5 解释返回 hit，还是解释指定 ID？

_search 的 explain:true 在 Fetch 对实际返回的 hit 调 IndexSearcher.explain，并补充 rescore 的解释；普通 size=1 即使命中2篇，也只回一棵树。它解释查询为何匹配与如何算分，不承诺告诉你字段排序、并列规则或全局淘汰的全部原因。字段 sort 的输入还要看 sort[]。

独立 POST /索引/_explain/ID 不要求该文档进搜索窗口，但它不是 realtime GET；源码用非 realtime Engine.Get，然后预处理查询、解释 rewrittenQuery，别名过滤可参与。文档存在但查询不匹配回200 matched=false；文档缺失回404。服务端也注册 GET，浏览器本项目的 ESClient 不发送 GET body，所以操作卡使用POST。独立入口没有跨片 DFS；同一刷新视图、查询和分片统计下可与普通 search 对齐，不能笼统说所有搜索都共享同一棵数值树。

20.6 改分数，和换排序键，是两类选择

function_score 的 score_mode 合并多个函数，boost_mode 合并查询分与函数结果，两者默认都是 multiply。weight:2 给所有匹配文档同一个正数因子，本例分数翻倍而顺序不变。一般 multiply 是查询分 × min(函数分,max_boost)。field_value_factor 读取 views，B2双词分乘10/100后 b胜；BM25仍在乘积中，不代表相关性仍是第一排序键。B3只给b乘零，b分数成为0，仍可返回但排后，若再用min_score或小窗口还可能被排除。

boost_mode:replace 用函数结果代替查询分，query仍限制匹配集合；本例两篇都2，没有可靠并列顺序。业务上要让相关性为首键、views只打破同分，可以显式 sort:[{"_score":"desc"},{"views":"desc"}]；要用业务信号改变相关性，则验证组合函数的尺度与缺值策略。

选择 比较键与分数 本例
默认或 _score desc 相关性分；_score是特殊分数排序 双词 a/b
views desc 字段 Doc Values；仅字段排序默认_score=null b/a
views desc + track_scores 仍按字段，旁路返回分数 b/a但a分更高
query_score × views 函数组合后的_score b≈25.069 > a≈8.755
replace weight2 函数_score；匹配集合由query限定 两篇同分2

单独显式 _score desc 可被 SortBuilder.buildSort 优化成默认分数路径，本课B7/B10响应没有 sort[]；不能只凭DSL里写了sort就断言用了TopField。固定源码优化分支。字段 sort 不需要相关性分来比较，但其他请求组件可能仍需要分数。显式 _score、_geo_distance、_script 各有自己的排序逻辑，不能全部概括成“从 Doc Values 读取普通业务字段”。_doc 是内部文档次序，可用于不需要业务排序的遍历，内部编号会变化；没有普遍“最快且稳定”的保证。

20.7 重打每片窗口，能救回谁？

B8/B9首轮只查 elasticsearch，b先、a后，重打查询是短语 elasticsearch tutorial，query_weight=1、rescore_query_weight=5、total相加。window_size=1只对b跑第二查询，a虽然含短语也得不到第二贡献；window_size=2包括a，它变≈4.559665并翻到第一。窗口外不执行第二查询，但本版本 QueryRescorer仍将其首轮分乘query_weight；“窗口外原分不动”只在query_weight=1时成立。

窗口按每片候选取，不是在协调节点最终窗口上补一轮 Fetch 后精排；多片召回和窗口大小须另评估。默认window_size=10（query rescorer）；size、from及窗口共同影响需保留候选数量。9.4.0允许无显式sort或_score降序，源码另接受_shard_doc升序 tie-break条件；B10实测_score成功，B11的views排序回400。本章不实测PIT的tie-break、多节点DFS、其他rescorer或吞吐收益。

思考题

1. 同查询新增一篇文档，分数一定变大吗？

不一定。C1含title且长度2使N变3、n不变、avgdl不变，故本例涨分；C4缺title不改变字段N。其他写入还受分片、刷新、长度和旧版本统计影响。

2. Fetch可生成解释树，为何还说先选窗口？

Query/可选rescore产生局部候选，协调节点先选全局hit。Fetch再对返回hit解释分数，可补rescore说明；解释树不用于重新选窗口。字段排序要结合sort数组阅读。

3. 乘views还能保证相关性主序吗？

不能。B2业务因子使b翻盘，B3乘零使b降到0；相关性只是一项。若要相关性首键、views仅同分打破并列，显式按_score desc再views desc排序。

4. 为什么a含短语，window_size=1却救不回来？

首轮b/a，每片只对首位b执行第二查询。扩大到2才覆盖a；窗口外仍乘query_weight，本实验设1所以数值不变。不能把全局size当重打窗口。

5. 独立Explain与search Explain何时对得上？

本例单片、同刷新读者、同普通查询可对齐。DFS多片统计、search的rescore或不同过滤/读者会有差异。独立Explain也不读未刷新的实时写入；浏览器用POST传body。

陷阱

把Deprecated当默认已切换9.4.0内置BM25仍创建Legacy，Explain默认boost2.2；同参数统一倍数与复杂混分的影响不同。
把N当索引总篇数N是字段docCount；缺title的d没进入本例字段统计。更新/删除也不保证立即恢复原统计。
把评分、排序与解释混成一步track_scores不改变sort键；Fetch可算Explain但不重新排名。Explain也不能单独解释字段排序次序。
以为重打禁止所有sort本版本允许_score降序，views排序拒绝；窗口外仍乘query_weight。API限制按请求参数核对。

速记

机制 条件与结论
默认BM25 ES9.4.0内置BM25是Legacy，k1=1.2、b=.75；boost2.2对应k1+1。
手算边界 字段N/n；单片、同读者、dl=avgdl=2；单词b胜，双词a胜。
分数与业务 同正数weight2只放大；views乘积可翻盘，乘零可失去高排名；replace保留函数分。
排序 字段sort换比较键；track_scores补分不改键；_score仍是分数比较。

两个Explain 搜索Fetch解释返回hit；独立POST按ID/routing读刷新视图，存在不匹配200，缺失404。

心法：先辨认比较键，再追分数来源；固定字段统计和读者，最后用 Explain 对账。
