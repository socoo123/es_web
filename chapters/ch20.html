评分与排序

Query 阶段比的就是 BM25,Fetch 之前名次已定 · 约 16 分钟 · 前置:第 16、18 课 · 12 个实验

学习目标

  • 用两篇文档、两个词的具体 TF / DF,手算谁的 _score 更高;并标出饱和:TF 从 1→2 的增幅远大于 20→21。
  • 打开 explain:true(以及 GET /idx/_explain/id),对上 Lucene BM25Similarity 的 idf / tf / k1 / b,并说出 ES 默认为什么多一个 (k1+1)(LegacyBM25Similarity)。
  • 用 function_score 的 weight: 2 + boost_mode: multiply 验证分数翻倍;再说清:改成按字段 sort 之后,第 16 课截 Top-N 的键不再是 BM25。

1. 心智模型:分数在 Fetch 之前就已经决定名次

默认路径里,相关性不是 Fetch 阶段才算的。第 18 课的 match 把查询变成若干 term;每个 term 扫倒排表时,Lucene 用字段的 Similarity 给命中文档打一个数;多个 term 的数加起来就是 _score。第 16 课的 Query 阶段带着它回去,协调节点按它排序、截窗口,Fetch 只给窗口里的 id 加载 _source。

本课索引 tut-l20-bm25 用 1 个 shard:默认 query_then_fetch 用各 shard 本地 IDF,单 shard 时本地就是全局,手算才能和 explain 对上。

4. Lucene 的实现,以及 ES 为什么包一层 Legacy

公式来自 Lucene 10.4.0 BM25Similarity(Gradle 依赖,version.properties: lucene = 10.4.0)。无参构造默认 k1=1.2、b=0.75、discountOverlaps=true(position increment 为 0 的 token,如同义词叠加,不计入文档长度);k1 必须 ≥ 0,b 在 [0,1]。ES 侧把默认值又写了一遍,创建的是 Legacy 包装:

// SimilarityProviders.createBM25Similarity(节选)
float k1 = settings.getAsFloat("k1", 1.2f);
float b  = settings.getAsFloat("b", 0.75f);
return new LegacyBM25Similarity(k1, b, discountOverlaps);

// LegacyBM25Similarity.scorer —— (1+k1) 折进 boost
return bm25Similarity.scorer(boost * (1 + bm25Similarity.getK1()), collectionStats, termStats);

Lucene 的 BM25Scorer.score 不写教科书分式,写成 weight - weight / (1 + freq × normInverse)(与经典式等价),分子里没有 (k1+1)——Lucene 认为它是与 freq 无关的常数、不改变排序,拿掉了;explain 树因此长成 tf = freq / (freq + k1×(1-b+b×dl/avgdl))。ES 的 Legacy 层把 (1+k1) 乘进 boost:查询 boost=1.0 时 Lucene 看到 2.2。所以 Legacy 分数 = (1+k1) × Lucene_BM25 = idf × freq×(k1+1) / (freq + k1×(1-b+b×dl/avgdl))——§3 手算用的经典形式。类已标 @Deprecated(新索引应直接用 BM25Similarity),但 9.4.0 默认路径仍是 Legacy,读 explain 必须带着这个倍数。读 BM25Similarity 盯三个入口:idf(docFreq, docCount)(公式本体)、idfExplain(给 explain 用,带 n/N 子解释)、scorer(boost, ...)(预计算 avgdl、256 档长度缓存,返回 BM25Scorer)。字段 mapping 里 "similarity" 按名字取 provider;boolean 对应 BooleanSimilarity(命中即常数分);内置还有 DFR / IB / LMDirichlet 等,默认路径就是 BM25。

5. explain:true 与 _explain/{id} 不是同一条路

两条 API 都调 Lucene IndexSearcher.explain(query, docId),看到的公式树是同一棵,差在谁被解释、走哪次往返。搜索请求上的 explain:true 真正算解释的是 Fetch 子阶段:

// ExplainPhase.getProcessor(节选)——只对已进全局窗口、正被加载 _source 的 hit
final int topLevelDocId = hitContext.hit().docId();
Explanation explanation = context.searcher().explain(context.rewrittenQuery(), topLevelDocId);
hitContext.hit().explanation(explanation);

对 size=10 的搜索开 explain,最多解释 10 篇,不是全部命中;每篇一次 explain 比 score() 重,别在生产热路径默认打开。GET /{index}/_explain/{id} 则是 TransportSingleShardAction:按 _id 路由到一个 shard(像 GET,不像 SEARCH),先 Engine.Get 确认存在再解释——哪怕这篇排在第 10000 名。源码留有 TODO:_explain 不做跨 shard DFS 收集,IDF 可能与带 explain 的普通 search 不一致。

6. function_score:在 BM25 之后再乘一层

BM25 只看词频、稀有度、长度;业务常要「同样相关,浏览量高的往前」。这条 DSL 9.4.0 里仍叫 function_score,默认把查询分和函数分相乘(DEFAULT_BOOST_MODE = MULTIPLY;另有独立的 script_score 查询,是另一条 Builder)。boost_mode 是「查询 BM25 ⋈ 函数结果」怎么合,score_mode 是多个 functions[] 之间怎么合:

// CombineFunction.MULTIPLY —— 默认 boost_mode 写得很直
return (float) (queryScore * Math.min(funcScore, maxBoost));

weight: 2 走 WeightBuilder:doToFunction 返回 null,父类包成 WeightFactorFunction(2, null),内部缺函数用常数 1.0 再乘 weight → 函数分就是 2。于是 Doc b:BM25 ≈ 0.251 × 2 = ≈ 0.502;乘的是已算完的 BM25,不改 IDF/TF——两篇同乘 2,名次不变,只是绝对值翻倍(实验 6)。其它函数仍在:field_value_factor 读数值字段、gauss 等 decay、脚本。boost_mode: replace 扔掉 BM25 只留函数分,效果接近字段 sort,但仍走「算一个 _score 再按分数截 Top-N」,不是换 Doc Values 排序。

7. sort:换掉截 Top-N 的尺子

不写 sort 时 SearchContext.sort() 保持 null,QueryPhaseCollectorManager 建 TopScoreDocCollectorManager——默认「按分数取 Top-N」。JSON 里出现 sort 后,SortBuilder.fromXContent 分流:字段名 "_score" → ScoreSortBuilder(默认 DESC),否则 FieldSortBuilder:

// SortBuilder.fieldOrScoreSort
if (fieldName.equals(ScoreSortBuilder.NAME)) {   // "_score"
    return new ScoreSortBuilder();
} else {
    return new FieldSortBuilder(fieldName);
}

按字段排换 TopFieldCollectorManager,读 Doc Values:「什么叫更大」从 _score 换成字段值——BM25 很高、views 很低的文档可能进不了窗口,Fetch 永远看不到它。按字段排时 _score 默认不进命中(track_scores 默认 false),要旁路看 BM25 就显式打开(实验 7、8)。

Rescore 是「先便宜后昂贵」:Query 阶段收集完 shard 本地 Top 之后,RescorePhase.execute 对每条 RescoreContext 用更贵的查询(常是 match_phrase)重打最多 window_size 篇(默认 10),rescored 分数再作为 (docId, score) 送回协调节点——不是 Fetch 之后的第三阶段,也不是全局合并后的精排;窗口以外的文档带着原始 BM25 离开,没有第二次机会。它禁止和普通 sort 同用(Cannot use [sort] option in conjunction with [rescore])。

清理

思考题

1. 在 tut-l20-bm25 再加一篇 {"title":"unrelated document"} 并 refresh。再搜 elasticsearch,原来 a、b 的 _score 变大、变小还是不变?

变大。N 从 2 变 3、n 仍是 2,IDF 从 ln(1.2)≈0.182 升到 ln(1+(3-2+0.5)/(2+0.5))=ln(1.6)≈0.470——词相对集合更稀有,同样 TF 贡献更高;TF 饱和项不变。若答「不变」,是把 IDF 当成了查询常量:它依赖当前 shard 的 N/n,默认 QTF 用本地统计(实验 9-10 验证)。

2. 为什么 Query 阶段必须先打完 BM25、Fetch 才取 _source?若先搬全部命中正文再算分,第 16 课哪条带宽不变量破了?explain:true 为什么放 Fetch 子阶段?

Query 只传 (docId, score),协调节点截完全局窗口再 Fetch 正文——「不要把 30 篇 _source 搬去只为丢掉 20 篇」。先搬正文再打分,带宽按命中全集涨,而评分并不需要 _source(BM25 用倒排里的 TF 和范数)。explain 树比一个 float 大几个数量级,所以 ExplainPhase 只对已经赢了、正要返回的 hit 跑;Query 阶段给每个候选 explain,窗口外的工作全浪费。_explain/{id} 是另一条单文档动作,专门解释「没进窗口的那篇」。

3. 要「浏览量高的往前」,选 sort: [{"views":"desc"}] 还是 function_score 把 views 乘进 _score?谁还能让 BM25 当主序?Rescore 能替代它们吗?

sort 把截窗口的键换成 views:BM25 冠军若浏览量低,根本不被 Fetch;_score 默认还不算。function_score 乘 views 时主序仍是一个分数,BM25 还在乘积里——相关但浏览量为 0 的文档不会仅因字段小被尺子扔掉。boost_mode: replace 效果接近字段 sort,但仍走打分收集器。Rescore 不能替代:只重打各 shard 已进 window_size 的那一小撮、禁止和 sort 同用;它解决「便宜模型粗筛 + 贵模型精排」,不是「业务字段当主键排序」。

陷阱

🕳 拿裸 Lucene BM25 对 ES 的 _score:差 (k1+1)=2.2 倍。ES 默认 LegacyBM25Similarity 把倍数折进 boost——explain 里 boost=2.2 不是查询写了 2.2,tf 描述里没有 (k1+1) 也不是公式变了。
🕳 以为 TF 越多越好:饱和项让 1→2 增 37.5%、20→21 只剩 0.3%。关键词堆砌在 BM25 里买不到排名;k1=0 时词频干脆不参与。
🕳 以为同查询同分数:IDF 依赖本 shard 的 N/n,写入不相干文档都会改老文档的分数(实验 10)。对比分数要固定语料,跨集群比绝对值更没意义。
🕳 sort 之后找 _score:按字段排时 _score 默认 null(track_scores=false);而且尺子已换成 Doc Values,BM25 冠军可能根本不进窗口——sort 不是 _score 的并列装饰。
🕳 rescore 和 sort 一起写:直接报错 Cannot use [sort] option in conjunction with [rescore]。rescore 只重打各 shard 本地 window_size 一小撮,不是全局精排,更不是第三阶段。
