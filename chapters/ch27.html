管道查询语言

你写的一行,已经是执行模型 · 约 15 分钟 · 前置:第 16-19 课 · 14 个实验 + 管道执行动画

学习目标

  • 对 5 行 views = 50/100/150/200/250 发出 FROM tut-l27-pages | WHERE views > 100 | STATS avg(views),先预测列名(avg(views),跟源码文本)、行数(一行一列)、均值(200,> 不含 100)与响应形状(columns+values,没有 hits),再用 POST /_query 对照。
  • 写出同等意图的 Query DSL(size:0 + range.gt + avg 聚合),验证数学相同(200.0);漏 size:0 看 hits 把 _source 搬回来而均值不变——「两棵树」与「一条管道」的形状差异。
  • 打开 EsqlPlugin.getRestHandlers 与 LogicalPlanBuilder.visitWhereCommand / visitStatsCommand:说出 REST 路径是 /_query 不是 /_esql(实测 POST /_esql 是 405);WHERE 变 Filter、STATS 变 Aggregate;并用 profile:true 在算子链上亲眼看见过滤下推(无 FilterOperator)与 avg 的 Sum/Count 改写。

1. 心智模型:查询本身就是一条管道

忘掉「Parser → Analyzer → Optimizer → Planner → Executor」那张阶段墙。ES|QL(Elasticsearch Query Language,8.11 起随发行版默认装载)要记住的是:你写的那一行,已经是执行模型。竖杠 | 和 Unix pipe 是同一件事:左边产出的表,是右边的输入。拿实验里的具体数字走一遍——5 行 views,WHERE views > 100 丢掉 ≤100 的两行,STATS 把剩下三行收成一个均值:

REST 入口也不是同一条:搜索是 POST /{index}/_search(第 16 课);ES|QL 是 POST /_query,仓库里没有 /_esql 这条路由。动作名倒是带着 esql:indices:data/read/esql——不要靠动作名去猜 URL。一个实测细节(实验 4):POST /_esql 回的不是 404 而是 405,allowed 列表是 [GET, PUT, DELETE, HEAD]——它撞上的是裸索引路由 /{index}(POST 不在其中),和第 7 课「未知路由 400、方法不匹配 405」的错误码阶梯对得上。和 Query DSL 的形状差别:同等「过滤后再平均」,ES|QL 是一条从左到右的管道;Query DSL 是两棵并排的 JSON 树——query 管命中、aggs 管桶。

_search(第 16-19 课)_query(本课)

3. 这条管道在源码里怎么接起来

REST 停在造 EsqlQueryRequest:路由写死在 RestEsqlQueryAction.routes() 里,只有一条 new Route(POST, "/_query")。进到 TransportEsqlQueryAction 时,真正干活的是插件在 createComponents 里造好的 PlanExecutor(解析/分析/优化/映射)和 ExchangeService(节点间传 Page),线程池是自己的 esql_worker——不复用第 16 课那条 _search 协调路径。解析的核心是竖杠的组合语义:

// x-pack/plugin/esql/src/main/java/org/elasticsearch/xpack/esql/parser/LogicalPlanBuilder.java(节选)
@Override
public LogicalPlan visitCompositeQuery(EsqlBaseParser.CompositeQueryContext ctx) {
    LogicalPlan input = plan(ctx.query());                                  // 先递归解析左边
    PlanFactory makePlan = typedParsing(this, ctx.processingCommand(), PlanFactory.class);
    return makePlan.apply(input);                                           // 左边的计划喂给右边
}

@Override
public PlanFactory visitWhereCommand(EsqlBaseParser.WhereCommandContext ctx) {
    Expression expression = expression(ctx.booleanExpression());
    return input -> new Filter(source(ctx), input, expression);             // WHERE → Filter
}

@Override
public PlanFactory visitStatsCommand(EsqlBaseParser.StatsCommandContext ctx) {
    final Stats stats = stats(source(ctx), ctx.grouping, ctx.stats);
    return input -> new Aggregate(source(ctx), input, stats.groupings, stats.aggregates);  // 非 TS 索引
}

所以三个命令各自变成:FROM → UnresolvedRelation(分析期由 ResolveTable 配上 field-caps 结果变成 EsRelation——views 必须在这时候能认成数值字段,否则 avg(views) 过不了 verifier);WHERE → Filter(没有叫 Where 的计划节点);STATS → Aggregate(没有叫 Stats 的节点;无 BY 时 groupings 为空)。树形 = Aggregate(Filter(EsRelation)):嵌套即管道,顺序即语义。优化器只留两条和本查询有关的行为:

// x-pack/plugin/esql/.../rule/PushDownAndCombineFilters.java 的 javadoc
// 过滤器要尽量往数据源推:
// "Ideally, the filter ends up all the way down at the data source
//  and can be turned into a Lucene query."

// x-pack/plugin/esql/.../expression/function/aggregate/Avg.java(节选)
@Override
public Expression surrogate() {   // avg 改写成 Sum / Count,没有叫 AvgOperator 的类
    return new Div(s, new Sum(s, field, ...), new Count(s, field, ...), dataType());
}

views > 100 推下去之后,LuceneSourceOperator 里的 Lucene Query 就带上了等价 range——被丢的行根本不进 Page。这不是改语义,是少算;不变量只有一条:源码管道仍是 FROM → WHERE → STATS,优化器可以少算,但不能改「先过滤再平均」。物理计划只是一张短表:Filter→FilterExec、Aggregate→AggregateExec;数据节点上 FROM 最终由 sourcePhysicalOperation 造出 LuceneSourceOperator.Factory(按 pageSize 吐文档号);无 BY 的聚合走阻塞式 AggregationOperator——javadoc 写明 only produces output once all possible input has been added:均值要看过滤后的全集,和第 19 课「聚合不能等 Fetch」同因。下面两条链不是示意图,是 profile: true 在本课实验数据上的实测输出(实验 8):

4. Page 是列,Driver 是单线程传送带

图 1 是命令,图 2 是算子;中间流动的东西叫 Page,它把「列式、按批」写在类注释里:

// x-pack/plugin/esql/compute/src/main/java/org/elasticsearch/compute/data/Page.java(节选)
/** A page is a column-oriented data abstraction that allows data to be
 *  passed between operators in batches. ... composed of a number of Blocks */
public final class Page implements Writeable, Releasable {
    private final Block[] blocks;      // 每列一个 Block
    private final int positionCount;   // 行数

同一列的 views 挨在一个 Block 里,过滤和聚合按列扫——这是它对 CPU 缓存/SIMD 友好的来源,不要画成架构盒。Operator.TARGET_PAGE_SIZE 默认按约 256KB 切批,5 行的实验看不见切批。FilterOperator.process 对每一行跑布尔 evaluator,null 和多值当成 false,留下的行号拿去重切 Page;Driver 的循环体则是:

// x-pack/plugin/esql/compute/src/main/java/org/elasticsearch/compute/operator/Driver.java(节选)
if (op.isFinished() == false && nextOp.needsInput()) {
    Page page = op.getOutput();          // 上游吐一页
    if (page == null) { /* 这一轮没有输出 */ }
    else if (page.getPositionCount() == 0 && page.batchMetadata() == null) {
        page.releaseBlocks();            // 空页直接释放
    } else {
        nextOp.addInput(page);           // 交给下游
    }
}

javadoc:*operates single-threadedly on a simple chain of Operators, passing Pages from one operator to the next*。没有扇出箭头:一个 Driver 一条链;分布式发生在多个 Driver 上(数据节点若干、协调节点再 reduce),由 ComputeService + ExchangeService 编排。对本课,Exchange 只是「数据节点算完局部聚合,把中间态送回协调节点再合并」。

5. 同等意图的 Query DSL 有多啰嗦

把图 1 翻成第 18、19 课的 JSON,最小等价是 size: 0 + query.range.gt + aggs.avg 三件事(实验 9-11)。你必须同时记住三件彼此分开的事:不要 hits、过滤写在 query、平均写在 aggs;漏掉 size: 0 会多搬三篇 _source 而均值不变。ES|QL 把这三件收成三个命令,顺序就是执行顺序。avg 在两条路上数学相同(200.0);选择哪条,看你要一张变换中的表,还是带分数的 hits:全文 match 与 BM25 排名(第 18、20 课)、highlight、_explain 仍是 _search 的主场;扫描、过滤、聚合一张表,管道更便宜——不是因为少打字,而是响应和执行模型都不再搬 hits。整条管道走一遍:

清理

思考题

1. 查询 A:WHERE views > 100 | STATS avg(views);B:同条但 STATS AVG(views);C:WHERE views >= 100;D:去掉 WHERE。四条的列名和均值各是什么?若 POST 到 /_esql 而不是 /_query,A 会怎样?

A:列名 avg(views),200.0;B:列名 AVG(views),仍 200.0(大小写只改列名字符串);C:175.0(把 100 算进去);D:150.0(五行之平均)。POST /_esql:405,allowed [GET,PUT,DELETE,HEAD]——它被裸索引路由 /{index} 捕获,不是 404;A 不会执行。allowed 列表是「这条路谁认领」的指纹:GET /_query 的 allowed 是 [POST]。

2. 为什么 STATS avg(views) 必须阻塞到看完过滤后的每一页,而不能像第 16 课那样「各 shard 只回 Top-10 再平均这 10 个 views」?WHERE 被推进 Lucene 后,哪条不变量仍成立、哪条预期会破?Avg 的 Sum/Count 改写会改变「先过滤再平均」吗?

均值的分母是过滤后的全集行数,不是 hits 窗口:Top-10 的 views 平均不是全集平均,分母会错。所以 AggregationOperator 必须等所有输入到齐才吐那一行(可以先各 shard 局部 Sum/Count、协调节点 FINAL 合并——那仍是全集)。下推后不变量「views≤100 的行不进平均」仍成立;破的是「profile 里一定看得到 FilterOperator」——这些行在源算子的 Lucene query 里就被丢了。Sum/Count 改写是同一批行上的代数等价,过滤集合不变。

3. 产品要「浏览量大于 100 的文章平均浏览量」,用 ES|QL 还是 Query DSL?什么时候值得付 Query DSL 那份嵌套 JSON?什么时候 ES|QL 的管道更便宜——不是因为少打字?

结果是一张分析表、不要 _score 时用 ES|QL:管道顺序即语义,响应没有 hits 形状,不走「先排名再 Fetch」,聚合的中间态按列流动。需要全文 match 的 SHOULD(第 18 课)、BM25 排序(第 20 课)、_explain、highlight 时付 Query DSL 的嵌套 JSON 走 _search。不要因为 ES|QL 字少就拿它替代 match——两边引擎的产物不同;也不要因为会写 aggs.avg 就拒绝一条三命令的管道——「少打字」从来不是重点,执行模型和响应形状才是。

陷阱

🕳 把 /_esql 当成 404:实测 POST /_esql 回 405 allowed [GET,PUT,DELETE,HEAD]——它撞上裸索引路由 /{index}(POST 不在其中),不是「无 handler」的 400,更不是 404。ES|QL 的同步路由只有 POST /_query;异步是 /_query/async。
🕳 用动作名猜 URL:indices:data/read/esql 带着 esql,URL 里却没有——和第 16 课 search 动作对的是 /_search 不是动作名直译,同一类陷阱。
🕳 在 profile 里找不到 FilterOperator 就以为 WHERE 没生效:WHERE 被下推进 LuceneSourceOperator 的 query(被丢的行根本不进 Page),链上可以没有 FilterOperator——下推只换执行地点,不变量「这些行不进平均」仍在。
🕳 找 AvgOperator / Where 节点 / Stats 节点:都不存在——avg 改写成 Sum/Count(除法在协调端 Eval),WHERE→Filter、STATS→Aggregate,列名仍按你写的呈现。
🕳 以为 ES|QL 更短所以 Lucene 路径更短:FROM 仍打 Lucene(LuceneSourceOperator),省下的是描述方式与 hits 形状;全文排名还得回 _search。也别忘了 FROM 只见已 refresh 的数据——第 16 课不变量没变。

速记

一句话内容
本课位置另一条 REST 入口:POST /_query 上的管道文本,你写的一行就是执行模型
命令 → 节点FROM→UnresolvedRelation→EsRelation;WHERE→Filter(可下推进 Lucene);STATS→Aggregate(无 BY 走阻塞式 AggregationOperator)
竖杠语义visitCompositeQuery:左边 LogicalPlan 喂给右边 PlanFactory——嵌套即管道
物理侧LuceneSourceOperator → ValuesSourceReader → Aggregation[INITIAL] → ExchangeSink;协调端 FINAL 合并 + Eval 除法
avg 的真身SurrogateExpression:Sum/Count 两聚合 + DivDoublesEvaluator;没有 AvgOperator
流动单元列式 Page(Block[] × positionCount),~256KB 切批;Driver 单线程一条链
与 _search 分工hits/_score/BM25/highlight 走 _search;扫描过滤聚合一张表走 _query;响应 columns+values

心法:竖杠把三步钉成一条链——顺序即语义;优化器只能少算,不能改「先过滤再平均」。
