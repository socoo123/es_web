摄取管道

写入前的数据预处理 · 约 18 分钟 · 前置:第 10、11 课 · 20 个实验

学习目标

  • 建一条 set + rename 管道,用 _simulate 在不写入的前提下说出字段会变成什么,并对上 SetProcessor.execute / RenameProcessor.execute 的关键行。
  • 带 ?pipeline= 写入后 GET,指出 _source 里多了哪些字段、哪个被改名;说出 pipeline 改的是「即将写入的那份 JSON」,不是已经躺在 Lucene 里的文档。
  • 预测 pipeline 把 _routing 改成 tenant-a 后,文档落在 hash(tenant-a) 那个 shard;用 _search_shards 和带/不带 routing 的 GET 验证第 10 课那条不变量。

1. 心智模型:先改 JSON,再选 shard

第 11 课把 Mapping 钉成 Schema:JSON 里的字符串凭什么变成倒排表上的 token。但有一类事不该等进 Lucene 再做——加字段、改名、把一行 syslog 拆开、甚至改 _routing。这些发生在 Ingest Pipeline 里,而它必须跑在文档被 hash 到某个 shard 之前。Pipeline 是一条 Processor 链:文档还没被路由、还没进 Mapping / Engine,链上每个 processor 依次改同一份内存里的 JSON。拿这份输入走路:

{ "hostname": "web-01", "level": "INFO" }

先 set 一个 environment,再把 hostname rename 成 host:

这张图钉死两件事:pipeline 改的是文档本身(字段出现、消失、改名),顺序就是 processors 数组的顺序——set 不会替你改名,rename 不会凭空造值,各做一步。更关键的是时间点:链跑完之后,协调节点才拿(可能已被改过的)_id / _routing 去 hash 选 shard。改 _routing 会改变文档落在哪一个 shard——这不是旁注,第 4 节用源码证,实验 13-18 用集群证。

Mapping 在 pipeline 之后、写入 Lucene 之时才看字段类型:pipeline 新加的 environment 如果索引里还没有这个字段,仍走第 11 课的动态映射,建成 text + keyword。一句话:ingest 先改 JSON,mapping 再决定这份 JSON 怎么进倒排。Pipeline 和 Processor 也不要画成两套架构:

PipelineProcessor

3. 一份 JSON 怎么被改掉:set 然后 rename

Processor 的契约是「拿到一份 IngestDocument,改完再交出去」。9.4.0 的接口分同步/异步两份,不要背旧材料那份「async 默认包一层 sync」的伪代码:同步实现覆盖 execute(IngestDocument);异步实现(enrich、第 5 节的 pipeline processor)覆盖带 handler 的那份,并让 isAsync() 返回 true。同步那份返回 null 表示 drop:这篇文档不会被索引,CompoundProcessor 看到 null 立刻结束整条链。

图 1 的第一步是 set。field 支持 Mustache 模板({{some_field}}),value 走 ValueSource(字面量,或含 {{_ingest.timestamp}});9.4.0 不再是旧材料的 this.value.copyAndResolve(document):

// modules/ingest-common/src/main/java/org/elasticsearch/ingest/common/SetProcessor.java
public IngestDocument execute(IngestDocument document) {
    String path = document.renderTemplate(field);   // field 支持 {{some_field}} 模板
    if (overrideEnabled || document.hasField(path) == false
            || document.getFieldValue(path, Object.class) == null) {
        document.setFieldValue(path, value, ignoreEmptyValue);  // copy_from 分支同理
    }
    return document;
}

override 默认 true:字段已存在就覆盖。copy_from 和 value 不能同时出现(Factory 里直接抛配置异常)。path 可以是 _source 里的普通字段,也可以是元数据名 _routing / _index / _id——IngestDocument.setFieldValue 对这两类走同一套路径 API,底层 IngestCtxMap 把以下划线开头的键交给 metadata。

图 1 的第二步是 rename:读出旧字段、删掉、写到新名字。目标已存在且 override 为 false(默认)会抛 field [target] already exists;写失败会把值写回原字段,避免「删了却没贴上」:

// modules/ingest-common/src/main/java/org/elasticsearch/ingest/common/RenameProcessor.java
Object value = document.getFieldValue(path, Object.class);
document.removeField(path);                  // 先删旧名
try {
    document.setFieldValue(target, value);   // 再写新名
} catch (Exception e) {
    document.setFieldValue(path, value);     // 贴不上就把值写回原字段
    throw e;
}

对应图 1 的中间态:hostname 先还在,set 之后多了 environment,rename 之后 hostname 消失、host 出现。实验 2 的 _simulate 要对的就是这份新 JSON,不是「pipeline 对象被创建了」。这两步都在 modules/ingest-common 里,不在 server/:Processor.Factory 由 IngestPlugin 注册进 IngestService 的 factory 表,pipeline 的 JSON 被解析时按 "set" / "rename" 找到对应 Factory(插件加载见第 4 课)。

4. 为什么必须在路由之前跑

第 10 课钉过选 shard:普通索引(IndexRouting.Unpartitioned)里,有 routing 就只 hash routing,不再混入 _id。如果 pipeline 能改 _routing,而改完之后才 hash,文档就会落到另一号 shard——9.4.0 仍然如此,不要凭记忆说「现在改不了了」。单条 PUT /idx/_doc/1?pipeline=... 也进这条路:TransportIndexAction 的 javadoc 标着 Deprecated use TransportBulkAction with a single item instead,它继承 TransportSingleItemBulkWriteAction,真正干活的是 bulk。

时间顺序用一份具体输入写出来:写入 PUT /tut-l12-routed/_doc/1?pipeline=tut-l12-routing,body 里没有 routing 字段,pipeline 里只有一步 set: {"field": "_routing", "value": "tenant-a"}:

源码把这四步拆在三个类里。第一站,协调节点发现请求带 pipeline(或索引的 default_pipeline / final_pipeline),先跑 ingest,再进入真正的写入——TransportAbstractBulkAction 的类注释直说:遍历请求要去的所有索引、执行所有 applicable pipelines、然后才 doInternalExecute。applyPipelines 里:若 hasIndexRequestsWithPipelines,本节点是 ingest 节点就 processBulkIndexIngestRequest,否则 ingestForwarder.forwardIngestRequest 转发到 ingest 节点;跑完之后的回调才 applyPipelinesAndDoInternalExecute(..., haveRunIngestService=true),最终 TransportBulkAction.doInternalExecute 走到 executeBulk → new BulkOperation(...).run()。选 shard 不在 ingest 之前。

第二站,IngestService.executeBulkRequest 为每条 IndexRequest 建文档、跑链、把元数据写回。构造时就把请求上已有的 routing 带进 IngestDocument(newIngestDocument 读 request.routing());每跑完一条 pipeline,把 metadata 同步回请求——_routing 在这里被写进 IndexRequest:

// server/src/main/java/org/elasticsearch/ingest/IngestService.java
private static void updateIndexRequestMetadata(final IndexRequest request, final Metadata metadata) {
    // ingest document holds their starting values before ingestion,
    // which might also get modified during ingestion.
    request.index(metadata.getIndex());
    request.id(metadata.getId());
    request.routing(metadata.getRouting());   // set 进去的 _routing 在这里写回
    request.version(metadata.getVersion());
    // ... versionType / ifSeqNo / ifPrimaryTerm / dynamic templates ...
}

全部 pipeline 结束后还有 updateIndexRequestSource:用 ingest 之后的 map 覆盖 IndexRequest 的 _source——所以实验 8 里 GET 到的是改过的 JSON。第三站,BulkOperation.doRun 调 groupBulkRequestsByShards,这里才出现 IndexRouting:

// server/src/main/java/org/elasticsearch/action/bulk/BulkOperation.java
IndexRouting indexRouting = concreteIndices.routing(concreteIndex);
docWriteRequest.preRoutingProcess(indexRouting);
int shardId = docWriteRequest.route(indexRouting);   // ← ingest 之后才发生
docWriteRequest.postRoutingProcess(indexRouting);

IndexRequest.route 就是 indexRouting.indexShard(this),普通索引落到第 10 课那条 Unpartitioned.indexShard → shardId(id, routing),仍是 hash(routing == null ? id : routing) 再对主分片数取模。pipeline 刚写回的 tenant-a 在这里变成有效键。时序索引(IndexMode.TIME_SERIES)走另一套 hashSource,本课建的是普通索引,别把那条分支套过来。

_routing 之所以能被 set 改掉,是因为 ingest 侧把它标成可写:IngestDocMetadata.PROPERTIES 里 ROUTING 是 StringField.withWritable().withNullable()(名字取自 RoutingFieldMapper.NAME,即 "_routing");IngestCtxMap 的 javadoc 还要求 _index / _id / _routing 必须是 String 或 null——你不能 set 一个数字进去当 routing。

请求 pipeline、default_pipeline、final_pipeline

不是只有 ?pipeline=。IngestService.setPipelineOnRequest 的规则:请求带的 pipeline 永远优先,没带才用解析出来的 default;final_pipeline 与二者无关、总是最后。

来源何时跑谁优先
请求 ?pipeline= 或 bulk meta 的 "pipeline"第一条请求覆盖索引上的 index.default_pipeline
index.default_pipeline请求没指定 pipeline 时,占据同一条「第一条」槽来自索引 settings 或匹配到的 index template
index.final_pipeline总是最后,与请求 pipeline 无关不能改目标 _index(改了抛 IngestPipelineException)

两者都是 _none(IngestService.NOOP_PIPELINE_NAME)时视为没有 pipeline,跳过 ingest。PipelineIterator 最多排出两格:先 default(请求或 default_pipeline),再 final。pipeline 改 _index 会触发重新 resolvePipelinesAndUpdateIndexRequest(文档 reroute 到另一个索引);无 reroute 标记、只是把 _index 改掉时,新索引的 default_pipeline 不会再跑(源码注释:backwards compatibility)。本节点不是 ingest 节点时,整份 bulk 会被 IngestActionForwarder 转到 ingest 节点跑完再回来;单节点通常自身就是 ingest 节点,实验不必处理转发。

5. CompoundProcessor:顺序执行,失败可拦可抛

Pipeline.execute 几乎只做三件事:记 metrics、把文档交给 compoundProcessor、回调里把 terminate 标志清掉好让外层 pipeline 继续。CompoundProcessor.innerExecute 按列表下标往前走:同步 processor 在一个 while 里直接 execute(ingestDocument),碰到异步的才切到带 handler 的那条。链是单线程顺序的:下一步看见的是上一步改过的 map,成功路径没有菱形。失败的出路有三条(executeOnFailureOuter):

出路条件结果
继续下一个整条 CompoundProcessor 带了 ignore_failure记下失败 metrics,接着跑
on_failure 链这个 processor(或 pipeline)配了 on_failure 列表先 putFailureMetadata 再跑补救链;链成功则文档留下
抛出都没有IngestProcessorException 交给 handler,这一篇写入失败(bulk 里其它条仍可成功,第 13 课)

失败时 putFailureMetadata 往管道元数据里塞四项(有 pipeline origin 才有第四项):

{ "_ingest": {
    "on_failure_message": "field [timestamp] not present",
    "on_failure_processor_type": "date",
    "on_failure_processor_tag": "parse-date",
    "on_failure_pipeline": "my-pipeline" } }

on_failure 里的 set 可以用 {{_ingest.on_failure_message}} 把原因写进 _source,于是「解析失败的日志」仍能进索引,而不是整条 400——实验 5 就是这个形状。on_failure 链跑完后这些键会被 removeFailureMetadata 清掉:它们活在 _ingest 元数据里,默认不进 _source。循环的出口还有 isReroute() / isTerminate():为 true 时不再跑后面的 processor;drop processor 返回 null,整篇被丢弃,回调会把 bulk 里这一 slot 标成 dropped。

嵌套 pipeline:pipeline processor 是异步的(isAsync() 恒为 true),它按模板取出名字、ingestService.getPipeline 拿到另一条 Pipeline、再 executePipeline。守卫在 IngestDocument:MAX_PIPELINES 默认 100(系统属性 es.ingest.max_pipelines 可改);executedPipelines 是 LinkedHashSet,加不进去说明同名 pipeline 已在栈上 → Cycle detected for pipeline: {id},超过上限 → Too many nested pipelines。

6. IngestDocument:一份 _source,外加可改的元数据

IngestDocument 不是「只有 JSON body」。它有三块:

块存在哪例子
文档内容ctxMap 的 sourcehostname、level、environment
文档元数据ctxMap 的 IngestDocMetadata_index、_id、_routing、_version、_dynamic_templates
管道元数据ingestMetadata_ingest.timestamp、当前 pipeline、on_failure 四字段

IngestDocument.Metadata 枚举把元数据名字钉死(INDEX / _type / ID / ROUTING / VERSION / …);_type 还在枚举里但标了 @UpdateForV10,不要再往文档里写它。字段 API 支持点号路径:getFieldValue("author.name", String.class)、setFieldValue("processed", true)、hasField、removeField;改元数据和改 _source 用同一套 setFieldValue("_routing", "tenant-a")——图 2 才能成立。_ingest.timestamp 在构造函数里写成 UTC 的 ZonedDateTime.now,set 的 "{{_ingest.timestamp}}" 才能展开;executePipeline 会把当前 pipeline id 放进 ingestMetadata["pipeline"],嵌套返回时再恢复——这就是 _simulate verbose 输出里「现在跑的是哪条 pipeline」的来源。

7. _simulate:同一条执行链,不选 shard、不落盘

建 pipeline 的 REST 是 PUT /_ingest/pipeline/{id}(RestPutPipelineAction)。试跑不要用真实写入,用 _simulate:RestSimulatePipelineAction 注册了四条路由——GET/POST /_ingest/pipeline/{id}/_simulate 和 GET/POST /_ingest/pipeline/_simulate。路径带 {id} 就跑已经 PUT 进去的那条;不带 id 则在 body 里内联一条 "pipeline": {"processors": [...]}。Action 权限是 cluster:admin/ingest/pipeline/simulate,不是写入那条 indices:data/write/...。

SimulatePipelineTransportAction.doExecute 若本节点不是 ingest 节点会转走(geoip 一类资源只在 ingest 节点上);是 ingest 节点则解析请求,交给 SimulateExecutionService,真正执行就是 ingestDocument.executePipeline(pipeline, ...)——和写入路径同一条 Pipeline / CompoundProcessor 链。verbose=true 时用 TrackingResultProcessor.decorate 把每个 processor 包一层,把每一步的 SimulateProcessorResult 收集起来,于是能看见「set 之后、rename 之前」的中间态。所以实验 2 能看见 host 和 environment;要看见 shard 号变了,必须走实验 15 的真实写入。_simulate 结果里就算出现 _routing,也只说明 metadata 被改了,没有经过 IndexRouting.shardId。生产习惯三条:改 pipeline 先 _simulate;用 verbose 看中间态;用真实脏样本(缺字段、日期格式不对)覆盖失败分支。不要用 _simulate 当写入。

思考题

1. 实验 15 已经用 pipeline 把 _id=1 写进 hash(tenant-a) 那个 shard。GET .../_doc/1?routing=tenant-b 会怎样?若再建一条管道把 _id set 成 99(不改 routing),GET 该用哪个 id?q=_id:1 还能找到吗?

tenant-b 的 GET 几乎总是 found: false:有效键既不是写入时的 tenant-a,也不是 _id,而 GET 仍然只打一个 shard,不会换去试 tenant-a 那份拷贝。set _id=99 之后,文档的 _id 就是 99——request.id(metadata.getId()) 在选 shard 之前就改了;GET 要用 /_doc/99(若同时还被 set 了 _routing,还得带那把键)。q=_id:1 找不到旧 id:倒排里的 _id 是 ingest 之后的值;SEARCH 不带 routing 仍可能找到 99 那篇,因为搜索扇出全部 shard。把 metadata 当成 _source 里的装饰字段,就会错判这两问。

2. 为什么 ingest 必须在 BulkOperation.route() 之前?若先按原始 _id 选 shard、再在数据节点上跑 pipeline,即使禁止改 _routing,改 _source 仍安全吗?final_pipeline 禁止改目标索引,保护的是哪条不变量?

route() 读的是当时 IndexRequest 上的 id / routing / index。先选 shard 再改 _routing,文档躺在 hash(旧键) 的拷贝上,而 GET 和后续写入用新键去另一号 shard——第 10 课「键必须一致」直接破裂,且 GET 不广播、没有补救。即便冻结 _routing,先选 shard 再改 _index 仍会把文档写进错误索引的某个 shard(mapping 推断也发生在具体索引上)。只改 _source 理论上可以延后,但 9.4.0 把元数据和 source 放在同一次回写里,没有「只改 source 的延后通道」。final_pipeline 禁改 _index,是让管理员钉死「进这个索引的文档最后必经这条链,且不能逃到别的索引」——请求 pipeline 和 default_pipeline 都可能 reroute,final 是最后一道不能搬目标的关卡。

3. 字段改名、加环境标签,可以在客户端做、在 ingest pipeline 做、也可以事后用 runtime field / reindex。什么时候值得付 ingest 这笔 CPU?什么时候应该坚持 index.final_pipeline 做脱敏?

客户端改名便宜但不强制:多个采集器各写各的 hostname / host,动态 mapping 会建出两套字段,搜索还得记别名。ingest pipeline 把契约收口到集群——所有写入(含改不动的 Beats / 旧程序)都过同一条链;代价是协调 / ingest 节点在写路径上多一次 JSON 解析和 processor CPU,bulk 吞吐受 ingest 线程池限制。进索引后再 reindex 能补历史,但双倍存储、延迟大;runtime field 不改倒排,不适合「按新字段热聚合」。脱敏、强制安全标签该用 final_pipeline:它在请求 pipeline 之后仍跑,调用方没法用 ?pipeline= 绕过。改新链前先 _simulate 加真实脏样本,别让 on_failure 在生产第一次触发。没有「写入零成本又保证字段契约」的免费午餐。

陷阱

🕳 「_simulate 顺手把文档写进去了」:它跑的是同一条 Pipeline.execute,但拿到结果就返回——不选 shard、不落盘;去 GET 只会 404(那个索引压根没被创建,路由命中、资源不存在)。要验证落盘,必须真实写入。
🕳 「pipeline 改 _routing 只是让响应里多个字段」:错。set 经 updateIndexRequestMetadata 写回 IndexRequest 之后,route() 用的就是这把键。不带键的 GET 会 404——那是路由算错了 shard,不是数据丢了;SEARCH 扇出全部 shard,不受影响。
🕳 「用过一次 ?pipeline= 就成了索引默认」:不会,它只作用于这一次请求。整索引默认要设 index.default_pipeline(请求 pipeline 会覆盖它);index.final_pipeline 与二者无关、总在最后跑,且不能改目标 _index。
🕳 「on_failure 的 _ingest.* 会留在文档里」:它们活在管道元数据,补救链跑完被 removeFailureMetadata 清掉,默认不进 _source;想要留证据,得在 on_failure 里自己 set 一个普通字段(如 date_parse_error)。

速记

一句话内容
链Pipeline 握 CompoundProcessor;顺序 = processors 数组顺序,单线程依次改同一份 JSON
时机ingest 在 route() 之前:TransportAbstractBulkAction → IngestService → BulkOperation.route
元数据_routing / _index / _id 可写(withWritable);updateIndexRequestMetadata 写回 IndexRequest,值必须 String 或 null
失败ignore_failure → on_failure(_ingest 四字段)→ 抛出;返回 null = drop;嵌套默认 100、环被检出
优先级?pipeline= 覆盖 index.default_pipeline;final_pipeline 总最后且禁改 _index;都为 _none 则跳过
验证_simulate 跑同一条 Pipeline.execute,不落盘不选 shard;verbose 看每步中间态
与 mappingingest 先改 JSON,mapping 之后才看字段;新字段仍动态建成 text + keyword

心法:pipeline 改的是「即将写入的那份 JSON」;链跑完,才轮到 hash 选 shard。
