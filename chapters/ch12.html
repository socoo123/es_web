12.1 管道跑完，才用哪份请求选分片？

本课锚定 Elasticsearch 9.4.0、Lucene 10.4.0，引用官方固定提交 2e8528e。主线限定新建普通 standard 索引、stored source、无匹配模板的 index 写入，不展开数据流 failure store、时序路由与重定向。Pipeline 是有名称的处理器列表；Processor 是其中一个步骤。注册定义与运行文档是不同操作：PUT 把定义提交到集群状态的 IngestMetadata，各节点再构造本地 Pipeline，不会因此创建文档。

单条 PUT /index/_doc/1 也复用 bulk 写入。TransportAbstractBulkAction.applyPipelines 先解析请求需要的管道：本节点有 ingest 角色就执行，否则转发。完成回调才进入具体 bulk 实现，随后 BulkOperation.groupBulkRequestsByShards 调 route 分组。它读的是处理后的 index / id / routing；Mapping 则在主分片解析这份 JSON 时决定索引结构。管道改字段，不会直接替你建立或修改 mapping。

成功回调中，IngestService.updateIndexRequestMetadata 回写元数据；所有适用管道结束后，updateIndexRequestSource 序列化改后的 source。这解释了两条证据：B4 读到新增的 environment 与改名后的 host；C8 读到由管道写入的 _routing。失败或 drop 提前终止，不能把图中的箭头理解为每次请求都必走到底。

源码依据：定义存储、执行入口与回写

putPipeline：验证并提交状态任务；状态任务写入 IngestMetadata；innerUpdatePipelines：构造本地执行对象。运行入口见 applyPipelines / 完成回调，回写见 updateIndexRequestMetadata / Source，路由见 groupBulkRequestsByShards。

12.2 set 与 rename 改的是哪块数据？

IngestDocument 同时提供三种信息：文档 source、_index / _id / _routing 等文档元数据，以及 _ingest.timestamp / 当前 pipeline / 临时失败信息等摄取元数据。字段 API 用路径读写；本课采用 classic 访问模式，点号表示路径。不是所有元数据都可任意赋值：_index、_id、_routing 在 ingest 侧是可写 String 或 null，仍要满足后续写入验证；数值字段等有各自类型约束。普通 routing 字段不会自动变成 _routing。

输入：{ "hostname": "web-01", "level": "INFO" }
set environment：{ "hostname": "web-01", "level": "INFO", "environment": "production" }
rename hostname → host：{ "host": "web-01", "level": "INFO", "environment": "production" }

set 的 override 默认 true；显式 false 时，字段不存在或为 null 仍可设置。字段名和值可使用模板，copy_from 与 value 互斥。rename 默认不忽略缺失，也不覆盖已有目标；先检查目标，再取值、删旧字段、设新字段，设置失败时尝试恢复原字段。这是 rename 的局部处理，不能推广成整条管道的事务回滚。

处理器按列表顺序依赖：下一步拿到上一步返回的文档；同步实现直接执行，异步实现通过 handler 完成后继续。顺序不等于一直占用同一线程。普通 bulk 协调使用 write_coordination；异步回调换线程后，继续协调可切回其 executor。这里没有一个可用来解释所有摄取吞吐的“独立 ingest 线程池”；实际成本受 CPU、处理器、异步外部工作及写入背压共同影响。

本课另用 grok 捕获日志中的字符串，再 remove 原始 message；捕获时间字符串不等于按 date mapping 索引。date 处理器按指定 formats 解析并写目标字段，本课显式 UTC；解析失败时仍有原始 raw_date。_ingest.timestamp 与失败元数据默认不进入 source，想保留应显式 set 到普通字段。

源码依据：字段操作、顺序与线程交接

SetProcessor.execute、set 配置与默认；RenameProcessor.execute、rename 默认；元数据属性；同步循环与异步回调；协调 executor、异步后继续协调。grok 捕获与date 解析 / UTC 回退分别回答值转换问题。

12.3 _simulate 成功，证明了什么？

POST /_ingest/pipeline/id/_simulate 使用已注册定义；不带 id 则在 body 中内联 pipeline。它在 ingest 节点构造独立 IngestDocument，运行同样的 Pipeline / CompoundProcessor，返回处理结果。verbose=true 包装处理器，收集每步快照；A3 能区分 set 后与 rename 后的文档。它不创建所填的 _index，也不进入分片路由、mapping 解析或 Engine。

因此 A6 对显式模拟名字执行 HEAD 应是 404，前提是它原本不存在；已有索引里的旧文档不会因为模拟消失。“没有落盘”不能推出任意 GET 必然 404。模拟也不按索引自动组合 default / final；final 禁改 _index 的约束在真实 IngestService 写入路径中检查。用该 API测试处理器，是实际写入验收之前的一步。

还要分开请求成功与文档成功：有效模拟请求中，一篇处理失败可返回 HTTP 200，并在该项包含 error；无 ingest 节点、错误配置或请求解析失败则可直接报错。真实写入有自己的单条 / bulk 错误结果。看 docs 中的 doc / error，而不是只看状态；动态时间与包装错误层级以真实响应为准。

依据：模拟节点选择与解析、构造模拟文档、执行与逐文档结果。

12.4 同一个错误，在哪层补救会改变后续步骤？

在 date 后放一个 set after_date，再输入 not-a-date。成功的处理器级补救让外层继续，于是 after_date 出现；未处理的失败上抛到管道根，根 on_failure 成功后当前管道返回，after_date 不执行。区别来自捕获失败的包装层，不是由补救字段名称决定。

配置层级失败后动作date 后的 set
处理器 ignore_failure:true忽略该失败，优先于同层 on_failure继续执行；不保证回滚修改
处理器 on_failure包装层执行局部补救，成功返回文档外层继续主列表
pipeline 根 on_failure根层执行补救并结束本管道不再执行本管道后续主列表
没有恢复 / 恢复也失败错误向外传播不执行；普通索引本项失败

进入补救时会放入 _ingest.on_failure_message / processor_type / processor_tag；有来源 pipeline 时还包括 on_failure_pipeline。补救成功返回前移除临时失败信息；把消息 set 成 date_parse_error 才会作为普通字段保留。错误信息不是自动持久化的审计日志。A5 / A7–A9 用同一坏日期分别验证恢复位置；不声称本轮已发送这些 API。

drop 返回 null，结束当前项，后续 final 和分片写入都不再执行；真实单条请求可得到 result:noop，首次全新 ID 的 GET 仍是 404。它也不会删除同 ID 的旧文档。嵌套 pipeline 的处理器使用异步接口；活动调用栈用名称检环，默认允许至 100 个活动管道（含外层，系统属性可调整）。这是嵌套深度约束，不是一条长列表只能执行 100 步；顺序完成后可再次调用同名管道。

源码依据：恢复层级、drop 与嵌套守卫

构造处理器失败包装、仅包装当前一个处理器、管道根 CompoundProcessor；忽略、上抛与补救返回、临时失败元数据；drop 返回 null、失败 / drop 提前停止、dropped 转 noop；默认深度、活动栈守卫与完成清理。

12.5 两个槽，为什么 final 也有提前停止条件？

普通 index 请求首先选择请求 pipeline，若未指定才选择索引 default_pipeline；随后是独立的 final_pipeline。不是 default、请求、final 三条相继运行。请求 pipeline=_none 跳过第一槽，不覆盖索引设置，也不跳过已配置的 final。D5–D8 对照三篇文档：默认标签、请求字段变换、跳过第一槽，它们在成功保留后都有 audited:true。

“final 总在最后”应读为：已配置 final 的正常路径里，前链成功保留文档后执行它；未处理失败或 drop 不会继续。这个设置能收口受其约束的 index 写入，不能泛化为所有更新 / 删除 / 其他写 API 的统一安全门。final 执行后的 _index 若改变，会在选分片前被拒；合法的 set 定义能 PUT，不代表执行到 final 就合法。D13–D16 触发该检查并恢复。

改变目标索引还会重新解析管道。直接 set _index 而未使用 reroute 标志时，为兼容旧行为，新目标的 default 不再执行，final 仍按新目标解析；reroute 路径不同，并受索引循环检查。这是图 01 省略的分支，不能用普通路径推断原目标 final 必定继续。

删除也有约束：仍被任意索引 default / final 引用的管道会拒删。GET pipeline 的多 ID 读取规则不能套到 DELETE；删除请求 id 是单个名称或简单通配模式，逗号不会拆成列表。本课先删三个索引，再逐条点名删五条管道，避免误删其他资源。

依据：选择两个槽、PipelineIterator、final 禁改目标、新目标重解析、删除匹配、引用保护。

12.6 _routing 改了，GET 会不会一定 miss？

C 组新建五主分片、0 副本、非分区路由索引，未要求 routing。管道 set _routing=tenant-a，成功回写后 route 用它选分片。对本课创建版本，分片号是 floorMod(Murmur3(有效键),5)；有 routing 用它，否则用 _id。旧创建版本还有 routingNumShards / routingFactor 分支，不能把当前节点版本当作旧索引的路由公式。

先用 _search_shards 比较键 1 与 tenant-a 的分片号；这个 API计算选择，不证明数据位于那里。异号时，不带 routing 的 GET 查错分片而 404；同号时可能命中。五个桶不意味着不同字符串必落在不同分片，routing 不是安全隔离键。带 tenant-a 的 GET 回显 _routing 与 source；写入已显式 refresh=true，所以不带 routing 的搜索可在全部分片找到文档。GET 的默认 realtime 可见性与这次搜索刷新是不同机制。

依据：回写路由、创建版本分支与取模、Unpartitioned 有效键。

前提：自建 ES 9.4.0 / Lucene 10.4.0，单节点具备 ingest 与数据角色；默认端点 http://localhost:9200、安全关闭、本地 CORS 已配置。其他端点可在连接设置选择；启用安全时需对应索引读写、管道 / 索引管理、健康监控权限。三个索引与五条管道的本课名称首次不存在，没有匹配模板、外部写入 / 刷新或修改管道的任务。探针 tut-l12-probe 也不存在，但本课只模拟和 HEAD，不建它、不清理它。

思考题

1. 同样复制错误消息，为什么处理器级补救有 after_date，管道级却没有？

处理器级失败只结束包装这个 date 的内层 CompoundProcessor；成功文档返回外层后，继续下一处理器。根管道捕获的是尚未恢复的失败；根 on_failure 完成就回调返回当前管道，不从 date 后继续。忽略优先、补救再次失败和 drop 都会改变这条路径。

2. 请求 pipeline=_none，为什么还有 audited？若请求管道 drop 呢？

_none 只选择第一槽无操作，final 槽独立，因此成功保留文档后写 audited。drop 返回 null，IngestService 提前返回，不执行 final，不提交新文档；旧同 ID 文档仍保留。这个结论限定本课普通 index 写入，不扩展到所有修改 API。

3. 不带 routing 的 GET 命中了，能否否定管道改 routing？

不能。两把不同字符串可能映射到同一分片。比较 _search_shards 的分片号，再看正确 GET 回显的 _routing；不要把键空间与分片结果空间混为一谈。换键演示时要同步修改管道和全部带键请求，并清理后重做。

4. _simulate 返回 200，能否直接发布新管道并断言所有写入安全？

先检查逐文档结果是否含 error，再对照真实写入的管道选择、final 约束、路由、mapping 与可见性。样本应覆盖缺字段、已有目标、坏日期等条件。模拟不证明历史文档已被回填，也不代表 processor 的运行成本或所有生产写入路径。

陷阱

顺序执行不等于同一线程或自动回滚异步处理器完成后才继续；ignore_failure 不承诺恢复 source，rename 的局部恢复不能当整条链的事务。
成功响应不等于新文档已存储模拟 HTTP 200 可含逐文档 error；drop 的 noop 不落新文档。是否持久化需结合实际写入与 GET / 搜索。
final 不是无条件的最后一步前链未处理失败 / drop 会提前结束；重定向重新选管道。不能把普通 index 的约束描述为所有写 API 的不可绕过安全保证。
_source 的变化不替换已有 mapping改名后的新字段仍按索引配置解析，旧字段和旧文档不会自动迁移；本课 text + keyword 结论有显式动态配置前提。
DELETE 的逗号清单不能照搬 GET管道逐条点名删除；先解除索引 default / final 引用。本课不使用通配清理，也不承诺重复删除仍 acknowledged。
