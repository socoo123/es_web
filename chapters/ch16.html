搜索流程总览

Query Then Fetch:先比分,再搬正文 · 约 16 分钟 · 前置:第 8、10 课 · 14 个实验

学习目标

  • 用「3 个 shard、size=10」这组数字说出:Query 阶段网上走 30 条 (docId, score),协调节点截全局 Top-10,Fetch 只搬 10 篇 _source。
  • 打开 SearchPhaseController.getTopDocsSize 与 QueryPhaseCollectorManager,写出每个 shard 必回 from + size 条;预测 from=10000&size=10 会被 index.max_result_window 拦在哪一步。
  • 读 profile:true 的响应,分出 searches(query 段)与 fetch 段;并说出 SEARCH 与 GET 的三处分野:打几个 shard、看哪份快照、单程还是两阶段。

1. 心智模型:SEARCH 不是「放大的 GET」

第 10 课把 GET 钉死了:按 _id 只打一个 shard,Realtime 走 VersionMap / translog,不必等 refresh。SEARCH 从第一步就分岔:POST /{index}/_search 默认打该索引的每一个 shard 组,而且看的是 refresh 之后的 EXTERNAL searcher——刚写入还没 refresh 的文档,GET 能命中,SEARCH 可能 0 hits。

如果每个 shard 都把本地 Top-10 的完整 _source 送回协调节点,3 个 shard 就是 30 篇正文,而客户端只要全局 Top-10——大部分带宽浪费在永远进不了响应的文档上。ES 的默认解法是 Query Then Fetch:

3. REST 停在造 SearchRequest

和第 10 课的 RestGetAction 同一模式:REST 只适配,不跑 Lucene。真正离开 REST 的是 TransportSearchAction.TYPE("indices:data/read/search",GET 是 "indices:data/read/get")。executeRequest 解析索引、处理 PIT / CCS 之后落到 executeSearch:合并 shard 迭代器、adjustSearchType,再构造异步动作——

// TransportSearchAction.AsyncSearchActionProvider.runNewSearchPhase
if (searchRequest.searchType() == DFS_QUERY_THEN_FETCH) {
    searchPhase = new SearchDfsQueryThenFetchAsyncAction(/* ... */);
} else {
    assert searchRequest.searchType() == QUERY_THEN_FETCH : searchRequest.searchType();
    searchPhase = new SearchQueryThenFetchAsyncAction(/* ... */);
}
searchPhase.start();

两条纪律藏在 SearchType 枚举里:默认值就是 QUERY_THEN_FETCH;老的 Query-And-Fetch 搜索类型已经不存在(字节值 2、3 已删,fromId 碰到直接抛)。单 shard 时「Query 阶段顺便 Fetch」仍然会发生,但那是 SearchService 的优化,不是一种 SearchType——见第 5 节。另外 adjustSearchType 会在单 shard 组时把类型归一成 QTF(kNN 除外,反向强制 DFS,见第 7 节)。

4. Query 阶段 · 协调侧:发完即返回

SearchQueryThenFetchAsyncAction 的阶段名是 "query",它继承 AbstractSearchAsyncAction:构造时 outstandingShards = new AtomicInteger(iterators.size()),3 个 shard 就是 3。start() → run() → doRun:

// AbstractSearchAsyncAction.doRun(节选)
for (int i = 0; i < shardsIts.size(); i++) {
    final SearchShardIterator shardRoutings = shardsIts.get(i);
    final SearchShardTarget routing = shardRoutings.nextOrNull();
    if (routing == null) {
        failOnUnavailable(shardIndex, shardRoutings);
    } else {
        performPhaseOnShard(shardIndex, shardRoutings, routing);
    }
}

循环结束方法就返回——没有 Future.get(),没有 CountDownLatch.await()。这是第 8 课的同一条不变量:扇出本身不是阻塞点。某个副本不可用会 nextOrNull() 换下一个副本;同一 shard 组的副本全失败才算这个 shard 组失败。成功路径上每份应答都走 finishOneShard:

private void finishOneShard() {
    final int outstanding = outstandingShards.decrementAndGet();
    if (outstanding == 0) {
        onPhaseDone();   // → getNextPhase() → FetchSearchPhase
    }
}

3 个 shard 就倒数 3 次,任意一次回调都可能发生在任意一条刚处理完该响应的线程上——归并永远在最后一份回调的线程上发生。不要把生产路径想成 latch:await() 会把调用线程堵死,恰好违反第 8 课。真正占 search 线程池的是数据节点上的查询 CPU(handler 先挂 DIRECT,再 runAsync 进 Names.SEARCH)。

💡 9.x 的批量查询优化:searchService.batchQueryPhase() 让同一数据节点上的多个 shard 打成一条 [query][n] 批量帧,减少跨节点往返。它不改变「先 Query 再 Fetch、每 shard from+size 条候选」这条数据模型;本地 shard 仍然不批(没有网络延迟)。

失败路径一句话:allow_partial_search_results 默认 true——某个 shard 组彻底失败时,若允许部分结果,响应里 _shards.failed > 0,hits 仍可能返回;若不允许,onPhaseFailure("Partial shards failure") 并取消任务。

5. Query 阶段 · 数据侧:Lucene 只收 from + size 条

数据节点 SearchService.executeQueryPhase 创建 SearchContext(第 17 课细讲)、跑 QueryPhase;只要 numberOfShards() > 1,回给协调节点的就只有 QuerySearchResult,不含 _source。collector 收多少条,写在 QueryPhaseCollectorManager:

final int totalNumDocs = Math.max(1, reader.numDocs());
if (searchContext.scrollContext() == null) {
    int numDocs = Math.min(searchContext.from() + searchContext.size(), totalNumDocs);
    return new WithHits(..., numDocs, ...);   // → TopScoreDocCollector(numHits=numDocs)
}

协调侧同一个公式,给合并缓冲区用(QueryPhaseResultConsumer 构造时 topNSize = getTopDocsSize(request)):

// SearchPhaseController.getTopDocsSize(节选)
return (source.size() == -1 ? DEFAULT_SIZE : source.size())
     + (source.from() == -1 ? SearchService.DEFAULT_FROM : source.from());

DEFAULT_SIZE = 10、DEFAULT_FROM = 0。所以缺省搜索(from=0, size=10)每个 shard 回 10 条、3 个 shard 共 30 条候选——不是「每 shard 回 10/3」,也不是「只回最终那页」。网上走的 QuerySearchResult 是真的会序列化的一包字段:

字段为什么这一阶段就要带量级
topDocs(doc + score)给协调节点做全局排序每条很小;条数 = from + size
from / size合并时知道窗口两个 int
totalHits / maxScore响应里的 hits.total 与 max_score很小
aggregations桶必须在 Query 阶段算——Fetch 看不到没进 Top-N 的文档可能很大
suggest补全建议同样等不了 Fetch可能有
timedOut / profileShardResults部分超时仍可出结果;profile 调试段标志位 / 仅调试
⚠ doc 不是 _id:doc 是 shard 内 Lucene 段的文档号,不是 _id。不同 shard 的 doc=5 是两篇文档。协调节点排序用 (shardIndex, doc, score) 三元组;Fetch 时必须回到同一个 shard用同一个 doc 加载 _source——这就是下一节分组的意义。

shard 很多、又带聚合时,QueryPhaseResultConsumer 不会把所有结果堆到最后一刻再 reduce:batched_reduce_size(默认 512)满了就做一次 partial reduce,只保留仍可能进 Top-N 的候选与已合并的聚合树;聚合内存按 circuit breaker 记账,爆了抛 CircuitBreakingException(第 25 课)。对本课的 3 shard × size=10:30 条很小,一次最终 reduce 就够。另外 can-match 预过滤只对 QTF 开——能 rewrite 成 match_none 的查询可以少打一些 shard;DFS 必须打全部 shard 收词频,所以直接关掉这扇门。

6. Fetch 阶段:只搬全局 Top-N 的正文

倒数到 0 之后,FetchSearchPhase.innerRun 先 reduce() 拿到 ReducedQueryPhase(全局排好的 sortedTopDocs),然后:

final List<Integer>[] docIdsToLoad = SearchPhaseController.fillDocIdsToLoad(numShards, scoreDocs);
// 按 ScoreDoc.shardIndex 把全局 Top-10 的 doc 分到各 shard 的列表:
// 某个 shard 一条都没进 → 槽位是 null → 不发 Fetch,只释放它的 reader context

有列表的才 sendExecuteFetch,动作名 indices:data/read/search[phase/fetch/id],请求体是 docId 列表,不是「再搜一遍」。数据节点 executeFetchPhase 用这些 id 跑 Fetch 子阶段(_source、stored fields、highlight……),最后 SearchPhaseController.merge 按全局顺序组装 hits.hits,每条带 _index/_id/_score/_source。客户端看到的条数是 size(或不足一页时更少),不是 30。

💡 单 shard 的 query-and-fetch 优化:numberOfShards() == 1 时,数据节点在 Query 阶段直接 addFetchResult() 返回 QueryFetchSearchResult,协调端不再发第二次往返——Fetch 的 id 用 shortcutDocIdsToLoad:按 from 跳过、只取 size 条,因为没有别的 shard 来竞争名次。这是 SearchService 里的优化路径,SearchType.QUERY_AND_FETCH 这个枚举本身已经删掉,别再去 search_type 里找它。

7. from + size:深分页贵在哪,DFS 何时开

每个 shard 在 Query 阶段必须返回的条数:topDocsSize = (size ?? 10) + (from ?? 0)。用数字走一遍:

请求每 shard 回几条 (docId,score)3 shard 候选总数Fetch _source
from=0, size=10(默认)103010
from=10, size=10(第二页)206010
from=10000, size=101001030030本该 10,但通常到不了 Fetch

第三行是深分页的代价:跳过前面 10000 条,每个 shard 也得先拿出自己的前 10010 名,否则协调节点无法知道「全局第 10001 名」在哪——网络与协调内存随 from 涨,不随「这一页只要 10 条」恒定。还有一道闸:

深翻页的正解不是调大 index.max_result_window(默认 10000,Dynamic,IndexScope),而是换翻页方式:

方式每 shard Query 回多少服务端上下文何时用
from/sizefrom + size无浅页(前几页)
search_after约 size(from 保持 0,带上一页末条的 sort values)无深翻页、导出
scroll批量 size有,占用 reader旧路径;新代码优先 PIT
PIT + search_after约 sizePIT 是可释放快照要稳定快照的深翻页

两段附注。其一,CCS(跨集群搜索)里 createSearchResponseMerger 会把发往各远程集群的 source 改成 from(0); size(from+size)——每个远程集群回一个 from+size 窗口、发起方二次截取,和「每 shard 回 from+size」是同一思想的另一层,不是本地路径的主公式。其二,DFS:默认 QTF 里每个 shard 用本地词频算 IDF,数据极少且严重倾斜时评分会不可比;search_type=dfs_query_then_fetch 在 Query 之前多一次 [phase/dfs] 扇出收集全局词频。代价是多一轮网络,数据量大、词频趋于一致时几乎白付——kNN 搜索会被 adjustSearchType 强制改成 DFS(向量检索需要全局信息),关键词搜索不要为了「更准」默认打开。

清理

思考题

1. 仍是 3 个 shard,请求 from=100&size=10(未超 max_result_window):每 shard 的 Query 阶段回几条?Fetch 几篇?客户端最多几条?

每 shard 回 100+10=110 条,3 shard 最多 330 条候选;协调节点取全局第 101–110 名,Fetch 10 篇;客户端 hits.hits 最多 10 条(总命中不足 110 时更少)。from 加大只膨胀 Query 窗口,不膨胀最终 hits。

2. 为什么每个 shard 必须回 from+size 条,不能只回 size 条让协调节点「自己翻页」?破了哪条不变量?

不变量是:全局第 from+size 名,一定出现在某 shard 的本地前 from+size 名里。反例:shard-0 包办全局前 20,shard-1 的本地 Top-10 全是全局 21 名开外——若每 shard 只回 10 条,第二页(from=10)会把 shard-1 的第 1–10 名误当候选,而真正的全局 11–20 还留在 shard-0 没送上来。

3. query_then_fetch 与 dfs_query_then_fetch 各在付什么、换什么?kNN 为什么不让你选?

QTF 付「各 shard 用本地 IDF,评分可能略不可比」,换「少一轮往返」。DFS 付多一次 phase/dfs 扇出,换全局词频后再打分。小索引、shard 间词频极不均时 DFS 有意义;文档量和词频都大时本地 IDF 已接近全局,多一轮几乎白付。kNN 需要跨 shard 的邻居信息,adjustSearchType 直接改成 DFS,不是用户偏好。别把 DFS 当「更正确所以永远打开」——默认 QTF 是为在线延迟选的。

陷阱

🕳 SEARCH 0 hits ≠ 写丢了:未 refresh 的文档在 buffer 里,GET(Realtime)读得到、SEARCH(EXTERNAL 快照)看不到。先 _refresh 或写入带 refresh=true/wait_for 再下结论——顺序反了会冤枉自己的写入。
🕳 把 hits 当成「shard 数 × size」:每 shard 回的 from+size 条只是候选,全局窗口截完才是 hits。反过来,单 shard 索引「一次往返就出正文」是 SearchService 的优化,不是一种 SearchType——QUERY_AND_FETCH 枚举已经删了。
🕳 深分页去调大 max_result_window:闸门拦的是 from+size,贵的是每 shard 的 Query 窗口与协调内存——调大闸门只是把代价放进来。深翻页换 search_after / PIT,别把 from 加到五位数。
