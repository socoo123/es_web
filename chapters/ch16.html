搜索流程总览

一次搜索为什么先返回候选名次，再取命中文档？因为协调节点必须先决定全局页，才能知道哪些分片上的哪些文档值得加载。Query 扩大的窗口与 Fetch 返回的一页，是两笔不同的工作。

16.1 先问：搜哪些分片，读哪个视图？

普通 GET /{index}/_doc/{id} 根据 _id 或显式 routing 定位一个逻辑分片；默认 realtime 可读尚未 external refresh 的写入。普通 _search 不带 routing 时选择目标索引的分片组，每组选择一份可用拷贝参与；副本存在并不表示主副本全部查询。routing、索引选择和 can-match 预过滤可缩小实际范围，因此“每次搜索必打所有分片”需要条件。

搜索使用已打开的 EXTERNAL 读者，只能看到该视图包含的写入。各分片读者分别打开，普通跨分片搜索不构成整个索引在同一瞬间的事务快照。PIT 能跨后续请求保留选定的读者视图，也不应称为全局事务时刻。第 10 课的 GET 可见性与本课 C 组从两条读取路径观察同一次写入。

一台节点可以承载三个分片，同时承担协调侧和数据侧角色。本课单节点实验验证分片处理结果，不能据此计算“网上走了多少包”。下面箭头表示处理和数据交接；发生远程传输时才涉及节点间网络。

16.2 为什么把 Query 与 Fetch 分开？

假设三个分片各有足量匹配，请求 from=0,size=10。各片先返回至多 10 条候选，协调节点从至多 30 条中选全局前 10。没有入选的候选无需加载完整正文。这个例子解释职责划分；正文大小随文档和返回字段变化，不能用固定字节数承诺节省比例。

RestSearchAction.prepareRequest 解析 body 和 URL 参数，构造 SearchRequest 后委托搜索动作。默认类型是 QUERY_THEN_FETCH。协调侧的 AbstractSearchAsyncAction.doRun 遍历分片迭代器，受每节点并发限制时可排队；失败可换同组其他拷贝。代码不等待全部响应，但异步接口可能同步回调，发送和处理本身也消耗 CPU，不能由 listener 推断“立即释放线程”。

分片执行 Query 后，results.consumeResult(result,next) 先消费结果，完成后才递减 outstandingShards。归零触发阶段推进；FetchSearchPhase.run 又通过 context.execute 调度 innerRun 中的 reduce，所以归并不固定在最后一份网络回调的线程。较多结果可增量 reduce，不必全部堆到最后；具体线程与批量行为要跟执行器和条件分支。

普通 Query 结果中的 doc 是当前分片读者空间的 Lucene 文档号，可跨该读者的多个 segment，不能称作单 segment 内编号，更不是 REST _id。跨片的相同 doc 数字可以指向不同文档。按分数排名携带 score；按字段排序还携带 sort values；聚合、suggest、统计与 profile 也可能出现在 Query 结果中。因此“Query 只是一对 doc/score”只是教学缩写。

协调端全局归并后，fillDocIdsToLoad 按 shardIndex 分组最终窗口。普通无 suggest 的本页至多 size 条；空组不发 Fetch，本例临时 reader 可释放。Fetch 请求携带上下文与文档号，回到选定读者加载 _id、默认 _source 和所需字段，再按全局顺序组装响应。这不是再次查询，也不是对每条结果发 REST GET；PIT / scroll 的 reader 保留规则另论。

16.4 from 扩大的是候选窗口

限定 size>0，普通非 scroll、无 rescore / rank / collapse / suggest，普通协调窗口为 k=from+size，缺省 from=0、size=10。本地 collector 容量先受 reader.numDocs() 限制，实际候选还受匹配数限制。它维护有限的 Top-k，但为找出 Top-k 仍可能处理很多匹配；“只收 k 条”不等于“只扫描 k 篇”。字段排序、过滤与提前终止也会影响工作量。

为什么每片不能仅给 size 条？全局前 from+size 的文档，一定在它所属分片的本地前 from+size 中。某片可能包办全局前 20；若第二页只让它返回本地前 10，全局第 11–20 名就丢了。这个推理建立在相同排序关系和普通分页上。

DefaultSearchContext.preProcess 检查索引级 index.max_result_window，默认 10000，本课显式设为同值。10010>10000 被拒；数据只有 30 篇也不能跳过参数检查。HTTP 400 的顶层是 search_phase_execution_exception，root cause 才是 illegal_argument_exception；相同原因可能分组显示，不能把 failed_shards 数组长度当失败片数。

深翻页可使用 search_after：保持 from=0，传入上一页末项的完整 sort 数组，从那个位置继续收集 size 条候选；这不保证查询处理成本固定。必须有稳定排序和唯一的最终区分项。本课 n 唯一且数据冻结，所以连续两批可直接对照；实际有并发更新时用 PIT 保留视图，并及时关闭（官方分页说明）。from/size 和无 PIT 的 search_after 也会创建临时上下文，只是不像 PIT / scroll 那样为后续请求保留读者。调大窗口会允许更大的候选工作量，是否合适要看负载，而不是把小 size 当保护。

16.5 profile 能证明哪些事情？

B 组保留 profile.shards.searches 和完整 fetch。三个分片的 searches 展示 Lucene query / collector 树；只有真正执行 Fetch 的分片带 fetch。普通 size=1 有唯一全局命中，本例三份 searches、仅一份 fetch。time_in_nanos 是时间；应结合 breakdown 的调用计数解读，不能当作文档数。

_source:false 是本次请求的返回选项，不修改 mapping 的 _source.enabled；B4 仍有 Fetch，因为命中元数据及其他字段工作也属于这一阶段。普通 size=0 且无 suggest 时不收普通 hits，B5 的聚合仍处理 30 篇文档，n 的 sum=465。本例各片 load_stored_fields_count 合计为 10；next_reader_count 是切换段读者次数，不应混加。profile 有额外开销，不包含完整网络传输或协调节点归并时间；它不能证明两次网络往返、精确候选字节数，或哪个实现更快（官方 profile 观测范围）。

16.6 两阶段有哪些例外？

普通搜索只参与一个分片组，且无 rank / kNN 时，可在数据侧执行 Query 后直接 Fetch，再返回 QueryFetchSearchResult，协调端无需单独再发 Fetch。这里“单分片”不同于“单节点”：A 组一台节点的三分片查询仍要全局选页，D 组才验证一个分片的对照。profile 中仍同时存在 query 与 fetch，不表示一定有第二个传输请求。已删除的 QUERY_AND_FETCH SearchType 不能作为参数使用。

dfs_query_then_fetch 在 Query 前收集分布式词项 / 集合统计，使词项评分采用跨片统计；默认 QTF 使用本地统计，词频分布差异会影响分数。DFS 增加阶段和通信工作，收益取决于数据、查询和部署，不能断言大数据集“几乎白付”。本版本 hasKnnSearch() 分支强制 DFS；这是该搜索请求路径的处理，不能推广为所有向量查询都走同一分支。

can-match 预过滤需满足 QTF、分片数量阈值及可 rewrite 等条件，DFS 路径不使用这道预过滤。按节点批量 Query 则受 feature flag / setting、远端连接等条件控制，不能写成所有 9.x 的默认行为。本课只观察普通单节点结果，其他分支按固定源码校对。

部分成功也要读分片统计允许部分搜索结果的代码默认值为 true，可由集群设置或请求覆盖。部分分片组全失败时可能仍返回成功片的 hits；所有片都失败则报错。读 _shards.failed 与失败原因，再判断结果是否完整。本轮未制造部分失败或多节点副本切换。

七步机制：跟着最终页走

下面使用虚构分数和文档号，假设三片均足量，演示从至多 30 条候选中取 10 条；3/5/2 是示意归属。它与本课 12/9/9 的真实数据分开。可逐步前后切换，系统减少动态效果时手动步进仍可用。

实验：四组按顺序运行

环境锚定 ES 9.4.0 / Lucene 10.4.0，单节点、http://localhost:9200、匿名认证；页面连接栏可调整端点。本课只修改 tut-l16-qtf 和 tut-l16-single。主索引显式三主片零副本、standard、strict mapping、stored _source、standard title、整数 n，无默认/最终管道，周期 refresh=-1、窗口 10000。

完整顺序与重做先执行末尾两张 DELETE 清理，再从 A → B → C → D → 清理运行。首次创建成功，重复创建报资源已存在；同次重写固定 ID 是 updated，不是新增。只重做 C 组须从 C1 删除旧 nrt 并刷新开始。不要在 C3 写入与 C6 计数之间运行 refresh / bulk；本例要求无并发写入、刷新、恢复等改变外部视图的操作。-1 只关闭周期刷新，不能阻止所有刷新。主索引重建后健康超时先处理，不继续实验。

A · 准备并观察三分片（6 卡）

版本 → 建索引 → 本索引健康等待 → 设置读回 → 固定 30 篇 bulk 且 refresh=true → 分布。本次实测 12/9/9，分片号为 0/1/2；不把分布当均匀保证。

B · 排名、Fetch 与翻页（10 卡）

普通搜索 → profile → size=1 → 关闭正文 → size=0 聚合 → 超窗错误 → 恰好过闸 → 最后一页 → search_after 前批 / 后批。此组使用还未写 nrt 的固定 30 篇；n 唯一，无 PIT 的对照只用于这个冻结数据集。

C · 同一次写入的两种可见性（7 卡）

删除旧 nrt 并刷新 → 0 基线 → 未刷新写入 → realtime GET → 搜索 count=0 → 显式 refresh → count=1。删除不存在文档的 404 是预期；它不表示索引不存在。

D · 一个分片组的优化（3 卡）

创建独立单分片索引 → 写两篇并刷新 → from=1,size=1 的 profile。返回第二篇，同时能看见 query / fetch；合并阶段的调用关系由源码证明。

点名清理与重做（3 卡）

仅删除两个本课索引及其设置，不使用通配符。ignore_unavailable 允许重复清理；最后 HEAD 主索引预期 404、无正文。需要再次实验时从 A1 开始。

思考题

1. 三片只有 12/9/9 个匹配，size=10 能得到 30 个候选吗？

不能。普通每片上限分别为 min(10,12)、min(10,9)、min(10,9)，合计至多 28；协调端从中取全局 10 条。若有超时、过滤或提前终止，实际还可更少。

2. 足量匹配时 from=100,size=10，每片与最终页分别要多少？

普通每片候选上限 110，三片总上限 330；最终页至多 10。若全局不足 101 条，则是空页。窗口条件检查与实际有几篇匹配是两件事。

3. _source:false 与 size=0 都没有正文，有什么差别？

前者保留命中，Fetch 可继续处理元数据和字段；只是本次不返回正文。后者在本例无 suggest 时没有普通命中待取，聚合仍可执行。它们均不修改 mapping 的 source 设置。

4. 一个节点的 profile 同时出现 query 与 fetch，证明了两次网络往返吗？

没有。多个分片可位于同一节点，单分片普通 QTF 又可合并 Query / Fetch。profile 记录分片执行工作，不记录完整网络和协调时序；需要结合固定源码条件与部署判断。

5. 刷新后再做 C 组为什么仍搜得到 nrt？

旧版本已进入外部读者，重复写不会让旧的可搜版本凭空消失。先 C1 删除并 refresh，C2 确认 count=0，再写入未刷新版本。关闭周期刷新只是前提之一，仍需避免其他刷新操作。

陷阱

把候选上限当固定条数from+size 是本课普通路径的窗口，实际匹配可不足；rescore、rank、collapse、suggest、scroll 等还有其他条件。三片乘以 size 得到上限示例，不是响应里必须出现的候选数。
把回调当固定线程先消费再倒数，归并还会经执行器调度；没有 await 全部响应不代表零 CPU 或立即释放线程。异步 API 也可同步回调。
把正文、Fetch 和 profile 混为一谈没有 _source 不等于没有 Fetch；fetch 时间不是文档数；profile 不证明网络往返。filter_path 必须保留真正要观察的字段。
把 refresh=-1 当永远不刷新它只关闭周期刷新。手动 refresh、其他写入带 refresh=true 或恢复等可改变视图。按 C 组删除刷新建立新基线；在 -1 下也不要使用依赖未来刷新的 wait_for 等待流程。
