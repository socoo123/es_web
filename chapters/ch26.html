26.1 编译复用、执行数据与查询入口

把一条脚本请求拆成三个问题。第一，这个 context 能使用哪些类型、成员和变量？score 提供评分接口，field 计算返回字段，update 操作文档源，ingest 操作摄取文档。第二，当前节点有没有这个编译键的 factory？命中时复用产物，未命中才进入 Painless 编译器。第三，本次执行要读哪篇文档、使用哪些 params？这些运行数据不等同于编译源码，也不会被 factory 缓存变成搜索结果缓存。

还有一层入口条件：script_score 的 doToQuery 会先检查 search.allow_expensive_queries。关闭时，无害的 return 1.0 也会被拒；这既不是允许列表失败，也不是编译次数超限。实验先保留完整错误链，再根据拒绝位置解释，不用一条最外层 reason 概括所有失败。

26.2 缓存未命中后，源码怎样成为 factory

PainlessScriptEngine 的构造与入口 为每个 ScriptContext 建 Lookup 与 Compiler。Compiler 先经 Walker / ANTLR 得到用户树，再做语义头部及表达式分析，随后转成 IR ClassNode，运行若干优化 pass，最后用 ASM 生成 JVM byte[]。图中归并了优化与 factory 细节，没有把每个 pass 都画成必读节点。

正常产物是生成类及相应 factory，调用方据此创建脚本实例。9.4.0 的 Loader 明确继承 ClassLoader，使用普通 defineClass；旧网页的 SecureClassLoader / UNTRUSTED_CODEBASE 说法与此版本不符。findClass 会考虑 additionalClasses 与 Lookup，父加载器委派也仍存在，所以不能将它讲成「JVM 无法加载任何允许列表外类型」的第二道绝对保证。

Painless 可以在运行时接收源码并编译，但它的正常执行链不是每篇文档都重新解释字符串。无需用所有 eval 实现作比较，也不能断言生成字节码常量池只含 txt 中的类型：factory、运行支持类与动态调用基础设施也参与生成。

26.3 允许列表：静态类型检查与 def 动态分发

PainlessPlugin 的列表装载与合并 提供基础资源，再叠加 context 资源与 PainlessExtension。默认列表包括常用数学、字符串、集合、时间与 NIO Buffer 等 API；它没有开放 java.io.File、java.lang.Runtime 或 java.lang.Class，Object 也没有 getClass 方法。类名是否出现与某个成员是否允许是两项检查，不能看到一个类就推断它的所有 Java 方法可用。

对 new java.io.File("/tmp/x")，visitNewObj 先查类型。默认 Lookup 查不到，抛出 Not a type [java.io.File].，引擎将原因与位置包装为 compile error；这次编译没有继续进入 IR / ASM。声明 java.io.File f = null 走 visitDeclaration，原因改为 cannot resolve type。普通未知类型没有任意类名加载兜底；数组分支会在元素类型已被识别后用 Class.forName 构造数组类，不能笼统说 Lookup 实现中完全没有 Class.forName。这里证明的是拒绝位置，本轮没有磁盘实测；Java 的 File 构造本身也不等于创建文件。

方法对照更能说明执行边界。String s="x"; s.getClass() 用静态 String 类型，在语义分析阶段查成员后失败；def x=1; x.getClass() 可以先生成动态调用，实际接收者是 Integer 时，执行期再查 runtime Lookup，缺失就报告 dynamic method not found。def 推迟了成员解析，没有绕过允许列表。因此「执行期只有方法调用、没有任何查表」也需要修正。

观察当前环境：/_scripts/painless/_context?context=score 是源码标为 internal 的调试 API，可查看当前允许项。不要承诺固定 404 个类或把它当永久稳定契约。图与错误预期限定默认 9.4.0 发行版；插件扩展、script.allowed_types / allowed_contexts 都可能改变前提。

script_score 的脚本返回评分，在本课默认 boost=1 时得到表中的数值；若脚本读取 _score，就由脚本明确组合内层分数。实现还会应用外层 boost，不能声称所有配置下都「完全替换后再无变化」。function_score 的组合由 boost_mode、score_mode 等控制，也不总是「原分数乘一层」。评分结果必须满足实现的非负与非 NaN 检查，最终以 float 参与搜索。

数值字段通常通过 doc values 读取；text 默认没有 doc values、fielddata 也禁用，不能直接假设 .value 取到文本或数值。实验显式把 popularity / views 映射为 long、price 为 double、title 为 keyword，并声明 strict mapping；update 的 views 因而也先有字段定义。

ScriptProcessor 的创建与执行 配合其 Factory.create 在建 processor 时调用 compile。因此坏 inline 脚本在 PUT pipeline 验证阶段已失败；正常 inline processor 持有预编译 factory。stored 脚本的 processor 不长期保存这个 factory，执行时再通过 ScriptService 解析当前 stored 源码，仍可以命中 ScriptCache。不能把「不持有 processor 的 factory」扩大成「stored 完全没有编译缓存」。

默认 /_scripts/painless/_execute 使用 painless_test context，不需要索引。本版本把其执行返回值转换为字符串，所以 D 组结果是 "52" 与 "78"。换成 score 等 document context 需要相应 context_setup；默认 test 环境成功不自动证明 score、update 或 ingest 也可用。

26.5 缓存键包含什么，params 为什么在外面

ScriptCache 的编译键与 computeIfAbsent 包含 projectId、lang、idOrCode、context.name 和编译 options。stored 类型在进入这里之前把 ID 解析为当前 source；执行 params 没有进入缓存键。固定 doc['price'].value * params.discount，只把 discount 从 0.8 改为 0.9，可以在同节点缓存保留时复用编译产物；把数值拼进 source 会形成另一把键。

缓存归当前节点的 ScriptService 管理，配置可选择 general cache 或 context cache。容量淘汰、访问过期、进程重启、相关配置替换都会影响复用；源码、context、语言或 options 改变也影响键。「通常整集群一生只编一次」不成立。同一键在缓存中的并发 computeIfAbsent 用于避免重复编译，但不能替代这些生命周期条件。

D 组用同一 painless_test 源码换 multiplier，对比相邻节点统计。第一次可能已命中历史缓存，第二次也只有在无并发、无淘汰/过期/配置切换的条件下才应不新增编译。compilations、cache_evictions、compilation_limit_triggered 都是累计观测，不是某一请求独占的计数；删索引不能把它们清零。查询卡显式 request_cache=false 只控制该请求的搜索结果缓存，不更改索引配置，也不关闭编译缓存。

26.6 允许列表、编译速率与 expensive 是三个条件

允许列表约束可用 API；编译速率限制在适用 context 的缓存未命中路径执行；search.allow_expensive_queries 控制 script_score 查询入口。缓存命中节省编译，不会消除脚本计算、doc values 读取或 def 动态分发成本。也不要把执行次数硬写成总命中数：ScriptScoreQuery.createWeight 有不需分数且无 minScore 时委托内层查询的分支，评分与收集条件仍会影响实际执行。

E 组只适用于隔离学习节点：前置确认 transient / persistent 都没有本键，节点有效基线 true。设置 false、读取确认、运行同一无害脚本后，立即把本次 transient 键设 null，再检查来源并重跑查询。null 的动作是删除指定层覆盖，不是强制恢复 true；如果起步有原覆盖，整组及对应设置清理都应跳过。本课不让读者先丢失旧值，再凭 defaults 字段猜测恢复。

思考题

1. 同一 source 只换 params，为什么结果不同而编译键相同？

缓存的是 factory，params 是调用方创建执行实例时传入的数据。同节点、同 project/lang/context/options 且缓存保留时可复用；这不等于缓存每篇文档的结果。

2. def.getClass 为什么能编译，却仍会失败？

静态成员解析被推迟到执行期；Def.lookupMethod 按接收者类型查 runtime 允许列表。默认 Integer.getClass 不在表中，所以 dynamic method not found。执行阶段仍可能查表。

3. 缓存已命中，expensive=false 能否阻止 script_score？

能。doToQuery 的设置检查在 compile 前；编译缓存节省的是编译成本，不取消查询入口条件，也不取消执行计算。

4. stored ingest 不保存 processor 的 factory，是不是每篇都重新编译？

它需要通过 ScriptService 重新读取最新 stored source，避免长期引用旧产物；当前 source 对应的 ScriptCache factory 仍可命中。解析更新与是否重编译是两件事。

5. null 一定恢复 true 吗？为什么本课限制 E 组的前置条件？

null 仅移除指定 transient 键；会落到 persistent、节点配置或默认值。本课起步要求两层无覆盖、节点有效基线 true，才可以用删除本次覆盖恢复 true。有原值则跳过，不丢失未知配置。

陷阱

把旧 Loader 描述带到 9.4.0：本版本继承 ClassLoader；File 拒绝的直接证据是允许列表语义检查，不把类加载器委派描述成封闭类型宇宙。
把 params 写进编译键：执行 params 不在键中；编译 options 在键中。引擎方法中同名 params 形参可能指编译参数，不能与 JSON script.params 混同。
认为缓存保证永久只编一次：各节点缓存及淘汰、过期、重启、设置替换都能改变复用；统计必须比较同节点增量。
宣称执行期再无查表：def 动态方法仍在执行期查允许项；script_score 也存在无需评分时的跳过分支。
把响应字段当文档修改：field 返回 fields，update 改 ctx._source，ingest 改 ctx；simulate 结果不等于索引写入。
只看默认 true 就清理：必须保留原设置来源，并只移除自己添加的 transient 覆盖；有旧配置的环境跳过 E 组。
