LESSON 26 · 第六篇 · 高级专题

脚本引擎

先过白名单再变字节码——不是 eval 一段字符串 · 约 15 分钟 · 前置:第 12、20 课 · 20 个实验 + 编译旅程动画

学习目标

  • 对两篇带 popularity 的文档发一条最小 script_score,先预测 _score 再对照:内层 match_all 是 1.0,popular 应得 1.0、cheap 应得 0.1;换成 price * 0.9 后分数是 90/72——完全替换内层分数,不是第 20 课 function_score 那种乘一层。
  • 预测 new java.io.File(...) 会不会落盘、HTTP 400 还是 500;用 POST /_scripts/painless/_execute 对照 compile error + caused_by: Not a type [java.io.File].;再把同一句写进 PUT _ingest/pipeline,验证它在第一条文档到来之前就被拒。
  • 打开 PainlessPlugin.baseWhiteList 与 DefaultSemanticAnalysisPhase.visitNewObj:说出白名单 txt 清单里没有 java.io、Lookup 返回 null 时为何走不到 ASM;并用 def 与静态类型的 getClass() 对照「运行期/编译期」两条拒绝路径。

1. 心智模型:一段脚本先过一张表,再变 class

Painless 的输入是一段源码字符串,产物是一个 JVM class。中间必须经过一张预先建好的表——哪些 Java 类、构造器、方法、字段允许出现。表里没有的名字,在语义分析阶段就失败,字节码生成器根本看不到它。拿旧课那句 doc['price'].value * 0.9 走一遍:编译器要确认 doc[...] 取值、value、乘法,都在当前 ScriptContext 的 PainlessLookup 里;全部在表,才有 byte[],最后 defineClass。

这张图证明一件事:Painless 不是 eval。eval 是运行时拿着源码字符串去找 java.io.File;这里源码先变成 AST、再对照 Lookup,通过之后才有字节码——类型名在表里不存在,编译在写出字节码之前就停了,磁盘 I/O 没有机会发生。默认语言就是 Painless(Script.DEFAULT_SCRIPT_LANG = "painless"),JSON 里可以省略 "lang"。同一段源码也不在所有地方通用:script_score 编进 ScoreScript.CONTEXT(名字 "score"),ingest 的 script processor 编进 IngestScript.CONTEXT("ingest")——上下文不同,Lookup 上多出来的绑定不同;基础白名单是共享的,java.io.File 在哪一张表里都没有。

3. 一段源码怎样变成 byte[]

入口在 PainlessScriptEngine.compile:先按 ScriptContext 取出这份上下文专用的 Compiler——构造引擎时已经用该 context 的 whitelist 建好 Lookup,之后再冻住:

// modules/lang-painless/src/main/java/org/elasticsearch/painless/PainlessScriptEngine.java(节选)
for (Map.Entry<ScriptContext<?>, List<Whitelist>> entry : contexts.entrySet()) {
    PainlessLookup lookup = PainlessLookupBuilder.buildFromWhitelists(entry.getValue(), dedup, filteredMethodCache);
    mutableContextsToCompilers.put(context, new Compiler(context.instanceClazz, ..., lookup));
    mutableContextsToLookups.put(context, lookup);
}

buildFromWhitelists 把每份 Whitelist 里的类/构造器/方法/字段填进几张 Map。之后脚本里出现的每个类型名都只问 PainlessLookup.canonicalTypeNameToType——表里没有就返回 null。然后是主路径的四步:

// modules/lang-painless/src/main/java/org/elasticsearch/painless/Compiler.java(节选)
SClass root = Walker.buildPainlessTree(scriptName, source, settings);          // ① 解析
new PainlessSemanticAnalysisPhase().visitClass(root, scriptScope);             // ② 对照 Lookup
new PainlessUserTreeToIRTreePhase().visitClass(root, scriptScope);            // ③ 降 IR
new DefaultConstantFoldingOptimizationPhase().visitClass(classNode, null);
new DefaultIRTreeToASMBytesPhase().visitScript(classNode);                    // ④ ASM 写字节码
byte[] bytes = classNode.getBytes();
Class<? extends PainlessScript> clazz = loader.defineScript(CLASS_NAME, bytes);
步骤谁做数据变成什么
① 解析Walker.buildPainlessTree → ANTLR PainlessParser源码字符串 → 用户树 SClass(节点带 Location,供报错画 ^---- HERE)
② 白名单检查PainlessSemanticAnalysisPhase(继承 DefaultSemanticAnalysisPhase)每个类型名/方法/new 对照 Lookup;失败抛 IllegalArgumentException,到不了 ③
③ 降 IR + 优化PainlessUserTreeToIRTreePhase、常量折叠、字符串拼接优化用户树 → IR ClassNode
④ 写字节码DefaultIRTreeToASMBytesPhaseIR → byte[];类名 PainlessScript$Script

Loader 继承 SecureClassLoader:defineScript 用一份指向 BootstrapInfo.UNTRUSTED_CODEBASE 的 CodeSource 做 defineClass,findClass 只从 Lookup 和 factory 需要的那几个类里找——即便有人设法在字节码里引用 java.io.File,这个 loader 也解析不到。编译失败不会漏成含糊的 500:PainlessScriptEngine 把异常收成 ScriptException("compile error"),具体原因在 caused_by.reason。编译结果按 context + 源码缓存在 ScriptCache(computeIfAbsent)——同一段 script_score 打 1000 篇文档只编一次,之后是调用生成类的 execute。这是「不是逐文档 eval」的第二条证据。

4. 白名单:txt 装表,File 在编译期被挡

白名单不是运行时拦一句 SecurityManager.checkRead。它是编译器用的类型宇宙:脚本能叫出名字的类,必须先写在资源文件里。PainlessPlugin.baseWhiteList() 装入这些 txt(都在 modules/lang-painless/src/main/resources/org/elasticsearch/painless/):

// modules/lang-painless/.../PainlessPlugin.java(节选,清单逐项核对过)
"org.elasticsearch.txt", "org.elasticsearch.net.txt", "org.elasticsearch.script.fields.txt",
"java.lang.txt", "java.math.txt", "java.text.txt",
"java.time.txt", "java.time.chrono.txt", "java.time.format.txt", "java.time.temporal.txt", "java.time.zone.txt",
"java.util.txt", "java.util.function.txt", "java.util.regex.txt", "java.util.stream.txt",
"java.nio.txt"

对着清单能直接核对四件事:有 java.lang.txt、java.util.txt、java.time*.txt、java.nio.txt(里面是 Buffer 家族,没有 java.nio.file.Path);没有 java.io.txt;java.lang.txt 有 RuntimeException、没有 java.lang.Runtime——旧课的 Runtime.exec 和 File 是同一类拒绝;也没有 java.lang.Class。最后这条有个精确的实测对照(实验 14):String s = "x"; s.getClass() 是编译期的 member method [java.lang.String, getClass/0] not found(静态类型当场查表);换成 def x = 1; x.getClass() 则是运行期的 dynamic method [java.lang.Integer, getClass/0] not found(def 把解析推迟到动态分发)——两条路都在同一张表上死,反射入口不存在。

每个 ScriptContext 还会叠加一份 org.elasticsearch.script.<context>.txt(文件名把 context 名里的 - 换成 _):score 给 ScoreScript 加 saturation / decayGeoGauss 绑定,ingest 给 ctx 一侧加 sha256()、Metadata.setRouting 等。这些是加法,不会把 File 加回来。new java.io.File("/tmp") 走进 visitNewObj:

// modules/lang-painless/.../phase/DefaultSemanticAnalysisPhase.java(节选)
Class<?> valueType = scriptScope.getPainlessLookup().canonicalTypeNameToType(canonicalTypeName);
if (valueType == null) {
    throw userNewObjNode.createError(new IllegalArgumentException("Not a type [" + canonicalTypeName + "]."));
}

REST 上一层是 reason: "compile error",caused_by.reason 才是那句原文;放进 script_score 会被包成 search_phase_execution_exception,往 root_cause 里挖还是同一句(实验 11)。ingest 更早一步:ScriptProcessor 在 PUT pipeline 时就 compile,所以坏脚本在第一条文档到来之前就 400(实验 12);stored 脚本故意不缓存 factory,以免集群里改了 stored 源码而 processor 还拿着旧 class。白名单允许的,是数学与字符串、集合、doc['field'].value、params、ingest/update 里的 ctx._source;不允许的是文件 I/O、网络套接字、反射、进程执行——不是靠运行时拦一句 exec,是这些类型从未进入 Lookup。

5. 同一套编译器,接到三个 ScriptContext

编译器只有一套,变化的是 context:接口不同(返回 double 还是改 ctx),Lookup 上多出来的绑定不同。9.4.0 这三处 API 名字都没换:

场景REST / DSLcontext脚本里能摸到什么 · 编译时机

script_fields 是第四个 context("field",FieldScript.CONTEXT):算返回给命中的额外字段,不改 _score 也不改磁盘上的 _source(实验 5 一组对照)。script_score 的 JSON 形状由 ScriptScoreQueryBuilder 钉死:query 与 script 都必填——REST 缺 query 实测 400 Required [query],Java 构造器传 null 则是 script_score: query must not be null;doToQuery 里第一件事查 expensive,然后才 compile:

// server/src/main/java/org/elasticsearch/index/query/functionscore/ScriptScoreQueryBuilder.java(节选)
protected Query doToQuery(SearchExecutionContext context) throws IOException {
    if (context.allowExpensiveQueries() == false) {
        throw new ElasticsearchException("[script score] queries cannot be executed when '"
            + ALLOW_EXPENSIVE_QUERIES.getKey() + "' is set to false.");
    }
    ScoreScript.Factory factory = context.compile(script, ScoreScript.CONTEXT);
    ScoreScript.LeafFactory scoreScriptFactory = factory.newFactory(script.getParams(), context.lookup());
    Query query = this.query.toQuery(context);
    return new ScriptScoreQuery(query, script, scoreScriptFactory, context.lookup(), minScore, ...);
}

设置键 search.allow_expensive_queries(默认 true)。关掉之后,白名单再干净、脚本再简单(return 1.0;),这条查询也不会跑(实验 16-17,实测包成 query_shard_exception)。这和「编译期挡 File」是两层:一层是安全宇宙,一层是集群愿不愿意付按文档执行脚本的代价。整条主路径走一遍:

思考题

1. 把实验 10 的源码改成 java.io.File f = null; return 1; 发给 _execute。caused_by.reason 还是 Not a type 吗?节点会因此加载 java.io.File 这个 JVM 类吗?

文案换成 invalid declaration: cannot resolve type [java.io.File](visitDeclaration,Lookup 同样返回 null)。不会加载:canonicalTypeNameToType 只查 txt 填出来的 Map,不会 Class.forName;Loader.findClass 也只认 Lookup 里的类。visitNewObj 与 visitDeclaration 是同一张表的两个入口——文件里 grep "Not a type" 还会命中 visitNewArray / visitInstanceof,死法一致。

2. 为什么必须在编译期用 Lookup 拒绝 File,而不是生成字节码之后靠运行时拦截 new File?改成运行时拦,哪条不变量破了?

编译期拒绝保证:不存在一份引用了 File 的 byte[]。运行时拦截是第二道墙,前提是 class 已经 define、指令已经在执行,那时 "/tmp/x" 可能已经进了构造器参数。白名单的不变量是「生成类的常量池里根本没有这个类型」;再往下一层,Loader 对非白名单类名抛 ClassNotFoundException,是定义期的第二道。两层都在产物诞生前后把关,而不是等它跑起来——这正是「不是 eval」的安全含义。

3. allow_expensive_queries=false 时 script_score 直接拒绝,哪怕脚本只是 return 1.0。为什么「已经白名单化的安全脚本」还要标成 expensive?这和 ScriptCache 解决的编译成本是同一笔账吗?

不是同一笔账。ScriptCache 摊的是编译一次的 CPU;script_score 的 execute 仍按命中文档逐篇调用,热路径上的算术与 doc values 读取没法靠缓存消掉——大索引上一个 O(命中数) 的脚本可以把搜索线程吃满(第 8 课的 search 池)。expensive 开关管的就是这笔执行账;白名单解决安全宇宙,expensive 解决容量意愿,互不代替。doToQuery 里先查 expensive 再 compile,顺序也说明它是入口闸,不是对某段具体源码的判决。

陷阱

🕳 把 Painless 当 eval:担心「运行时拿着字符串执行任意代码」。类型在 txt 宇宙里不存在,编译在写出字节码前就停了——Not a type 是 HTTP 400 的 compile error,不是 500,更不是运行时 SecurityException;磁盘路径从未被当成文件系统参数。
🕳 以为 def 晚绑 = 不检查:实测对照:def x = 1; x.getClass() 是运行期 dynamic method [java.lang.Integer, getClass/0] not found,静态类型 String s 是编译期 member method ... not found——def 只是把查表推迟到动态分发,同一张表,反射入口不存在。
🕳 script_score 忘写 query / 以为会乘一层:REST 缺 query 是 400 Required [query],连 match_all 都要显式;分数是整体替换内层(实验 4 的 90/72),和第 20 课 function_score 的乘一层不是一回事。
🕳 混淆两层开关:白名单(File 能不能编译)与 search.allow_expensive_queries(集群愿不愿意按文档跑脚本)是两个维度。关掉后者,return 1.0; 也拒(query_shard_exception);开着前者,java.io.File 仍编不过。
🕳 等 ingest 坏脚本「写入时才爆」:PUT pipeline 时就 compile,第一条文档之前就 400(实验 12)。反过来的坑:stored 脚本故意不缓存 factory——集群里改了 stored 源码,processor 不会拿着旧 class 继续跑。
