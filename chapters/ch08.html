异步编程模型

两条不变量:等网络不占线程、回调只响一次 · 约 17 分钟 · 前置:第 6、7 课 · 10 个实验

学习目标

  • 拿到 listener.map(fn) 与 ActionListener.wrap(...) 各一段代码,说出 fn 抛异常、下游 onResponse 再抛各自走哪条路——一个进 onFailure,一个被视为 bug。
  • 用 GET /_cat/thread_pool 对上 search / write / cluster_coordination 的隔离;说出队列满时抛的异常类名、HTTP 状态码,以及为什么 generic 永不 429。
  • 预测 PUT /_cluster/settings 改 thread_pool.search.queue_size 的结果并用实验验证;解释这个设置为什么不是 Dynamic。

1. 心智模型:发出去就释放线程

一个搜索可能要问几十个分片,每个分片可能在另一台节点上,网络往返以几十毫秒计。如果协调线程发完请求就原地 join() 等响应,它整个等待期唯一的「工作」就是占着一条线程。池子是固定大小的,几十个这样的等待就能把池填满——新搜索进不来,连写入都得跟着排队。

ES 的解法不是把池开大,而是换编程模型:凡是要等网络的方法,签名一律 void + ActionListener——发出请求后立刻返回,把「接下来干什么」写成回调;响应到达时,传输层用一小段 CPU 时间调 onResponse / onFailure。这就是本课第一条不变量:等待网络时,线程必须回到池里。

顺带纠正一个旧名字:老教程里的 SAME_THREAD 池在当前仓库已不存在,等价物是 EsExecutors.DIRECT_EXECUTOR_SERVICE——execute() 就是当场 run(),在调用者线程上跑完,不进任何池、不排队、不切换。它名字里没有「池」,因为它真的不是。

3. 不变量在搜索里怎么落地

TransportSearchAction 构造时传入的执行器是 DIRECT_EXECUTOR_SERVICE,所以过滤器链和 doExecute 的开头跑在调用者线程(通常是 Netty HTTP 线程)上;rewrite 被显式提交到 search_coordination 池。然后是对每个 shard 的发送——AbstractSearchAsyncAction.doRun:

protected void doRun(Map<SearchShardIterator, Integer> shardIndexMap) {
    for (int i = 0; i < shardsIts.size(); i++) {
        final SearchShardIterator shardRoutings = shardsIts.get(i);
        ...
        performPhaseOnShard(shardIndex, shardRoutings, routing);  // 发送,不等待
    }
}   // 循环结束,方法返回——没有 Future.get(),也没有 latch.await()

发送最终落到 SearchTransportService.sendExecuteQuery → transportService.sendChildRequest(...),返回类型是 void:帧写进连接(或排进 Netty outbound)之后,调用者继续走自己的路。

数据节点这一侧,query 的 request handler 不是注册在 search 池上——SearchTransportService 把 indices:data/read/search[phase/query] 挂在 DIRECT_EXECUTOR_SERVICE 上:传输线程先接住并解码,再由 SearchService.executeQueryPhase 自己 fork:

transportService.registerRequestHandler(QUERY_ACTION_NAME,
    EsExecutors.DIRECT_EXECUTOR_SERVICE, ...,
    (request, channel, task) -> searchService.executeQueryPhase(
        request, (SearchShardTask) task, new ChannelActionListener<>(channel)));

// SearchService:真正占 search 池的是这一行
private static <T extends RefCounted> void runAsync(Executor executor,
        CheckedSupplier<T, Exception> executable, ActionListener<T> listener) {
    executor.execute(ActionRunnable.supplyAndDecRef(listener, executable));
}

getExecutor 对普通索引返回 threadPool.executor(Names.SEARCH);系统索引走 SYSTEM_READ / SYSTEM_CRITICAL_READ,隔离逻辑同款。提交成功之后,传输线程立刻回去读下一帧——这是不变量在数据节点上的版本:等 Lucene 查询的不该是 Netty worker。

合并发生在回调里。每份 shard 结果(或该 shard 全部副本失败)都进 finishOneShard:

private void finishOneShard() {
    final int outstanding = outstandingShards.decrementAndGet();
    assert outstanding >= 0 : "outstanding: " + outstanding;
    if (outstanding == 0) {
        onPhaseDone();   // 进入 fetch 阶段,或组 SearchResponse
    }
}

3 个 shard 就倒数 3 次;任意一次回调都可能落在「刚处理完那份响应」的任意一条线程上,所以 outstandingShards 是 AtomicInteger、结果收集用 AtomicArray,「最后一份到齐」必须被设计成只发生一次。失败路径一条带过:单个副本失败会 shardIt.nextOrNull() 换下一个副本,同一 shard 的所有副本都失败才算一次 finishOneShard;allowPartialSearchResults=false 时还会取消整个 task。老教程用 CountDownLatch 写的合并伪代码方向对,但 latch.await() 本身就会堵死调用线程——生产路径没有这个调用;通用的扇入组合子是 RefCountingListener,搜索这条专用路径就是 outstandingShards。

4. ActionListener:两个方法,一层层包

ActionListener 文件头的 javadoc 把设计说得很硬:回调让代码「异步且不阻塞」,而 ES 明确避开 CompletableFuture,理由两条,都不是口味问题:

  1. Future 支持 get() 阻塞,而 ES 的线程太贵——一处 get() 就能把本课的不变量整个拆掉,极端时直接死锁;
  2. CompletableFuture 会接住 Error:JVM 本该立刻退出的时刻,被推迟到有人观察那个 result——可能是很久以后,也可能永远没有。

接口本体只有两个方法。Java 的一个方法要么返回值、要么抛异常,两个继续方式正好一一对应:

public interface ActionListener<Response> {
    void onResponse(Response response);
    void onFailure(Exception e);
}

组合、扇出、超时,全部靠「再包一层 listener」完成,不发明第二种回调类型。还有一条工程配套容易记错归属:安全身份、X-Opaque-Id、headers 的传递发生在线程池提交那一刻——EsThreadPoolExecutor.execute 会 contextHolder.preserveContext(command)。这是线程池的功能,不是 listener 的魔法;纯 JDK Future 不会帮你做这件事。

组合子只记会改变控制流的几个,其余打开 ActionListener.java 现查:

方法成功时失败时记住
wrap(onResponse, onFailure)调前者调后者onResponse 里抛的异常会转交 onFailure(wrap 特有)
map(fn)fn 转换后交给 delegate原样透传fn 抛 → delegate.onFailure;delegate 的 onResponse 再抛视为 bug,不会回头进 onFailure
delegateFailureAndWrap自己写成功分支,可在里面发起下一步异步自动委托到底链式首选,比手写 listener::onFailure 便宜
runAfter(listener, cleanup)完成后跑清理同左异步版的 finally:方法 return 不等于结束
notifyOnce(delegate)第一次照常同左第二次静默丢弃,并放开 delegate 引用
assertOnce(delegate)第一次照常同左仅断言构建有效:第二次 AssertionError;断言关闭时是恒等包装

wrap 和 map 的失败模型不是一回事,这是最容易被想当然的地方。看 ActionListenerImplementations.MappedActionListener 的关键行:

mapped = fn.apply(response);     // fn 抛异常 → onFailure(e):走失败 continuation
delegate.onResponse(mapped);     // delegate 自己抛 → expectNoException:视为 bug,不转 onFailure

javadoc 原话:it is considered a bug if the listener's onResponse or onFailure fails. onResponse failures will not call onFailure. continuation 自己必须把异常处理干净——把 map 当 wrap 用,会把下游 bug 悄悄变成「看起来正常的失败处理」。

5. 只完成一次:assertOnce 是断言,notifyOnce 是吞掉

第二条不变量与第一条正交:同一个 listener 恰好完成一次。HTTP 响应写两次、引用计数多减一次、RefCountingListener 减成负数,根源都是同一条 continuation 被完成两次——双回调不是「多通知一次」,是非法状态。

notifyOnce 用 getAndSet(null) 保证只有第一次拿到 delegate,第二次直接 return,顺手放开引用——即使 wrapper 还躺在某个 pending 列表里,delegate 和它抓着的大对象也能被 GC(ActionListenerTests.testNotifyOnceReleasesDelegate 专门验证)。assertOnce 则在断言开启时用 compareAndExchange 记下第一次的栈,第二次把两份栈一起打出来:

static <Response> ActionListener<Response> assertOnce(ActionListener<Response> delegate) {
    if (Assertions.ENABLED) {
        ...  // compareAndExchange 记下第一次;第二次 assert 失败,带两份栈
    }
    return delegate;   // 断言关闭:恒等包装,不设防
}

第 7 课见过 NodeClient.executeLocally 无条件包一层 assertOnce——那是给测试构建抓双回调用的;生产发布包断言默认关闭,别指望它兜底。另外「一个结果、多个订阅者」用 SubscribableListener:它自己就是 ActionListener,完成超过一次时第一次之后全部静默丢弃,来晚的订阅者立刻用已有结果完成;andThen / andThenApply / newForked 把嵌套回调拉直,失败自动沉底。

6. 线程池:按职责隔离,而不是一张大池

异步解决的是「等网络别占线程」;CPU 密集的活——跑 Lucene、写 segment、刷 translog、选主——仍然要线程来跑。ES 的答案是按职责拆池:一个池排队甚至拒绝,别的池照常服务。反例不用画图:假如所有请求共用 16 条线程,100 个慢搜索就能把它们全部占住,refresh 没人跑、master 发布没人处理、_cluster/health 也得排,节点看起来「死了」。拆开后,search 可以对客户端 429,write 和 cluster_coordination 不受牵连。

数字锚定 9.4.0:N = EsExecutors.allocatedProcessors(下表以 12 核节点为例),来源是 DefaultBuiltInExecutorBuilders 与 ThreadPool.searchOrGetThreadPoolSize——不是旧文档的「一律 CPU+1、search 队列 1000」。

cluster_coordination 是 Fixed 却配 -1 无界队列:1 条线程换互斥(避开 Coordinator#mutex 争用),无限排队换「集群任务绝不因队列满而丢」——与 search 的「宁可 429」正好是相反的权衡,第 22 课还会遇到它。DIRECT_EXECUTOR_SERVICE 则不在两种类型里:不排队、不拒绝、不切线程;Transport 大量 handler 挂在它上面,目的就是先尽快离开 Netty 读循环,再由业务代码决定 fork 到哪个具名池。

把图 2 展开成职责清单,一次搜索实际经过:

  1. Netty HTTP 线程:RestController.dispatchRequest → REST handler → NodeClient。并没有「先 hop 进 generic」的硬性步骤;
  2. 调用者线程(DIRECT):TransportAction 过滤器链与 doExecute 开头;
  3. search_coordination:Rewriteable.rewriteAndFetch;
  4. Transport 写路径:sendChildRequest 把帧交给 Netty,立即返回;
  5. 数据节点传输线程(DIRECT handler)→ search 池:SearchService.runAsync;
  6. 回调:最后一份 finishOneShard 触发 fetch 或组响应,HTTP 写回原 channel。

TransportAction.execute 自己也会 fork,但仅当构造传入的 executor 不是 DIRECT(走 doExecuteForking)——「这个 Action 在哪个池跑」没有全局答案,每个 TransportAction 构造函数传入的那个 executor 说了算。

7. 背压:队列满 → EsAbortPolicy → 429

Fixed 池的有界队列满了,ES 选择拒绝而不是把堆撑爆。拒绝策略是 EsAbortPolicy:

public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
    if (executor.isShutdown() == false && isForceExecution(r)) { /* 强行塞回队列 */ }
    incrementRejections();                        // 就是 _cat/thread_pool 的 rejected 列
    throw newRejectedException(r, executor, ...); // EsRejectedExecutionException
}

REST 一侧,ExceptionsHelper.status 认出它:

} else if (t instanceof EsRejectedExecutionException) {
    return RestStatus.TOO_MANY_REQUESTS;          // 429
}

客户端拿到 429 的正确反应是退避、换节点、降速——不是立刻重试把队列再打满一次。两件不要想当然的事:

  1. 不是所有池都会拒绝。generic 的 javadoc 写明 does not reject any task;Scaling 池走 ForceQueuePolicy。_cat/thread_pool 里 search/write 的 rejected 上涨,才是用户流量的背压信号。
  2. 队列长度改不了运行时值。FixedExecutorBuilder 把 thread_pool.<name>.size / queue_size 登记为 Property.NodeScope(没有 Dynamic),EsThreadPoolExecutor.setMaximumPoolSize 直接抛 UnsupportedOperationException。想改:yml + 重启——实验 3 踹的就是这堵墙。

forceExecution 是给「内部不能丢的任务」留的口子(某些 cluster task);普通搜索没有这个标记,该拒绝就拒绝。

清理

思考题

1. listener.map(GetResponse::getId) 包装之后:(a) getId 抛 RuntimeException;(b) map 成功但下游 delegate.onResponse 又抛。各走哪条路?ActionListener.wrap 在 (b) 情形走哪条?

(a) 进 delegate.onFailure——fn 的异常是「转换失败」,MappedActionListener 用 try/catch 接住、转进失败 continuation。(b) 不会进 onFailure:delegate 的 onResponse 抛异常被 expectNoException 接住,断言构建直接失败,javadoc 称之为 bug。wrap 不同:它的 onResponse 抛异常会被转进 onFailure。把 map 当 wrap 用,等于把下游 bug 悄悄变成「看起来正常的失败处理」。

2. 同一个 listener 被回调第二次:notifyOnce 和 assertOnce 分别怎样?生产构建里 assertOnce 还设防吗?NodeClient.executeLocally 包的是哪个?

notifyOnce:getAndSet(null) 第二次拿到 null 直接 return,静默丢弃,还放开 delegate 引用帮 GC。assertOnce:断言开启时第二次抛 AssertionError,把两次的栈一起打出来;Assertions.ENABLED 为 false 时 return delegate,恒等包装——生产发布包不设防。NodeClient.executeLocally 包的是 assertOnce,给测试构建抓双回调;生产路径的防线是调用方自觉、RefCountingListener 内部的 assertOnce,或关键处再包 notifyOnce。

3. 某插件在协调路径上对每个远程 shard 写了 responseFuture.get(50ms)。3 个 shard、各 50ms 网络时,那条协调线程被占多久?客户端还会「异步」收到响应吗?不变量破了吗?

约 150ms 量级——三次串行等待,而不是发出去就释放的几毫秒。HTTP 层看起来仍异步:REST 方法早已 return,响应由 listener 写回。但 ES 内部那条协调线程被 get() 占死,图 1 右边翻成左边;并发一高,当前承压的池(那条 DIRECT/HTTP 线程或 search_coordination)先耗尽,新搜索进不来。「客户端最终收到响应」不代表不变量还在。

4. cluster_coordination 为什么选 1 条线程 + 无界队列,search 为什么有界 + 拒绝?把 search 队列再加大两个数量级,和更快 429 比,各在付什么代价?

集群任务丢了等于丢状态更新,所以单线程换互斥、无界队列换「绝不因满而拒绝」;搜索丢一条可以重试,所以有界 + EsAbortPolicy 把过载显式推回客户端。队列加大两个数量级:峰值能多撑一会儿,代价是尾延迟变成「在队列里等」,客户端以为节点还活着、继续打,堆压力和延迟都在涨;更快 429 让过载立刻可见,好节点仍可服务。两种相反的背压,根源是「任务能不能丢」。

陷阱

🕳 旧数字别背:search 线程数不是 CPU+1,是 ((N*3)/2)+1;队列不是 1000,是 size×1000;「write 队列比 search 大一个数量级」在 9.4.0 已反转(write 是 max(N*750,10000))。SAME_THREAD 已改名 EsExecutors.DIRECT_EXECUTOR_SERVICE。一切以 DefaultBuiltInExecutorBuilders + _cat/thread_pool 实测为准。
🕳 把 map 当 wrap:onResponse 里抛的异常,wrap 会转进 onFailure,map 不会——它把下游抛异常当 bug(expectNoException)。写转换逻辑前先想清楚要哪种失败模型。
🕳 指望 assertOnce 在生产兜底:生产发布包断言关闭,assertOnce 是恒等包装,双回调不会在这里炸。运行时防线是 notifyOnce / RefCountingListener,以及 code review。
🕳 想用 _cluster/settings 在线调线程池:thread_pool.*.size / queue_size 是 NodeScope 非 Dynamic,PUT 必 400;改 yml 重启才是正路。看到 429 先降客户端并发,不是先改队列。
