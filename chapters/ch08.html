1. 方法返回，为什么还没有响应？

一个协调节点向远程分片发出 query 后，结果要经过网络往返才到达。如果用 future.get() 或 latch.await() 阻塞等待，当前线程会在等待期被占用。ES 的主要请求路径用 ActionListener<Response> 表达“结果可用时继续做什么”：发起方安排工作后返回，成功由 onResponse 接续，失败由 onFailure 接续。等待期间仍保留任务、listener、请求状态和可能的网络缓冲；省掉等待线程不等于工作没有资源成本。

异步接口不保证延后完成，也不保证换线程。本地快捷路径、已完成的结果和立即失败都可能在方法返回前调用 listener。map、wrap 本身不会 fork；EsExecutors.DIRECT_EXECUTOR_SERVICE.execute 在调用者线程执行 command.run()。所以判断线程位置，要追到具体的提交点或 response handler，而不是看返回类型是不是 void。依据：DIRECT.execute、addListener 的同步完成与 executor 规则。

搜索初始阶段的 AbstractSearchAsyncAction.doRun 遍历分片，调用 performPhaseOnShard，其中每节点并发上限可能把待发工作留在 PendingExecutions；它没有阻塞等齐所有响应的 await。远程 query 的 handler 注册为 DIRECT，再由 SearchService 在普通查询路径调用 runAsync 提交到普通索引的 search executor。系统索引另经 executorSelector 选择；不能套用普通索引的池名。依据：调度循环与并发限制、runAsync 提交点。

结果完成也不是“最后一帧到了就立刻合并”。成功结果先进入 results.consumeResult，其处理完成回调才调用 finishOneShard；倒数归零后 onPhaseDone 进入下一阶段。副本失败可换下一份尝试，所有候选失败才结束该分片组；禁止部分结果时还尝试取消搜索。线程位置随响应处理、结果消费与显式调度而变，不能把整个合并锁定成“最后一个 Netty 回调里的小段 CPU”。

rewrite 的一个细节：TransportSearchAction 给 Rewriteable.rewriteAndFetch 传 search_coordination executor，用于完成 listener；rewrite 先通过 SubscribableListener.newForked 发起，它直接调用 consumer。已同步完成时 addListener 可能就在订阅线程继续，未完成时使用指定 executor。旧文案“rewrite 总提交到 search_coordination”过于绝对。见 rewriteAndFetch 和 newForked。

本课实验只有一个主分片，普通无 rank 的请求可在数据侧合并 query 与 fetch。它便于看结果与统计，却不能当作多节点网络往返的实测证据。图里的远程等待来自源码分析，单节点 API 不证明每一步都走网络。依据：单分片 QueryFetchSearchResult 优化。

2. 同样是包 listener，失败边界相同吗？

ActionListener 的两种完成方式是 onResponse(Response) 与 onFailure(Exception)。接口与设计说明解释为何尽量避开 CompletableFuture：阻塞等待会耗尽工作线程；把 JVM Error 留在 future 结果里也可能推迟致命错误的处理。这是主要异步路径的设计约束，不表示仓库没有任何同步接口，也不保证用户代码里的 listener 永不阻塞。

组合方式成功 / 失败语义边界
wrap(success, failure)success consumer 抛 Exception，交给 failure consumer便利的异常适配，不增加调度或去重
map(fn)fn 抛 Exception 转 delegate.onFailure；成功转换后委托 onResponsedelegate.onResponse 的 RuntimeException 走 expectNoException，被视为 bug，不回头转失败
delegateFailureAndWrap替换成功分支，失败自动委托；成功分支可发起下一步异步成功 consumer 的 Exception 也转委托失败，仍须遵守一次完成协议
runAfter(listener, cleanup)成功或失败回调后，在 finally 执行 cleanup不是发起方法 return 时清理；它本身不提供运行时去重

例如给 listener.map(Response::getId) 的 fn 抛异常，是“转换没有得到结果”，所以转失败；fn 成功后下游又抛异常，是下游违反回调约定。这两段 try/catch 的分界不能合成一个“任何异常都调 onFailure”。直接依据：MappedActionListener.onResponse、wrap、RunAfterActionListener。

跨线程还要保存请求上下文。EsThreadPoolExecutor 包装提交任务时调用 contextHolder.preserveContext；部分 listener 包装也显式保存 / 恢复 ThreadContext。普通 map 或 wrap 不自动携带身份与 headers。“切线程”与“携带上下文”要分别查提交点和包装，不能全归给 listener 或只归给线程池。见 wrapRunnable、preserveContext。

3. “只完成一次”由谁保证？

每个独立操作应以成功或失败结束一次。多次完成可能重复响应、重复清理引用；零次完成则留下悬挂请求。接口本身不强制恰好一次，notifyOnce 也只保证至多一次。它用 getAndSet(null) 竞争 delegate：第一次成功或失败拿走 delegate，后来者忽略，并释放包装持有的引用。如果所有参与者都没回调，它不会生成一个完成结果。见 NotifyOnceActionListener。

assertOnce 是诊断：Assertions.ENABLED 为真时记录首次完成栈，重复完成触发断言；为假时直接 return delegate。第 7 课的 NodeClient 用它发现违约，但是否检测取决于断言状态。不要把“生产”写成固定的断言开关，也不要把 assertOnce 当作每次部署都有的运行时去重。见 assertOnce。

扇入与订阅：RefCountingListener / SubscribableListener

RefCountingListener 在自身关闭且所有 acquire 的子 listener 完成后结束 delegate，可以收集有限数量的失败，不阻塞等结果。delegate 在最后完成的子回调线程上运行；若关闭时已经没有未完成的子 listener，则在关闭线程运行。每个子操作仍须按自己的完成协议结束，不能把它画成同步 CountDownLatch.await。

SubscribableListener 支持一次结果的多个订阅者，忽略重复完成，已完成后新订阅可立即通知；andThen / andThenApply 串起后续步骤。newForked 的名字不代表它一定向线程池提交。来源：扇入协议、发起 consumer、订阅与线程。

4. 默认池大小，怎样与实际节点对上？

异步减少阻塞等待，查询、写入与管理仍需要线程执行。多个池分开容量和队列，能减少一种工作的拥塞占满另一种 executor；它们仍共享 CPU、堆、磁盘与节点生命期。search 饱和时，不能保证 write 或集群协调毫无影响。

下表限定 自管 ES 9.4.0 默认 BuiltInExecutorBuilders，无 thread_pool 覆盖、普通索引。N 是 EsExecutors.allocatedProcessors(settings) 的整数值；node.processors 允许小数，取整方式是向上取整。Nodes OS 的 allocated_processors 已按该整数返回；不能拿物理核数或 available_processors 直接代替。公式中的除法按 Java 整数除法。依据：node.processors 与 roundUp、OS 输出。

池类型 / 默认线程默认队列N=12 示例
searchFixed，floor(3N/2)+1默认线程大小×100019 / 19000
search_coordinationFixed，floor((N+1)/2)10006 / 1000
writeFixed，Nmax(750N,10000)12 / 10000
write_coordinationFixed，N1000012 / 10000

clamp(x,a,b) 表示 min(b,max(a,x))。默认来源是 getBuilders 与 整数公式。search 的默认 queue_size 在构造 builder 时根据默认大小计算；size 和 queue_size 是独立 Setting。只覆盖 search.size，不能保证 queue_size 自动随实际 size 重算。include_defaults 的视图还可含处理 REST 请求节点的 yml 设置；实际配置以各节点 CAT / Nodes 信息对照。

Fixed worker 上限固定；队列为负时无界，否则按容量限制。Scaling 从 core 到 max 扩张，无法再增 worker 时 ForceQueuePolicy 把工作放回无界队列，正常运行不因容量满拒绝，但等待对象和内存压力仍可增长。cluster_coordination 的一个 worker 串行执行该池任务，不等于整个集群永远互斥；DIRECT 就地运行，也不意味着尽快离开当前线程，耗时任务一样会阻塞调用者。

5. 有界队列满，与客户端 429 是什么关系？

用“下一步”逐帧对照触发条件，或重置后播放；手机可在机制快照内横向滑动，每一步的解说保持可读。下图不代表本轮压测结果。

播放器以默认 N=12 的 search 池作概念快照：worker 全忙、队列满、普通新任务无法提交。EsAbortPolicy 检查强制执行与 shutdown 分支，普通拒绝增加计数并产生 EsRejectedExecutionException。EsThreadPoolExecutor.execute 遇到 AbstractRunnable 可通过 onRejection 交给其失败路径，不保证调用者总直接捕到抛出的异常。依据：拒绝与 forceExecution、execute 的拒绝转交。

status把该异常映射为 TOO_MANY_REQUESTS；只有最终 REST 错误以它或相应封装呈现时，才是顶层 HTTP 429。Bulk 可以在 HTTP 成功响应的 items 中报告失败，搜索可能返回部分结果；其他限流或熔断路径也会返回 429。不能由状态码反推出哪个池已满，也不能由 generic 没有有界队列拒绝推出整个请求永不 429。

客户端应结合错误内容降低并发，采用有上限的退避；写入重试还要考虑幂等与单项结果。扩大队列只是容纳更多等待，不能保证处理更快。size / queue_size 设置只标 NodeScope，没有 Dynamic；本课尝试经 cluster settings 更新会被拒绝。需要修改时在支持该键的自管节点配置并重启，再逐节点验证实际值。

统计是证据，不能替代因果链。CAT 的 active 和 queue 是采样瞬间，rejected 与 completed 是当前节点进程的累计任务统计。它们没有按 HTTP 请求或索引分账。历史拒绝不会因排空队列或删除索引变成 0；一次请求可能调度多个任务，也可能同步走过部分阶段。先保存同一 node_id 的基线，再比较差值，并把其他索引、预热、后台任务和重启纳入解释。代码依据：poolStats / poolInfo 列。本章不以压测触发 429。

思考题

1. map 的转换函数和 delegate.onResponse 各抛 RuntimeException，会走同一失败分支吗？

不会。转换 fn 的 Exception 转 delegate.onFailure；转换成功后下游 onResponse 抛 RuntimeException 是程序错误，走 expectNoException，不回头通知失败。wrap 的成功 consumer 抛 Exception 会转失败 consumer。Error 不在这两个业务 Exception 捕获范围内。

2. notifyOnce 从未被通知，会替你完成吗？assertOnce 在断言关闭时还能去重吗？

都不能。notifyOnce 保证竞争通知至多一次，但不提供完成活性；assertOnce 关闭断言时直接返回 delegate。操作必须自行安排成功、失败、取消或超时完成，并维护资源持有协议。

3. 给 rewriteAndFetch 传 search_coordination executor，为什么仍不能保证 rewrite 和回调总在那个池？

该参数是 responseExecutor；newForked 发起 rewrite 时直接调用 consumer。已同步完成的结果可在订阅线程立即通知；未完成时才以传入 executor 包装订阅回调。要确定线程，必须把提交与完成分开追踪。

4. B6 发现 completed 涨 3、rejected 原来是 5，能推断本课搜索用了三个任务并触发五次拒绝吗？

不能。completed 包含节点所有任务；rejected 是进程历史累计值。需要同一 node_id 前后基线、后台流量条件及请求级跟踪。当前 active/queue 为 0 不清除历史拒绝，清理索引也不重置。

5. search 和 write 分池，search 排满时 write 就一定无影响吗？

分池隔离 executor 的线程与队列容量，不隔离共享 CPU、堆、磁盘。search 过载可能争用共享资源。增大 search 队列也不增加处理能力，只增加可等待的任务与延迟 / 内存成本。

陷阱

异步就是后台线程：DIRECT、map、wrap 以及同步完成的订阅都可能就地执行；耗时回调照样占当前线程。读具体 executor 提交点。
一次包装就等于一定完成：notifyOnce 只保证至多一次；assertOnce 依赖断言。二者都不能解决没人回调的悬挂请求。
每请求计数固定 +1：completed 是 executor 工作量，refresh=true 是可见性语义，不能推出 refresh 池 completed 必 +1。统计须留基线并考虑同步路径和后台任务。刷新调用见 PostWriteRefresh 的 IMMEDIATE 分支。
429 就证明 search 队列满：其他层可产生 429；Bulk 单项错误和搜索部分失败也要单独读。Scaling 无界队列不是整个请求永不出错的保证。
默认公式适用于任何部署：本表限定默认自管 9.4.0，存在节点设置覆盖或其他 builder 时需重新核对；search.size 与 queue_size 是独立键，NodeScope 不等于 Dynamic。
