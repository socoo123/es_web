Realtime GET 的三层拆解 · 约 16 分钟 · 前置:第 6-9 课 · 19 个实验

学习目标

  • 从 RestGetAction.routes() 一路指到 TransportGetAction.shardOperation,说出 REST 层的全部产出:一个填好参数的 GetRequest,外加一句 client.get()——没有一行 Lucene。
  • 关掉 refresh_interval 后实测三连:默认 GET found:true、立刻 SEARCH 0 hits、?realtime=false 返回 404,并分别指出三条结果各自读的是哪份快照(VersionMap/translog 还是 EXTERNAL searcher)。
  • 带 routing 写入、不带 routing 去读,预测 found:false;用 _search_shards 展示两把有效键落在不同分片,并说出 GET 只打一个 shard、失败只在副本间换。

1. 心智模型:一次 GET 只换三次身份

第 6 到 9 课把 REST 路由、Action 表、异步框架、传输层一件件拆开看过。这一课把它们装回一次真实的 GET /tut-l10-nrt/_doc/1:请求在集群里只换三次身份——HTTP 报文变成类型安全的 GetRequest;Action 层按 _id 算出一个分片并把动作名换成 get[s];最后 Engine 在那个分片上按 _id 取出 _source。Netty、PathTrie、Filter、Lucene 都是零件,不是今天的图。

这一课同时是第二篇的收官:前四课的每个零件都要在这次 GET 里被点到名。哪一层对不上,回哪一课补。

3. REST 入口:到 client.get() 为止

第 6 课的 PathTrie 在这里兑现:/{index}/_doc/{id} 命中 RestGetAction,路径里抽出 index 和 id 两个参数。9.4.0 的这个类不到百行,路由只登记两条——GET 与 HEAD 共用同一套逻辑,存在性判断和 realtime、routing 语义必须一致:

// RestGetAction.java
@Override
public List<Route> routes() {
    return List.of(new Route(GET, "/{index}/_doc/{id}"),
                   new Route(HEAD, "/{index}/_doc/{id}"));
}

prepareRequest 把路径参数和查询串写进同一个 GetRequest,然后返回一个 lambda——真正离开 REST 层的就是这一句:

GetRequest getRequest = new GetRequest(request.param("index"), request.param("id"));
getRequest.refresh(request.paramAsBoolean("refresh", getRequest.refresh()));    // 默认 false
getRequest.routing(request.param("routing"));
getRequest.realtime(request.paramAsBoolean("realtime", getRequest.realtime())); // 默认 true
return channel -> client.get(getRequest,
    new RestToXContentListener<>(channel, r -> r.isExists() ? OK : NOT_FOUND));

注意最后一行的三元:HTTP 状态码在这里二选一,found:false 时 JSON 正文照样由 GetResult.toXContent 写出 _index、_id,只是没有 _version 和 _source。别把两种「错」混淆:路径配不上任何 Route 是 400(第 6 课),文档不存在才是 404。另外 getName() 返回的 "document_get_action" 只出现在 _nodes/usage 的 rest_actions 统计里;_tasks 里看到的是 "indices:data/read/get"——两套名字空间,第 7 课对照过。

4. Action 层:选出一个 shard,再把名字换成 [s]

TransportGetAction 没有覆盖 doExecute——执行模式写死在基类 TransportSingleShardAction 里:new AsyncSingleAction(request, listener).start()。过滤器、校验、Task 登记都在更外层的 TransportAction.execute(第 7 课)做完了。AsyncSingleAction 从 ClusterState 解析出具体索引、检查 READ block,然后调用子类的 shards():

// TransportGetAction.java — 先算出一个 shard,再排它的可搜索副本
ShardIterator iterator = clusterService.operationRouting()
    .getShards(project, request.concreteIndex(),
               request.request().id(),       // hash 键之一
               request.request().routing(),   // 有它就替换上面的键
               request.request().preference());
return ShardIterator.allSearchableShards(iterator);

OperationRouting.getShards 内部用 IndexRouting.getShard(id, routing) 得到一个 shard 号,再按 preference 把该 shard 的可搜索副本排成迭代器。SEARCH 打全部 shard;GET 只打这一个。推论很重要:routing 错了不是「换个 shard 再找」,而是在错误的那份拷贝上得到 found:false——第 6 节实验会撞这堵墙。

构造函数里登记了两个 Transport handler 名,对应两种到达姿势:

动作名谁处理做什么
indices:data/read/getTransportHandler协调入口:再跑一遍 AsyncSingleAction 选 shard
indices:data/read/get[s]ShardTransportHandler已带 shardId,直接 asyncShardOperation

即使目标就是本节点,也走 TransportService 的本地连接——源码里没有「if 本地就跳过框架」的旁路。失败路径一句话:某副本连接失败或超时,onFailure 让 perform 取 shardIt.nextOrNull() 换下一个副本;迭代器耗尽仍不成功,包成 NoShardAvailableActionException 或把最后一个异常交给 listener。不存在「读一半」的降级。这套请求跑在 get 线程池上,和 SEARCH 的 search 池分开(第 8 课)——by-id 读不会被重查询拖死,反过来也一样。

数据节点上真正读文档的是 shardOperation,而何时调它由 asyncShardOperation 决定:realtime=true 直接 asyncGet(不绑定 refresh 周期);realtime=false 先 ensureShardSearchActive。还有一个容易想当然的分支:asyncGet 里只有 realtime=false 且 refresh=true 才会先 externalRefresh 再读——默认 realtime 下,单加 ?refresh=true 什么都不会刷新(实验 1 第 5-6 步专门验证它)。至于构造函数里那个 TransportGetFromTranslogAction(内部动作 get_from_translog),是 GET 落到不可提升为主分片的 search shard(serverless 形态)时向可写主分片「借」realtime 结果的接力;本课实验的分片可提升为主,不走它,别画进主路径。

5. Engine 层:未 refresh 的文档,凭什么立刻读得到

第 1 课实验 3 留过一个悬念:关掉自动 refresh、刚写完一篇,立刻 GET 拿得到、立刻 SEARCH 扑空,当时只说「机制在第 10 课拆」。现在拆。先看动画,再对源码:

数据节点上,ShardGetService.doGet 先造一个 Engine 侧的查询对象——构造参数是 (realtime, readFromTranslog, id),HTTP 传进来的 realtime 同时填了前两个布尔:要实时,就也允许从 translog 读:

// ShardGetService.java — 两个布尔都来自同一个 realtime
var engineGet = new Engine.Get(realtime, realtime, id)
    .version(version).versionType(versionType);
try (Engine.GetResult get = engineGetOperator.apply(engineGet)) {
    // exists == false → found:false;否则 innerGetFetch 加载字段与 _source
}

往下 IndexShard.get → InternalEngine.get,分支只有两个:

// InternalEngine.java
if (get.realtime()) {
    return realtimeGetUnderLock(get, mappingLookup, documentParser, searcherWrapper, true);
} else {
    // 只读「已经 refresh、对外可见」的快照 —— 与 SEARCH 同源
    return getFromSearcher(get, acquireSearcher("get", SearcherScope.EXTERNAL, searcherWrapper), false);
}

非 realtime 就是那一行:只读 EXTERNAL searcher——refresh 之后才换的那份 segment 快照。刚写入未 refresh 的文档在这条路上不存在,found:false。realtime 分支则分三站:

  • VersionMap 是第一站。堆里的 LiveVersionMap,按 uid 记录「这篇最近写过没有、删没删、写在 translog 哪个位置」,查找顺序写死:current → old → tombstones → archive。删除是 tombstone,realtime GET 直接 NOT_EXISTS;refresh 之后 afterRefresh 会把 searcher 已能看见的条目清掉。
  • translog 是有 location 时的主路径。translog.readOperation(location) 按 generation 读出 Translog.Index 操作,再在内存里为这一条建临时 DirectoryReader,走与 segment 完全相同的 getFromSearcher 取回文档。
  • INTERNAL searcher 是后备。location 不是天生就有的:trackTranslogLocation 默认 false,写入时只有它在跟踪才会把 translog 位置挂进 VersionMap。第一次 realtime GET 撞上「命中但 location 为空」,会打开跟踪并 refreshIfNeeded(一次内部 refresh,让 INTERNAL searcher 追上这条 seqNo)后从 INTERNAL 读;之后的写入才带 location,后续 GET 稳定走 translog。注意 INTERNAL 是引擎内部快照,EXTERNAL 才是 SEARCH 用的对外那份——两个名字别混。

两条路最后都汇进 ShardGetService.innerGetFetch:translog 路径并不把 JSON 字节直接吐给 HTTP,而是先变成可被同一套 SourceLoader 阅读的内存索引,再按 DocIdAndVersion 取 _source;_source_includes/_source_excludes 只影响这一段的 SourceFilter,不另开 Engine 路径。这也是「从 translog 读比从 segment 读更贵」的根:多一次操作解析加一个临时 reader,而 segment 路径的 stored fields 早就躺在磁盘映射里。命中时响应带全 _version、_seq_no、_primary_term;再 PUT 同一 _id,version 变 2、seq_no 递增——VersionMap 里那条 IndexVersionValue 整个换成新值。带 version/if_seq_no 的冲突检查在 VersionMap 命中和 searcher 命中处各做一次,失败抛 VersionConflictEngineException。

6. routing:hash 的键必须与写入时相同

选 shard 的公式在 IndexRouting(普通非分区索引)里就一行三元:

// IndexRouting.java — 有 routing 就完全替换 _id,不混入
protected int shardId(String id, @Nullable String routing) {
    return hashToShardId(effectiveRoutingToHash(routing == null ? id : routing));
    // 9.x 新索引:Math.floorMod(Murmur3HashFunction.hash(有效键), numberOfShards)
}

写入 PUT /idx/_doc/3?routing=user123 时有效键是 "user123";GET 不带 routing 时有效键退回 "3"。两把键各自取模,经常不是同一个 shard——而 GET 只打一个 shard,打错了就 404,看起来和「文档不存在」一模一样。

SEARCH 默认扇出全部 shard,不带 routing 也能找到这篇(代价是收窄不了);GET 严谨一击,键不一致就静默 404。想让这种错误显式化,得在 mapping 里声明 _routing: {required: true}——缺 routing 会直接抛 routing_missing_exception(HTTP 400),而不是假装文档不存在。想肉眼核对某把键的落点,用 GET /idx/_search_shards?routing=键:不带 routing 时它返回全部 shard,所以要「模拟不带自定义 routing 的 GET」,应查 ?routing=3(id 字符串恰好是那时的有效键)。别背任何 hash 数字,以 _search_shards 的真实返回为准。GetRequest.routing() 的 javadoc 只有一句话,说的就是这件事:Using this value to hash the shard and not the id.

思考题

1. 实验 2 那篇 routing=user123 的 _id=3 已在索引里。GET ?routing=user456 会怎样?SEARCH 呢?把 mapping 改成 _routing.required: true 再不带 routing,错误还是 found:false 吗?

user456 是第三把键:既不是写入时的 user123,也不是 _id 的 "3"。hash(user456) % 5 落到哪算哪,GET 只打那一个 shard,不改去试 user123 的 shard、也不广播——几乎总是 found:false(HTTP 404)。SEARCH q=_id:3 照样命中,因为搜索扇出全部 shard,routing 只是可选收窄。required: true 之后,缺 routing 在路由检查处就抛 routing_missing_exception(HTTP 400)——请求根本进不到「错误 shard 上的 found:false」,和静默 404 不是同一种错(实测两种请求都返回 400)。

2. 为什么 realtime GET 必须先查 VersionMap,而不是「每次 GET 都 refresh 一遍再读 EXTERNAL」?拆掉 VersionMap 只扫 translog,或永不跟踪 location,分别破坏什么?

refresh 要开新 searcher,是 SEARCH 可见性的成本,摊到每个 by-id 读上等于把「写后即读」变成「写后停顿」。VersionMap 是「这篇 uid 最近写过没有、写在哪、删没删」的 O(1) 索引;只扫 translog 没有 uid 索引,找一篇要顺 generation 翻,translog 越长越慢,删除墓碑的精确判断也没了。永不跟踪 location 则每个未 refresh 的 GET 都可能触发一次 refreshIfNeeded(INTERNAL 后备),正确但贵——location 是给「确实有 realtime 负载的 shard」省钱的优化,所以 trackTranslogLocation 默认 false、首次需要才打开。SEARCH 更不能默认 realtime:它要的是倒排表上的词 → 文档,translog 里没有可用的倒排,硬做等于每条查询先 refresh。

3. 一个高 QPS、只按 _id 读、能接受「最多 1 秒旧」的服务,要不要把默认 GET 改成 realtime=false?改了之后,「写入确认」接口还能用默认 GET 吗?

可以改,但要明白换的是什么:realtime=false 读的是 EXTERNAL 快照,行为变成「读已 refresh 的世界」,省掉 VersionMap 锁竞争和 translog 解析,对缓存式 by-id 读更稳。代价是刚 PUT 立刻 GET 会在 refresh 前 404——和第 1 课实验正好相反。「写完确认」类接口必须保持 realtime(或写入时 refresh=wait_for,把成本算进写入侧)。两种负载别共用一个默认值;translog 路径贵在 readOperation 还原操作 + 临时 reader + 仍走一套 fetch,segment 路径的 stored fields 是现成的。

4. GET 用 get 线程池、SEARCH 用 search 池(第 8 课)。如果把 by-id 读塞进 search 池,什么场景会先出事?

重查询把 search 池队列打满时,再轻的 by-id GET 也排队甚至被拒——「确认接口」「详情页」这种低延迟场景被不相干的搜索拖死。分池就是分背压:by-id 读是 O(1) 定位、耗时可控,值得独立的队列上限;search 池的拒流策略按重查询的水位设计。第 8 课的线程池表在这里落地:知道一个动作跑在哪个池,才知道它会跟谁互相排队。

陷阱

🕳 「GET 带 ?refresh=true 就会刷新索引」:默认 realtime=true 时不会。源码条件是 realtime=false 且 refresh=true 才 externalRefresh——单加 refresh=true 之后 SEARCH 依旧扑空。要「先 refresh 再按搜索可见性读」,写 ?refresh=true&realtime=false,或干脆先调一次 _refresh。
🕳 带 routing 写入、忘带 routing 读取:得到的是一份「看起来文档不存在」的 404——不是 bug,是有效键换了(hash(routing ?? id)),GET 只打一个 shard 且失败只换副本不换 shard 号。普通索引没有保护;要显式报错就设 _routing.required: true(400 routing_missing_exception)。排障用 _search_shards?routing=键 对落点。
🕳 把「近实时」套到 GET 上:「写完要等 1 秒才可见」只对 SEARCH 成立。GET 的实时由 VersionMap/translog 保证,且不是免费的:translog 路径多一次解析加临时 reader,首次 realtime GET 还可能触发一次内部 refresh。高 QPS 纯缓存式 by-id 读,认真考虑 realtime=false。
