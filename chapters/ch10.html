学习目标

  • 沿 RestGetAction → TransportGetAction → ShardGetService → InternalEngine 定位具体方法，分清动作名、分片子动作与 HTTP 响应。
  • 在显式关闭自动 refresh 的新索引上，对照默认 GET、非实时 GET 与 SEARCH；更新同一 ID 后，解释为什么非实时 GET 也能成功返回旧值。
  • 用两次 _search_shards 比较写入与读取的有效键，解释不同分片导致的 404，以及 routing 碰撞、必填检查与副本重试的边界。

10.1 带着一个请求读源码

本课固定 Elasticsearch 9.4.0、Lucene 10.4.0，源码锚定官方提交 2e8528e。主线是 GET /tut-l10-nrt/_doc/1：普通索引、可提升为主的分片、路由表不变。前四课的路由、动作、listener、Transport 在这里串起来。一次 GET 先定位一个 shard，再尝试它的一个可搜索副本；成功响应沿 listener 返回，最终写回 HTTP。

读源码时保持输入不变：索引名、ID、routing、realtime、refresh。每到一层只问它改变了什么：HTTP 路径变成 GetRequest，协调侧补上具体索引与 shard，数据侧取得 Engine.GetResult，再组装 GetResponse。这些是职责分工，不能据图推断每次交接都创建新线程或释放线程。

10.2 REST 只准备读取，不决定存储路径

RestGetAction.routes() 为 GET / HEAD 登记 /{index}/_doc/{id}。prepareRequest 读参数、构造对象并返回消费 channel 的 lambda；真正执行时调用 client.get。GET 路由匹配与请求校验完成，不代表文档存在。这里的 listener 按 r.isExists() 选 200 或 404；HEAD 的存在性沿相同读取语义，HTTP 层抑制正文。

// 摘录关键条件，省略 preference、字段、version 等参数解析
GetRequest getRequest = new GetRequest(request.param("index"), request.param("id"));
getRequest.refresh(request.paramAsBoolean("refresh", getRequest.refresh()));
getRequest.routing(request.param("routing"));
getRequest.realtime(request.paramAsBoolean("realtime", getRequest.realtime()));
return channel -> client.get(getRequest,
    new RestToXContentListener<>(channel, r -> r.isExists() ? OK : NOT_FOUND));

依据：RestGetAction.routes / prepareRequest、GetRequest 默认值。found:false 是正常读取结果；GetResult.toXContent 保留 _index、_id 与 found，不输出存在文档才有的版本和 source。索引不存在、路由未命中、参数不合法是另外的失败原因，不能只凭状态码区分。响应序列化

本次请求参数默认与作用边界
realtimetrue，允许实时读取路径不保证每次读 translog，也不禁止内部 refresh
refreshfalse，普通分片显式刷新条件见 10.4不是修改 refresh_interval；GET 与写入的 refresh 语义不同
routing / preference有效键 / 副本候选顺序或限制一个决定去哪个 shard，一个影响读哪份拷贝
_source_includes / stored_fields过滤 source / 另取 stored fields只控制本次响应，不改 mapping 或原文档
version / version_type可限制读取版本Engine 有 seqNo 条件不表示此 REST GET 暴露 if_seq_no

10.3 先选一个分片，再考虑副本

TransportGetAction 继承 TransportSingleShardAction。基类的 doExecute 启动 AsyncSingleAction：读项目集群状态、解析具体索引、合并别名 routing、检查 READ block，然后由 shards() 生成候选迭代器。OperationRouting.getShards 先求 shard 号，再按 preference 排该分片的拷贝；GetAction 进一步保留可搜索候选。执行入口、AsyncSingleAction 构造、shards / resolveRequest

// 本实验：9.4.0 新建普通非分区索引，无 routing_path / resharding
有效键 = routing != null ? routing : id
shard = Math.floorMod(Murmur3HashFunction.hash(有效键), 主分片数)

这条简式受索引创建版本约束：hashToShardId 的旧分支用 routingNumShards / routingFactor；分区路由还混入 ID，时序 / routing_path 索引另有策略。当前节点为 9.4.0 不足以把全部旧索引套进新公式。本实验显式创建普通非分区索引，使用索引本名且没有 resharding；B4 / B5 的 _search_shards?routing=3 与 routing=user123 分别模拟两把有效键。路由策略选择、创建版本与取模、普通与分区路由

操作有效键与范围能推出什么
写 _id=3?routing=user123本实验 hash user123文档只写到所选 shard
GET 同 ID，不带 routing本实验 hash 3两把键落点不同才会找错 shard；同片时可读到
GET 带 user123回到写入时的有效键在数据仍存在 / 分片可用等条件下 found=true
SEARCH 不限 routing普通请求考虑所有分片搜得到不能证明 GET 的路由正确

routing 缺失与错误要分开。新建索引可声明 _routing.required:true，CRUD 缺 routing 会在路由检查中报 routing_missing_exception（400）；提供错误字符串仍通过“已提供”的检查。routing 不同也可能哈希落在同片，不能推断必然 404。它还是文档元数据，会保存和返回；不同 shard 上可以有相同 ID、不同 routing 的两篇文档。getShard / checkRoutingRequired、routing 元数据保存

基类将动作名加 [s]，发送带 shardId 的请求，收到后调用 asyncShardOperation。常规异常进入 perform 尝试下一候选拷贝；候选耗尽时按已有异常返回失败或 NoShardAvailableActionException。found:false 属于正常响应，不触发这条重试。此外 StaleRequestException 是重要例外：resharding 使摘要过时时，可等待新路由后从头解析，不能把“只换副本”写成全部情况的不变量。perform / waitForRoutingUpdateAndRestart

preference（9.4.0）具体限制
缺省此 GET 路径未传 ARS 的 collector / nodeCounts，保留随机化的候选顺序；不能套用 SEARCH 的排名解释
_local / _only_local优先本地 / 只允许本地候选；不改变 hash 有效键
_prefer_nodes:… / _only_nodes:…优先节点 / 按节点选择条件限制
不以 _ 开头的字符串按该字符串和 shardId 生成候选顺序；拓扑 / 分配变化或失败后不能保证永久同一副本
_primary / _replica本版本不支持；A15 对照 400，去掉参数恢复

依据：Preference.parse、GET 未传排名统计、偏好与排序、null 统计跳过排名。普通索引的业务读取使用 get executor，系统索引另由 ExecutorSelector 选择；DIRECT 接收入口与业务调度不同。get / search 分开队列，仍共享 CPU、堆、磁盘等资源，不能许诺两种负载互不影响。getExecutor / asyncGet

10.4 实时读取读哪份“现在”

ShardGetService.doGet 构造 Engine.Get(realtime, realtime, id)：HTTP realtime 同时决定实时语义与是否允许 translog 读取。IndexShard.get 再交给 Engine。realtime=false 在普通 InternalEngine 上读 EXTERNAL searcher；默认 true 先检查 VersionMap，再按当前状态走 translog 或 INTERNAL。doGet、InternalEngine.get

  • VersionMap 记录版本，不是一份完整文档库。按 uid 查 current、old、删除墓碑与 archive；unsafe 时为安全访问可能先内部 refresh。命中删除条目返回 NOT_EXISTS。内部 reader 已接收的条目可在刷新后清理，墓碑有自己的过期规则；不能说条目永远留在堆里。
  • 可读 location 才能走 translog。未删、允许读 translog 且有位置时 readOperation；读到 Index 操作后创建对应 reader，复用 getFromSearcher。位置并非每条写入都有：trackTranslogLocation 初始 false，需要时开启，后续写入才可能存位置。
  • INTERNAL 是真实的回退路径。命中但无可读操作时，必要时让内部 reader 的 checkpoint 追上该 seqNo；VersionMap 未命中时也可从 INTERNAL 查。第一次 GET 不能固定宣称走 translog，实时 GET 也不能宣称绝不 refresh。

依据：刷新与 getUnderLock、realtimeGetUnderLock 全部分支、unsafe 检查、写入按跟踪状态保存 location、refreshIfNeeded 只刷内部视图。

非实时 GET 也不是“刷新前必 404”。如果文档从未发布到 EXTERNAL，它可能不存在；如果版本 1 已发布、版本 2 还没发布，则可成功返回版本 1。实验 A12–A14 专门让这两种状态分开。下方播放器保留逐步解释，显示条件分支与新旧视图；它是机制例子，不是本轮 API 采样。

TransportGetAction.asyncShardOperation 在普通可提升分片上，realtime 直接进入 asyncGet；非实时先 ensureShardSearchActive，有待发布 refresh location 时唤醒可能刷新，之后继续读取。因此一般场景下“非实时 GET 永不触发刷新”也不准确。asyncGet 的显式外部刷新条件是 request.refresh() && !request.realtime()：等所选分片的 externalRefresh 后读；不是整个多分片索引的 _refresh。本实验索引只有一个主分片，才容易用后续 SEARCH 对照。分片执行分支、显式 refresh 条件、搜索唤醒

默认 GET 的 refresh 标志，有适用范围本课自建节点的可提升分片：只加 ?refresh=true 不走上述显式 externalRefresh，但 realtime 本身可内部 refresh。不可提升分片先进入 handleGetOnUnpromotableShard，refresh 标志另走刷新接力；不能把普通分支写成所有部署的规则。不可提升分片的特殊处理

10.5 取回 _source，不等于只拷贝 JSON

Engine 提供存在标记、reader 与文档定位。ShardGetService.innerGetFetch 用 SourceLoader / StoredFieldLoader 取字段，按 _source_includes 等过滤本次输出，最后组装响应。routing 元数据也在这一步回显。源数据启用方式、source mode、请求字段都会影响工作量；本实验明确 stored source、keyword / integer，避免 synthetic / 动态映射干扰。loader 与 routing、source 过滤与结果

translog 路径并不每次都重新分析并建完整内存索引。9.4.0 的 TranslogDirectoryReader 对普通 source 可创建 TranslogLeafReader，直接提供 ID / source 等；synthetic source 或某些额外字段需求才会提前或按需建内存索引。它仍走 reader / fetch 体系，也不能概括为“GET 从不使用 Lucene”或“translog 必比 segment 更慢”。选择 realtime=false 需先接受旧视图，再按真实数据、字段与负载测量性能。普通与 synthetic reader 分支、直接读取 stored source / routing

普通命中响应包括 _version、_seq_no、_primary_term；单独重写同一 ID 时版本递增，实验要对照实际写入响应。REST GET 接收 version / version_type；虽然 Engine 还实现 seqNo / primaryTerm 检查，这个 REST 路由没有解析 if_seq_no / if_primary_term，而且对应 getService 调用传入未指定值。不要把写入的条件更新参数搬到这里。GET 的 seqNo 条件未指定、Engine 冲突检查

实验：先固定数据，再比较视图与落点

前提：自建 ES 9.4.0 / Lucene 10.4.0、单节点、默认 http://localhost:9200，关闭安全且配置本地站点 CORS；其他端点在连接设置中选择，启用安全时需相应索引与监控权限。使用没有匹配模板、默认摄取管道或其他写入 / 刷新任务的本课资源，首次为空。显式 settings / mapping 覆盖本课变量；不用于 serverless 或不可提升分片的分支验证。

本轮源码已核对，真实 API 未实测云端 9200 未连接，现有启动记录显示 ES 9.4.0 被运行时缺少 /proc/self/coredump_filter 阻塞。本轮未执行首次及清理后重做；卡片是固定版本源码预期，不是模拟响应。目录、播放器与控制台请求传递的浏览器检查另行记录。

完整顺序：先核对版本；A1 创建 → A2 等待 → A3–A8 比较未发布数据 → A9–A11 发布与字段过滤 → A12–A14 新旧版本对照 → A15 预期参数错误。B1 创建 → B2 等待 → B3 写入并刷新受影响分片 → B4 / B5 比落点 → B6–B8 对照读取。最后两张 DELETE 点名清理。清理后从版本核对、创建、等待重新开始；不要依赖操作够快。

周期 refresh 已显式设 -1，不保证环境完全没有外部刷新；flush、恢复、后台管理或其他请求也可能改变视图。比较不符时先停止，核对本索引设置和操作记录。A 的新旧视图必须用清理后的完整顺序恢复；B 若两把键同片，GET 不带 routing 可命中，应核对创建版本 / 配置或另选经两卡确认不同片的 routing，同时修改后续请求。单独重复写入会出现 updated / 递增版本，单独重复创建会报资源已存在。

思考题

1. A4 found=true，是否证明 translog 路径命中，且 SEARCH 已可见？

两者都不能推出。实时 GET 可走可用 location，也可内部刷新后读 INTERNAL；EXTERNAL 是否发布另由 A5 / A8 对照。这个 API 响应没报告内部路径，若需区分应另用与版本相符的观测手段。

2. 把 realtime 关掉为什么可能得到 200，而不是 404？

非实时读 EXTERNAL。未发布过文档时可能不存在；发布过第一版、第二版未发布时可返回旧第一版。A12–A14 证明教学预期如何区分，不能只检查 found，应比较 source 与实际版本。

3. routing 改成错误值为什么有时仍能读到？required 能挡住吗？

普通索引按有效键映射有限个 shard；不同键可同片，此时同 ID 的文档可命中。required 只拒绝缺 routing，不能验证字符串是否等于写入值。路由不是授权条件；同 ID 跨不同 routing 分片也可能对应不同文档。

4. 是否可以给 GET 带 if_seq_no / if_primary_term 做条件读取？

本章 REST GET 未解析这两个参数；Engine 有这套能力不等于该路由暴露它。读取可核对 version / version_type；写入的并发条件须回到对应 REST 接口确认，不能按底层字段猜。

5. realtime=false 能否保证“最多一秒旧”，并隔离重查询影响？

不能。refresh_interval 是调度条件，不是可见性截止时间；刷新配置、空闲唤醒、负载、失败和副本状态都会影响结果。分开 get / search 队列也仍共享资源。先定义允许的旧视图、必要的发布 / 等待条件，再实测延迟与性能。

陷阱

把实时误读成“从不 refresh”实时 GET 不依赖周期外部 refresh 才能读取近期写入，但内部安全检查与回退可刷新 INTERNAL。refresh_interval=-1 也只关闭周期调度，不关闭一切刷新。
把 GET refresh=true 当作全索引 _refresh普通分片还需 realtime=false，显式刷新的是所选分片；不可提升分片有另一个处理分支。PUT 的 refresh=true 则用于写入后发布受影响分片，不能混用解释。
遗漏 routing 就必 404要两把有效键落点不同才会找错片；同片可命中。found=false 不触发换副本，required 只检查缺失，resharding 的 stale 处理也不是普通失败轮换。
GET 比 SEARCH 快，所以可以承诺固定成本这是不同读取问题与视图。reader、source mode、字段、缓存、刷新、资源竞争影响实际成本；本章没有性能实测，也没有“最多一秒旧”的保证。
旧实验索引直接重写就能重做旧 EXTERNAL 视图仍可能存在，造成 SEARCH 命中和版本不再为 1。按点名清理 → 创建 → 健康等待 → 完整操作恢复前提，不把已存在 / updated 当成首次响应。
