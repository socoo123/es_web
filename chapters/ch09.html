传输层

节点间二进制协议 · 约 17 分钟 · 前置:第 6、7、8 课 · 7 个实验

学习目标

  • 按 TcpHeader.writeHeader 的字段顺序写出 23 字节固定头的加法,并说出 action 为什么不在固定头里、响应帧为什么不写 action。
  • 把 GetRequest.writeTo 与 GetRequest(StreamInput) 逐字段配对,指出新字段的版本闸门 TransportVersion.fromName("get_split_shard_count_summary"),并解释闸门为什么必须读写两侧成对出现。
  • 用 _cat/nodes 的 port 列与 _nodes/stats/transport 在单节点上验证「传输层存在、但本地路径跳过序列化」,并把地址、计数、并不存在的 _cat/transport 三者分开。

1. 心智模型:HTTP 停在协调节点

第 6 课的 REST 把 GET /tut-l09-docs/_doc/1 解析成 GetRequest;第 7 课靠 action 名 "indices:data/read/get" 找到 TransportGetAction;第 8 课保证 sendRequest 把请求交出去就立刻释放线程。这一课打开那个「交出去」的黑盒:如果目标 shard 在另一个节点上,协调节点不会转发 HTTP——它把 GetRequest 序列化成 ES 自己的二进制帧,发到对方的 Transport 端口(transport.port,默认范围 9300-9399,与 HTTP 的 9200 是两个绑定)。数据节点读帧、执行 GET、把 GetResponse 写成另一帧发回来,协调节点再翻译成你 curl 里看到的 JSON。

为什么节点之间不顺便复用 HTTP?每秒成千上万条小消息的场景下,三件事叠在一起:

要解决的HTTP 做节点间协议ES 二进制帧
开销文本头(Host、Content-Type……),小消息里头比体大固定头 23 字节;length 前缀 6 字节就能切开下一帧
版本字段增减靠约定,滚动升级时新旧节点难对齐StreamOutput 携带 TransportVersion,writeTo 里按版本开关字段
多路HTTP/1.1 一条连接一请求一响应,要多路得换 HTTP/2每条消息一个 long requestId,一条 TCP 上并发无数请求

一个容易混淆的数字:「切帧前缀」只有 6 字节('E''S' + 4 字节 length,即 TcpHeader.BYTES_REQUIRED_FOR_MESSAGE_SIZE),它只负责把流切成一帧一帧;整颗固定头是 23 字节。两个数都对,但不是一句话。

3. 帧布局:23 字节固定头 + 可变头 + body

先把最容易读错的一点钉死:action 字符串不在固定头里。固定头每段都是定长:

2(魔数) + 4(length) + 8(requestId) + 1(status) + 4(version id) + 4(可变头长度) = 23

action 在固定头之后的可变头里,而且只有请求帧才写。固定头定长的意义是偏移量恒定:接收端还没收齐可变头时,就已经能从固定头里拿到 requestId 和 TransportVersion 做该做的事。

写出侧与读出侧互为镜像。发送在 OutboundHandler.serialize:先把 23 字节空出来,写可变头和 body,最后回到偏移 0 用 TcpHeader.writeHeader 回填(length 此时才知道该填多少);接收在 InboundDecoder.readHeader:先用前 6 字节拿到 length,再从 offset 6 起读固定头剩余部分,最后 finishParsingHeader 读可变头。固定头的写法:

public static void writeHeader(StreamOutput output, long requestId, byte status,
        TransportVersion version, int contentSize, int variableHeaderSize) throws IOException {
    output.writeBytes(PREFIX);              // 'E' 'S'
    // length = 这一行之后的所有字节:body + requestId + status + version + 可变头
    output.writeInt(contentSize + REQUEST_ID_SIZE + STATUS_SIZE + VERSION_ID_SIZE + VARIABLE_HEADER_SIZE);
    output.writeLong(requestId);            // 8B
    output.writeByte(status);               // 1B
    output.writeInt(version.id());          // 4B
    output.writeInt(variableHeaderSize);    // 4B
}

serialize 里与 action 相关的关键行——只有请求方向才写名字:

byteStreamOutput.skip(TcpHeader.HEADER_SIZE);   // 空出 23 字节
threadContext.writeTo(byteStreamOutput);        // 可变头:ThreadContext
if (messageDirection == MessageDirection.REQUEST) {
    byteStreamOutput.writeString(action);       // 请求帧才写 action
}
// body:writeable.writeTo(stream);最后 seek(0) 回填固定头

status 这 1 个字节用低 4 个 bit 当标志位,不是字符串 flags:

bit含义普通 GET 请求帧
0 STATUS_REQRES0 = 请求,1 = 响应0
1 STATUS_ERROR响应是否携带异常(body 走 writeException)0
2 STATUS_COMPRESSbody 是否压缩多数情况 0(见下)
3 STATUS_HANDSHAKE是不是握手消息0

压缩是可选的,不是「每帧都压」:transport.compress 默认 INDEXING_DATA(有索引数据才压),transport.compression_scheme 默认 LZ4——实验 5 可以现场核对。

魔数还兼职挡误接。TcpTransport.readHeaderBuffer 看前两个字节是不是 'E''S':不是,就按开头几个字节猜对方在说什么——像 HTTP 方法就抛 HttpRequestOnTransportException("This is not an HTTP port"),像 0x16 0x03 就提示「TLS 打到了没开 TLS 的口」。抓到 HTTP 误打时,不会回一份 JSON 400:onException 把这句话的 UTF-8 字节直接写回 socket,然后关连接(思考题 1)。

最后是 keep-alive 特例:PING 只有 6 字节,'E''S' + int(-1),没有 requestId、没有 action、没有 body。解码器看到 length 为 -1 就按 PING 消耗 6 字节;业务帧的 length 必须 > 0,且不能超过本节点堆的某个比例上限。

4. Writeable:body 里的字段必须成对出现

body 的契约在 Writeable 接口——javadoc 的原话是,实现它就是为了「thrown across the wire」:

public interface Writeable {
    void writeTo(StreamOutput out) throws IOException;   // 接口里没有 readFrom
}
// 读侧按约定是 Xxx(StreamInput) 构造函数:GetRequest::new 就是一个 Reader

没有公共的 readFrom;可空字段走 readOptionalString / readOptionalWriteable,Reader 不允许返回 null。GetRequest 继承自 SingleShardRequest,读写都要先 super(父类写 internalShardId、index),然后才是自己的字段——顺序就是线上的字节顺序:

public GetRequest(StreamInput in) throws IOException {
    super(in);                                   // internalShardId, index
    id = in.readString();                        // 1
    routing = in.readOptionalString();           // 2
    preference = in.readOptionalString();        // 3
    refresh = in.readBoolean();                  // 4
    storedFields = in.readOptionalStringArray(); // 5
    realtime = in.readBoolean();                 // 6
    versionType = VersionType.fromValue(in.readByte());            // 7
    version = in.readLong();                     // 8
    fetchSourceContext = in.readOptionalWriteable(FetchSourceContext::readFrom); // 9
    forceSyntheticSource = in.readBoolean();     // 10
    if (in.getTransportVersion().supports(SPLIT_SHARD_COUNT_SUMMARY)) {
        splitShardCountSummary = new SplitShardCountSummary(in);   // 11:有版本闸门
    }
}
// writeTo 逐字段同序镜像;闸门在写侧也是同一个 supports(...)
顺序字段线上方法备注
superinternalShardId / indexwriteOptionalWriteable / writeOptionalString父类先走
1idwriteString文档 _id
2routingwriteOptionalString可空
3preferencewriteOptionalString可空
4refreshwriteBooleanGET 前 refresh?
5storedFieldswriteOptionalStringArray可空数组
6realtimewriteBoolean第 10 课的主角
7-8versionType / versionwriteByte / writeLong乐观并发控制

10forceSyntheticSourcewriteBoolean
11splitShardCountSummary仅当版本闸门通过见下

第 11 个字段的闸门是具名版本,不是和发行号绑死:

private static final TransportVersion SPLIT_SHARD_COUNT_SUMMARY =
    TransportVersion.fromName("get_split_shard_count_summary");

9.x 的趋势是给序列化版本起名字、用 supports(...) 判断,而不是 onOrAfter(V_8_7_0) 那种「发行号 = 协议号」。滚动升级时,新旧节点各按自己一侧的 TransportVersion 决定写不写、读不读这一段,缺闸门的一侧两边都跳过,字节流才对得齐——这也是闸门必须读写两侧成对出现的原因:只在 writeTo 加字段、忘了构造函数,对端下一个 readBoolean 就会吃到半截 UTF-8。

最后看一眼 StreamOutput 的原语为什么要那么多样:writeVInt 对小于 128 的非负整数走单字节快路径(负数反而总占 5 字节,注释建议负数改用 writeInt);writeString 先写 VInt 长度再写 UTF-8 字节。文档数、数组长度、字符串长度多数很小,所以 "indices:data/read/get[s]" 的长度前缀通常只占 1 字节——这是二进制协议相对 HTTP 文本头的另一处省。

5. 调用链:往程认 action,回程认 requestId

把图 1 的「写出帧」展开。TransportGetAction 自己不发请求,基类 TransportSingleShardAction.AsyncSingleAction.perform 才发,而且 action 不是主名,是 actionName + "[s]":

this.transportShardAction = actionName + "[s]";        // "indices:data/read/get[s]"
transportService.registerRequestHandler(
    transportShardAction, EsExecutors.DIRECT_EXECUTOR_SERVICE, request, new ShardTransportHandler());

对 GET 来说,线上那串就是 "indices:data/read/get[s]";主名 "indices:data/read/get" 的 handler 留给「请求已经在目标节点上」的执行。注意注册的执行器是 EsExecutors.DIRECT_EXECUTOR_SERVICE——和第 8 课 search 的 query handler 一样,先在传输线程上把请求接住,真正占 get 池的是后面的 asyncShardOperation → getExecutor(shardId).execute(...)。「谁从 TCP 接住」和「谁执行 shard 操作」是两层。

发送侧,TransportService.sendRequestInternal 做三件和帧直接相关的事:一是 responseHandlers.add(handler, connection, action) 拿到 requestId(一个 AtomicLong 递增,把 id 映射到「回来之后调谁」);二是可选超时,到期从那张 map 里 remove 并回调异常;三是 connection.sendRequest(requestId, action, request, options)——远程连接走进 OutboundHandler,就是 § 3 的 serialize。

数据节点这一侧:TCP 字节先进 InboundPipeline(TCP 是流,一帧可能拆成多次到达,pending 队列负责拼碎片),InboundDecoder 按 § 3 剥头,InboundAggregator 等内容收齐后交给 InboundHandler.messageReceived。它看 status 的请求/响应位:请求就 requestHandlers.getHandler(action),用登记时的 reader(就是 GetRequest::new)重建对象,交给 ShardTransportHandler → asyncShardOperation 进 GET 池,做完 channel.sendResponse(response);响应就用 requestId 从发送侧那张 map 里 remove,调当初挂上去的 listener。

RequestHandlers 就是「action 字符串 → handler 注册表」。同一个名字登记两次,启动期直接 IllegalArgumentException: transport handlers for action … is already registered——和第 7 课 ActionModule 按 ActionType 名去重是同一思想在传输层的副本:名字是身份证,冲突在启动时炸,不拖到第一帧。

本节点是这条链的捷径。shard 恰好在接到 HTTP 的节点上时,getConnection 返回 localNodeConnection,它的 sendRequest 直接 sendLocalRequest:按 action 取同一个注册表,在 DIRECT 上当场调用,或丢进登记时的线程池。对象还是那个 GetRequest,不走 writeTo、不过 TCP;但 requestId 照样登记——本地和远程共用一套「按 id 找回调」的模型。省的是序列化和系统调用,不是省略回调机制。单节点上你做的几乎每一次 GET 都走这条捷径,所以实验 4 里传输计数全是 0。

6. 连接画像与两层握手

一对节点之间不是一条 TCP 了事。ConnectionProfile.buildDefaultConnectionProfile 按 TransportRequestOptions.Type 分组建连,默认值在 TransportSettings(全部 NodeScope,启动时钉死):

Type设置 key默认条数用来干什么
RECOVERYtransport.connections_per_node.recovery2(非数据节点 0)分片恢复,大块文件
BULKtransport.connections_per_node.bulk3批量写入
REGtransport.connections_per_node.reg6常规:搜索、GET、多数 action
STATEtransport.connections_per_node.state1(非 master-eligible 0)集群状态发布
PINGtransport.connections_per_node.ping1keep-alive

master + data 节点对一个对端:2+3+6+1+1 = 13 条(实验 5 可核对)。注意这是「连接远端时按画像一次建满」的上限——单节点没有对端,出站连接自然是 0。GET 走 REG 组(组内 round-robin)。既然 requestId 已经能在同一条连接上多路,为什么还要分组建多条?因为应用层多路救不了 TCP 队头阻塞:恢复在灌 segment 时,不能让 GET 的小帧排在同一条 socket 的内核发送队列后面几秒;多条 REG 还能让多个 Netty worker 并行读。分类型解决的是优先级和调度,不是「二进制不会多路」(思考题 3)。

新 TCP 连上之后,还不能立刻发业务帧,要先过两步握手:

  1. TCP 层,TransportHandshaker,action "internal:tcp/handshake":双方交换能接受的 TransportVersion,之后 OutboundHandler 用 min(本地, 远端) 写后续业务帧。握手本身用两个特殊的协议 id(常量 V8_HANDSHAKE_VERSION / V9_HANDSHAKE_VERSION)——它们只是「碰巧」落在帧头 version 那个位置,已经不再表达「发行号 = 协议号」。
  2. 传输服务层,TransportService.handshake,action "internal:transport/handshake"(和上一步不是同一串名字):响应带回 DiscoveryNode、ClusterName、Version、build hash。默认校验集群名匹配、对端身份等于你以为在连的那个节点、发行版本兼容(CCS 连远程集群时刻意放宽为不比集群名)。失败就关连接——先对齐「怎么说话」,再对齐「你是不是我要连的人」。

身份对不上时的报错会提到 publish address:每个节点必须有网络可达的发布地址,否则「连错人还继续写业务帧」。这是运维上最常见的握手失败,和序列化无关。

清理

思考题

1. 对 Transport 端口发一个 HTTP GET,响应是什么形态?为什么不是 JSON 400?

纯文本 This is not an HTTP port,然后断开连接——curl 会抱怨收到「不像 HTTP 的响应」(连状态行都没有)。前两字节是 'G''E' 不是 'E''S',TcpTransport 的 appearsToBeHTTPRequest 认出方法名后抛 HttpRequestOnTransportException,onException 把异常消息的 UTF-8 字节 sendBytes 出去就关 socket——REST 层那套把异常渲染成 JSON 的机制在 Transport 口根本不存在。它同样能认出 TLS(0x16 0x03)。浏览器做不了这个实验(Transport 口没有 CORS),所以它是思考题而不是动手实验。

2. 响应帧为什么不带 action、只靠 requestId 对号?如果 action 挪进固定头、定长 64 字节,会破坏什么?

两个并发 GET 的 action 字符串完全一样,按名字匹配会把别人的 GetResponse 交给错误的 listener;按 requestId 从 map 里 remove 才是 O(1) 且无歧义的。响应不写 action(收端填 NO_ACTION_NAME_FOR_RESPONSES)是因为回程不需要再查 handler 表。action 放可变头,固定头才能保持定长:requestId 永远在 offset 6、version 永远在 offset 15——解码器在可变头还没收齐时就需要 version 做兼容判断。action 改成定长 64 字节虽然也「偏移确定」,但每帧都要为短名字白付几十字节的空洞,还要给所有 action 名定长上限,变长字符串放可变头正是为了让这两层互不干扰。

3. 已经有 requestId 做应用层多路,为什么还要 5 类、默认 13 条 TCP?为什么不干脆上 HTTP/2?

requestId 解决的是同一条 socket 上的并发;多条连接解决的是不同优先级的流量别排进同一个 TCP 发送队列。恢复灌 segment 时,GET 的小帧排在同一条 socket 后面等几秒,是内核发送队列的队头阻塞,应用层 id 救不了;多条 REG 还能让多核的 Netty worker 并行读。HTTP/2 能多路,但仍是文本语义 + HPACK + 一套和 TransportVersion.supports 完全不同的演进模型,还得把整个 Writeable 生态换成别的序列化——「能多路」只是节点间协议要解决的问题之一。

4. 本节点跳过 writeTo,换来的是什么?「单节点测试绿了、多节点才炸」的序列化错位,付出的代价具体在哪?

换来零拷贝、零 UTF-8 编解码、零版本闸门判断:单节点快,本地语义就是普通方法调用,回调模型还和远程统一(照样登记 requestId)。代价是不出进程的路径永远不执行 GetRequest.writeTo:给对象加个字段、只改了内存路径的代码,单节点全绿;第一对跨节点(尤其跨版本)之间,字段错位才在字节流上炸出来——典型症状是对端某个 readBoolean 吃到半截 UTF-8。所以闸门和字段必须严格成对地写在 writeTo 和 Xxx(StreamInput) 里,不能指望测试替你发现。

陷阱

🕳 「消息头 6 字节」:6 只是切帧前缀('ES' + length);固定头是 23 字节,而且 action 不在其中——它在后面的可变头里,响应帧甚至不写。把 6 和 23 混成一句话,读偏移量必错。
🕳 「节点间就是转发 HTTP」:跨节点那一跳没有 URL 也没有方法;对 Transport 口误发 HTTP,得到的是纯文本 This is not an HTTP port 加断连,不是 JSON 400——别拿 REST 的报错形态去套 Transport 口。
🕳 单节点传输计数是 0 ≠ 传输层没事:本地路径走 localNodeConnection,连 writeTo 都不执行,计数自然不动;13 条也是「连远端时才建」的画像上限。真正的暗雷:序列化 bug 在单节点上永远不触发。
🕳 「加字段就改 writeTo 一行」:构造函数不同步加读取、或版本闸门只写在一侧,对端下一个 readBoolean 就吃到半截 UTF-8。字段与闸门必须读写两侧成对出现,错位是静默的。
