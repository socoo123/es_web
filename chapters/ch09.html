跨节点后，请求如何回来？ · 约 22 分钟 · 前置：第 6、7、8 课 · 2 组实验 / 12 张操作卡 · 2 幅交互图（2 幅路径动画）· 0 个机制播放器

HTTP 请求在入口节点变成动作对象。目标分片在远端时，Transport 传递带编号的二进制帧：请求按 action 找处理器，响应按 requestId 找回调。本课把帧格式、版本契约、本地捷径与统计边界连起来，说明一个 GET 成功究竟验证了什么。

  • 分别观察绑定 / 发布地址、默认连接画像与同节点统计基线，说明单节点实验的证明范围。

1. 节点之间传的还是 HTTP GET 吗？

客户端向 HTTP 端点发送 GET /tut-l09-docs/_doc/1，入口节点解析请求、选择分片副本。分片在另一节点时，GET 基类发送的是 GetRequest 对象与子动作名 indices:data/read/get[s]；节点间这一跳不把原 HTTP URL 转发给对端的 RestController。数据节点执行后，经 Transport 响应回到原节点，再由入口层组织 HTTP 响应。默认 transport.port 是 9300-9399 范围；本课 HTTP 端点为 http://localhost:9200，实际端口以绑定与发布配置为准。

发起方先把响应处理器登记到 responseHandlers，获得递增的 requestId，然后才调用 connection.sendRequest。登记项保留原 handler、连接和 action；相同 action 的两个并发 GET 由不同编号区分。远端按 action 找 RequestHandlerRegistry，用其 Reader 重建请求。回程不需要再用 action 选业务处理器：按编号移除登记项，使用原 handler 的 Reader 读响应，调用 handleResponse。依据：sendRequestInternal、ResponseHandlers.add / onResponseReceived、请求查表与 Reader、响应 Reader 与回调。

GET 的主动作和 [s] 子动作都能登记 handler；主动作处理完整 GET 的路由流程，并不只用于“已经在目标节点”的请求。子动作处理选中的分片。两者注册为 DIRECT，普通分片操作在 asyncShardOperation 中再提交到 get executor；系统索引可另选执行器。响应反序列化和回调也受 handler.executor() 控制。不能从“sendRequest 是异步接口”推断它必立即返回、必切线程或完全没有当前线程成本。见 登记与分片调度、普通 / 系统索引 executor。

编号也有生命周期：配置了请求超时才安排超时处理；超时、发送失败或断连会移除相应登记。远端操作不因本地不再等待而自动取消，晚到响应可能已经找不到 handler。单个编号对回调，不等于无限在途请求、无限缓冲或业务“恰好执行一次”。见 TimeoutHandler.run。

2. 6 字节与 23 字节，各解决什么？

TCP 给的是字节流，一帧可能分多次到达，也可能与其他帧连在一次读取里。普通业务帧开头的 'E''S' 与 int length 共 6B，告诉切帧逻辑后续消息的长度。固定头总计 23B，另有编号、标志、协议版本与可变头长度；它不是完整消息，也不包含 action。

固定头偏移字段 / 字节职责
0'E''S' / 2B识别 Transport 格式
2length / 4B全帧长度减去前 6B
6requestId / 8B对回程编号
14status / 1B请求 / 响应、异常、压缩、握手标志
15version.id / 4B本帧 TransportVersion
19variableHeaderSize / 4B可变头长度

加法为 2 + 4 + 8 + 1 + 4 + 4 = 23。固定头之后先写 ThreadContext 头部；普通请求再写 action，响应不写 action，由读端填内部响应名称。body 才是请求 / 响应对象的序列化数据，错误响应走 writeException。关键代码：固定头常量与 writeHeader、finishParsingHeader。

写侧预留固定头，写完可变头和 body，知道总大小后再回填。可选压缩包住 body，不压整个固定头与 action。读侧先切帧，再解析固定 / 可变头，随后按 action 找 Reader；Reader 的 stream 必须使用本帧协议版本。依据：serialize 的写出与回填、body 序列化与可选压缩、readHeader。

展开：标志位、PING 与错误端口

status 低四位分别标识响应、异常、压缩和握手；请求 / 响应位为 0 是请求，为 1 是响应。TransportStatus。应用层 PING 是 6B 特例：'ES' + int(-1)，无编号、action 或 body。它与操作系统 TCP keepalive 不是一回事；普通业务帧 length 必须正数，并受本节点最大堆约 30% 的长度检查。PING 常量与字节、readHeaderBuffer。

向未启用 Transport TLS 的普通 Transport 口误发 HTTP，源码识别方法前缀后发送 This is not an HTTP port 原始 UTF-8 消息并关闭连接，不是 REST 的 JSON 400。TLS 或其他协议前置处理会影响实际结果；本课不让浏览器把它当 HTTP 实验，也不把问题仅归因于 CORS。见 HTTP 误接处理。

3. 加一个字段，为什么必须改两侧？

Writeable.writeTo 是写侧契约，读侧通常为接受 StreamInput 的构造函数，也可以是静态 Reader。接口没有强制统一的 readFrom 方法名；可空值使用 optional 方法，Reader 本身不应返回 null。父类先写、子类接着写，读侧顺序完全镜像，不能依靠字段名从流里跳到任意位置。见 Writeable 与 Reader。

GetRequest 的本层顺序读写原语
先 super父类链；SingleShardRequest 有可选 internalShardId、index
id → routing → preferenceString → OptionalString → OptionalString
refresh → storedFields → realtimeBoolean → OptionalStringArray → Boolean
versionType → versionByte → Long；GET 的读版本条件
fetchSourceContext → forceSyntheticSourceOptionalWriteable → Boolean
splitShardCountSummary通过同一具名版本闸门才读 / 写

这是本层顺序概览，不是整个对象的全部字节；更上层父类同样有契约。新字段的闸门是 TransportVersion.fromName("get_split_shard_count_summary")，两侧都按 stream.getTransportVersion().supports(...) 判断。使用的是本次传输格式，不能让两端各用自己的发行号独立猜测。具名版本还可覆盖回移补丁，supports 不应简单改写为所有场景下的发行号比较。见 GetRequest 构造函数 / writeTo、父类读取、设置 body stream 版本、supports 与补丁分支。

只写不读、顺序不同、或只在一侧加闸门，都会破坏契约；表现可能是反序列化异常、读后残留字节或错误值，不能保证“静默错位”，也不能固定成“下一次 readBoolean 吃到 UTF-8”。一个容易忽略的细节：writeString 的 VInt 长度是 Unicode code units（Java char 数），不是 UTF-8 字节数；ASCII action 名两者才相等。非负整数小于 128 的 writeVInt 可用 1B，负数会用 5B。依据：writeVInt、writeString 长度定义。

4. 单节点 GET，能验证线上的帧吗？

目标就在本节点时，getConnection 返回 localNodeConnection；它调用 sendLocalRequest，直接传请求对象给同一 handler 表，按登记的 executor 执行。回程也使用 DirectResponseChannel。请求编号和响应处理器仍登记，但这一跳不走请求 / 响应的 wire 编解码或 TCP，DIRECT 分支可就在当前线程接续。它节省了该跳的网络和序列化工作，不能扩成整个请求“零拷贝、零分配”。见 localNodeConnection、getConnection、sendLocalRequest。

观察量源码口径怎样读
server_open当前 acceptedChannels 数量即时网络通道快照
total_outbound_connections累计成功建立的 NodeChannels 连接组数不是当前打开的 socket 数，也不是 13 个通道
rx_count / tx_count本节点网络消息累计统计同节点取前后基线；不是按 HTTP 请求 / 索引分账

计数口径来自 getStats 和 成功建连后的累计值，收发累计见 StatsTracker。安静的单节点可观察到全零，已有探测、历史连接或其他流量时也可非零；本地 GET 不增加该网络统计，不能据此断言整个节点没有网络流量。删除索引不会归零计数；节点重启或基线节点 ID 变化则重新记录。

地址也要分口径。CAT 的 port 虽描述为 bound transport port，实现取 DiscoveryNode 的发布地址端口；http_address 取 HTTP 发布地址。用 _nodes/_local 的 bound_address 与 publish_address 分别核对监听和公布地址，不能固定猜 9300 / 9200。见 CAT 地址的实际取值；A3 使用 NodesInfo 的节点 / metric 路由。

本课 B4 → B5 → B6 把 GET 的前后值分开保存。这个实验支持本地路径解释，不能验证远程字段兼容，更不能证明没有序列化 bug。需要远端分片与真正的 wire / 混合版本测试才能验证那些路径。本章没有把两节点抓包或压测结果当作本轮证据。

5. 为什么一对节点要多条连接，还要两层握手？

requestId 区分同一连接上的在途调用；连接画像按工作类型分配 TCP 通道。把恢复大流量和普通请求放在不同通道，可减少共用一个 TCP 流的排队，但仍共享 CPU、内存与网络资源，不保证零等待。无覆盖的默认自管 9.4.0 画像如下，角色条件指本地发起节点：

Type默认通道数画像条件
RECOVERY2本地可承载 data；否则画像为 0
BULK3批量请求
REG6默认普通请求类型，包括本课 GET
STATE1本地 master-eligible；否则画像为 0
PING1请求类型分组；不等于定时 PING 已开启

同时满足 data 和 master-eligible 且无覆盖时，默认画像合计 13 个通道；设置覆盖、专门的单通道画像与远程集群连接都可能不同。13 不构成整个节点连接总量上限。默认 transport.compress=INDEXING_DATA 按消息是否具有索引数据能力选择压缩，compression_scheme=LZ4；ping_schedule=-1 禁定时应用层 PING，不等于关闭 TCP keepalive。这些设置只标 NodeScope，不带 Dynamic；cluster settings 的 defaults 可含响应节点本地配置，不能当成当前连接的实测画像。见 端口、压缩与 ping 默认设置、连接默认数、角色修正后的画像、按请求类型选通道、defaults 的合成来源。

TCP 通道建好后，低层 internal:tcp/handshake 交换 TransportVersion 并协商兼容格式；9.4.0 还会考虑对端版本是否已知与 bestKnownVersion，不能概括成所有情况都取简单 min。连接组复用协商结果，握手协议本身的特殊 ID 不等于发行号。随后服务层 internal:transport/handshake 返回 DiscoveryNode、ClusterName、Version 与 build hash，校验版本与调用者提供的集群名谓词；connectionValidator 还核对预期节点身份，但它使用 Predicates.always()，并非所有建立连接都强制比较集群名。默认 handshake 重载使用集群名相等谓词，具体连接流程必须看调用点。见 低层版本协商、连接组握手、节点身份校验、服务层握手与谓词。

思考题

1. 两个 GET action 相同，为什么响应不会交给同一个 listener？

每次发送先登记不同 requestId，响应按编号取出原 handler。action 选请求处理器，编号选这一轮回调；它们的粒度不同。响应不写 action。

2. 6B 前缀够切帧，为什么还需要 23B 固定头？

length 决定普通帧边界；后续固定字段提供编号、标志、协议版本和可变头长度。action 位于可变头。PING 才是没有其余内容的 6B 特例。

3. 本地 GET 成功、rx/tx 无增量，能说明新字段兼容旧节点吗？

不能。本地捷径不走 wire 编解码。兼容需要同一 stream 版本下的读写镜像与闸门，并实际覆盖远程 / 混合版本路径；零增量只是一项观测。

4. total_outbound_connections=1 与默认 13 个通道冲突吗？

不冲突。前者累计成功建立的连接组，后者是特定默认画像中一个组的通道数。还要区分当前已接受通道、累计建连和角色修正后的配置。

5. 握手版本一定等于两端发行号的较小者吗？集群名必比较吗？

TransportVersion 与发行号分工不同，协商有兼容性与已知版本分支。服务层的集群名判断由传入谓词决定；默认重载比较集群名，connectionValidator 使用 always 并另核对节点身份。

陷阱

🕳 编号多路不等于无限并发：登记表、缓冲、执行池与网络都消耗资源。协议能区分回调，不提供无限容量或恰好一次的业务保证。
🕳 设置与实际连接混算：defaults 可含本地配置，画像按角色再修正；13 是一组通道数，不是累计连接组指标或整节点上限。
🕳 单节点计数必须零：历史和其他流量可使总值非零。先取同一节点基线，读差值；本地路径成功不验证序列化兼容。
🕳 所有帧都一样：普通请求有 action，响应没有；PING 仅 6B，特殊握手另有格式。固定头不是完整消息。
🕳 错位固定静默发生：漏字段、顺序与闸门不匹配可造成多种错误；读侧会检查消费情况。源码核对与 wire 测试都要覆盖。

问题记住的边界
