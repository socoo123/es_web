学习目标

1. 心智模型:一篇文档的四种时刻

第 13 课把文档送到了主分片门口。门里是谁?是一个 Engine——单个分片的存储抽象,管着 Lucene 的 IndexWriter、预写日志 translog、两套 searcher 和一张 LiveVersionMap。忘掉类名,先看一篇 _id=1 的文档写入后依次经历的四种时刻:

3. index():先 Lucene,后 translog

这是 ES 最核心的写入路径。当前仓库(9.4.0)的顺序不是教科书里「先写 WAL 再改数据结构」的排列:

// InternalEngine.java — index() 成功路径(省略 seqNo 生成与节流)
if (plan.indexIntoLucene || plan.addStaleOpToLucene) {
    indexResult = indexIntoLucene(index, plan);            // ① 先 Lucene
}
if (index.origin().isFromTranslog() == false) {
    if (indexResult.getResultType() == Result.Type.SUCCESS) {
        location = translog.add(new Translog.Index(index, indexResult)); // ② 再 translog
    } else if (indexResult.getSeqNo() != UNASSIGNED_SEQ_NO) {
        location = innerNoOp(noOp).getTranslogLocation();  // 失败也要占住 seqNo
    }
    indexResult.setTranslogLocation(location);
}
final Translog.Location translogLocation =
    trackTranslogLocation.get() ? indexResult.getTranslogLocation() : null; // 默认 null
versionMap.maybePutIndexUnderLock(index.uid(), new IndexVersionValue(...));

四件必须钉死的事实:

一,version 检查在 Lucene 之前。indexingStrategyForOperation 在 primary 上走进 planIndexingAsPrimary:带外部 version 或 if_seq_no 时先 resolveDocVersion,冲突则直接跳过,根本碰不到 IndexWriter。同一 uid 的并发修改靠 versionMap.acquireLock(index.uid()) 串行。

二,Lucene 这一步仍是内存语义。indexIntoLucene 按计划调 indexWriter.addDocuments(append)或 indexWriter.softUpdateDocument(软删除旧 uid 再加新文档)。EXTERNAL searcher 还看不见它。

三,translog.add 在 Lucene 成功之后。这样 Lucene 文档级失败时,translog 记下的是一条 NoOp 而不是一条「索引里其实没有」的 Index——seqNo 已经发出去了,空洞比脏日志更难收拾(思考题 2 展开)。

四,VersionMap 里的 translog location 经常是 null。trackTranslogLocation 是个默认 false 的 AtomicBoolean;第一次 realtime GET 撞上「命中但 location 为空」才把它打开(见第 7 节)。

append 优化:POST /idx/_doc 自动生成 _id 时,若 canOptimizeAddDocument 成立,走 optimizedAppendOnly:跳过 VersionMap 查找直接 addDocuments。重试或副本乱序会抬高 maxUnsafeAutoIdTimestamp,后续退化为完整路径。本课实验都用显式 _id。

4. translog:耐久性,不是搜索可见性

IndexWriter 的新文档在内存里;就算 refresh 落出了 NRT segment,没 commit 掉电仍会丢。translog 补的就是这块缺口:每个未 commit 的操作记一份,崩溃后按 seqNo 重放。它在磁盘上的布局(Translog 类注释):

${shard_path}/translog/
├── translog-1.tlog      # 已滚动、只读的那一代
├── translog-1.ckp       # 该代的 checkpoint 副本
├── translog-2.tlog      # 当前正在写的 generation
└── translog.ckp         # 当前 checkpoint(单盘块写入,视为原子)

当前 writer 写到 index.translog.generation_threshold_size(默认 64MB)或 primary term 变化就 rollGeneration():旧 .tlog 冻结为只读,新文件接着写。滚动不是 flush——flush 才 commit 并裁掉不再需要的 generation。

translog.add 只保证写进文件(进程读得到),不保证已 fsync。耐久时机由 index.translog.durability 决定:

设置默认回 201 之前做什么掉电窗口
durability = request是默认AsyncAfterWriteAction 调 syncAfterWrite → ensureSynced已成功的请求不应丢
durability = async需显式打开不在这条请求上 fsync最多约一个 sync_interval(5s)

所以在默认配置下,「写入已持久化」指的是 201 返回时 translog 已 fsync;Lucene commit 可能几分钟之后才发生。SEARCH 能不能看见,和这张表毫无关系。未 commit 的量在 _stats 里看,字段名以 TranslogStats.toXContent 为准:operations、size_in_bytes、uncommitted_operations、uncommitted_size_in_bytes——没有叫 uncommitted 的短键。uncommitted_* 统计的是 safe commit 的 local checkpoint 之后那些 generation(Translog.stats() 用 minGenerationForSeqNo(localCheckpointOfSafeCommit + 1)),refresh 不推进 commit,所以只 refresh 它掉不下去——实验 2、3 就是用数字打这句话。

5. refresh:换 searcher,不碰磁盘

refresh 的对象是 searcher,不是 commit 点。Engine.refresh(source) 在 InternalEngine 里被钉死为 EXTERNAL、阻塞:

@Override
public RefreshResult refresh(String source) throws EngineException {
    return refresh(source, SearcherScope.EXTERNAL, true);   // 对外 refresh
}
protected final RefreshResult refresh(String source, SearcherScope scope, boolean block) {
    ReferenceManager<ElasticsearchDirectoryReader> referenceManager = getReferenceManager(scope);
    if (block) referenceManager.maybeRefreshBlocking();     // Lucene NRT:打开看得见新文档的 reader
}

两套 searcher 不要混:

SearcherScope谁在用何时换新 reader
EXTERNALSEARCH;GET ?realtime=false定时 refresh_interval、手动 _refresh、refresh=wait_for
INTERNALrealtime GET 的后备;引擎自己的 version 查找内部 refresh(realtime_get、version_table_flush)

ExternalReaderManager 的实现是:先让 INTERNAL maybeRefreshBlocking(),再把那份 reader 偷过来给 EXTERNAL——一次对外 refresh,内部一定已追上;反之只做内部 refresh,SEARCH 仍看不见。LiveVersionMap 实现了 RefreshListener,refresh 后 afterRefresh 丢掉已被新 searcher 接住的条目:VersionMap 不是缓存,只盖「searcher 还没接住的那一小段」。tombstone(删除)按 index.gc_deletes(默认 60s)单独过期。

🕳 refresh_interval=-1 不是「实时」,是关掉定时:0 才是每次写入都试图 refresh——高写入下会制造大量小 segment,文件描述符和 merge 一起炸。想「写完立即可读」,GET 本来就是实时的,轮不到 refresh。

6. flush:commit 之后,才能裁 translog

Engine.flush(force, waitIfOngoing) 走到 InternalEngine.flushHoldingLock,按图 3 的顺序执行。commitIndexWriter 往 Lucene commit user data 里写 translog_uuid、local_checkpoint、max_seq_no——下次崩溃恢复从最后一个 commit 打开 Lucene,只重放其后的 translog。这也解释了 uncommitted_operations 的语义:还没被 commit 覆盖、崩溃后必须重放的那些操作。

为什么 commit 之后还要 refresh("version_table_flush")?VersionMap 里的条目可能挂着旧 generation 的 translog location,generation 被 trim 之后再按 location 去读会读空。内部 refresh 让 INTERNAL searcher 接住这些文档,afterRefresh 丢掉相关条目,后续 GET / version 检查走 Lucene,不再指向已删除的 .tlog。

定期 flush 的阈值,以 9.4.0 的 IndexSettings 为准,不要背旧博客:

触发默认(9.4.0)作用
index.translog.flush_threshold_size10GB,且与磁盘总量的 1% 取小(下限 10MB)未 commit translog 体积触发
index.translog.flush_threshold_age1 分钟距上次 flush 的时间触发
POST /<index>/_flush手动(wait_if_ongoing 默认 true)实验 3 用
节点关闭 / 快照前内部保证留有一个安全 commit

shouldPeriodicallyFlush 看的是未 commit translog 的 generation 体积和上次 flush 时间,不是 IndexWriter 堆缓冲——refresh 再勤,这两个阈值也不会因为「已经可搜索」而清零。

一次没 flush 到 0?rest api 测试 20_translog.yml 在写一条后断言 uncommitted_operations: 1,flush 两次之后才断言 0——第二次是为了让 global checkpoint 跟上、形成 safe commit。本地 1 主 0 副本往往一次就够;若没掉到 0,再 flush 一次,不要改预测。

7. Engine.get:与第 10 课对齐

读取侧第 10 课已走完整链路,这里只钉死和本课时间线有关的三句:

一,InternalEngine.get 在 realtime==true 时走 realtimeGetUnderLock;否则只读 EXTERNAL searcher——未 refresh 就是 found: false。二,VersionMap 是第一站(current → old → tombstones → archive),命中且 getLocation() != null 才 translog.readOperation。三,因为 trackTranslogLocation 默认 false,第一次 realtime GET 常撞上「命中但 location 为空」:此时 trackTranslogLocation.set(true),refreshIfNeeded("realtime_get") 推 INTERNAL searcher 从段里读;之后的写入才带 location,后续 GET 才稳定走 translog。另外,只加 ?refresh=true 而 realtime 仍为 true,不会在 GET 上触发外部 refresh——第 10 课踩过的坑,不重复踩。

8. 段合并:后台的清道夫

refresh 几乎每次都留下新的小 segment。Lucene 在后台把小段合成大段:搜索打开的文件变少,被软删除的旧文档在合并时物理丢掉。代价是 CPU 和磁盘带宽;合并落后时 InternalEngine 的 IndexThrottle 会经 throttle.acquireThrottle() 卡住写入线程——这是背压,不是错误。POST /<index>/_forcemerge?max_num_segments=1 能把段数打到 1,只适合归档后的只读索引;写入还在继续时强制合并,成果立刻被新写入拆散。策略细节(tier、floor segment)是 MergePolicy 的事,本课不展开。

持续 index + refresh变多仍占空间(软删除)通常否
后台 merge变少合并时回收落后时 IndexThrottle
_forcemerge可打到 1尽量回收很重,别当例行

思考题

1. refresh_interval=-1,连续 PUT _id=1,2,3,只 _refresh 不 _flush:SEARCH 能命中几篇?uncommitted_operations 是多少?此时 kill -9,重启后这 3 篇还在吗?

SEARCH 命中 3 篇——refresh 换了 EXTERNAL searcher。uncommitted_operations 仍是 3(或略高):refresh 不 commit、不裁日志。kill -9 后未 commit 的 NRT segment 作废,但默认 request 耐久下这 3 条操作在回 201 前已 fsync 进 translog,恢复按 seqNo 重放,都还在。若当时是 async 且没到 sync_interval,可能丢。可见 ≠ 已 commit;已 fsync ≠ 已 commit——三件事三个开关。

2. 把 indexIntoLucene 与 translog.add 对调,Lucene 文档级失败会破坏什么?失败路径为什么还要写一条 NoOp?

对调后,失败时日志里留下一条「索引里其实没有」的 Index:恢复时重放同样会失败的操作,或更糟——seqNo 对应的内容与 Lucene 永久不一致。现码是 Lucene 成功才 translog.add(Index);失败但 seqNo 已分配则 innerNoOp 记一条 NoOp,保证序号连续、恢复时跳过。primary 上这类文档级失败不 failEngine,所以补偿必须落在 translog 里。空洞(seqNo 跳号)和脏日志(记了没发生的事)相比,后者让恢复语义彻底崩坏。

3. durability=async 什么场景能开?refresh_interval=0 能不能替代 realtime GET?trackTranslogLocation 为什么默认 false?

日志类索引可以开 async:丢最多约 5 秒通常可接受,换来少 fsync 的吞吐。写后立刻 GET 做确认的接口不能开:201 不再意味着掉电还在,GET 可能读到一份崩溃即消失的文档。refresh_interval=0 不能替代 realtime GET——那是把「每次写入造一个小 segment」的成本摊到写路径上,换来的仍只是 SEARCH 可见性;GET 要的是 VersionMap / INTERNAL,根本不走 EXTERNAL。trackTranslogLocation 默认 false,因为不是每个 shard 都会被 realtime GET:一创建就跟踪,等于每个写入都在 VersionMap 里挂一个 location。第一次真正需要时再打开,之后的写入才付这份钱。

陷阱

🕳 「能搜到 = 已落盘」:refresh 只换 EXTERNAL searcher,不 commit、不裁 translog。可搜索之后 uncommitted_operations 照样 ≥1,掉电恢复仍要靠日志重放。把可见性当持久化,是本课最大的坑。
🕳 「ES 是教科书 WAL,先写日志再改数据」:9.4.0 的 InternalEngine.index 是先 indexIntoLucene 后 translog.add。耐久语义不在调用顺序里,而在 durability=request 时回 201 前的 ensureSynced fsync 里。
🕳 旧博客的 flush 阈值:「512MB 或 30 分钟」是老黄历。9.4.0 的 IndexSettings:体积阈值 10GB(与磁盘 1% 取小、下限 10MB),时间阈值 1 分钟——以源码为准,别背二手数字。
🕳 在热索引上例行 _forcemerge:强制合并是全量重写,写入不停就立刻再裂出新段;它只属于归档只读索引。平时交给后台 merge,落后时 IndexThrottle 自己会背压。
