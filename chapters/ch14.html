学习目标

  • 在显式 refresh_interval=-1 下，对照 realtime GET、非实时 GET 与 SEARCH，验证 INTERNAL 和 EXTERNAL 读取视图的区别。
  • 从固定源码指出成功写入的 Lucene→translog 顺序，以及冲突、已分配序号的文档失败和日志同步的不同分支。
  • 记录 refresh / flush 前后的日志与段统计，用“直接 flush 后仍搜不到”验证提交不等于发布搜索视图，并读回强制合并后的业务版本。

14.1 四种观测，别画成必经时间线

第 13 课把操作交给主分片；本课进入单个分片的 Engine。普通可写分片使用 InternalEngine，它协调 IndexWriter、translog、最近版本图和 reader。Engine 是抽象接口，插件与其他部署形态可以提供不同实现；不能把本课路径说成所有存储引擎唯一的实现。

先提出四个互不替代的问题：当前能否 GET？新的 SEARCH 能否读到？日志位置是否已同步？Lucene commit 是否已经覆盖写入？fsync 是耐久同步，refresh 发布读取视图，flush 建立提交与恢复起点。三者可能由不同任务触发。merge 又是一项独立维护，既不必等到 flush 之后，也不必发生在每次 refresh 之后。

观测或动作可以说明不能直接推导
realtime GET 命中当前读取路径拿到该版本一定命中 translog、已经 fsync 或 commit
SEARCH 命中该请求的 EXTERNAL reader 可见日志已同步、Lucene 已提交
request 写入成功写后阶段满足所需日志同步条件已经发布新搜索视图或完成 commit
普通 flush 成功执行或确认提交及相关维护未刷新文档已可搜、所有日志文件消失

写入 API 是外部观测，不能逐条显示 IndexWriter 的内部缓存和磁盘文件。IndexWriter 可以因内存压力自动落段；旧 reader 仍可能不见这些数据。把“SEARCH 还看不见”解释成“任何 segment 都没有”，会把 reader 的视图与文件存在混为一谈。A 组用三个读取请求和一次显式 refresh 验证视图，C 组再用 flush 拆开提交与可见性。

14.2 成功写入为什么先 Lucene，后 translog？

以下只追踪普通引擎、显式 ID、非恢复来源的成功主路径。协调是角色，可能与存储分片处在同一个节点；路由后 IndexShard 准备引擎操作，再进入 InternalEngine.index。图中最后一个同步节点属于写后阶段，不能把它当成 index() 内部的一次调用。

index() 在 uid 锁下制定计划。显式 ID 的普通主分片分支先解析现有版本与并发条件；版本冲突可提前失败。通过检查后分配 seq_no，再选择 addDocs 或软更新。新 ID 不必总走 update，自动生成 ID 还有有条件的追加优化；本课的固定 ID 避免把优化分支误当通用顺序。

成功结果随后写 Translog.Index；按计划把版本信息放入 LiveVersionMap。这张图只保存近期版本信息和可选日志位置，不是整篇文档缓存。trackTranslogLocation 初始为 false；首次需要日志而条目没有 location 时才打开跟踪，今后的写入才可能携带位置，仍不能保证每次 GET 都走日志。

失败也要分清：版本冲突等提前失败可能没有分配 seq_no；已分配序号的特定文档级失败才会记录 NoOp。严重 I/O 或引擎故障还可能使分片失败。不能把任何 400/409 都说成“补一条 NoOp”，也不能通过一张卡片的状态码断言进入了哪个 Lucene 失败分支。

箭头表示成功主路径的处理顺序，省略解析、映射、摄取、复制、节流与内部版本查找刷新。复制与写后等待的完整请求边界在第 13 课；本课强调的是同一引擎内 Lucene 先于日志的调用关系，而成功响应所需的耐久条件另在写后层完成。

八步机制：一条可能的轨迹

播放器以 1 主 0 副、request、refresh=-1、新 ID 为前提。第六步显式 refresh，第七步 flush，第八步是可选 merge；这是一个示例，后台任务没有这种固定排队顺序。下层三列是状态对照，不是串行调用链。

14.3 日志追加、同步和提交各回答什么？

translog.add 追加操作并返回位置，不等于该位置已 fsync。普通 durability=request 且有日志位置时，写后动作调用 syncAfterWrite，等待同步回调；一次同步可覆盖多个操作，不能把每个请求都描述成独占的一次磁盘同步。硬件、文件系统与成功存储的正常前提仍适用。

设置普通默认响应与风险
index.translog.durability=request是等待所需日志位置同步；复制与其他写后条件另算
durability=async显式选择不要求此请求等待 fsync，已应答但未同步的数据存在损失风险
index.translog.sync_interval5s后台同步调度周期；不是最多丢 5 秒的保证

async 下实时 GET 仍可读。读得到不能证明抗掉电，读不到也不是耐久配置的必然结果；是否接受风险要看业务能否重新采集或重建数据。B 组临时改 async、写入读回、恢复 request，再读回设置；不制造崩溃，也不把耗时或 GET 当作磁盘同步证据。

日志按 generation 管理；滚代会同步旧日志，冻结为只读并开启新 writer，空代且 primary term 未变时可以不滚。默认代次体积阈值 64MB，与 flush 阈值是两个设置。translog.ckp 保存当前同步 checkpoint；本课不把文件布局图或文件存在当成一次 API 写入的耐久证明。

14.4 refresh 的边界是 reader，不是“不碰磁盘”

对外 refresh(source) 选择 EXTERNAL 并等待 reader 更新；外部管理器先刷新 INTERNAL，再接过 reader。只推进 INTERNAL 则不负责更新 EXTERNAL。默认 realtime GET 可以读日志，也可以通过 INTERNAL 后备读取；非实时 GET 与 SEARCH 使用外部视图。

NRT reader 打开可能把内存文档落成 segment 文件，因此旧标题“refresh 不碰磁盘”不成立。它的关键边界是不以此建立 Lucene commit，也不因数据可见而裁日志。相反，已有文件或已 commit 的数据仍要被新的外部 reader 接住，才能成为新的搜索视图。

LiveVersionMap 在刷新前切换新旧图，刷新后使旧 live 条目失效；删除 tombstone 与历史保留另有规则。并发写入仍可留在新图中，不能说 refresh 后 VersionMap 全空。第一次 realtime GET 也不是固定走日志或固定打开跟踪，具体取决于版本条目和位置。

刷新设置与请求策略：普通索引周期默认 1s，search idle 可推迟周期刷新；1s 不是可见性时限。-1 关闭周期任务，0 也不能描述成每次写入都刷。refresh=true 主动刷新涉及分片；wait_for 等满足可见性条件，监听容量等情况可导致强制刷新。二者不修改索引间隔。

14.5 flush 建恢复起点，为何日志未必归零？

普通 flush 成功主线先同步并滚代，再提交 Lucene，随后内部 refresh 让版本查找接住旧日志位置的数据，最后裁剪不再需要的旧代。锁等待、跳过条件、提交耐久等待和并发写入在图中省略；流程名称不表示每个调用一定生成新代或新 commit。

提交元数据含 translog_uuid、local_checkpoint、max_seq_no 等信息。恢复按所选提交与 checkpoint 衔接日志；最后提交未必已经成为可用的 safe commit。global checkpoint 与引用锁影响保留，裁剪不能删除仍被恢复或读取所需的代次。

Translog.stats() 从 safe commit 的 local checkpoint 后首个所需 generation 开始汇总；uncommitted_operations 是代次范围的操作数，可夹带该代中已经被提交覆盖的操作，不是逐条精确待重放计数，更不是未 fsync 计数。refresh 自身不推进 commit，但后台 flush 可以在两次观测之间发生。C8 若仍为正，应查 checkpoint 与并发，而不是承诺 flush 两次必归零。

普通 9.4.0 设置默认与条件
translog.flush_threshold_size10GB；运行时与磁盘 1% 保护阈值取小，保护阈值至少 10MB；显式值仍可低于 10MB
translog.flush_threshold_age1 分钟；调度与实际执行条件不构成精确时间承诺
本课显式年龄阈值1h，仅推迟年龄触发，不关闭全部后台 flush

普通 flush 的刷新作用域是 INTERNAL。C9 新写第二篇后直接 flush，C11 精确搜索它仍应为 0；C12 外部 refresh 后才变 1。这个对照解释了为什么“flush 一定可搜”的表格结论错误。若期间有人外部刷新，就应恢复实验前提，不能靠“动作够快”挽救预测。

14.6 用段统计观察，不用段数替代业务结果

段合并重写文件，减少碎片并回收可以删除的历史；软删除保留策略根据 safe commit、global checkpoint、retention lease 等条件保留恢复所需操作。旧业务版本不可见，不意味着它立刻物理消失。强制合并也受保留规则约束，不保证 deleted_docs=0。

_segments 中逐段看 num_docs、deleted_docs、size_in_bytes、committed 和 search，不存在 deleted_in_bytes。段数受自动落段与后台 merge 影响，一批 bulk 加一次 refresh 不保证恰好生成一个段；重复数据和嵌套文档还会改变物理计数，所以本课用严格的非嵌套 mapping。

D 组写六个 ID、更新第一个、记录真实段状态，随后设置本索引 write block 再 force merge。wait_for_completion=true 同步等待，正常响应带 _shards；flush=true 还会做 flush 和外部 refresh，这个组合动作不能证明普通 flush 自己发布了外部视图。最后 GET 读回 n=99，验证当前业务版本。

强制合并会使用 CPU、I/O 和临时空间，不应从六篇实验推导生产性能。持续写入会继续产生新段；日常 merge 由策略和调度控制，合并压力可触发引擎节流。本课的停止写入步骤明确了维护前提，不需要更改集群级配置。

思考题

1. GET 成功，SEARCH 0，uncommitted_operations=1，能判断是否耐久吗？

GET 与 SEARCH 描述不同 reader；未提交统计描述所需日志代次。它们都不暴露逐条 fsync。普通 request 成功响应与同步配置、源码共同说明写后耐久条件；async 下不能以 GET 命中代替这种条件。commit 还要另查。

2. 为什么版本冲突不一定补 NoOp？

提前版本失败可发生在 seq_no 分配前；已分配序号的特定文档级失败才有补 NoOp 的条件。严重故障可能失败引擎。不能将任意 HTTP 400/409 都当成同一个存储分支。

3. 新文档直接 flush，为什么仍可能搜不到？

普通 flush 内部刷新选 INTERNAL，旧 EXTERNAL reader 可以继续使用旧视图。C 组第二篇必须再做外部 refresh 才发布；force merge 的 flush=true 组合另有外部刷新，不能混用其结果。

4. flush 后未提交统计仍正数，要把预测改成“个位数也算 0”吗？

不应混淆数值。记录实际值，查 safe commit / global checkpoint、并发写入与代次汇总口径，条件恢复后再 flush 复查。计数可包括已被提交覆盖但处于所需代次的操作；日志文件头字节也不会因此消失。

5. force merge 后 deleted_docs 没归零，就是失败吗？

不是。retention lease、safe commit 等可保留软删除历史。先核对合并响应与实际段状态，再 GET 当前版本；业务文档数和物理历史是不同口径，不能把“不可搜索”解释成“已经从文件删除”。

陷阱

🕳 refresh 不碰磁盘：NRT reader 打开可能落出段文件；关键是未由此建立 commit 或裁日志。
🕳 flush 等于可搜、日志归零：普通 flush 只刷新 INTERNAL，保留受 safe commit 与引用约束，文件头和所需历史仍可存在。
🕳 async 最多丢 5 秒：sync_interval 是后台周期，执行、负载和故障时刻会影响窗口；不是最坏损失界限。实时 GET 也不能证明同步。
🕳 每次 refresh 一个段、merge 清所有删除：自动落段与后台合并独立；恢复所需软删除历史可以留下。看真实字段，不制造固定段数。
🕳 -1 关闭全部维护、0 每写一次刷新：它们都不能用来承诺这种写入行为；本课用显式外部 refresh，且后台 flush 仍可能发生。

机制记住边界
普通成功写入计划 → Lucene → translog → 条件性版本图；写后层满足同步条件再应答
失败与序号提前冲突可无 seq_no；已分配序号的特定失败可 NoOp，严重故障另算
