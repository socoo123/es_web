24.1 基线决定缺口，最新提交不是唯一选择

第 23 课解决“当前约束允许把副本放哪里”，本课解决“该节点怎样得到可用的数据”。对普通本地索引，可以先从一份 Lucene commit 的文件建立基线，再按序号补操作。但这个模型有两个条件：文件恢复选择的是 safe commit，有旧历史的目标还可能直接走 operations-based recovery，不传 phase1 文件。

safe commit 的选择与持久化的 global checkpoint 有关：通常选择 max_seq_no 不超过该检查点的最新提交；实现还处理历史 translog UUID 与没有可用安全提交的兼容情形。因此它可能旧于磁盘上最新的 commit，不能说“先 flush 后就一定不再发送这篇文档的操作”。文件路径的起点是 所选 safe commit.local_checkpoint + 1，操作路径的起点来自目标恢复请求。

举例：本次选中的安全提交覆盖 0–9，当前源端已有 10–12，空目标进入文件路径。phase1 获取基线文件，phase2 补所需的后续历史。数字是示意；并发写入、检查点、目标本地恢复和源端保留的历史都能改变真实工作量。refresh 决定搜索可见性，不能单独证明一篇文档是否被本次选中的安全提交覆盖。

源码依据：安全提交选择 · 两条分支与起点。

历史不只活在 .tlog 文件中当前普通 InternalEngine.newChangesSnapshot 刷新内部读取视图，从 Lucene 的历史构建 LuceneChangesSnapshot 或 synthetic source 变体，再以 Translog.Operation 形式发送。类名与协议中的 translog 不等于直接读取、整份拷贝源端的 .tlog。

源码依据：历史快照的物理来源。

24.3 来源、恢复进度和路由状态，各回答一个问题

来源 type普通索引中的典型用途基线来源
EMPTY_STORE新索引的首次主分片创建空 store 与空 translog
EXISTING_STORE已有本地磁盘的主分片恢复、close/open本机提交和适用的本地 translog
PEER普通副本、搬迁目标活动源分片与目标已有历史；可选文件计划
SNAPSHOT从仓库恢复普通主分片所选快照的文件清单
LOCAL_SHARDS传统 resize 的本地分片路径本机已有源分片
RESHARD_SPLIT当前版本的 reshard split 路径对应本地分裂源；本课不展开

type 表示这次路由指定的来源；stage 是 RecoveryState 的进度，枚举为 INIT、INDEX、VERIFY_INDEX、TRANSLOG、FINALIZE、DONE。检查索引是否真正开始服务，还需区分 IndexShardState 的 RECOVERING / POST_RECOVERY / STARTED，以及路由的 INITIALIZING / STARTED。恢复完成报告后，Master 更新路由；目标应用 active 路由时，才把 POST_RECOVERY 转为 STARTED。重试和本地准备可重置进度，不把这六个枚举当不可回退的全局状态机。

全面重启时，Gateway 的集群状态恢复还受配置的数据节点门槛与定时条件影响；它移除 STATE_NOT_RECOVERED_BLOCK 并触发 reroute。解封不表示所有分片已恢复，也不是第三套数据复制协议；实际主分片来源仍由恢复与分配情形决定。

源码依据：六种来源 · 进度枚举 · DONE 与 POST_RECOVERY · 应用 active 路由 · 数据节点门槛 · 解封与 reroute。

24.4 Peer 先选分支，再开启网络恢复的 Engine

目标先尝试 recoverLocallyUpToGlobalCheckpoint。有旧安全提交但本地尚有已确认的操作时，可能临时开 Engine、重放本地 translog 到读取的 global checkpoint，再关闭它并生成恢复起点。空目录、无可用提交或准备失败时，会报告没有有效起点。随后请求带上目标元数据，源端判断能否只补操作。

操作分支同时检查：有效的 startingSeqNo、相同 history UUID、源端拥有完整所需历史，以及适用的 retention lease 条件。有 lease 还要检查完整历史。走不通则取源端 safe commit，计算文件计划。文件是否复用不只是“名字相同”或“checksum 相同”：isSame 还比较长度、hash，双方 writer UUID 存在时也要一致；peer 的按段分组比较可能把某些单独匹配文件一起归入重传计划。

文件路径完成后，或者操作路径返回空文件结果后，PREPARE_TRANSLOG 调用 openEngineAndSkipTranslogRecovery。这次开启入口不重放本地 translog，要求 RECOVERING 且 currentEngine == null；它不否认前面已经做过临时本地恢复，也不意味着销毁全部本地 .tlog。单独的 EXISTING_STORE 路径则通过 openEngineAndRecoverFromTranslog 本地重放。

目标 Engine 就绪后，源端 先 initiateTracking 接入正常复制，再采样 endingSeqNo 并建立历史快照。恢复分批补这一区间，后续正常写入经复制进入目标，避免文件复制期间仍在写入造成遗漏。目标以 PEER_RECOVERY 应用原有序号与 primary term；完成时同步 checkpoint 和 lease、清理适用的旧 term 操作，必要时 flush，随后报告完成。主分片搬迁还有 primary context 交接；本例只演示普通副本。

源码依据：复制接入、区间和收尾 · prepare 与 finalize · 操作来源与应用。

24.5 快照共享文件，成功快照保存完整引用

普通索引的快照取得各分片的 Lucene commit 和文件元数据，Master 协调快照状态与仓库级收尾，数据节点通过 Repository 保存分片文件信息。它不是打包目录为一个 zip，也不保存一条要求逐份重放的文档增量链。下面画的是普通索引的 blob 仓库文件路径；searchable snapshot 挂载、特殊 store 和全局状态备份不在本图范围。

findPhysicalIndexFile 按物理名查找仓库已有文件，再用 isSame 比较元数据。匹配则把旧 FileInfo 加入本次完整文件清单；未匹配则登记新文件，只有内容需要写入时才放入上传队列，小文件的内容可能直接内联到元数据。还有整份 shard state 已等价时的快速复用路径。因此 incremental_file_count 不等于数据 blob 上传调用数，更不等于新文档数。

假设 S1 与 S2 都引用一个未变的段文件，S2 的清单直接引用同一文件。删除 S1 时，S2 所需的文件仍需保留；仓库删除流程依据更新后的存活引用处理无用 blob。S2 逻辑上完整，即使物理上大多复用了 S1 创建时的文件，也可以独立恢复。段合并、写入和 commit 文件变化会改变新增集合，不承诺第二次只上传几个固定文件或总为 0。

普通 restore 将主分片设为 SNAPSHOT 来源，按所选清单把文件写入 Store，文件就绪后 bootstrap 并开启 Engine。本课的条件实验恢复到另一个专属索引，并覆盖为 1P0R；若另加普通副本且有合格节点，副本通常经 peer 恢复。不能把“从仓库恢复主分片”与“peer 文件计划也可能借助仓库下载”混为同一种来源：后者仍是 PEER。

源码依据：分片快照上下文 · 快照完整集合与复用 · 旧文件匹配 · 无存活引用的 blob · 普通 restore 开启顺序 · peer 的快照辅助。

24.7 字节限速、请求并发和分配门槛，是不同约束

源端 RemoteRecoveryTargetHandler.writeFileChunk 与目标 FILE_CHUNK 接收路径调用恢复 RateLimiter，受 indices.recovery.max_bytes_per_sec 等实际配置影响。indexTranslogOperations 的发送链不调用同一文件限速器，但仍受分批、操作请求并发、网络、CPU 与磁盘影响；“不走该调用”不构成不限速或必然追得上的性能承诺。默认值可按节点角色和内存变化，前提卡读取本环境配置与覆盖。

分配层的 THROTTLE 决定当前能否开始另一场恢复；恢复层控制已开始任务的文件和操作工作。retention lease 主要保护可用于操作恢复的历史，当前普通引擎的该历史可由 soft deletes 留在 Lucene；不能把 lease 直接解释为保存整个源端 .tlog。文件计划还可选择已有快照帮助传输，适用条件与失败回退都由计划处理。

源码依据：源端文件限速 · 目标文件限速 · 操作发送链 · 分批与操作发送 · 历史保护条件。

清理与重做 · 10 张操作卡

清理仅点名 tut-l24-rec、tut-l24-gap、tut-l24-restored，以及 tut-l24-repo 内的 s1/s2 和仓库注册。成功快照扩展先删 s1/s2；未进入扩展跳过前两卡。默认注册失败时仓库可能不存在，404 是对应的清理核对。注销仓库不会删除目录内文件，不能替代快照删除。核对三个 HEAD 和点名仓库均为 404 后，从前提检查与各组起点重做。

思考题

1. 副本节点回来时，为什么不能从“主分片先 flush 了”判断一定只传文件？

先看目标能否本地恢复并提供有效起点，源端是否同历史、有完整操作和满足 lease 条件。满足时可走操作恢复，跳过文件；否则选 safe commit，它可能旧于最新 commit。flush 会改变提交，但不能独自决定恢复分支、所选基线或某篇文档的发送形式。

2. PEER 为什么既可能先 replay 本地 translog，又调用 openEngineAndSkipTranslogRecovery？

前者是目标端的本地准备：临时 Engine 尝试恢复到本地 global checkpoint，完成后关闭。后者是正式网络恢复的开启入口，不再次本地重放，而是接收源端历史与正常复制。两个时刻、两个开启用途，不矛盾。

3. _recovery.translog.recovered 和 _stats.translog.uncommitted_operations 为什么不能对等？

一个统计这次恢复应用的操作，可能包含本地准备与网络补齐；另一个统计本地 translog 相对本地提交的未提交操作。peer 基线、起点、结束区间和保留历史不同，当前源端还能从 Lucene 构建操作快照，两项不共享一个固定边界。

4. S2 大量复用了 S1 的文件，为什么删掉 S1 后仍能从 S2 恢复？

S2 保存恢复所需的完整引用，不是只保存“相对 S1 的差量”。删除依据存活快照引用清理，S2 仍引用的文件必须保留；手动删“由 S1 上传”的 blob 会破坏这个关系。

5. 一个 _recovery 行是 DONE，是否保证索引 Green、集群 Green、文件不再占带宽？

DONE 是该次恢复进度，路由 STARTED 还需报告和应用；其他副本与索引可能未完成。文件恢复可复用或传输、也可由快照辅助；操作恢复可不传 phase1 文件，均须按当前任务与计数判断，不能从一个行推断整个集群。

陷阱

🕳 最新 commit 就是 safe commit检查点和历史条件会影响选择。只做 refresh 或 flush 不能推出未来某篇一定走 phase1 或 phase2。
🕳 translog 命名就是 .tlog 物理来源当前普通源端操作历史可从 Lucene 读取；本地统计不能当网络恢复工作量。
🕳 所有 PEER 都“先传文件，且从不本地 replay”目标可先临时本地恢复，完整历史可跳过传文件；skip 仅指网络 Engine 的这次开启入口。
🕳 没调同一个限速器就是无限制操作仍受并发、分批和资源约束；文件获取也可能有快照辅助，不把源端箭头当全部来源。
🕳 注册失败就要求所有仓库都不存在只核对本章仓库；失败阶段决定是否已登记，path.repo、目录共享与权限必须分别检查。
🕳 删快照或注销仓库等于删“它上传的文件”快照删除按存活引用，注销只删注册配置；恢复后的索引又是另一份资源。

速记

问题记住的边界
从哪开始文件分支用所选 safe commit 的 local checkpoint 后；操作分支用目标请求起点
文件一定传吗完整历史与 lease 条件满足可不传；传文件时先比较元数据和恢复计划
Engine 怎样开可先有临时本地恢复；网络 prepare 再开并 skip 此入口的本地重放
并发写入怎么办先接入复制，再采样结束序号并补历史；收尾报告与路由启动分开
怎么读统计恢复账、当前 translog 账、搜索视图各有边界，不用 uncommitted 推算 phase2
快照为什么增量文件匹配可共享引用，小文件可内联；每份成功快照仍有完整恢复清单
怎样重做显式点名删除快照、索引和仓库注册，核对 404，再从前提与各组起点开始

心法：先问用哪份基线、从哪段历史开始，再问文件和操作怎样到位；快照共享的是文件，保留的是完整引用。
