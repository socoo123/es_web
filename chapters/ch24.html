分片恢复与快照

先拷 Lucene segment,再重放缺失 translog · 约 16 分钟 · 前置:第 14、15、23 课 · 20 个实验 + peer recovery 旗舰动画

学习目标

  • 对 tut-l24-rec 跑 GET /{index}/_recovery:新建读出 type: EMPTY_STORE、stage: DONE,_close 再 _open 变成 EXISTING_STORE、reused 上涨;并说出 index.files / translog 各对应两阶段里的哪一块。
  • 打开 RecoverySourceHandler:指出 phase1 拷 safe commit 里的 Lucene 文件、phase2 按 seqNo 发送 translog operations;再说出 peer 目标走 openEngineAndSkipTranslogRecovery(origin PEER_RECOVERY)、本地走 recoverFromTranslogInternal(从 localCheckpoint+1 起)——仓库里没有叫 RecoverFromTranslog 的类。
  • 说出快照是仓库里的增量文件(同 checksum 的 blob 直接 reuse);并解释 start-local 没配 path.repo 时注册 fs 仓库为什么失败——如实呈现这条失败,不假装快照成功。

1. 心智模型:拷文件,再补操作

第 23 课停在「R0 被 same_shard 拒绝,RoutingTable 写着 UNASSIGNED」。分片一旦落到某个节点,数据从哪来?第 14 课已经钉死:写入是 Lucene 再 translog、refresh ≠ flush——磁盘上能打开的是 last commit,commit 之后的操作躺在 translog。恢复就是沿着这条缝把对端补齐,两步:已 commit 的 Lucene segment 按文件拷(快、可校验 checksum、目标立刻有一份能打开的 Directory);commit 点之后的操作按 ops 增量重放(少,且与写入路径同一套 apply)。用一份具体输入:primary 的 shard 0 已 flush,commit 覆盖 seqNo 0–9(commit user data 里 local_checkpoint=9);之后又写了 3 条还没再 flush,translog 里躺着 seqNo 10、11、12——SEARCH 可能已经看见这 3 条(refresh 换了 searcher),但它们不在那个 commit 里。

恢复的「来源」有六种,先把它们和文件从哪来分开记(两阶段只属于 PEER):

场景RecoverySource.Type文件从哪来Engine 怎么起来(第 15 课)
新索引首次分配 primaryEMPTY_STORE空 Directory + 空 translogopenEngineAndRecoverFromTranslog(没什么可放)
节点重启,本地磁盘还在EXISTING_STORE本机 last commit先 createEngine,再 replay 未 commit 的 translog
replica / relocation 目标PEER从 primary 拷 segment,再收缺失 opsopenEngineAndSkipTranslogRecovery(本地 .tlog 不再放)
从仓库恢复SNAPSHOT仓库里的增量文件落到 Store文件就绪后同样开 Engine
shrink / splitLOCAL_SHARDS同节点上别的 shard本课不展开
resharding 分裂RESHARD_SPLIT同节点分裂源9.4.0 新增

集群全面重启时,Master 上的 GatewayService 先挂 STATE_NOT_RECOVERED_BLOCK 挡住读写,等够数据节点再 reroute——那是 ClusterState 何时解封,不是第三套拷文件协议。解封之后 primary 走 EXISTING_STORE(本地磁盘),缺的 replica 再走 PEER。

3. _recovery 读什么:type、stage 与两个计数块

REST 入口 RestRecoveryAction:GET /_recovery 和 GET /{index}/_recovery。RecoveryState.toXContent 原样写出 type(RecoverySource.Type)和 stage,再加上两个计数块:index.files(total / reused / recovered,对应 phase1)和 translog(recovered / total / percent,对应 phase2)。注意 stage 不是 IndexShardState、也不是 _cat/shards 的 ShardRoutingState,它是这次恢复自己的进度条:

RecoveryState.Stage这一步在干什么
INIT刚开始
INDEX恢复 Lucene 文件:reuse 本地的,或从 primary / 仓库拷新的
VERIFY_INDEX可选 check index
TRANSLOG打开 Engine,重放 translog / 收 peer ops
FINALIZEtranslog 放完之后的收尾
DONE结束。实验里你几乎总是看见它——空索引的恢复只有几十毫秒

?detailed=true 才会在 index.files.details 里列出每个文件;?active_only=true 只返回还没 DONE 的。yaml 测试 indices.recovery/10_basic.yml 对新建索引断言 type: EMPTY_STORE、stage: DONE,对 close 再开的索引断言 EXISTING_STORE——实验 1-6 就是把这两条在本地跑一遍。PEER 时 JSON 会多一个 source 节点(对端 primary);SNAPSHOT 的 source 带 repository / snapshot。单节点上你抓不住正在跑的 PEER 恢复——那要第二台节点接 replica;本课用 _recovery 看字段、用动画和源码钉两阶段。

4. Peer recovery:phase1 拷文件,phase2 发 ops

源端真正干活的是 RecoverySourceHandler。recoverToTarget 先决定走文件恢复还是纯序号恢复:目标已有 startingSeqNo、历史 UUID 相同、retention lease 罩得住历史时可以跳过拷文件(SendFileResult.EMPTY)——这是优化不是另一套模型:文件阶段可以为空,ops 阶段照发。走不通就退回文件恢复:

// indices/recovery/RecoverySourceHandler.recoverToTarget(节选)
final Engine.IndexCommitRef safeCommitRef = acquireSafeCommit(shard);
startingSeqNo = Long.parseLong(
    safeCommitRef.getIndexCommit().getUserData().get(SequenceNumbers.LOCAL_CHECKPOINT_KEY)
) + 1L;   // local_checkpoint=9 → startingSeqNo=10
phase1(safeCommitRef.getIndexCommit(), startingSeqNo, () -> estimateNumOps, sendFileStep);

phase1 拷的是这份 IndexCommit 里的文件,不是 IndexWriter 缓冲里没 commit 的 NRT segment——refresh 看见但没 flush 的文档,只能靠 phase2 的 ops 补(和第 14 课同一条缝)。phase1 的 javadoc 把「缺什么才拷、什么能 reuse」钉死:对比目标节点上已有的 segment 文件,只有 size 和 checksum 都相同的才能 reuse,缺的才传(节点离开又回来、目录没清干净时省钱)。文件拷完,源端调 prepareTargetForTranslog:不是「再造一份 .tlog 拷过去」,而是让目标打开 Engine准备收 ops(动作 internal:index/shard/recovery/prepare_translog)。然后 phase2:

// RecoverySourceHandler.phase2(节选)
logger.trace("recovery [phase2]: sending transaction log operations
              (from [" + startingSeqNo + "] to [" + endingSeqNo + "]");
final OperationBatchSender sender = new OperationBatchSender(
    startingSeqNo, endingSeqNo, snapshot, sendListener);
sender.start();   // 分批调 recoveryTarget.indexTranslogOperations(...)

没有把 .tlog 文件整份 scp 过去——传的是已解码的 Translog.Operation 列表。目标收到后 indexShard.applyTranslogOperation(op, Engine.Operation.Origin.PEER_RECOVERY):origin 是 PEER_RECOVERY 不是写入路径的 PRIMARY,因为这些 ops 在 primary 上已分配过 seqNo,副本不能再生成一份。两阶段对照:

phase1phase2
搬的是什么Lucene 文件(safe commit)translog operations(seqNo ≥ startingSeqNo)
内部动作FILES_INFO / FILE_CHUNK / CLEAN_FILESPREPARE_TRANSLOG 之后 TRANSLOG_OPS
_recovery 里看index.files:total / reused / recoveredtranslog:recovered / total / percent
限速走 recovery RateLimiter(indices.recovery.max_bytes_per_sec)不走——ops 必须尽快追上,不和大文件抢阀门
和第 14 课对应 flush 之后磁盘那份 commit对应 flush 没盖住的 uncommitted_operations

5. 目标端何时 createEngine:两个入口,同一扇窗

第 15 课的不变量这里不变:innerOpenEngineAndTranslog 要求 state == RECOVERING 且 currentEngine == null。peer 和本地走两个入口,汇合到同一段 createEngine:

// index/shard/IndexShard.java(节选)
public void openEngineAndRecoverFromTranslog(ActionListener<Void> listener) {
    recoveryState.validateCurrentStage(RecoveryState.Stage.INDEX);
    innerOpenEngineAndTranslog(replicationTracker);
    getEngine().recoverFromTranslog(translogRecoveryRunner, Long.MAX_VALUE, listener);
}

public void openEngineAndSkipTranslogRecovery() throws IOException {
    assert routingEntry().recoverySource().getType() == RecoverySource.Type.PEER
        : "not a peer recovery [" + routingEntry() + "]";
    recoveryState.validateCurrentStage(RecoveryState.Stage.TRANSLOG);
    innerOpenEngineAndTranslog(replicationTracker);
    getEngine().skipTranslogRecovery();
}

peer 为什么 skip?缺失 ops 已经(或即将)经 PEER_RECOVERY origin 写进这个刚打开的 Engine,本地磁盘那份 .tlog 不是要 replay 的来源。顺序是:先拷完文件(INDEX 阶段),再 PREPARE_TRANSLOG 打开 Engine(仍是 RECOVERING),再 TRANSLOG_OPS 往 Engine 里放 ops——不是「先建 Engine 再等文件」。第 15 课的 assert currentEngine.get() == null 保护的就是这扇窗:拷文件时 Directory 上不能已经挂着 IndexWriter。

本地 EXISTING_STORE 的重放里,pendingTranslogRecovery.set(false) 之后才允许 flush——恢复中途不能把半成品 commit 出去;放完还会 flush(false, true, ...) 一次。StoreRecovery.recoverFromStore 对空目录走 store.createEmpty() + 空 translog(EMPTY_STORE),磁盘上已有 commit 就把 Lucene 文件登记为 reused 再一律 openEngineAndRecoverFromTranslog——所以 close/open 之后 index.files.reused 会上去:文件没从别人那拷,是本机已有的。

6. 快照:索引变成仓库里的增量文件

Peer recovery 的对端是另一份 live shard;快照的对端是 Repository(S3 / GCS / Azure / fs 同一套接口)。Master 上 SnapshotsService.createSnapshot 把这次快照记进 ClusterState 的 SnapshotsInProgress,数据节点按 shard 调 snapshotShard,全部返回后 Master finalizeSnapshot 写仓库级元数据。blob 仓库的实现不是把索引打成一个 zip:它列出当前 Lucene commit 的每个文件,拿 StoreFileMetadata 去已有快照里找「物理名 + size + checksum」都相同的 blob——

// repositories/blobstore/BlobStoreRepository.doSnapshotShard(节选)
BlobStoreIndexShardSnapshot.FileInfo existingFileInfo = snapshots.findPhysicalIndexFile(md);
if (existingFileInfo == null) {
    indexIncrementalFileCount++;   // 仓库里没有:上传
    filesToSnapshot.add(snapshotFileInfo);
} else {
    // a commit point file with the same name, size and checksum
    // was already copied to repository — we will reuse it for this snapshot
    indexCommitPointFiles.add(existingFileInfo);
}

恢复快照:RestoreService 给 primary 的 RecoverySource 标成 SNAPSHOT,restoreShard 按清单把文件写进 Store,然后走和第 15 课一样的「文件就绪 → createEngine」;缺的 replica 仍走 peer recovery,不会每个副本都去仓库拉一遍。fs 仓库在 9.4.0 仍要求节点配置 path.repo:FsRepository 构造时 environment.resolveRepoDir(location) 对不上就抛 RepositoryException,文案直说 ... doesn't match any of the locations specified by path.repo because this setting is empty。start-local 通常没配——实验 15-16 会如实打到这条错误,不要改 elasticsearch.yml 去凑一个假的快照成功 Demo。

清理

思考题

1. 两节点集群,索引 1 主 1 副已 Green。停掉持有 replica 的那台,写入 _id=2 并 _refresh(不 _flush),再把节点拉起来:新 replica 的 _recovery 里 type 是什么?_id=2 在 phase1 的文件里还是 phase2 的 ops 里?若节点回来前先 _flush 了,答案哪格会变?

type: PEER(replica 从活着的 primary 拷)。只 refresh 没 flush:_id=2 不在 safe commit 里,phase1 拷走的文件没有它,它走 phase2,计数落在 translog.recovered。先 _flush 再让节点回来:这篇进了新的 IndexCommit,phase1 把它当文件拷(或目标 reuse),translog 从新的 local_checkpoint+1 起,不再为这篇付一次 ops。可见 ≠ 已 commit——与实验 14-18、第 14 课同一不变量。

2. 为什么必须「先拷 commit 文件再重放缺失 ops」,不能「从 seqNo 0 重放全部 translog」,也不能「把 .tlog 整份拷过去当 Directory」?若对调成「先开 Engine 再拷文件」,第 15 课哪条断言先破?peer 目标为什么 skip,本地 EXISTING_STORE 为什么不能 skip?

从 seqNo 0 全量重放等于丢掉 Lucene 已整理好的 segment(压缩、已删文档清理、列存),恢复时间从「拷文件」退化成「重新 index 整个历史」,translog 也根本存不下那么长的窗口。整份拷 .tlog 更不行:Translog 不是 Lucene 索引,IndexWriter 打不开它。先开 Engine 再拷文件:currentEngine == null 的断言破掉,已打开的 IndexWriter 和正在写入 Store 的文件流抢同一份 Directory。peer skip 本地 translog,因为 ops 已(将)经网络以 PEER_RECOVERY origin 写进这个 Engine,本地 .tlog 可能过期或不完整,再放一遍是重复;本地 EXISTING_STORE 没有对端发 ops,未 commit 的历史只活在本地 translog 里,不能 skip。

3. 快照按文件增量、peer recovery 在历史完整时可以完全跳过 phase1 只发 ops:为什么不把「只发 ops」当快照的默认路径?retention lease 把历史留得更久,谁在为谁付磁盘?若去掉第 23 课的 THROTTLE,80 个 replica 同时 phase1,代价落在哪?

快照必须在 primary 已经不在时仍能还原出一份可打开的 Lucene 目录:仓库里只能放文件(加 shard 元数据),不能假设将来还有一台引擎能 replay ops。retention lease 拉长「只发 ops」的窗口,代价是 primary 不能过早 trim translog / soft-deletes——用 primary 的磁盘换网络带宽。80 路同时 phase1 会打满磁盘和 indices.recovery.max_bytes_per_sec,恢复互相拖死;第 23 课用 THROTTLE 而不是 NO,就是为了排队而不是把 replica 永久留在 UNASSIGNED。

陷阱

🕳 单节点加副本就想看 PEER:_recovery 不会多出 PEER 行——第 23 课 same_shard 已把唯一节点剔除,replica 停在 UNASSIGNED,根本没开始恢复。「需要 peer recovery」不等于「正在 peer recovery」。
🕳 拿旧课的 RecoverFromTranslog 类名去源码里找:9.4.0 没有这个类。本地是 Engine.recoverFromTranslog → InternalEngine.recoverFromTranslogInternal(从 localCheckpoint+1);peer 是 openEngineAndSkipTranslogRecovery(断言 Type.PEER)。
🕳 以为 refresh 过的文档会随 phase1 拷走:phase1 拷的是 safe commit(IndexCommit)里的文件;refresh 只换 searcher 不推进 commit。flush 之前,可见的文档只能靠 phase2 的 ops 补——uncommitted_operations 就是那截(实验 14-18)。
🕳 把 stage 当分片状态:stage 是这次恢复的进度条(INIT→INDEX→…→DONE),不是 IndexShardState,也不是 _cat/shards 的 ShardRoutingState。空索引几十毫秒就 DONE,你抓不住中间档。
🕳 在没配 path.repo 的 start-local 上假装快照成功:注册 fs 仓库会失败,错误文案直说 path.repo is empty。这是预期行为:增量语义读 findPhysicalIndexFile + indexIncrementalFileCount,不要改配置硬凑 Demo,更不要照抄「创建成功再 restore」的旧示例。
🕳 以为删快照就是删它上传的文件:blob 按 checksum 跨快照共享,新快照的元数据引用旧 blob;删除要等没有任何快照引用才能物理清理。

速记

一句话内容
本课位置第 23 课给了节点,这一课给数据:phase1 拷 commit 文件,phase2 重放缺失 ops——第 14 课那条缝的两半
六种来源EMPTY_STORE / EXISTING_STORE / PEER / SNAPSHOT / LOCAL_SHARDS / RESHARD_SPLIT;_recovery 的 type 就是它
phase1 vs phase2文件(FILES_INFO/FILE_CHUNK,走限速,对应 index.files)vs ops(TRANSLOG_OPS,不走限速,对应 translog)
