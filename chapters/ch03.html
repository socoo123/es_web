节点启动全流程

从 main() 到 ready · 约 14 分钟 · 前置:第 2 课 · 2 个实验 · 1 个动画

学习目标

  • 说出启动四站(加载插件 → 锁数据目录 → 加入集群 → 打开 HTTP)各自对世界做了什么。
  • 解释为什么 HttpServerTransport 必须是 Node.start() 里最后启动的服务。
  • 说出两个进程指向同一 path.data 时,谁在哪个阶段失败、为什么走不到绑端口。

1. 心智模型:四站,不是一张类名网

类名是车站,要记的是每站对世界做了什么。客户端能打到 9200 时,插件已加载、node.lock 已拿到、节点已在加入(或组成)集群——HTTP 是最后一扇门,不是第一扇。

2. 真正的 main:argv 是空的,参数在 stdin

JVM 入口是 org.elasticsearch.bootstrap.Elasticsearch。main 很短,分三个阶段:

public static void main(final String[] args) {
    Bootstrap bootstrap = initPhase1();
    try {
        initPhase2(bootstrap);
        initPhase3(bootstrap);
    } catch (NodeValidationException e) { bootstrap.exitWithNodeValidationException(e); }
    catch (Throwable t) { bootstrap.exitWithUnknownException(t); }
}

String[] args 几乎用不上:脚本/server-cli 先解析 -E、配置路径、keystore,再 fork 服务器进程,把解析好的 ServerArgs 写进子进程的 stdin。IDE 里搜 main 别被 CliToolLauncher、JarHell、Version 这些工具入口带走。

阶段约束原因
Phase 1不能用 logger日志系统未 configure,失败只能打 stderr;日志必须是本阶段最后一步
Phase 2不能 new Node沙箱、JarHell、插件层未就绪;这里加载 modules/plugins、禁 root、试 mlockall
Phase 3可以构造并启动checkLucene → new Node → start() → 给 CLI 发 READY
Settings 谁覆盖谁:InternalSettingsPreparer 先读 elasticsearch.yml(顺手做 ${ENV} 替换),后放命令行覆盖,最后放进程传入的 Settings——后写的赢。优先级:进程传入 > 命令行 > yml > 代码默认值。

3. Node 构造:先锁盘子,再装配服务

构造函数立刻把活交给 NodeConstruction.prepareConstruction():创建线程池、脚本、分析器、集群服务,用 Guice 装配上百个组件——start() 里那一串 injector.getInstance(Xxx.class).start() 就是按这张装配图往外拉。对磁盘的副作用很早:

nodeEnvironment = new NodeEnvironment(envSettings, environment);
// 每个 path.data 上:locks[dirIndex] = luceneDir.obtainLock(NODE_LOCK_FILENAME);

拿不到锁直接启动失败,异常文案:「failed to obtain node locks … maybe these locations are not writable or multiple nodes were started on the same data path?」这就是「一块数据目录只能跑一个进程」的不变量:第二个进程在构造阶段就死,走不到 start(),更不会去绑 9201。

${path.data}/
├── _state/                 # 节点级元数据(节点 ID)
├── indices/
│   └── <index-uuid>/
│       ├── _state/         # 索引元数据
│       └── 0/              # shard 0:Lucene + translog(第 14 课进去)
└── node.lock               # 进程锁,在根上

4. Node.start():HTTP 是最后一扇门

构造完成时服务对象都在,但没有对外端口。start() 按依赖点亮它们:

源码用一行注释把这扇门焊死:

// ------- DO NOT ADD NEW START CALLS BELOW HERE -------
injector.getInstance(HttpServerTransport.class).start();
必须先才能后否则
TransportService.start()Coordinator 选主/入群没有节点间通信
GatewayMetaState.start()Bootstrap ChecksChecks 看不到盘上的元数据
Coordinator.startInitialJoin()HttpServerTransport客户端打到尚未入群的节点

GatewayMetaState 在 Checks 之前,源码自己说了:先把磁盘上上次的集群元数据读出来(to pass it to the bootstrap checks),Checks 和插件才能按「这个节点以前管过什么」做前置判断。HTTP 打开后,initPhase3 才给 CLI 发 READY——对外 ready 和内部 ready 是同一时刻的两面。

Bootstrap Checks:绑定非 loopback 才强制

三条同时成立(绑定地址不都是 loopback、非 snapshot 构建、discovery.type 非 single-node)→ 检查失败就拒绝启动;开发时绑 127.0.0.1 同一批检查只打 WARN。network.host: 0.0.0.0 会让节点离开 loopback 进入强制模式。常见检查:堆 Xms==Xmx、文件描述符(≥65535)、mlockall 是否真锁上、vm.max_map_count、系统调用沙箱(seccomp,8.0 起不可关)。

5. 生命周期:三态就够

源码枚举是 INITIALIZED → STARTED → STOPPED → CLOSED,对外记三条:构造完、在服务、资源已还。close() 若发现还在 STARTED 会先 stop()——所以别从 STARTED 直接画到 CLOSED。关闭顺序与启动相反:HTTP 最先停(不接新请求),IndicesService 最后停(让进行中的搜索/恢复跑完);node.lock 要到 CLOSED 才还——这就是「杀不干净的旧进程会挡住新进程」的原因。

启动后半关闭前半
HTTP最后打开最先关闭
集群先入群再对外先对外关门再退群
索引很早就 IndicesService.start()最后 IndicesService.stop()

思考题(= 原课的仓库实验)

1. 服务器进程的 main 是哪个?ServerArgs 从哪来?

Elasticsearch.java 的 main(三阶段)。ServerArgs 从 System.in 反序列化——CLI 进程先解析参数再 fork,把结果写进子进程 stdin。以为「main 里读 argv / 直接读 elasticsearch.yml」的错觉,来自把 CLI 进程和服务器进程当成同一个。

2. 两个进程指向同一 path.data(HTTP 端口改成 9201),谁失败?在哪一步?

第二个进程在 new Node → NodeConstruction → new NodeEnvironment 就失败(Lucene LockObtainFailedException,文案提到 multiple nodes on the same data path),走不到 start()。「端口冲突才失败」的错觉来自把 HTTP 绑定当唯一互斥;真正的互斥是数据目录锁。

3. yml 里写 network.host: 0.0.0.0、文件描述符只有 1024,能启动吗?

大概率失败。0.0.0.0 非 loopback → enforceLimits 为 true(除非 snapshot 或 single-node),fd 检查不过就 NodeValidationException。绑 127.0.0.1 同一检查只 WARN——「开发模式 vs 生产模式」的分界是绑定地址,没有 production: true 这种开关。

陷阱

🕳 「能 curl 通 = 还没做检查」:反了。HTTP 是最后一扇门,curl 得通说明 Transport、读盘、Checks、入群都已做完。
🕳 双开失败 ≠ 端口冲突:同一 path.data 的 node.lock 才是第一道互斥,死在构造阶段,连端口都不会去绑。
🕳 grep main 找到好几个:CliToolLauncher/JarHell/Version 是工具入口;数据节点的 main 只在 bootstrap/Elasticsearch.java。

速记

一句话内容
四站加载插件 → 锁数据目录 → 加入集群 → 打开 HTTP
入口Elasticsearch.main 三阶段;参数在 stdin 的 ServerArgs
互斥node.lock:一块 path.data 一个进程,构造期就死
顺序HTTP 最后开、最先关;注释禁止再往下加 start()
Checks非 loopback 且非 single-node 才强制;localhost 只 WARN
生命周期INITIALIZED → STARTED → CLOSED(close 先 stop)

心法:对外服务之前,内部必须已经自洽——启动顺序和关闭顺序都是这句话的展开。
