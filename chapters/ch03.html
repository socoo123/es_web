节点启动全流程

从启动器到对外服务 · 约 18 分钟 · 前置:第 2 课 · 2 个只读 HTTP 操作 · 2 幅交互图（均含路径动效）· 1 个逐步机制动画

节点启动不是把 9200 端口打开就结束。它先接收配置、取得数据目录锁，再启动通信、检查运行条件并发起入群。本课沿着这些副作用读代码，同时区分“HTTP 可访问”“启动方法返回”和“集群健康”。

学习目标

  • 从 ServerLauncher.run() 找到准备器与服务器两个子进程，追踪 ServerArgs 的 stdin 输入和 READY 的 stderr 通知。
  • 在 Node.start() 中定位目录元数据、启动检查、入群等待与 HTTP 的顺序，并解释超时后继续启动的条件。
  • 根据 Lifecycle 和 Node.close() 区分状态标志与资源释放，判断同一数据目录为何不能同时运行两个节点。

1. 谁启动服务器：先分清进程，再找 main

本课锚定 Elasticsearch 9.4.0 / Lucene 10.4.0 的普通节点启动路径。9.4.0 的启动脚本先进入 ServerLauncher：启动准备器 server-cli，读取它生成的 LaunchDescriptor，再创建服务器 JVM。准备器负责配置、安全设置与 JVM 参数等准备工作；启动器负责进程创建、参数管道和启动结果监视。

服务器入口是 org.elasticsearch.bootstrap.Elasticsearch.main()。这里不重新解析用户的 -E 参数；initPhase1() 从 System.in 反序列化 ServerArgs。READY 走另一条通道：服务器向 stderr 写特殊标记，启动器的 ErrorPumpThread 等待它。stdin 是启动参数及后续关闭通知通道，stderr 承载日志和启动标记。

服务器阶段本阶段解决什么读代码时抓住的边界
initPhase1()接收 ServerArgs，建立初始环境，配置日志日志配置必须留在本阶段最后；更早的异常直接写 stderr
initPhase2()原生初始化、root 检查、JarHell、插件模块层与 Entitlements先准备加载环境和权限，再进入节点构造；此处的插件 bundle 加载不等于所有插件服务已启动
initPhase3()核对 Lucene，构造 Node，关闭已读取的安全设置，启动并通知 READYREADY 在启动返回及必要后处理之后发送

本阶段配置合并的关键顺序是 yml → properties 覆盖 → input Settings，随后还有 forced settings 和占位符处理。不要把它推广成所有配置源、所有阶段的统一优先级；ServerArgs 里也不是只有路径。依据见 InternalSettingsPreparer.prepareEnvironment()。

2. 构造：先取得目录所有权，再进入 start

Node 构造函数委托 NodeConstruction.prepareConstruction()。这里加载插件实例、合并设置、建立线程池与服务，并使用 injector 装配对象。NodeEnvironment 在设置校验后创建，通过 Lucene 的 NativeFSLockFactory 在每个数据路径取得 node.lock。

假设第一个节点仍持有目录锁，第二个节点即使改用另一个 HTTP 端口，也会在构造阶段取得锁失败，尚未进入 Node.start()。异常提示还包含目录不可写的可能原因，因此排障要看底层 cause；不能见到“failed to obtain node locks”就一律认定双开。

Node 构造
  → NodeConstruction.prepareConstruction(...)
  → 设置校验 / new NodeEnvironment(...)
  → FSDirectory.open(..., NativeFSLockFactory.INSTANCE)
  → obtainLock("node.lock")

node.lock 文件留在磁盘上不代表仍有人持有锁。互斥依赖实际锁状态，正常 NodeEnvironment.close() 会释放锁；进程退出时操作系统也会释放进程持有的文件锁。排障应检查进程、权限与锁异常，不能靠删除锁文件来判断或解除占用。数据目录还包含 _state/、indices/<index-uuid>/ 等持久化内容，本课只追节点级所有权，不展开 Lucene 和 translog 文件格式。

构造与目录锁的源码依据

Node 构造委托 → 设置校验与 NodeEnvironment → 取得锁与异常包装；释放位置见 NodeEnvironment.close()。

3. Node.start：HTTP 前面有哪些门禁

start() 开头先把生命周期移到 STARTED，再启动插件及索引、搜索等内部服务。随后启动 TransportService，确定节点通信地址；GatewayMetaState 读取磁盘元数据，把持久化集群状态交给启动检查。读盘放在检查前，是为了让检查及插件能根据恢复的元数据判断前置条件。

通过这里的校验流程后，代码启动 coordinator 与 cluster service，调用 acceptIncomingRequests() 接收 Transport 请求，再执行 startInitialJoin() 发起选主或入群。发起入群不等于已经入群成功。本课保留逐步播放器，把关键调用逐站解释；它省略部分内部服务与可选后处理。

八步走读：标志、检查、等待与 HTTP

discovery.initial_state_timeout 默认是 30s。若等待启用且当前没有 master，观察器等待含 master 的状态；等待超时只告警并放行，不是抛出入群失败。设置为 0 时跳过等待；启动过程中收到关闭通知则另有提前返回分支。

接着才调用 HttpServerTransport.start()。熟悉的 DO NOT ADD NEW START CALLS BELOW HERE 注释强调对外入口的顺序，但 9.4.0 在 HTTP 后仍可能启动 ReadinessService，写端口文件并执行插件 onNodeStarted 回调。Node.start() 返回后，入口还完成自己的后处理，才发 READY。因此 HTTP 可访问、启动器收到 READY、集群达到 yellow/green 不能画成同一瞬间。

端口默认值不是状态定义：HTTP 常用 9200、Transport 常用 9300，但实际绑定端口可配置。9200 可访问只能说明对应 HTTP 入口可用；是否有 master、是否分片恢复完成，应另外检查集群状态、健康与启动日志。
启动与等待的源码依据

Node.start：服务、元数据、Checks、Transport 接收与初始入群；等待、超时、HTTP 与后处理；默认值见 INITIAL_STATE_TIMEOUT_SETTING；READY 见 initPhase3()。

4. Bootstrap Checks：看 Transport 地址，也看例外

普通检查自动强制执行，需要同时满足：Transport 绑定地址或发布地址存在非 loopback、非 snapshot 构建、discovery.type 不是 single-node。判断对象是节点间通信的 Transport 地址，不是 HTTP 地址；仅改 http.host 不能据此推出生产检查模式。

还有两条不能省略的路径：JVM 系统属性 -Des.enforce.bootstrap.checks=true 可显式强制；检查自身的 alwaysEnforce() 也可要求失败必须阻止启动。只有这三种强制条件都不适用时，该项失败才作为告警。single-node 不是关闭所有检查的开关；root 等更早的初始化错误也不会被它豁免。

条件普通失败检查的处理
非 loopback Transport + 非 snapshot + 非 single-node收集失败并抛出 NodeValidationException
显式 es.enforce.bootstrap.checks=true即使 loopback 或 single-node 也强制执行
单项 alwaysEnforce() 为 true这一项失败仍会阻止启动
以上均不适用该项失败记录 WARN；不表示其他启动错误也被忽略

检查覆盖堆设置、文件描述符、请求的内存锁定、线程数与适用的 mmap 条件等。具体项目与阈值有操作系统、存储设置等适用范围，本课不把一组数字当作跨环境通用清单。依据见 BootstrapChecks.check() 与 enforceLimits()。

5. 生命周期：四个标志不等于四个完成时刻

四个状态都要保留：INITIALIZED、STARTED、STOPPED、CLOSED。正常已启动节点执行 close() 时先 stop()，再转为 CLOSED 并释放资源；尚未启动的节点允许 INITIALIZED 直接 close。STOPPED 或 CLOSED 后不能重新 start。

stop() 先改变标志，再依次停止已启动组件；HTTP 较早停止，但前面还有可选 readiness 和周期服务等。协调、集群与传输服务随后停下，IndicesService 最后 stop，为索引相关资源释放安排顺序。它不是把每一项 start 调用机械倒放。

close() 同样先设 CLOSED，再按列表关闭资源。线程池在后段 shutdown，随后关闭 GatewayMetaState 与 NodeEnvironment；实际目录锁在后者的 close 中释放。等待线程池有效终止另见 awaitClose()。因此“看见 CLOSED 标志”并不等于所有资源已释放，更不能据此保证另一个进程已能立即取锁。

生命周期与清理的源码依据

Lifecycle：允许与拒绝的转移；Node.stop / close 开头；关闭后段与 awaitClose。

实验：观察启动结果，再回源码找原因

前提：连接到已运行的 ES 9.4.0；多节点会返回多行或多个节点对象。使用当前控制台端点及所需认证。以下两张卡都只读，不创建资源，也无需清理，可重复执行；它们观察运行后的快照，不能还原本次启动的全部时序。

实验 1：节点身份与 HTTP 发布地址

成功响应表示这次集群节点信息请求可完成。http 列实际取 HTTP publishAddress，不是全部 bind 地址；代理入口、容器映射端口也可能与它不同。地址字段来自 RestNodesAction.buildTable()。要判断分片健康，另查 GET /_cluster/health；本卡不能证明 green。

实验 2：实际进程号与内存锁定结果

process.mlockall 报告实际内存锁定状态。false 可能是没请求锁定，也可能是请求后未成功，不能单凭这个值反推出配置；应结合 bootstrap.memory_lock、运行限制与启动日志。PID 来自服务器 JVM，在容器中可能属于容器 PID 命名空间；见 ProcessProbe.processInfo()。

思考题

1. 为什么在 Elasticsearch.main 里找不到用户的 -E 参数解析？

准备器已处理配置并把序列化 ServerArgs 放入 LaunchDescriptor；启动器创建服务器进程并写入其 stdin。服务器 main 消费这条管道，而不是重复解析用户 argv。准备器与启动器的职责也不能混为一个进程。

2. 第二个节点换了 HTTP 端口，却仍用正在占用的 path.data，会在哪里失败？

目录锁不能取得时，在 Node 构造中的 NodeEnvironment 阶段失败；尚未进入 Node.start 的 HTTP 绑定。看完整 cause 区分锁冲突与目录权限错误；不要通过删 node.lock 文件恢复运行。

3. single-node 或 loopback 是否保证所有启动检查失败都只告警？

不保证。普通自动强制规则可不触发，但显式 es.enforce.bootstrap.checks=true 和单项 alwaysEnforce() 仍会强制。判断地址时要看 Transport 的绑定与发布地址；root 等更早的错误另有约束。

4. HTTP 能响应而没有 master，是否与本章启动顺序矛盾？

不矛盾。startInitialJoin 是发起动作，初始等待可能超时告警，或设为 0 跳过，然后 HTTP 仍可打开。具体 API 是否依赖 master、是否受到集群 block 限制另行判断；用健康、状态和日志核对，不能只测端口。

5. CLOSED 标志已经设置，为什么不能说 node.lock 此刻已释放？

Node.close 先设置 CLOSED，后面才执行关闭列表；NodeEnvironment.close 位于后段，并在那里释放锁。生命周期标志用于控制转移与幂等性，不能代替实际清理完成的证据。

陷阱

🕳 HTTP / READY / green 混成一件事：HTTP 可达不保证入群或分片恢复；READY 在入口启动返回后发送；green 是另一层集群健康结果。
🕳 把状态名当作完成证据：STARTED 在 Node.start 开头设置，CLOSED 在关闭列表执行前设置。状态和完成时刻要分开读。
🕳 只看 HTTP 地址推断检查模式：自动规则检查 Transport 的 bind / publish 地址，还受 snapshot、single-node 影响；显式强制和 alwaysEnforce 另有路径。
