为什么一个副本一直 Yellow，新节点来了又为什么不立刻均匀？本课把三个问题分开：目标模型想放哪里，当前约束允许哪一步，路由和恢复实际走到哪。合法目标不等于马上落位，Green 也不等于所有写请求一定成功。

  • 用B组读实际覆盖和磁盘信息，用C组解除索引过滤、恢复普通写块；计算带headroom的水位，解释健康颜色为什么不能代替写入准入。

23.1 目标布局与当前落位，是两件事

第21、22课解释了新集群状态的计算、提交与应用，本课看谁在计算路由变化。AllocationService 先让已有副本分配器处理未分配分片，先主后副；具体索引可以选择已有副本allocator，默认Gateway路径处理它能接手的恢复信息。新建空store主分片并不意味着已存在一份磁盘目录可直接复用。

默认 cluster.routing.allocation.type=desired_balance。外层提交新输入，后台 DesiredBalanceComputer 用 BalancedShardsAllocator 在模型中多轮模拟落位与启动；Master上的 DesiredBalanceReconciler 再从当前状态向可用目标迈一步。新计算尚未完成时，本轮可以先执行已有目标，不是每次reroute都停下来等一份全新布局。

“约束管能不能，模型帮助选哪里”是有用的心智模型，但不能画成一个所有过滤先结束、打分器之后才首次看到节点的严格流水线。Balanced的解释路径会计算节点权重，再收集该节点决定；即使NO节点也可出现在解释与权重排名里。真正不能跨越的是实际落位的约束，而不是打分器永远看不见NO节点。Reconciler也会在未分配、必要移动和普通平衡各动作中重新判断。

23.3 单节点Yellow：同号两份不能叠在一个node

A组建立 tut-l23-yellow，1主1副、auto-expand关闭。先确认只有一个合格数据节点，等待主分片active。此时P0有位置，R0若也请求同一节点，same_shard 返回NO；这个NO足以阻止叠放。还可能有磁盘、角色、过滤等其他NO，不把same_shard预先指定成唯一故障。

SameShardAllocationDecider 的node级禁叠与 cluster.routing.allocation.same_shard.host 分开。后者默认false，可允许同一host上的不同node各放一份；不同node不自动形成独立物理故障域。机架/可用区打散还要结合实际部署和awareness/filter等配置，不能以两个进程的名字证明高可用。

Replica的前提是active primary；在路由模型里 active() 包括STARTED和RELOCATING，不应只写“主必须是STARTED枚举”。健康颜色则按所需分片是否active判断：主未就绪可能Red；主就绪但副本缺少可能Yellow；所有所需副本就绪才Green。索引颜色要限定本课资源，全群还包括其他索引。Green不保证没有写块，Yellow也不意味着每类请求都一定成功。

把副本数改为0后变Green，只是取消第二份的需求，不是恢复了冗余。再改回1，副本会重新进入路由；unassigned_info.reason 可能从INDEX_CREATED变为REPLICA_ADDED。这个字段说明进入未分配的历史原因，当前不能分配的条件仍要看deciders。

23.4 四种决定，有两种比较口径

同一节点上的多个Decider合并时，取更严格结论，普通OFF路径遇NO短路；解释模式不这样提前结束，以便保留更多具体决定。节点之间的选择又有另一口径：某个节点当前THROTTLE，可能比立刻去一个NOT_PREFERRED节点更值得等。不能用一个枚举声明顺序代替两种方法。

使用场景源码比较序（从低到高）含义
同节点决定汇总NO < THROTTLE < NOT_PREFERRED < YES取更低、更严格结论；THROTTLE压过NOT_PREFERRED，保持节流约束
不同节点决定比较NO < NOT_PREFERRED < THROTTLE < YES允许等待较合适节点，不能只看能否马上分配

实际策略也使用权重与平局规则，不保证所有节点选择都只调用这一比较方法。默认Reconciler初始化未分配分片时可接受YES或NOT_PREFERRED；THROTTLE本轮不初始化，NO也不落位。必要移动与普通平衡又有自己的目标检查，NOT_PREFERRED不在所有动作中等价YES。

NO是当前条件下不能做，不是永久拒绝、只许人工修。条件变化、后续reroute或恢复完成后可以重评。THROTTLE是暂缓，不是性能保证或“所有恢复最多2条”：默认incoming与outgoing各2，初始本地primary恢复另默认4，并且这些设置都可调整。

23.5 小磁盘系数，不等于磁盘只微调

默认普通权重模型有四项：总分片数、同索引分片数、预测写入负载、模型中的分片字节使用。它们先对系数求和归一化，再对节点与模型均值之差加权。实际磁盘“整个文件系统已用字节”与模型里估计/预测的分片字节不是同一测量。

cluster.routing.allocation.balance.*默认比较的维度
shard0.45总分片数量差
index0.55同索引分片数量差；不强制主角色均匀
write_load10.0模型的预测写入负载差；缺预测时不是实时CPU百分比
disk_usage2e-11分片字节差，不是百分比
threshold1.0模型改进门槛，结合minWeightDelta缩放
θ_i = factor_i / Σ factor
W(node,index) = θ_shard × Δ总分片数
              + θ_index × Δ本索引分片数
              + θ_write × Δ预测写入负载
              + θ_disk  × Δ分片字节
// 示意原始贡献：2e-11 × 1e11 bytes = 2
// 小系数乘大字节差，不能断言只做微调。

这个模型帮助规划较合适布局，同时仍受角色、tier、过滤、磁盘与动作条件限制。threshold不是“片数差超过1必迁移”，实现会结合 minWeightDelta 比较改进；平局和其他指标可以改变选择。三节点四份分片的2/1/1是可行示意，不保证某个具体副本必迁、主角色平均或最终永久保持这个数字。

23.6 一次搬迁，同时存在源和目标

普通搬迁从一个STARTED源路由开始。获得当前动作许可后，源变为RELOCATING、目标变为INITIALIZING，两个路由成对并存；源仍active，目标尚未active。目标恢复完成并启动后，源路由才移除。这是路由记录推进，不是所有节点在同一瞬间完成组件切换。

副本从B搬到C时，“搬迁源节点”与“数据恢复源节点”不必相同。普通replica目标向active primary所在节点恢复；若P0在A，本例数据箭头是A→C，B/C只是搬迁配对。Primary搬迁的恢复来源又有另一分支，本课不把一张副本图泛化为所有角色。

若初始化的搬迁目标失败且源仍存在，路由处理可取消源搬迁、删目标，源回STARTED；不是任何失败都一定留下一个UNASSIGNED副本。源也故障、主提升、恢复重启等情况有其他路径，本图不覆盖它们。不要以某次explain说明预测固定完成秒数。

23.7 水位先换算空闲字节，再谈分配与写入

下面限定普通非frozen路径、磁盘决策启用且有可用统计。百分比水位表示已用比例，绝对字节水位表示最低空闲字节；low/high/flood三档须采用一致口径且有序。对比例水位，有效headroom上限会限制所需空闲量；它不是额外再加一份空闲要求。

普通路径的默认水位未显式改该水位时的headroom主要边界
low=85%200GB限制普通新分配；新空store/新clone主分片有条件豁免
high=90%150GB影响canRemain与部分预计落位后的空间检查；不保证一定有目标能迁
flood_stage=95%100GBMonitor设置相关索引read_only_allow_delete块，不是另一次节点打分
// 百分比且相应max_headroom有效的示意：
所需空闲 = min(容量 × (1 - 已用水位比例), max_headroom)
// 显式配置相应watermark而未配max_headroom，其默认为-1（无此上限）。
// 绝对字节watermark直接表示最低空闲，不再套百分比。

例如同一单位下容量10,000GB，low的15%本来要求1,500GB空闲，默认headroom把它限制为200GB。已用86%仍有1,400GB空闲，不能仅凭86>85断定此条件必NO。实际还有搬迁空间、预留、预计分片大小、路径与统计时刻等输入；CAT的disk.percent不是完整政策快照。

新空store或新clone的非active primary可跳过low检查，但仍有high相关条件；replica不能套这项新主豁免。其他路径还会检查预计分片装入后的high空闲，不代表每个clone/特殊分片都执行完全同一分支。high会影响存量能否留下并触发reroute，但可用目标、过滤、节流等仍可能让它搬不走；只超过low也可能因其他平衡/过滤原因搬迁，不能说存量保证不动。

超过普通flood时，Monitor对相关索引设置 index.blocks.read_only_allow_delete，并在相关条件恢复后考虑自动解除。ES9.4.0这个默认WRITE块使用429（TOO_MANY_REQUESTS），不是把所有磁盘错误写成403。它允许释放整个索引资源，不表示可删除任意文档；单文档删除也是写。C组用的是另一种明确且可恢复的 index.blocks.write，默认403，只证明Green与可写分开，不冒充flood触发或真实磁盘压力。

23.8 explain解释当前选择，不是分配执行按钮

浏览器操作卡使用POST JSON body指定 index/shard/primary，避免GET body不被客户端发送。空请求会优先找可访问项目里的未分配primary，再找replica，不保证选到本课索引；没有未分配分片时也不能靠空请求解释一个任意STARTED分片。

响应的 node_allocation_decisions[].deciders[] 给出decider、decision、explanation。默认解释模式省略YES；include_yes_decisions=true 显示更多具体决定，ALWAYS哨兵仍不进入数组，不保证每个注册Decider都有一项。初始化/搬迁中的分片有专门在途说明，源码可返回 NOT_TAKEN，不能承诺任意时刻都得到一整份新落位决定。

默认desired_balance的explain委托Balanced按当前状态解释；它不是未来目标的完整历史，也不触发落位。NO节点可以有权重排名，“看见weight_ranking”不证明可分配。include_disk_info 也是附加当前可用信息；DiskThresholdDecider在统计缺失时有fail-open YES路径，不能把所有YES翻译成磁盘一定充足。

动手实验：3 组 / 33 张操作卡

版本为ES9.4.0，默认课程Docker免认证单节点；先检查接入节点角色和合格数据节点数。A组限定单合格数据节点，有更多数据节点时副本可能成功分配；B组只读当前配置与统计；C组只改另一个本课索引的require条件和普通写块。33张卡包含末尾4张清理确认，严格按顺序建立前提。

本轮实际验证范围固定版本源码已核对。本轮重新启动官方9.4.0镜像后，云运行环境仍缺 /proc/self/coredump_filter，ES启动退出，真实API与两轮重做未实测；多节点搬迁和真实磁盘水位也未实测。以下是条件化预期，不是本轮采集响应；图解和HTTP检查单列记录。

A · 副本需求、路由与指定解释（13卡）

tut-l23-yellow 显式1主1副、auto-expand=false、strict keyword。确认不存在后创建，等待本索引主就绪再解释。副本改0后等Green，改回1再等并解释；不依赖读者点得快。重复创建通常400，删除后重建恢复初始原因。

B · 配置与磁盘统计（3卡）

读defaults也读persistent/transient覆盖，节点文件配置仍影响实际结果。普通/frozen与禁用/信息缺失分支分开；本组不改全局阈值，不声称达到85/90/95%时已真实演过故障。

C · 过滤NO、恢复前提与Green写块（13卡）

tut-l23-filter 与A组分离，1主0副、auto-expand=false。虚构require._name先确保无节点匹配，创建时wait_for_active_shards=0，随后解释未分配P0；移除过滤后等Green。写入固定ID文档后设普通写块，观察Green与预期403，显式移除块后更新同ID。这个普通块不会由磁盘Monitor按恢复条件自动清除，避免要求操作够快。

点名清理与第二轮（4卡）

先完成C12恢复，再点名删除两本课索引，清掉它们全部映射与文档；不使用通配符或改其他索引。重复删除通常404；两次HEAD分别404才证明两个资源都不存在。再从A3–A13、C1–C13各做一轮并清理；节点名、版本、磁盘统计不用完全一样，前提与动作语义才是重复目标。

思考题

1. include_yes_decisions=true出现更多票，same_shard的NO能变YES吗？

显示参数只改变解释可见性，不改变配置和许可。OFF执行路径可NO短路，解释模式保留更多具体票；ALWAYS哨兵仍省略。same_shard阻止同号两份叠同node，开关不能绕过它。

2. 一个Decider给THROTTLE，另一个给NOT_PREFERRED，可以马上初始化吗？

同节点汇总保留THROTTLE，默认Reconciler本轮不初始化该目标。节点之间有另一顺序，具体选择还用权重与平局规则；NOT_PREFERRED在初始化、必要移动、普通平衡中的处理不完全相同，不能把非NO一概叫立即允许。

3. 本索引Green，普通写块却拒绝了更新；是健康接口错了吗？

没有。Green说所需分片active，写块说WRITE级操作不允许，是两个边界。C组index.blocks.write默认403；flood-stage默认read_only_allow_delete块在9.4.0用429，也不能用这次403证明磁盘过水位。

4. Replica从B搬到C，B的源还是什么状态？数据一定B→C吗？

源是RELOCATING但仍active，目标是INITIALIZING；不是源枚举保持STARTED。普通replica目标向active primary恢复，本例P0在A，所以数据A→C。目标STARTED后移除源；目标失败且源仍在可取消搬迁删除目标，其他故障有别的路径。

5. 默认low=85%，容量10,000GB、已用86%，该条件一定NO吗？

不一定。未显式改相应水位时low headroom默认200GB：所需空闲min(1500,200)=200GB，而实际空闲1400GB。仅这个阈值条件并未失败；还需判断统计、预计大小、预留、路径和其他Decider。显式设置相应watermark而不设headroom时，上限默认可能为-1。

陷阱

把目标图当成真实落位记录后台模型可模拟start，当前执行仍受条件与节流约束；新目标也可能尚未完成。explain不是未来目标历史或强制执行按钮。
把四种决定压成一个永久序汇总与节点比较不同，THROTTLE不立即落位；NO可在条件变化后重评。
把RELOCATING叫“仍STARTED”它仍active，但路由枚举已经变；目标独立INITIALIZING，恢复来源也不由B/C搬迁关系直接推出。
把小系数、颜色和百分比当保证磁盘字节差可很大，Green不保证可写，85/90/95%还要结合headroom与实际分支。
把所有写块都报403普通写块与默认flood块不是同一个块；9.4.0的flood WRITE块使用429，文档删除也受WRITE约束。
