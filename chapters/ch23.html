分片分配

过滤链先投 NO,通过的才进 balancer · 约 16 分钟 · 前置:第 1、21 课 · 11 个实验 + 均衡迁移动画

学习目标

  • 在单节点上建 tut-l23-yellow(1 副本),用 POST /_cluster/allocation/explain 读出未分配 replica 的 deciders,指出 same_shard 投的那张 NO——第 1 课只看见 Yellow,这一课看见投出 Yellow 的那一票。
  • 打开 AllocationDeciders.withDeciders 与 SameShardAllocationDecider.decideSameNode,说出过滤链「NO 即短路」的顺序与四种票(NO < THROTTLE < NOT_PREFERRED < YES)的排序语义。
  • 写出磁盘三档水位的 setting 名与默认值(85% / 90% / 95%),并用 DiskThresholdDecider.canAllocate 的分支回答:过 low 之后,新分片怎样、存量分片怎样、从未分配的 primary 有没有豁免。

1. 心智模型:先过滤,后平衡

第 21 课把「每个分片在哪个节点」钉在 ClusterState.routingTable 里;这一课解开谁执笔。答案不是一张组织架构图,而是两段清晰的流水线:过滤链(AllocationDecider)先回答「这个 shard 放这个节点行不行」,投 NO 的组合当场作废;全部放行的节点才交给 balancer 打分挑人。最短的例子就是第 1 课见过的单节点 Yellow:

分配引擎是 AllocationService,一次 reroute 大致三步:先给磁盘上已有副本找家(GatewayAllocator),再对每个「未分配 shard × 候选节点」跑过滤链,最后只在投出 YES(或 THROTTLE / NOT_PREFERRED)的节点里让 allocator 挑人。默认 allocator 由 cluster.routing.allocation.type 决定,默认 desired_balance:外层 DesiredBalanceShardsAllocator 异步算目标位置再 reconcile,内层打分引擎仍是 BalancedShardsAllocator。触发 reroute 的场景:索引创建、节点加入/离开、手动 POST /_cluster/reroute,磁盘水位监控(DiskThresholdMonitor)也会踢一脚。

3. reroute:先已有副本,后 allocator

Master 上任何会改 RoutingTable 的变化,最终都要算「下一步该把哪些未分配分片放到哪些节点」。这步贵,所以生产路径尽量经 RerouteService.reroute 批处理,不是每个事件直接打 AllocationService.reroute。核心顺序:

// cluster/routing/allocation/AllocationService.java(节选)
private void reroute(RoutingAllocation allocation, RerouteStrategy rerouteStrategy) {
    rerouteStrategy.removeDelayMarkers(allocation);
    allocateExistingUnassignedShards(allocation); // 磁盘上已有的副本优先
    rerouteStrategy.execute(allocation);          // 默认:shardsAllocator.allocate(...)
}

「已有副本优先」不是口号:allocateExistingUnassignedShards 先扫完所有 unassigned primary,再扫 replica。对新建索引,primary 的 recovery source 是 EMPTY_STORE,Gateway 这边很快结束,真正挑节点的是后面的 shardsAllocator;节点重启、从磁盘恢复,才轮到 GatewayAllocator 问「哪台机器上已经有这份 Lucene 目录」——第 24 课的 peer recovery 从这里接。

shardsAllocator 类型setting 值谁上场
DESIRED_BALANCE_ALLOCATORdesired_balance(默认)DesiredBalanceShardsAllocator,内部仍 new BalancedShardsAllocator(...)
BALANCED_ALLOCATORbalanced直接 BalancedShardsAllocator

4. AllocationDecider 是过滤链,不是组织架构图

每个 Decider 只回答一件事:把「这个」shard 放到「这个」节点,行不行。接口 AllocationDecider 的 canAllocate / canRemain / canRebalance 默认都是 Decision.ALWAYS,真正干活的是子类;组合它们的是 AllocationDeciders,不是一张「磁盘 / Zone / 版本」并列的架构盒。生产路径(DebugMode.OFF)碰到 NO 立刻 break,后面的 Decider 根本不问:

// cluster/routing/allocation/decider/AllocationDeciders.java(节选)
if (debugMode == RoutingAllocation.DebugMode.OFF) {
    Decision mostNegativeDecision = Decision.YES;
    for (AllocationDecider decider : deciders) {
        var decision = deciderAction.apply(decider);
        if (mostNegativeDecision.type().compareToBetweenDecisions(decision.type()) > 0) {
            mostNegativeDecision = decision;
            if (mostNegativeDecision.type() == Decision.Type.NO) {
                break;   // 已经 NO,后面不必再问
            }
        }
    }
    return mostNegativeDecision;
}

票的序是 NO < THROTTLE < NOT_PREFERRED < YES,链的汇总取「最负面」那张:一个 THROTTLE 压过所有 YES,一个 NO 压倒一切。NOT_PREFERRED 是较新的第四种票(节点资源画像偏高,允许放但不优先);explain JSON 里偶尔会见到它。explain 把 debugMode 打开时走 else 分支:构造 Decision.Multi,把每个非 ALWAYS 的票收进数组——这就是响应里 deciders 的来源,§7 展开。

同节点 NO 的那一票:SameShardAllocationDecider

类名是 SameShardAllocationDecider(不是旧图写的 SameShardDecider),NAME = "same_shard",会原样出现在 explain 的 deciders[].decider 里。Javadoc 写得很死:禁止同一 shard 的多份落在同一 node——跟 cluster.routing.allocation.same_shard.host(默认 false)无关,那是给「同一物理机起多个节点」再比一层 host address 用的开关;node 级禁叠永远生效。R0 问 Node-A 时,真正投 NO 的是 decideSameNode:

// SameShardAllocationDecider.decideSameNode(节选)
for (ShardRouting assignedShard : assignedShards) {
    if (node.nodeId().equals(assignedShard.currentNodeId())) {
        return debug ? debugNo(shardRouting, assignedShard) : Decision.NO;
    }
}
return YES_NO_COPY;  // "this node does not hold a copy of this shard"

生产路径直接返回常量 Decision.NO(热路径不建 explanation 字符串);explain 路径才走 debugNo,文案两种:「这份分片本身已在该节点」或 a copy of this shard is already allocated to this node——单节点 Yellow 时你在 JSON 里看到的就是后者。

THROTTLE 不是「暂时不知道」:ThrottlingAllocationDecider 的意图写在类注释里——节点正在恢复的分片太多时返回 THROTTLE,让上游按批次分配,避免 100 个 replica 同时 recovery 把磁盘和网络打满。YES 会立刻开冲,NO 会让分片一直黄着等人工,THROTTLE 是「这轮先别动,下一轮再问」。

5. 全部放行之后,balancer 才挑人

过滤链的产出是「这个节点能不能接」;能接的可能有好几个,谁最终拿到分片是 allocator 的事。把场景换成 3 个节点:Node-A 已有 P0,B、C 空着——R0 问完全部节点,A 被 same_shard 剔除,B、C 全链 YES,balancer 只在 B、C 上打分,选权重最低(偏差最小)的那个:

BalancedShardsAllocator.allocate 自己也是三步,而且每步都要再问 deciders:allocateUnassigned()(给未分配的找家)→ moveShards()(节点离开等场景的迁移)→ balance()(平衡)。给未分配分片找家时,先问 shard 级「这个 shard 现在能不能分配」,再对每个节点 canAllocate(shard, node),只有 YES / THROTTLE / NOT_PREFERRED 才进入选最小权重。权重四因子的 setting 与默认值仍在类顶部:

setting默认想拉开的差距
cluster.routing.allocation.balance.shard0.45各节点总分片数
cluster.routing.allocation.balance.index0.55同一索引的分片不要堆在一台
cluster.routing.allocation.balance.write_load10.0数据流写索引的写入负载
cluster.routing.allocation.balance.disk_usage2e-11磁盘用量(系数极小,只微调)
cluster.routing.allocation.balance.threshold1.0低于阈值的「更平衡」不搬,防抖动

选的是偏差最小的节点,不是「分片最多的机器再加一个」。disk_usage 的 2e-11 看着像笔误,源码就是这个数量级:磁盘的大头由 DiskThresholdDecider 用硬阈值卡死,balancer 只在「都没过水位」的节点之间微调。DesiredBalance 外层把「算理想位置」(DesiredBalanceComputer 异步)与「往理想走一步」(DesiredBalanceReconciler.reconcile)拆开;THROTTLE 时目标已算好,只是这轮搬不完,下一轮继续——reconcile 仍要问 deciders,过滤链的不变量不变。

6. 磁盘水位:low 卡增量,high 才动存量

水位不是链上的「架构层」,它是 DiskThresholdDecider 这一环的输入,setting 声明在 DiskThresholdSettings:

low / high / flood 可以写绝对空闲字节(如 500mb),但三档必须同一单位。未显式改水位时还有 max headroom 上限(low 200GB / high 150GB / flood 100GB)——大磁盘不会因为 85% 这个百分比而要求腾出十几 TB。canAllocate 的分支把「新分片」说死了:

// DiskThresholdDecider.canAllocate(节选)
if (freeBytes < freeBytesThresholdLowStage) {
    if (skipLowThresholdChecks == false) {
        return Decision.NO;   // "the node is above the low watermark ..." 新分片,含 replica
    } else if (freeBytes > freeBytesThresholdHighStage) {
        return YES_UNALLOCATED_PRIMARY_BETWEEN_WATERMARKS;
        // "above the low watermark, but less than the high watermark,
        //  and this primary shard has never been allocated before"
    } else {
        return Decision.NO;   // "the node is above the high watermark ..."
    }
}

skipLowThresholdChecks 只给「还没 active 的 primary 且是空 store / clone」开:集群必须先有主分片,否则是 Red 而不是 Yellow。Replica 没有这个豁免——DiskThresholdMonitor 越过 low 时打的日志就是 replicas will not be assigned to this node。用具体数字走一遍:Node-A 用到 86%,新 replica 进不来,已 STARTED 的分片原地不动;用到 91% 才开始迁存量;95% 是 Monitor 把这台上的索引标只读,写入 403——那已经不是分配问题了。

7. _cluster/allocation/explain:把票箱读成 JSON

第 1 课用 _cat/shards / _cat/health 看见 Yellow;本课用 explain 把「为什么」从源码票箱里倒出来。路由 GET|POST /_cluster/allocation/explain,Transport 动作 cluster:monitor/allocation/explain。空 body = 「解释你找到的第一个 unassigned shard」(响应带 note);指定分片用 body:index / shard / primary。两个常用开关:include_yes_decisions(默认 false → DebugMode.EXCLUDE_YES_DECISIONS,deciders 里几乎只有 NO/THROTTLE;true → DebugMode.ON,整条链都在)和 include_disk_info(默认 false)。单节点上 R0 的响应骨架:

清理

思考题

1. 两节点集群,索引 1 primary + 1 replica,本来 Green。停掉持有 replica 的那台:剩下那台同时握着 primary,集群什么颜色?对这条 unassigned replica 做 explain,same_shard 会对活着的那台投 NO 吗?把 number_of_replicas 改成 0,颜色怎么变?

Yellow(主分片在,能读写)。explain 时活着的那台已持有同号 P0,same_shard 会投 NO——不是「节点刚离开所以暂时不行」,是「唯一活节点已经有一份」。过滤链问的是「还能不能放」,不是「曾经放过」。replica 改 0:不再需要第二份,集群 Green。同一不变量贯穿第 1 课和本课,区别只是这次你能在 JSON 里指出那一票。

2. 为什么必须禁止「同一 shard 的 replica 和 primary 同节点」,而不能「同节点也算高可用,省一台机器」?same_shard.host 默认 false,又在放什么、挡什么?

高可用的不变量是:一份数据的故障域必须大于一个。同节点两份,进程崩溃、磁盘坏、OOM kill 会两份一起没,集群从这个 shard 的 Yellow 直接掉到没有主分片的 Red。省一台机器换来的不是省,是一份假副本。same_shard.host 默认 false:允许同一宿主机起两个节点时 P、R 分坐两个 node(开发测试常见);设 true 则连同一 host address 也不行,把故障域抬到物理机。node 级禁叠与这个开关无关,永远生效。

3. Decision 为什么要有 THROTTLE,而不是只有 YES/NO?节点重启后有 80 个 replica 要 recovery:全 YES 代价是什么?全 NO 等人工 reroute 代价又是什么?NOT_PREFERRED 和 THROTTLE 各在保护哪种资源?

THROTTLE 让分配排队而不是拒绝。80 个 replica 全 YES,会在同一节点同时 INITIALIZING,磁盘、网络、node_concurrent_recoveries(默认 2)全被打满,recovery 互相拖死;全 NO 则分片长期 UNASSIGNED、集群长期黄,自动愈合没了。THROTTLE 保护瞬时并发(recovery 槽位):这轮先别动,下一轮再问;NOT_PREFERRED 保护已经偏高的资源画像:还能放,但别优先放。过滤链把 NO 当硬约束,THROTTLE / NOT_PREFERRED 交给 allocator 在「能放的节点」里排序。

陷阱

🕳 把 Yellow 当「副本没创建」:副本分片是真的想要而放不下——过滤链合法拒绝了唯一候选节点。读 explain:can_allocate=no、same_shard NO,票箱里写得明明白白。
🕳 以为 explain 默认只跑一个 Decider:deciders 里只有一条 NO,是因为 DebugMode.EXCLUDE_YES_DECISIONS 把 YES 滤掉了;include_yes_decisions=true 才看到整条链。打开 YES 不会把 NO 改成 YES。
🕳 把 low 水位当 high:85% 只挡新分片,存量原地不动;90% 才开始迁存量;95% flood 是把索引标只读(写入 403),根本不是再投一次 NO。三档单位必须一致(全百分比或全字节)。
🕳 以为 balancer 会推翻 NO:被投 NO 的节点根本不进候选集,balancer 看不到它。过滤是硬约束,打分只在「能放的节点」里选偏差最小者——不是「分片最多的机器再加一个」。
🕳 拿旧课类名 SameShardDecider 去源码里找:9.4.0 全名 SameShardAllocationDecider,NAME="same_shard"。另记住:从未分配过的 primary 在 low~high 之间有豁免,replica 没有任何豁免。
