请求入口层

HTTP 到 Action 的第一公里 · 约 20 分钟 · 前置：第 1、5 课 · 2 组实验 / 17 张操作卡 · 2 幅交互图（2 幅路径动画）· 0 个机制播放器

一个请求为什么返回 400、405 或 404？REST 层先选择处理器，再把路径和查询参数变成内部请求；Action 执行后，监听器把结果适配成 HTTP 响应。沿着 GET 一篇文档的路径，分清“没匹配到入口”“参数不合法”与“资源不存在”。

1. URL 匹配到的究竟是什么？

HTTP 传输实现把请求交给 RestController。它实现 HttpServerTransport.Dispatcher，持有 PathTrie<MethodHandlers>。本课从 RestRequest 开始：传输解码、TLS 与压缩先留在外围，重点看谁选择处理器、谁读参数、谁决定响应。

例如 GET /tut-l06-docs/_doc/1 可以匹配 /{index}/_doc/{id}：第一段由命名通配符捕获为 index，中间的 _doc 是字面量，末段捕获为 id。叶子的值是 MethodHandlers；它再按 HTTP 方法与 REST API 版本找到处理器。这一步只产出入口与参数，还没有读文档。

图中把四种 TrieMatchingMode 折叠成候选检索：显式节点、根通配、叶通配、全部通配。RestController.getAllHandlers 每次检索前恢复原查询参数，避免上一次通配捕获污染下一次匹配。MethodHandlers.getHandler 优先取请求 API 版本，没有对应版本时可回退当前版本。固定路径并不等于一张精确 URL 哈希表；也不能把所有请求描述为只走一次贪心下降。

本课请求与条件失败阶段预期响应
GET /_this_path_is_not_registered/at/all，默认注册集合没有可用路由400，error 字符串含 no handler found
DELETE /_cat/health路径可匹配，方法不支持405，Allow 包含 GET
GET /tut-l06-no-such-index，索引不存在命中 GET /{index}，索引元数据 Action 失败404，index_not_found_exception
GET /tut-l06-docs/_doc/missing-id，索引存在文档 GET 已执行，结果不存在404，found:false

路由声明还要被注册才生效。启动时 ActionModule.initRestHandlers 注册内置 RestGetAction，也收集 ActionPlugin.getRestHandlers 返回的入口；Controller 遍历 routes() 并调用 insertOrUpdate。同一路径的方法归入一个 MethodHandlers，重复的“方法 + API 版本”组合会被拒绝。这是第 4 课插件扩展与本课请求分发的接点。

状态码是线索，还要读错误原因。结构化 error 也可能来自处理器之前的内容检查或拦截，不能据此证明已执行 Action。文档缺失的 404 则是正常 GetResponse 的业务结果。实验 A 用同一组资源把这些分支逐一对照。

普通 OPTIONS 到达 RestController 时会返回 200；合法方法集合非空才附 Allow，没有匹配路径也可以 200。浏览器的 CORS 预检还带有 Origin 与 Access-Control-Request-Method，启用 CORS 时可能由更外层 CorsHandler 处理。预检成功不保证后续业务请求成功。

2. 参数读取为什么是一种“消费”？

RestRequest 先解析查询串；PathTrie 随后把命名通配段写入同一个参数容器。ES 9.4.0 使用 RequestParams 保留重复查询值，并提供单值 Map 视图；param(key) 读取最后一个值并把 key 加入 consumedParams。专门读取重复值时可使用 repeatedParamAsList。路径捕获写入会替换该键，不要用查询串覆盖 URL 的 index 或 id。

// RestRequest.param：读值并登记；省略其他方法
public final String param(String key) {
    consumedParams.add(key);
    return params.get(key);
}

BaseRestHandler.handleRequest 是 final 模板。处理器若声明支持参数集合，会先做白名单检查；本课的 RestGetAction 沿用默认 null，不走这段可选检查。随后调用 prepareRequest，让子类读取参数、构造内部请求并返回 consumer；再检查未消费的键与未消费的完整 body，通过后才 accept(channel)。因此“未知参数只在 prepare 之后查”不是所有 Handler 的完整描述。

响应参数有专门的消费位置：AbstractRestChannel 构造时读取 format/filter_path/pretty/human；可选白名单也自动接受它们。未消费检查另排除 RestResponse.RESPONSE_PARAMS 与 Handler 声明的 responseParams。不能把 ALWAYS_SUPPORTED 理解为跳过后置检查就直接放行所有全局参数。

在文档 GET 上，?realtimee=false 留下一个未消费的键，触发 400；拼写建议从已消费及响应参数候选中按 Levenshtein 相似度挑选，阈值大于 0.5，候选不足时不保证有建议。?fields=title 则在 RestGetAction.prepareRequest 内被读取后立即抛错，提示改用 stored_fields 或 _source。两个 400 都阻止本次 GET consumer 执行，触发位置不同。

?_source=title 只过滤本次返回的 source，不改原文档或 mapping；filter_path 筛选整个响应结构。stored_fields 依赖字段映射的 store:true，字段类型是 keyword 并不自动表示已单独存储。实验 B 会用合法过滤请求恢复旧 fields 请求的意图，再重新 GET 验证 views 仍在。

3. 哪一行真正进入 Action？HEAD 又在哪里去掉正文？

RestGetAction.routes() 把 GET 与 HEAD 的 /{index}/_doc/{id} 注册到同一个处理器。prepareRequest 构造 GetRequest(index,id)，读取 routing、preference、refresh、realtime 与字段过滤等参数。请求对象默认 refresh=false、realtime=true；构造对象本身尚未访问分片。

// RestGetAction：先构造 GetRequest，再返回待执行的 consumer
return channel -> client.get(getRequest,
    new RestToXContentListener<>(channel,
        r -> r.isExists() ? OK : NOT_FOUND));

真正跨过本课边界的是 consumer 中的 client.get。NodeClient 将内部请求交给注册的 Action 执行；分片定位与读取留给后续章节。成功回调的 RestToXContentListener 序列化 GetResponse 并用 isExists 选择 200 或 404，异常则走失败监听路径。回调可能同步完成，也可能稍后执行；图里的纵向顺序不承诺固定线程。

HEAD 同样执行 GET Action，仍受 realtime、routing 和存在性条件影响。DefaultRestChannel 在写 HTTP 响应时把 HEAD 待发送的内容替换为 BytesArray.EMPTY，保留状态码。对本课常规非分块响应，还会按原表示计算 Content-Length；压缩、代理和其他响应类型会影响具体头值，不写死某个字节数。实验 B 对存在与缺失的同一 URL 做 GET / HEAD 对照。

REST 与 Action 分层让 HTTP 适配和内部执行可以各自变化。现代 Elasticsearch Java API Client 也通过 HTTP 访问服务，并不是直接把服务器的 GetRequest 塞进 NodeClient；不要把本课内部调用边界与已移除的 TransportClient 混为一谈。

编码斜杠为什么不打乱路径段？

若 ID 是 http://example.test/a，URL 中要把它编码成一个段：http%3A%2F%2Fexample.test%2Fa。Controller 使用 rawPath 做路径解析，PathTrie 捕获通配段后才由 decoder 解码。先对整个路径解码再切段，会把 ID 中的斜杠误当分隔符。两张编码卡直连 ES 验证这一机制；反向代理可能提前解码或拒绝编码斜杠，需单独核对。

4. Handler 前的保护和路由统计说明了什么？

路由命中之后还有入口检查：校验内容类型、处理可选 API 保护、向 in-flight breaker 记账，再经过 RestInterceptor 与请求校验才调用 Handler。插件可以在拦截阶段拒绝请求，所以“路由命中”并不意味着准备阶段或 Action 一定会开始。

普通完整 body 路径中，Controller 给 breaker 的增量是 contentLength；ChildMemoryCircuitBreaker 的子限额检查按 (已记账字节 + 增量) × overhead 估算。9.4.0 的 network.breaker.inflight_requests.overhead 默认仍为 2.0，可动态配置。调用点没写乘 2，不代表估算不含系数；这也不是精确 JVM 堆占用公式。canTripCircuitBreaker=false 的处理器走 addWithoutBreaking，仍记账。非流式 Handler 还可能先聚合请求体，因此不能声称这一步能阻止任何请求体预先占用内存；流式收取的细节不在本图范围内。

MethodHandlers 懒创建路由 tracker；RestController.getStats 只输出请求或响应计数大于 0 的路径模式。同一路径的方法与版本共享统计，它不等于 GET 专属计数，也不是完整的路由目录。计数属于各节点进程，其他客户端流量会叠加；删除本课索引不会移除路由或清零计数。没有 Handler、未进入记账通道的失败也不能期待在某个已注册模式下出现。

思考题

1. 单段路径为什么可能是业务 404，多段路径却是路由 400？

GET /{index} 已注册。不存在的单段索引名进入索引元数据 Action，得到 index_not_found_exception；本课未注册三段路径在默认路由集合下无 Handler，得到 no handler found 的 400。不是按段数普遍决定状态码，要看完整路径与方法是否匹配。

2. “先 prepare 再校验”是否概括了所有参数检查？

后置消费检查确实要等 prepare 读完参数；可选参数白名单检查在 prepare 之前，fields 的显式拒绝在 prepare 之内。RestGetAction 默认不声明白名单；realtimee 留给后置检查。任何错误位置都要与具体处理器和请求对照。

3. HEAD 为什么仍需 Action；404 能否独自证明文档不存在？

HEAD 与 GET 共用 GetRequest 和 listener，只有写 HTTP 时省略 body。要判断具体文档缺失，先确认索引存在、权限与端点正确；缺失索引也可能返回 HEAD 404。本课通过 GET 正文 found:false 交叉验证。

4. Controller 只传 contentLength，为什么不能说 breaker “不再乘 2”？

调用点传的是记账增量，子 breaker 比较的是累计记账量乘 overhead，默认 overhead=2.0。配置可以变，估算也不是精确堆用量；必须跟到 breaker 的实现才能解释最终检查。

5. 删除索引后 routes 统计为什么还在？

路由模式和 tracker 挂在节点 REST 注册结构上，不属于某个具体索引。同一路径的 GET/HEAD 等共同记账，其他请求也会增加计数；删除索引不清零，节点重启会重新建立进程内统计。

陷阱

只凭状态码或 error 形状定位400 可能来自路由、参数或入口检查；404 可能来自索引或文档缺失。结合 reason、found、请求方法与已建立的资源前提判断。
把 GET 都当作不能带 body本课文档 GET 不消费 body，因此完整 body 被拒绝；ES 的其他 GET API 可以支持请求体。网站 fetch 不能发送 GET body，验证需用 curl。
用 OPTIONS 成功证明接口存在普通 OPTIONS 无匹配路由也可 200；CORS 预检可能在 HTTP 外层处理。确认具体方法的业务响应才有意义。
把注册表、统计与业务实现混为一层routes 只给已记账模式；NodeClient 是服务器内部 Action 入口。现代 Java API Client 经 HTTP 调用，不等于直接复用服务器 GetRequest。
