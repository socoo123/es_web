LESSON 06 · 第二篇 · 请求处理

请求入口层

HTTP 到 Action 的第一公里 · 约 16 分钟 · 前置:第 1、5 课 · 10 个实验

学习目标

  • 拿 GET /tut/_doc/1 按路径段说出 PathTrie 的匹配过程:哪些段走命名通配符写进 params、哪个段必须字面量命中、叶子上挂的是什么。
  • 用真实请求把三种失败配对:未注册路径 400(no handler found)、Method 不对 405(带 Allow)、文档不存在是 Handler 选的 404(found:false);并解释单段 GET /missing-index 为什么不是路由未命中。
  • 说出 RestGetAction.routes() 注册了什么、prepareRequest 做了什么没做什么,并区分 ?fileds=(拼错,未消费)与 ?fields=(旧参数,显式拒绝)两种 400 的机制。

1. 心智模型:一条 URL 怎么找到它的 Handler

第一篇停在「配置怎么读」。从这一课起换挡:请求怎么进来。你敲下 GET /tut/_doc/1,最先接住它的是 REST 层——Netty 把 HTTP 字节解码成 ES 自己的 HttpRequest,再包成 RestRequest;而真正决定「这个 URL 交给谁」的是 RestController:它实现 HttpServerTransport.Dispatcher,手里握着一棵 PathTrie<MethodHandlers>。Netty pipeline 里的 SSL、压缩、pipelining 是传输细节,读 REST 层不必先啃那张管道图。

URL 先按 / 切段,再从树根逐段下走。GET /tut/_doc/1 一共四步:

tutchildren 里没有 tut 这个字面量,回落到通配 *(插入 {index} 时用的 key),名字记在节点的 namedWildcard 字段index=tut
_doc字面量命中,没有商量余地不变

3. RestRequest:两类参数挤在同一张地图

RestRequest 把 ES 的 REST 层从 Netty 解耦出来:底层仍握着 HttpRequest/HttpChannel,对外只暴露自己的 method、path、params、body。工厂方法 RestRequest.request(...) 里,params(httpRequest.uri()) 只解析查询串(? 后面);路径上的 {index}/{id} 此刻还不在 map 里——那是 PathTrie 匹配时 recordWildcardParam 写进去的。于是同一张 Map<String,String> 里最终并排躺着两类键:

核心读取器每次取值都记账:

// RestRequest.java
public final String param(String key) {
    consumedParams.add(key);   // 取一次,记一笔
    return params.get(key);
}

用户写了 ?fileds=title(拼错 fields),Handler 从没 param("fileds"),这个键就留在 unconsumedParams() 里;BaseRestHandler 在真正执行前检查它,返回 400 而不是默默忽略。content()/contentStream() 同样把 contentConsumed 置位:GET 不该带 body,带了又没被消费,也会 400。

HTTP 方法是枚举(GET…CONNECT),不是自由字符串;非法 method 抛 IllegalArgumentException,RestController 把它收成 405。rawPath() 是未解码路径——匹配必须用它,才接得住 _id 是 http%3A%2F%2F… 这种 URL;path() 才是解码后的。四个查询参数被所有 Handler 自动放行(BaseRestHandler.ALWAYS_SUPPORTED):format、filter_path、pretty、human——不必每个 Handler 自己 param()。RestResponse.RESPONSE_PARAMS 目前只有 error_trace。

4. BaseRestHandler:final 的模板方法

RestHandler 是 @FunctionalInterface,核心一个 handleRequest;Route 是它的内部类,最常见的构造就是 new Route(GET, "/{index}/_doc/{id}")。需要弃用或替换旧路径时走 builder——deprecatedForRemoval(即将删除,响应带警告)、replaces(旧路径也注册成弃用包装)、deprecateAndKeep(弃用但保留)——用到再查,不用背。

几乎所有内置 Handler 继承 BaseRestHandler,而 handleRequest 在这里是 final:先做 supportedQueryParameters() 白名单校验(没覆盖时默认 null、整段跳过),然后 prepareRequest,再检查未消费参数,通过才 usageCount.increment()、action.accept(channel) 真正发走:

// BaseRestHandler.java(骨架,有删节)
public final void handleRequest(RestRequest request, RestChannel channel, NodeClient client) {
    // …白名单校验 allSupportedParameters…
    try (var action = prepareRequest(request, client)) {
        var unconsumed = request.unconsumedParams();      // 排除 RESPONSE_PARAMS / responseParams
        if (unconsumed.isEmpty() == false) {
            throw new IllegalArgumentException(unrecognized(request, unconsumed, …));
        }
        usageCount.increment();
        action.accept(channel);                           // 这一行才真正执行
    }
}

子类唯一必须实现的是 prepareRequest;javadoc 写明:实现必须在返回 runnable 之前消费完请求参数,响应阶段才用的参数(少见)放进 responseParams()。有 body 却没被 content() 消费,会在 accept 之前抛「does not support having a body」。

拼写建议用的是 Lucene 的 LevenshteinDistance,阈值 >0.5;unrecognized() 拼出的句子形如 request [/idx/_doc/1] contains unrecognized parameter: [realtimee] -> did you mean [realtime]?,多个候选时是 any of [a, b]?。注意它被包进标准 REST 错误对象(error.type/error.reason/status:400),和「路径未注册」那种扁平的 {"error":"no handler found …"} 不是一种东西——实验 1、5 对照看。

5. RestController:分发、注册与 400 / 405

RestController 的树就一棵字段:PathTrie<MethodHandlers> handlers,构造时传入 RestUtils.REST_DECODER(通配符捕获路径段时做 URL 解码)。注册用 insertOrUpdate:同一路径的 GET 和 HEAD 合并进同一个 MethodHandlers,再按 Method 分到同一个 Handler 实例;addMethod 不允许覆盖已存在的 (method, version) 组合,重复注册直接抛;OPTIONS 禁止注册,由内部处理。对外入口是 registerHandler(RestHandler):遍历 handler.routes()。启动时 ActionModule.initRestHandlers 里那行 registerHandler.accept(new RestGetAction()) 你要能指认;插件走同一函数——循环 actionPlugins 调 ActionPlugin.getRestHandlers(...),被 filter 掉的也会注册一个 placeholder,好让错误信息仍从 RestController 发出。

匹配比想象的执拗:getAllHandlers(params, rawPath) 用的是 rawPath(注释原话:不解码才能处理 my_index/_doc/http%3A%2F%2Fwww.google.com 这种 id),且每轮迭代前重置 params——因为 PathTrie 会往这张 map 里写通配符。retrieveAll 对四种 TrieMatchingMode 各试一次(只显式节点 / 允许根通配 / 允许叶通配 / 全允许),Controller 按迭代顺序取第一个能 getHandler(method, version) 的就返回;全部落空才 handleBadRequest。MethodHandlers.getHandler 先按请求的 API 版本取,取不到回落 RestApiVersion.current()(minor 新加的 API 视为兼容)。

情况谁决定HTTP响应要点
路径一个 Handler 都配不上handleBadRequest400扁平 JSON:"error": "no handler found for uri […] and method […]"(不是 404)

两个易踩的坑。其一:单段 GET /some-missing-index 会命中 RestGetIndicesAction 的 GET /{index},得到的是 index_not_found 的 404,不是 no handler found——想复现「路由未命中」必须用多段、对不上任何模式的路径。其二:GET / 返回的是集群版本和 tagline(RestMainAction),不是「所有 REST 端点清单」;路由只活在那棵 PathTrie 里,想看它得靠实验 8 的 per-route 统计。

命中 Handler 之后、进 handleRequest 之前还有三件事:校验 Content-Type;按 canTripCircuitBreaker() 向 IN_FLIGHT_REQUESTS 熔断器预留 contentLength 字节(9.4.0 不再乘 2;GET 无 body 预留 0,这是记账,不是「每个 GET 都占一大块堆」);过 RestInterceptor(安全插件在这里拦)。canTripCircuitBreaker()==false 的 Handler 走 addWithoutBreaking:仍记账,但不允许这次请求把 breaker 打爆。

6. RestGetAction 走读:REST 到此为止

最典型也最短,全文 76 行。先看它声明了哪些入口:

// RestGetAction.java
@Override
public String getName() { return "document_get_action"; }   // 给 _nodes/usage 用,不是类名

@Override
public List<Route> routes() {
    return List.of(new Route(GET, "/{index}/_doc/{id}"),
                   new Route(HEAD, "/{index}/_doc/{id}"));
}

9.4.0 里没有旧映射 /{index}/{type}/{id}——那是 7.x 时代的 type 段,已被 replaces 清掉。HEAD 和 GET 共用这一个类:HTTP 语义不同(HEAD 不要 body),取文档的方式相同。prepareRequest 主干:

GetRequest getRequest = new GetRequest(request.param("index"), request.param("id"));
getRequest.refresh(request.paramAsBoolean("refresh", getRequest.refresh()));
getRequest.routing(request.param("routing"));
getRequest.preference(request.param("preference"));
getRequest.realtime(request.paramAsBoolean("realtime", getRequest.realtime()));
if (request.param("fields") != null) {
    throw new IllegalArgumentException("the parameter [fields] is no longer supported, …");
}
// 之后:stored_fields、FetchSourceContext.parseFromRestRequest 的 _source 过滤等
return channel -> client.get(getRequest,
    new RestToXContentListener<>(channel, r -> r.isExists() ? OK : NOT_FOUND));

GetRequest 的构造只是把 index/id 存进 Action 请求对象,此刻没有访问任何分片;可选参数全来自查询串,默认值跟 GetRequest 字段一致(refresh 默认 false、realtime 默认 true)。注意 fields 那个 throw:参数先被 param() 消费、再立刻拒绝——所以它不走「未消费参数」的拼写建议,是明确赶人去用 stored_fields 或 _source(实验 6)。

真正离开 REST 层的是返回的那个 lambda。client 是 NodeClient,get 会按 ActionType indices:data/read/get 找到 TransportGetAction——第 7 课的表。RestToXContentListener 在回调里调 GetResponse.toXContent,状态码用 isExists() 在 OK 和 NOT_FOUND 之间选。

HEAD 为什么还能共用?Handler 照样序列化一份响应,剥 body 发生在更外面的 DefaultRestChannel:isHeadRequest 时把 content 换成 BytesArray.EMPTY。所以「HEAD 与 GET 共用一个 Action」的不变量是:存在性、版本、realtime 语义必须一致;差别只在 HTTP 要不要消息体。实测印证:curl -I 同一 URL,200 的 Content-Length 照报(比如 134)但线路上没有 body;换成不存在的 id,HEAD 也是 404、无 body——只看状态码就知道文档在不在。Handler 从不直接写 TCP:RestChannel 只有 newBuilder/sendResponse 这类方法,JSON/YAML/CBOR 按 Accept 选。本课停在 listener 把 GetResponse 变成 RestResponse。

清理

思考题

1. 对一个存在的索引发 GET /tut-l06-docs(没有 /_doc/1)会返回什么?换成三段 GET /tut-l06-docs/missing-type/1 呢?

前者 200:命中 RestGetIndicesAction 的 GET /{index},返回 mappings/settings 元数据——和实验 2 同一条路由,只是索引这次存在。后者 400 no handler found:9.4.0 没有 /{index}/{type}/{id},中间段必须是字面量 _doc 才进 RestGetAction,missing-type 对不上任何三段模式。猜「三段一定是取文档」的人,是把 7.x 的 type 段当成了还活着的路由。

2. handleRequest 为什么必须 final、校验为什么必须放在 prepareRequest 之后?若挪到之前会发生什么?

final 是让「未知参数必须失败」「不支持的 body 必须失败」成为所有 Handler 的不变量,而不是每个子类的自觉——跳过检查,?fileds= 会被静默忽略,用户以为过滤生效了、实际全字段返回,这是协议层在撒谎。校验必须在之后:路径上的 index/id 是 PathTrie 写进 params 的,只有 prepareRequest 里的 request.param("index") 才把它们标成已消费;若先查 unconsumed,路径参数全部「未消费」,每个合法 GET 都会 400。模板顺序本身就是不变量:先让子类消费,再对剩下的键问责。

3. 为什么不在 RestGetAction 里直接读 Lucene/IndexShard,而要 new GetRequest + client.get()?这和「HEAD 由 Channel 去 body」是同一类设计吗?

Action 才是传输无关的「取一篇文档」:节点间走 Transport 帧和 ActionType 名字(indices:data/read/get),不套 HTTP;Java 客户端同样构造 GetRequest。把 Lucene 读放进 REST 层,等于强迫所有入口假装自己是 HTTP,换传输实现也会碰坏业务代码。多一跳的代价是多一个对象、一次分发;换来 Action 层同时服务 REST、复制、内部调用。HEAD 去 body 是另一类决策:业务结果必须与 GET 相同(所以共用 GetRequest),字节要不要上线是 HTTP 语义(所以放 Channel)。前者是层间切分,后者是同一层内按 method 剥响应。

4. 用 curl -I(HEAD)分别请求存在与不存在的文档:状态码和 body 各是什么?不看 body 怎么知道文档在不在?

存在:200,无 body,但 Content-Length 仍照报——DefaultRestChannel 对 HEAD 把 content 换成 BytesArray.EMPTY,只是不发送,长度信息保留。不存在:404、无 body。所以存在性判断只看状态码即可(这正是 HEAD 的用途);而 GET 版本的 404 带 found:false 的 JSON。两条路由指向同一个 prepareRequest,不存在「HEAD 只查路由表」的捷径——不执行 client.get() 就无法知道文档在不在(realtime、routing 都得算)。

陷阱

🕳 「URL 打错就是 404」:PathTrie 未命中是 400 no handler found;而且单段 GET /missing-index 会命中 /{index},得到的是 index_not_found 的 404。排障先看错误体形状:扁平 error 字符串 = 路由没接住;结构化 error.type = 接住了、后面出的错。
🕳 「400 都是路由没匹配上」:路由命中之后照样有 400——拼错参数(未消费)、旧参数 fields(显式拒绝)、GET 带 body 未消费,都发生在 BaseRestHandler.handleRequest 或 prepareRequest 内部。看 error.reason 区分,别急着改 URL。
🕳 旧资料写 in-flight breaker 预留 contentLength×2:9.4.0 只预留 contentLength 字节,GET 无 body 预留 0。读二手资料里的数字,先对着当前版本核一遍。

速记

一句话内容
职责REST 层 = 路由 + 适配:收 HTTP、匹配 Handler、抠 params、造内部 Request;不取文档、不跑查询
