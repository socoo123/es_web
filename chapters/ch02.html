项目结构全景

从 10000 英尺俯瞰代码库 · 约 12 分钟 · 前置:第 1 课 · 2 个实验

学习目标

  • 说出五大源码区域的依赖方向,以及为什么 server 不能依赖 modules。
  • 拿到一个功能名(比如 GET 文档),能按定位表找到它源码的真实路径。
  • 说出 modules 和 plugins 的发布差别,以及把插件塞进 server/ 会破坏哪条不变量。

1. 心智模型:五大源码区域,箭头只往下

仓库巨大,但读源码时反复进出的只有五块。上层依赖下层;server 永远不依赖 modules、plugins、x-pack。这保证核心引擎可以单独编译、单独测试——没装云存储插件的发行版,照样能编译。

这条不变量在 server/build.gradle 里肉眼可见:生产依赖只有 libs 和 Lucene——

api project(':libs:core')
api project(':libs:logging')
api project(':libs:x-content')
// …更多 libs
api "org.apache.lucene:lucene-core:${versions.lucene}"

没有 api project(':modules:…')。同一文件里确实会出现 modules,但配置名是 internalClusterTestImplementation——集成测试拉模块来搭更完整的节点可以,主代码编译不行。另外 generateModulesList 会在构建期枚举模块名写进 modules.txt,那也不是编译依赖。

3. modules vs plugins:代码像,发布不像

为什么必须拆开:拆的是发布与失败域。transport-netty4 缺了节点起不来,必须打进发行版;analysis-smartcn 只服务中文语料,不该成为所有人的启动依赖。若「全部当插件、默认装一部分」,发行版与插件目录的边界就糊了,禁用/卸载的语义也不再清楚。

libs/ 下的库(x-content、geo、grok、plugin-api…)不依赖 ES 本身,可被外部项目独立引用;塞进 server/ 的代价是:想复用 JSON 序列化的人必须拖上整份引擎。x-pack/ 与 modules 同级、同样依赖 server,是商业许可功能(安全、ML、ESQL、ILM),第 27-29 课再进去。

4. Gradle 怎么把目录变成子项目

settings.gradle 用 addSubProjects() 递归发现带 build.gradle 的目录——新模块只要在对应目录放一个 build.gradle 就会被扫进去。版本钉在 build-tools-internal/version.properties:

组件版本(本教程锚定)
Elasticsearch9.4.0
Lucene10.4.0
Bundled JDK26.0.1+8(GET /_nodes 的 jvm.version 只显示 26.0.1)
Netty / Jackson / Log4j / ANTLR44.1.132.Final / 2.15.0 / 2.19.0 / 4.13.1

依赖校验的 SHA256 在 gradle/verification-metadata.xml——知道有这道闸即可。测试基础设施用 test/framework(ESTestCase 等)和 qa/(滚动升级、混合版本),不要自己搭。

5. 快速定位指南:「这个功能的代码在哪?」

想找的去这里

命名规律:ES 命名非常规范——RestXxxAction 是 REST 入口类,TransportXxxAction 是内部执行类。IDE 按 ⌘⇧N 搜文件名即可秒定位。

思考题(= 原课的仓库实验)

1. server/build.gradle 的 dependencies{} 里会出现 project(':modules:…') 吗?以什么配置名?

会出现,但只在 internalClusterTestImplementation(集成测试拉模块搭完整节点)和构建期枚举(generateModulesList 写 modules.txt)里;生产依赖 api/implementation 只有 libs 和 Lucene。把「测试依赖/构建期枚举」当「编译依赖」,就是这个实验要抓的错觉。

2. GET /{index}/_doc/{id} 的 REST 入口文件在哪层目录?

server/src/main/java/org/elasticsearch/rest/action/document/RestGetAction.java(包 org.elasticsearch.rest.action.document)。注意 GetRequest 在 action/get/——REST 入口和 Transport 执行不在同一层,这是最常见的第一层混淆。

3. 把 plugins/analysis-smartcn 整份搬进 server/ 会怎样?

server 被迫带上 smartcn 的实现与它的 Lucene 分析器依赖;图 1 的「引擎不能依赖可选功能」断裂——所有发行版都编译进中文分词,用户再也无法不装它。留在 plugins/ 靠 loadPluginsBundles 按需加载,才与「核心独立」相容。

陷阱

🕳 grep 到 modules ≠ 依赖:server/build.gradle 里能搜到 modules(测试配置、构建期枚举);判断依赖看配置名是不是 api/implementation。
🕳 REST 层和执行层不是一个包:RestGetAction 在 rest/action/document/,GetRequest/TransportGetAction 在 action/get/。按名字找错层,后面的走读全乱。
🕳 plugins/ 里的东西不会随发行版分发:默认可用的都在 modules/(或 x-pack 对应发行版);要用 smartcn 得 elasticsearch-plugin install analysis-smartcn。

速记

一句话内容
依赖方向libs → server → modules/plugins/x-pack,箭头只往下
证据server/build.gradle 生产依赖只有 libs + Lucene
阅读顺序rest → action → index → cluster → common
modules vs plugins代码同构;一个随发行版打包,一个手动装;两个加载入口
定位规律RestXxxAction = 入口;TransportXxxAction = 执行

心法:读 ES 源码先问「这块代码被谁依赖」——方向错了,后面全错。
