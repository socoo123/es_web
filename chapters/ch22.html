主节点选举与共识

pre-vote → 选举 → publish → commit,同一条多数派不变量 · 约 17 分钟 · 前置:第 21 课 · 10 个实验 + 选举时序旗舰动画

学习目标

  • 用 GET /_cat/master 与 GET /_cluster/state?filter_path=master_node 指出当前 Master(两条 API 读同一份 DiscoveryNodes.getMasterNodeId());打开 Coordinator.Mode,写出它仅有的三个枚举值,并说出本节点竞选前、当选后、跟随时各是哪一个。
  • 对 3 个 master-eligible 节点,用 VotingConfiguration.hasQuorum 的那行算式推出 quorum=2;并解释被隔离的旧 Master 为什么在哪一道门都过不去——它不能再把新 ClusterState 变成「集群真理」。
  • 按源码顺序说出三道门槛:pre-vote 拿假投票凑多数才 startElection;Join 凑真投票多数才 becomeLeader;PublishResponse 凑多数才发出 ApplyCommitRequest。

1. 心智模型:一份新状态要过四道门

第 21 课把 ClusterState 钉成不可变快照,Master 单线程算出 version N+1。但那份新快照不会因为 Master 本地算完就算数——真正让它成为「集群真理」的,是 Coordinator(实现 ClusterStatePublisher)上的四道门:pre-vote 先用假投票试探「联系得到的节点够不够一次选举多数」,够了才正式选举;选举抬 term、收真正的 Join;赢了只是拿到了 publish 资格;新状态还要凑齐 publish 多数,再广播 commit 才落地。选上 Master 和改集群状态,走的是同一条多数派不变量。

这条算法不是「大概照着 Raft 写的」。CoordinationState 的类注释第一句就把自己钉在一份形式化模型上:directly implementing the formal model(elastic/elasticsearch-formal-models 的 ZenWithTerms)。和教科书 Raft 能对上号的只有几个词:term、多数派投票、两阶段提交。本课只走 9.4.0 源码里真实存在的名字:Mode.CANDIDATE / LEADER / FOLLOWER、PreVoteRequest、StartJoinRequest / Join、PublishRequest / PublishResponse、ApplyCommitRequest。

本机 docker 是单节点(discovery.type=single-node):voting configuration 里只有自己,quorum=1,自己投自己就算数。正文例子按 3 节点、quorum=2 讲;实验会先看清单节点上的 Master 与投票配置,隔离实验在单节点上做不出分区——那条失败路径用源码的四道门对照,不要硬演。

文件这一课用它证明什么

3. Coordinator.Mode:只有三个值

打开 Coordinator.java 的枚举,不要凭记忆写成 Raft 教科书的一长串状态:

// cluster/coordination/Coordinator.java
public enum Mode {
    CANDIDATE,
    LEADER,
    FOLLOWER
}

三个值对应三件互斥的事。竞选这条链是单向的:先 CANDIDATE,赢了 Join 多数才 LEADER;别的节点走的是另一条链——收到别人的 PublishRequest 才 FOLLOWER。becomeLeader 的断言把顺序钉死:

// Coordinator.becomeLeader(节选)
assert mode == Mode.CANDIDATE : "expected candidate but was " + mode;
assert getLocalNode().isMasterNode() : ... + " became a leader but is not master-eligible";
mode = Mode.LEADER;

4. pre-vote:还没抬 term,先问「我联系得到多数吗」

正式选举会把 currentTerm 加 1(getTermForNewElection = max(currentTerm, maxTermSeen) + 1),而 term 只增不减。麻烦在分区里的孤立节点:它要是每次心跳超时都直接开选,term 会被抬得比健康一侧还高;分区愈合时,健康集群会被这份更高的 term 逼着重新选举——明明什么都没坏,却要中断一次。ES 的解法是 pre-vote:用假投票先试探「现在联系得到的节点,够不够一次选举多数」,够了才 startElection,才真正抬 term。

调度也前置了守门:节点发现逻辑更新 peer 列表时,若自己还是 CANDIDATE,先用已发现的 peer 加自己凑一份 VoteCollection 跑 isElectionQuorum——连理论上都不够多数,election scheduler 根本不启动。scheduler 到期再查一遍:还是 CANDIDATE、ElectionStrategy 认为本地节点可能赢、健康检查不是 UNHEALTHY,才 preVoteCollector.start。

真正干活的是 StatefulPreVoteCollector(动作 internal:cluster/request_pre_vote)。收到 PreVoteResponse 之后它不抬 term,而是把每份响应伪装成一个 Join 丢进 VoteCollection,再用和正式选举同一套 electionStrategy.isElectionQuorum 判断;达多数才 startElection.run()。对端的回答规则里藏着本课最重要的一句:

// StatefulPreVoteCollector.handlePreVoteRequest(节选)
if (leader == null) { return response; }        // 没 leader:给票
if (leader.equals(request.getSourceNode())) {
    return response;   // 罕见:leader 自己站下了,给它一张帮它连任
}
throw new CoordinationStateRejectedException(
    "rejecting " + request + " as there is already a leader");

已经有 leader,且请求不是那个 leader 发来的,直接拒绝。被隔开的那个节点联系到的另外两个,要么还认旧 Master、要么已经选出新 Master——都会拒绝。于是孤立节点凑不齐假投票多数,不会 startElection、不会抬 term。「Pre-vote 的好处」就钉在这一行异常上:它保护的是仍有 Master 的多数派,让健康一侧不必为少数派的试探进入选举。

5. 正式选举:抬 term、收 Join,quorum=2 从哪一行来

pre-vote 过了才真选。startElection 再次确认自己还是 CANDIDATE、自己可能赢,算出新 term,向发现到的节点广播 StartJoinRequest(动作 internal:cluster/coordination/start_join)。对端 CoordinationState.handleStartJoin 拒绝 term 没有严格变大的请求,然后持久化新 term、清空本 term 的选票、electionWon = false,回一张 Join(投票人=自己,候选人=发起者):

// CoordinationState.handleStartJoin(节选)
if (startJoinRequest.getTerm() <= getCurrentTerm()) {
    throw new CoordinationStateRejectedException("incoming term ... not greater than ...");
}
persistedState.setCurrentTerm(startJoinRequest.getTerm());
electionWon = false;
joinVotes = new VoteCollection();
return new Join(localNode, startJoinRequest.getMasterCandidateNode(), ...);

候选人把 Join 收进 joinVotes,用同一套多数派公式重算 electionWon;注意它会拒绝「比自己还新」的投票者——对方 last-accepted 的 term/version 更新,说明它见过自己没见过的状态,不能让过时节点靠拉票当选。electionWon 从 false 翻 true 的那一刻,processJoinRequest 才调 becomeLeader()。之后再来的 Join 不决定胜负,只服务以后的投票配置变更。

「3 节点要 2 票」不靠背,打开 VotingConfiguration.hasQuorum:

// cluster/coordination/CoordinationMetadata.java
public boolean hasQuorum(Collection<String> votes) {
    int votedNodesCount = 0;
    for (String nodeId : nodeIds) {
        if (votes.contains(nodeId)) { votedNodesCount++; }
    }
    return votedNodesCount * 2 > nodeIds.size();
}
投了票的节点(3 个 master-eligible)算式结果
n11 * 2 > 3 → 2 > 3不够:孤立的 Master 选不出,也 commit 不了
n1 + n22 * 2 > 3 → 4 > 3达多数:quorum=2
n1 + n2 + n33 * 2 > 3 → 6 > 3达多数(全体一致只是多数的特例)

VoteCollection.addVote 只统计 isMasterNode() 的节点——data-only 节点不进投票配置,没有票。给人看的版本是 ClusterFormationFailureHelper 那句 requiredNodes = nodeIds.size() / 2 + 1(3/2+1=2);单节点 start-local:1 * 2 > 1 为真,quorum=1,自己投自己就算数。选举多数还要比「当前一份配置」更严:ElectionStrategy.isElectionQuorum 要求 lastCommittedConfiguration 和 lastAcceptedConfiguration 同时达多数(联合共识——换投票配置的中途,新旧两份名单都要同意,才不会出现一半集群认旧名单、一半认新名单):

// ElectionStrategy.isElectionQuorum(节选)
return joinVotes.isQuorum(lastCommittedConfiguration)
    && joinVotes.isQuorum(lastAcceptedConfiguration)
    && satisfiesAdditionalQuorumConstraints(...);  // 默认策略恒 true

6. publish → commit:accept 不等于 committed

当上 LEADER 只是「这个 term 的选举赢了」。第 21 课 MasterService 算出的下一份状态要经 Coordinator.publish 发布,第一行守卫就验身份:

// Coordinator.publish(节选)
if (mode != Mode.LEADER || getCurrentTerm() != newState.term()) {
    throw new NotMasterException("node is no longer master for term " + ...);
}

handleClientValue 再挡一层(electionWon 为 false、或上一份还没被自己 accept,都拒绝),然后构造 PublishRequest,发给 ClusterState 里的每一个节点(不只投票配置成员)。两阶段的状态机在 Publication 里:每个目标先 sendPublishRequest(状态 SENT_PUBLISH_REQUEST);对端 handlePublishRequest 把新状态写入持久化的 last-accepted——此时还没 committed;Master 每收一份 PublishResponse 就记进 publishVotes,凑齐 publish 多数(同样要对 lastCommitted 和刚发布那份配置同时成立)才构造 ApplyCommitRequest:

// CoordinationState.handlePublishResponse(节选)
publishVotes.addVote(sourceNode);
if (isPublishQuorum(publishVotes)) {
    return Optional.of(new ApplyCommitRequest(localNode, term, version));
}
return Optional.empty();

拿到这份 ApplyCommitRequest 之后,才向仍卡在「等多数」的目标 sendApplyCommit(动作 internal:cluster/coordination/commit_state);对端 handleCommit → markLastAcceptedStateAsCommitted()——这一步之后才是「集群已经承诺这份状态」。若部分节点始终没回,剩余可能成功的节点凑不齐 quorum,Publication.onPossibleCommitFailure 直接判负:

// Publication.onPossibleCommitFailure(节选)
if (isPublishQuorum(possiblySuccessfulNodes) == false) {
    Exception e = new FailedToCommitClusterStateException("non-failed nodes do not form a quorum");
    ...
}

这个异常的语义写得很窄:抛它表示「已经 publish 出去,是否 committed 不确定」——下一任 Master 可能已经接受了这份状态;确定失败还没发出去用别的异常;已经不是 Master 用 NotMasterException。发布失败时 CoordinatorPublication 会调 becomeCandidate,本节点站下来。为什么必须两阶段?若一枪广播「这就是新状态」就算数:部分节点 apply、部分停在 N,下次选举时双方 last-accepted 不一致,按 fresher 规则拒票,集群可能选不出人。先让多数 accept 同一份 (term, version) 再广播 commit,少数派即便 accept 了、没 commit,也能在下次选举里被多数派的 fresher 状态带回来。默认 cluster.publish.timeout=30s;单节点 discovery 不挂这个超时——自己就是全部投票者。

7. 旧 Master 被隔离:四道门,哪道都过不去

把 3 节点集群的旧 Master n1 单独隔开(它听得见自己,听不见另外两个)。预测:它不能再成功更新 ClusterState。源码里有四道独立的门:

门机制结果
① pre-vote 被拒另外 2 个节点「已经有 leader」,抛 CoordinationStateRejectedException凑不齐假投票多数,不会抬 term
② publish 凑不齐onPossibleCommitFailure:非故障节点 1 * 2 > 3 不成立FailedToCommitClusterStateException,站下来
③ 站下来后直拒publish 要求 mode == LEADER 且 term 一致NotMasterException
④ applier 挂 blockbecomeCandidate 发现 applier 还写着 Master id → 加 no-master block(默认 cluster.no_master_block=write)写入类请求 503 "no master"

另一侧,多数派的 2 个节点:LeaderChecker 发现旧 Master 心跳失败 → becomeCandidate → pre-vote 彼此同意 → 选出新 Master → 正常 publish/commit。分区愈合后旧 Master 看到更高的 term,变成 FOLLOWER,接受多数派已经 committed 的状态。整场戏连起来走一遍:

本机单节点做不出这个实验:投票配置长度 1,1 * 2 > 1 恒真,自己就是多数。Coordinator.doStart 甚至要求:开了 discovery.type=single-node 就必须本地节点已在 committed configuration 里拥有 quorum,否则拒绝启动——一个「我发誓是单机」的进程带着 3 节点配置跑起来,既发现不了同伴、又选不了主,不如启动即失败。实验 5-7 验证的是另一面:quorum=1 时,PUT 索引这种真状态更新会成功、term 不变。

清理

思考题

1. 3 个 master-eligible 节点,当前 Master 是 n1。拔掉 n1 的网线(n2、n3 仍互通):n1 上立刻 PUT 一个新索引会怎样?n2 上同一条 PUT 呢?几秒后 n2 的 _cat/master 应看到谁?

n1 上失败——3 节点 quorum=2,它单独凑不成 publish 多数;具体走哪条失败路径取决于时机:还在自认 LEADER 时 FailedToCommitClusterStateException,站下来之后 NotMasterException 或 503 no master。n2 上:新 Master 选出前可能短暂 503,选出后成功(n2+n3 两票)。几秒后 n2 的 _cat/master 显示 n2 或 n3,不再是 n1;分区愈合后 n1 变 FOLLOWER,接受多数派已 committed 的状态。

2. 为什么必须有 pre-vote?若每次心跳超时都直接 startElection 抬 term,分区愈合时哪条不变量破了?handlePreVoteRequest 在「已经有 leader」时抛的那句异常,保护的是哪一侧?

term 只增不减。没有 pre-vote,孤立节点每次超时都把 term +1,愈合时它的 term 高于健康一侧;健康 LEADER 在 updateMaxTermSeen 里发现更高的 term 会自己站下来重选——一次「什么都没坏」的分区,变成一次全集群重新选举。pre-vote 让孤立节点在抬 term 之前就因凑不齐假投票多数而停手。"already a leader" 那句拒绝保护的是仍有 Master 的多数派:它们不必为少数派的试探进入选举。另一个细节:若请求恰好来自旧 leader 自己(它站下了但本节点还是 FOLLOWER),仍给一票帮它快速连任,而不是逼集群换人。

3. ElectionStrategy 要求 lastCommitted 和 lastAccepted 两份配置同时达多数:改成只看 lastCommitted,便宜了什么、冒了什么险?反过来,3 节点集群把 discovery.type 设成 single-node,doStart 为什么直接拒绝启动?

只看一份,换投票配置的中途会便宜(选举更容易凑票),但已经 accept 新名单、还没 commit 的节点,可能和停在旧名单的节点各选出一位自认达多数的 Master——脑裂窗口。两份同时要求多数,付的是「reconfiguration 期间选举更难」,换的是「新旧名单的交集必须同意」,这是联合共识。single-node 拒绝启动是同一枚硬币的另一面:doStart 要求本地节点对 committed configuration 自己就构成 quorum,3 节点名单上 hasQuorum({自己}) 为假,启动即 IllegalStateException——避免一个声称单机的进程带着 3 节点配置既不发现同伴、又永远选不出主地僵着。

陷阱

🕳 把 Mode 写成 Raft 教科书的一串状态:9.4.0 的 Coordinator.Mode 只有 CANDIDATE / LEADER / FOLLOWER 三个;没有 PRE_CANDIDATE,没有 LEARNER。形式化模型是 ZenWithTerms,不是 Raft 课文。
🕳 以为 LEADER 掉线可以直接切 FOLLOWER 跟新主:禁止 LEADER→FOLLOWER 直切。必须先 becomeCandidate 站下来,再从 CANDIDATE 走选举或跟随链——断言 mode == Mode.CANDIDATE 钉死了顺序。
🕳 把 accept 当 committed:对端写入 last-accepted 只是第一阶段;凑齐 publish 多数、广播 ApplyCommitRequest、对端 markCommitted 之后才算承诺。FailedToCommitClusterStateException 的语义是「committed 与否不确定」,不是「确定没成」。
🕳 在单节点上硬演「隔离 Master」:投票配置长度 1,quorum=1,永远凑得出多数——做不出 3 节点分区。失败路径对照源码四道门;真要演,起 3 个 master-eligible 节点的集群再拔网线。
🕳 data-only 节点也想要选票:VoteCollection.addVote 只统计 isMasterNode() 的节点。投票配置里全是 master-eligible 的 id;data-only 节点收 PublishRequest、apply 状态,但没有选举票。

速记

一句话内容
本课位置第 21 课的「Master 算出 N+1」之后:pre-vote → 选举 → publish → commit 四道门,全走完才算集群真理
Mode只有 CANDIDATE / LEADER / FOLLOWER;先 CANDIDATE 才能选,Join 多数才 LEADER,收到别人的 PublishRequest 才 FOLLOWER
quorumhasQuorum:votedNodesCount * 2 > nodeIds.size();3 节点=2 票,单节点=1 票;选举与 publish 各执行一次
pre-vote假 Join 试探多数,不抬 term;对端已有 leader 直接拒绝——保护多数派不被少数派的试探打扰
两阶段publish 多数 accept(term,version)→ 才发 ApplyCommitRequest;accept ≠ committed
隔离的旧 Master四道门:pre-vote 被拒 / publish 凑不齐 / NotMasterException / no-master block(写 503)
两份配置ElectionStrategy 要求 lastCommitted 与 lastAccepted 同时达多数(联合共识,防换名单脑裂)

心法:选上 Master 和改集群状态是同一件事的两个回合——都要 quorum;pre-vote 先问「联系得到多数吗」,term 只在真选举里加一。
