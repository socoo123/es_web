旧 master 被隔离后，谁还能决定新的集群状态？答案不是“谁的 term 大”，而是两个检查点：候选节点先取得有效选举多数，leader 发布的状态再取得有效接受多数。提交决定形成后，各节点的应用仍可先后完成。

22.1 先问“谁能领导”，再问“哪份状态能提交”

第 21 课的 MasterService 负责计算新的不可变状态；本课解释它凭什么成为共同承诺。以下主线按默认协调策略，插件可以增加选举或提交条件。一台机器把自己的 Mode 写成 LEADER，不代表它在网络故障后仍能推进状态。有效选举检查候选状态、任期和选票；默认策略下，有效发布检查同一份 (term, version) 的接受响应及投票配置。赢选举获得发布资格，不能代替下一次状态的多数接受。

先看候选节点这条路径。图中的“有效多数”不是“连接到两个地址”：响应还要通过健康、状态新鲜度、任期和策略条件；算票使用配置里的节点 ID。主线展示普通可当选节点的概念控制步骤，启动引导、传输重试和插件特例放在正文说明。

稳定运行期间，不是每个状态更新都重新选举。已有 leader 可以在同一 term 中发布多份状态。相反，正式选举先推进节点的 currentTerm，随后才可能拿到足够 Join；失败的一轮也会留下更高任期。同一节点在更高任期再次当选也很正常。因此“term 只在成功换主时加一”把协议轮次和成功结果混在了一起。

22.3 资格、名单、当前 master：三个不同的问题

node.role 中的 m 表示 master-eligible；master 列的星号表示这份状态中的当选节点；last_committed_config / last_accepted_config 才给出计算多数的名单。配置可以保留暂时离线的 ID，也可以从合格节点中选择一个子集。重配置器按存活情况、退役排除、现有名单和自动收缩设置选人，并倾向奇数规模；不能用当前节点总数或 m 的个数直接算 quorum。

每个非空配置独立计算 floor(N/2)+1。VoteCollection.addVote 先排除非 master-eligible，再按 ID 去重；hasQuorum 只统计配置成员。data-only 节点能收到状态并应用，但不会增加配置内有效票。它有十个数据分片，也不等于十票。

// CoordinationMetadata.VotingConfiguration.hasQuorum
有效票数 × 2 > 配置成员数
// 不同配置分别算；不是把两个名单合成一个 N。
选举 = majority(lastCommitted) && majority(lastAccepted)
       && additionalQuorumConstraints
发布 = majority(lastCommitted) && majority(latestPublished)
固定配置例子票 / 算式结论
{n1,n2,n3}{n1}：1×2>3 为假本配置不足多数
{n1,n2,n3}{n2,n3}：2×2>3 为真本配置达到2票多数
C={a,b,c}；A={b,c,d}{a,b}：C 有2票，A 仅1票不能只看 C 就宣布选举成功
同上两份配置{b,c}：两份各2票双多数条件满足，仍需其他协议检查

“两份都够多数”不是要求两个名单完全一致，也不是只统计两个名单的交集。对于相同配置，任意两个多数集合必相交；结合任期、投票规则、状态新鲜度和配置变更限制，才能维持协议安全。把全部保证压成“同一时刻全网只能有一个自称 master”的一句话，会漏掉本地认知滞后和跨 term 的故障过程。

voting_only 为什么也有 m？

它参与投票，但不承担稳定 master 的职责。9.4.0 的插件策略还有启动或转移更鲜状态时的内部选举特例，不能只看一行 m 就判断最终领导资格。 VotingOnlyNodeElectionStrategy 增加约束；传输拦截器让此类节点不把状态转移的成功响应当成正常发布成功。本课图和分区动画限定普通可当选节点，不演这条特例。

22.4 pre-vote 不是正式票，正式票也不是见票就收

候选节点的调度先检查能否参选、发现到的节点和自身健康，再发起 pre-vote。接收方不健康会拒绝；已知其他 leader 时会拒绝；无已知 leader 时通常回复；如果请求来自自己仍认定的旧 leader，则有允许回复的例外。候选方还会忽略比自己 last-accepted 更鲜的响应。将有效响应造为假 Join 后，使用选举双多数与策略检查；足够才发起正式选举。

pre-vote 的用途是降低隔离或落后节点轻易打断健康 leader 的机会，但“试探绝不碰任何任期信息”仍过强。接收和处理响应都调用 updateMaxTermSeen；若当前 leader 观察到更高 term，会安排推进任期与后续选举。准确说法是：假票不会直接变成正式票或自动写入一个新 currentTerm，不是所有高任期信息的副作用都被禁止。

正式 StartJoinRequest 提议 max(currentTerm,maxTermSeen)+1，可能跳号。接收方只接受严格更高的任期，先保存 currentTerm、清空本轮选票、置 electionWon=false，再返回带自己 last-accepted term/version 的 Join。候选方检查 Join 的 term 是否匹配，拒绝来自“比候选已接受状态更新”的投票者；相同接受 term 才继续比较接受 version。够双多数且满足策略，才完成当选。状态新鲜度不是“当前任期最大的机器无条件胜出”。

22.5 三个 Mode 与两个 term 视角

本地 Mode做什么怎样变化
CANDIDATE发现、试探或竞选；尚未获得有效领导权Join 满足条件转 LEADER；有效发布或满足条件的 follower check 可转 FOLLOWER
LEADER在匹配 currentTerm 的身份下发布高任期、发布失败等可回 CANDIDATE；不直接切 FOLLOWER
FOLLOWER跟随已知 leader 接收状态leader 失联可回 CANDIDATE；仍受任期检查

currentTerm 是节点协议状态，可先于本轮成功发布增长；metadata.cluster_coordination.term 属于 API 返回的集群状态快照。API 并不是把节点持久化 currentTerm 和所有失败轮次直接列出来。9.4.0 的 _cluster/state 通过 TransportLocalClusterStateAction 直接读取接入节点的本地状态，默认也不转发到 master；?local=true / false 已弃用且没有效果。不同接入节点的已应用视图在传播时可以不同，不能把增加 local 参数解释成换读取位置或触发选举。

同一稳定 term 中，master 为有变化的新状态推进 version，新快照有新的 state_uuid。一条创建索引请求还可能包含元数据创建、分片初始化和启动等多次更新；其他索引或节点活动也可能推进版本。无变化操作则可能不推进。实验可以比较“首次变更后版本增长、快照 term 保持”，不能预先把差值写死为1，更不能由两次状态 term 相同推断中间没有失败选举。

22.6 accept、commit、apply：三个不同边界

发布入口首先检查本节点仍是 LEADER 且 currentTerm 匹配新状态；handleClientValue 再检查 electionWon、版本推进、上次状态接受情况和配置变更条件。发布目标是新状态中的节点，包含本节点与非投票节点。实际传输可用 diff 或完整状态；本图不展开字节编码。

边界已经做到还不能推出
accept校验并保存 last-accepted；回复匹配 term/version单节点 accept 不证明已达提交多数；保存接口也不等于每种角色都做相同落盘
commitLeader 得到发布双多数接受，生成提交决定并通知所有目标都已收到通知、所有本地组件都已切换
apply目标节点对匹配快照标记 committed，交本地 applier 并确认全群任意节点视图完全同步，或文档副本写入已经成功

关键提交点是默认策略下的有效双多数 accept，不是全体收到 ApplyCommitRequest 或全体应用完成。默认 ElectionStrategy.beforeCommit 立即成功；插件可让这个钩子延后或失败，不能泛化为所有策略只需票数。晚到的接受响应也能被通知提交。跟随节点在 commit 通知处理中进入本地应用；leader 自己的实际 apply 在发布结束阶段。投票响应、应用确认和创建索引响应中的 acknowledged / shards_acknowledged 属于不同层，不能混成一个 ACK。

如果尚未提交且未来可能成功的节点也不够多数，发布判断无法成功；超时也可取消。默认 cluster.publish.timeout 为30s，single-node 的实现不调度这项发布超时；这不消除其他 API 等待和请求超时。FailedToCommitClusterStateException 的契约允许提交不确定性，master 动作还可能重试。客户端见到错误后，应读回资源再决定重做，不能认定状态已自动回滚。

22.7 分区：少数侧不能正常提交，不承诺即时退下

现在固定两份名单都是 {n1,n2,n3}，并把旧 leader n1 与另外两台完全隔开。n1 尚未检测到故障时仍可自认 LEADER，但它只有自己的有效票，不能正常完成需要2票的发布。n2/n3 检测失联后，若彼此可通信、状态和健康允许，就能经历试探、正式选举和新 leader 的发布；具体哪台当选、是否要重试、耗时多久，不能仅由三个节点数推出。

观察阶段协议或请求层边界
旧节点仍自认 leader发布不足有效多数，可能等待、失败或受后续故障检测影响
旧节点已经退为候选不能再以匹配 leader 身份正常发布；本地状态可加 no-master block
候选试探完全隔离时首先是联系不到多数；不是“网络断开还能收到另外两台拒票”
多数侧恢复新 leader 需通过任期、状态新鲜度和双多数，首份状态也需正常提交

默认 cluster.no_master_block=write 覆盖 WRITE 与 METADATA_WRITE，块的状态为503；可配置为 all 或 metadata_write。实际请求可能先等待 master、重试或在另一层超时，不能把每次故障响应写死为立刻503。这个块不是文档复制一致性的全部协议；本课讨论的是集群状态的选举与发布边界。

思考题

1. 三台都带 m，是否一定 quorum=2？四台都带 m，是否必须3票？

先读实际两份投票名单。非空名单 N 决定 floor(N/2)+1，并分别达到双多数；master-eligible 角色数量不等于名单数量。配置可能保留离线成员、排除退役成员或倾向奇数规模。仅当某份名单确实有3人，才在那份配置里需要2票。

2. term 从5变成6，能否证明新 master 成功当选并提交了一份状态？

节点 currentTerm 先在 StartJoin 中增长，随后才收 Join，可能本轮失败或同节点再次当选。API 返回的 coordination.term 又是快照任期，不能混为 currentTerm 全历史。成功当选与状态发布提交仍有各自的检查，不可仅看数字推断。

3. 名单 C={a,b,c}、A={b,c,d}，收到 a/b 的有效票够吗？

C 有2票够多数，A 只有 b 一票，不够。必须分别判断，不能以两份名单并集作一个 N，也不能只检查旧名单。若 b/c 都投有效票，两份均够2票；仍需匹配任期、候选状态与附加策略。

4. 两个投票者已经 accept，第三个还没 apply，状态是否一定尚未 committed？

按本课默认策略，若两个有效接受响应在需要2票的两份发布配置中均够多数，Leader 已形成提交决定，不必等第三台应用。它会发送提交通知；各节点匹配 term/version 后标记并进入本地 apply。单节点 accept、协议提交与全体本地应用不同步。

5. 隔离旧 master 后立即 PUT 失败，就能判定索引未创建且三秒后必恢复吗？

不能。旧节点可能暂时自认 leader，但固定三人名单下它不能正常完成新状态提交；请求还可能等待、重试或留下提交不确定性，应读回资源确认。多数侧选举取决于检测、通信、健康、新鲜度与重试，不给固定恢复秒数。集群状态协议也不能替代文档复制协议的解释。

陷阱

把当前角色当作全网瞬时共识局部节点可暂时自认旧 LEADER；安全结论应落在有效选举、任期、新鲜度与有效提交多数上。
把 term 当作成功换主计数器正式轮次可以失败、跳号或由原节点再次获胜；快照 term 与节点 currentTerm 也不是同一个观测接口。
把提交点推迟到全体收到 commit有效双多数 accept 已形成协议提交决定；通知、标记、apply 与请求 ACK 是后续不同层。
把前后差值写死为 +1建索引与分配、其他活动可推进多份状态；同定义重提可能无变化。先检查观察前提，不把 HTTP 成功与状态更新一一对应。
用单节点证明三节点故障single-node 的名单和发布等待有专门条件；本章分区动画是源码支持的概念路径，真实多节点故障需另行实测。

分区与错误固定名单少数侧不能正常提交新状态；不承诺即时退下、固定秒数或请求自动回滚

心法：先确认观察的是哪份状态，再检查谁有有效多数；选举资格、状态提交和节点应用分别判断。
