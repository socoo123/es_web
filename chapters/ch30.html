学习目标

  • 自己追一次搜索:从 POST /tut-l30-docs/_search 指出 REST handler、ActionType 名字、TransportAction 的 happy path、Query Then Fetch 的两阶段、SearchService 的异步签名、Engine 的 EXTERNAL searcher 各停在哪——用本页 13 个自测实验验证,不只是看图。
  • 知道测试里该找什么:对一条不变量(非法 search_type 的解析边界、from+size 撞窗口的 10010、默认 hits),能说出该打开同包 *Tests 还是 yaml REST 用例,以及断言长什么样——实测文案与测试断言一字不差。
  • 选出下一个要读的模块:用三步主链(REST → TransportAction → 测试)从一条真实 REST 路径走进一条教程没走完的路(kNN、ES|QL、某个 x-pack),而不是从包名闲逛。

1. 心智模型:六篇接到一次请求上

收官不把 29 课再贴成一张墙。一次 POST /idx/_search 在集群里换了几次身份、碰了几块存储——六篇的职责都挂在这条链上。前提:索引里已有文档并且已经 refresh。

篇接到这次 POST /idx/_search 上的角色
全局认知(ch01-05)集群、节点、索引、分片已经存在;请求打到某个节点;配置决定这台节点是谁
请求处理(ch06-10)HTTP 适配成内部请求、凭动作名找到执行器、异步扇出不占线程、节点间帧
数据写入(ch11-15)SEARCH 读的是 Engine 已 refresh 的 EXTERNAL searcher,不是 realtime GET 那条 VersionMap → Translog
搜索查询(ch16-20)默认 Query Then Fetch:网上先走 (docId, score),每个 shard 回 from+size 条,再只 Fetch 全局 Top-N 的 _source
分布式(ch21-25)协调节点拿一份不可变 ClusterState 快照选 shard;副本不与同号 primary 同节点;内存尖峰熔断 429 杀请求不杀节点
高级专题(ch26-29)安全先于 handler;ES|QL / ILM / Painless 是另一条 REST 入口,不在本链上

单节点上扇出可能根本不出网,Fetch 对单 shard 还可能跳过第二次往返——但模型仍然是 Query Then Fetch。不要因为本地看不到两跳,就把 SEARCH 理解成「放大的 GET」。

3. 第 1 步:从 REST 路径找到 Handler,停在 execute(TYPE)

不要从 org.elasticsearch.search 逛起。全局搜路径字面量命中 RestSearchAction,先抄路由(确认 9.4.0 没有 7.x 那种 /{index}/{type}/_search):

// server/src/main/java/org/elasticsearch/rest/action/search/RestSearchAction.java(节选)
@Override
public String getName() { return "search_action"; }        // REST usage 名,_nodes/usage 里见(实验 12)

@Override
public List<Route> routes() {
    return List.of(
        new Route(GET, "/_search"),   new Route(POST, "/_search"),
        new Route(GET, "/{index}/_search"),   new Route(POST, "/{index}/_search"));
}
// prepareRequest 只做适配:
cancelClient.execute(TransportSearchAction.TYPE, searchRequest, new RestRefCountedChunkedToXContentListener<>(channel));

路径在 PathTrie 上配不上任何 Handler 是 400 no handler found,不是 404;404 是 Handler 自己决定的「资源不存在」(实验 4 实测)。GET 和 POST 都能打 _search。这一步必须抄下的接头是 execute 的第一个参数 TransportSearchAction.TYPE;HTTP 断开时 RestCancellableNodeClient 负责取消对应 task——适配层的附加职责,仍然不是搜索算法。两套名字最容易追丢:getName() = "search_action"(REST usage);TYPE.name() = "indices:data/read/search"(Action,_tasks 里看到的是它);分片相位再挂后缀 [phase/query] / [phase/fetch/id](SearchTransportService 的常量)。三套名字不混,追丢率减半。

4. 第 2 步:凭 Action 名走进 TransportAction,只跟 happy path

NodeClient 不 new TransportSearchAction()——连接两层的是全局唯一的操作名。happy path 四跳:doExecute → executeRequest(开头就 clusterService.state() 拿一份不可变快照,RoutingTable 从这份快照来)→ executeSearch → SearchQueryThenFetchAsyncAction(默认搜索类型)。数据节点上 Query 相位的 handler:

// server/src/main/java/org/elasticsearch/search/SearchService.java(节选)
public void executeQueryPhase(ShardSearchRequest request, CancellableTask task,
                              ActionListener<SearchPhaseResult> listener) {
    // 注意:返回 void,结果从 listener 回去——方法 return 时 Lucene 不一定跑完(第 8 课的形状)

// server/src/main/java/org/elasticsearch/index/engine/Engine.java(节选)
public final Searcher acquireSearcher(String source) throws EngineException {
    return acquireSearcher(source, SearcherScope.EXTERNAL);   // 只看见上次 refresh 之后的快照
}

无参/单 source 的 acquireSearcher 默认 EXTERNAL:刚写入、还没 refresh 的文档,Realtime GET 可以走 VersionMap → Translog 命中,SEARCH 这条链看不见它(实验 7-11 当场对照)。这一步允许你在 2000 多行的 TransportSearchAction 里迷路,规矩是只跟 happy path。两个工具兜底:

命名模式含义追 SEARCH 时的例子
RestXxxActionHTTP 入口:routes() + prepareRequestRestSearchAction
TransportXxxAction内部执行:TYPE + doExecuteTransportSearchAction
XxxService组件,不直接暴露 RESTSearchService、SearchTransportService
InternalXxx / AbstractXxx核心实现 / 扇出与生命周期框架InternalEngine、AbstractSearchAsyncAction
XxxTests / yaml约束清单RestSearchActionTests;search/30_limits.yml
XxxPlugin另一条入口的装载点EsqlPlugin → POST /_query(不是 /_esql)

「先接口后实现」:先在抽象 Engine.acquireSearcher 上确认默认 scope,再决定要不要进 InternalEngine 的 3000 行——一上来就读实现,会把 GET 的 VersionMap 和 SEARCH 的 searcher 缠在一起。别的模块同理:先 ClusterState 的字段再 Master 怎么发布;先 AllocationDecider 的 Decision.NO 再 balancer 怎么打分。接口上的方法名是不变量,实现是代价。

5. 第 3 步:用测试钉不变量,不要把测试当小说读

源码说「代码会怎么走」,测试说「作者认为怎样算对、必须怎样失败」。先按命名找:

你刚打开的生产类第一份测试往哪放
RestSearchAction同包 RestSearchActionTests
TransportSearchAction / SearchPhaseController同包同名 Tests(如 testReduceTopNWithFromOffset)
SearchServiceSearchServiceTests / SearchServiceSingleNodeTests
HTTP 契约、状态码、错误文案rest-api-spec/.../test/search/*.yml(yaml 走真实 HTTP)

打开之后用问题当过滤器,四类各举一例:解析边界——RestSearchActionTests.testIllegalSearchType 把 search_type=some_search_type 钉成 "No search type for [...]"(实验 5 实测同文案);窗口不变量——yaml search/30_limits.yml 用 catch: 配 from: 10000,断言文案含 10010(实验 6 实测同文案);默认行为——yaml search/20_default_values.yml 的 Basic search 断言 refresh 后的 hits.total;分片执行——SearchServiceTests 的 testCanMatch* 系列,等你能指认 executeQueryPhase 之后再打开。跑 yaml 的形态(TESTING.asciidoc):./gradlew ":rest-api-spec:yamlRestTest" --tests "…test {yaml=search/30_limits.yml}"——本课不强制跑通,要练的是看见 catch: 就知道它在钉错误文案。测试基类分工读文件头就对上:ESTestCase 单测 / ESSingleNodeTestCase 单节点 / ESIntegTestCase 多节点 / yaml REST 走真实 HTTP。

6. 哲学当过滤器,不当海报

迷路时问:这段代码在保护哪条不变量?能当问题问的才留下:

不变量追这次 SEARCH 时你会看见
分片是最小执行单元协调节点扇出;不在本节点扫全集倒排
近实时SEARCH 用 EXTERNAL searcher,未 refresh 则 0 hits;GET realtime 是另一条路
全异步executeQueryPhase 把结果交给 ActionListener;扇出发完就释放入口线程
快照不可变executeRequest 开头 clusterService.state();RoutingTable 来自已 commit 的共识产物
过滤先于平衡副本不与同号 primary 同节点——SameShardAllocationDecider 在分配期,搜索期不再决定
防御性拒绝from+size 撞窗 → 请求失败;聚合内存尖峰熔断 429,不是把节点 OOM
可插拔新查询类型走 Plugin 扩展点,不把 server/ 的代码塞去依赖 modules/

思考题

1. 追这次 POST /tut-l30-docs/_search,你仍然不能独立走完的是哪一层(REST 接头、Action 名字、扇出、SearchService、Engine searcher、测试定位)?卡住的具体症状是名字对不上、方法找不到,还是单节点让你以为没有 Query Then Fetch?

不必「答对一层」,把卡住处写成可验证的缺口:getName() 与 TYPE.name() 分不清 → 回 RestSearchAction 与 TransportSearchAction 文件头(实验 12 的两套名字对照);单节点看不见两跳 → 记住 Fetch 对单 shard 可跳过第二次往返,但 (docId, score) 与 _source 仍是两阶段;进了 InternalEngine.get → 已经滑到 GET 的 VersionMap/Translog 去了(实验 8-9 的 0 hits vs 200 就是分界线)。缺口就是下一小时要打开的文件,不是再读一遍 29 课目录。

2. 假设要给「每个 shard 回 from+size 条」补一条保护,避免以后有人改 getTopDocsSize 却不改窗口检查。你会先打开哪一份已经存在的测试?要找的是异常消息、hits 条数还是 catch: 正则?为什么不先写一个新的 500 行集成测试?

先打开已有约束:yaml search/30_limits.yml 的 catch:(from+size → 10010,实验 6 实测同文案),或 SearchPhaseControllerTests.testReduceTopNWithFromOffset。已有用例更短、断言已经钉死文案——catch: 正则就是「这条错误文案不许变」的契约。500 行集成测试会把「窗口算术」淹没在集群启动里;而补一条 catch: 断言恰好也是贡献的第一步(CONTRIBUTING.md 的 good-first-issue 多是这类)。

3. 教程到此结束。下一个你要读的模块是哪一个(Lucene 倒排实现、dense_vector/kNN、某个 x-pack 插件、还是 CONTRIBUTING 里的 good-first-issue)?你准备用三步主链从哪一条 REST 路径走进去?

答案因人而异,判据只有一条:入口必须是一条真实路径。向量:搜 _search body 里的 knn 或 RestKnnSearchAction 的 routes(),不要从 Lucene HNSW 实现倒爬;ES|QL:POST /_query(第 27 课已给全链);安全深入:9201 上把 API key 的 role_descriptors 走一遍(第 29 课留的口子);贡献:先读 CONTRIBUTING.md,从补 yaml/单测开始,正好练第 3 步。「浏览 server/src/main/java」不算计划。

陷阱

🕳 把 SEARCH 当放大的 GET:SEARCH 走 acquireSearcher 默认的 EXTERNAL(只看 refresh 后快照),realtime GET 走 VersionMap → Translog——同一毫秒 0 hits vs 200(实验 8-9)。不要去 InternalEngine.get 里找 SEARCH,那是另一条请求。
🕳 混三套名字:search_action 是 REST usage 名(_nodes/usage);indices:data/read/search 是 Action 名(_tasks);[phase/query] / [phase/fetch/id] 是分片相位名。路径没配上 Handler 是 400 no handler,不是 404;404 留给资源不存在。
🕳 从包名闲逛,或一头扎进 2400 行:入口是路径字面量 → routes() → execute(TYPE);进了 TransportAction 只跟 happy path(doExecute → executeRequest → executeSearch → 两阶段),跨集群/PIT/DFS/canMatch 记「存在」即可,不画进主图。
🕳 把测试当小说读:用问题当过滤器:解析边界找同包 Tests 的非法输入用例,窗口找 yaml 的 catch:,默认行为找 20_default_values.yml。看见 catch: 就知道它在钉错误文案;不要从第一个 test* 读到最后一个。
