配置框架

配置如何读值与生效 · 约 18 分钟 · 前置:第 3、4 课 · 2 组实验 / 12 张操作卡 · 2 幅交互图（1 幅路径动画）· 0 个机制播放器

配置写进文件或 API 后，怎样变成业务代码读到的值？ES 用 Setting<T> 声明读值契约，用 Settings 保存一版键值；动态更新经过主节点校验、集群状态传播和节点消费者应用。读懂这三层，才能解释“文件里写了，为什么运行值不同”。

学习目标

  • 从 cluster.max_shards_per_node 的声明读出默认值、最小值、作用域与可变性，并预测数值 0 的请求结果。
  • 区分集群覆盖层与节点默认值；更新并清理一个 persistent 设置，用读回请求确认结果。
  • 对照主分片与副本设置的更新结果，说明准备阶段与消费者执行阶段各自保证什么。

1. 一串配置怎样变成 Integer？

Settings 保存当前这一版键值，Setting<T> 描述某一项的 key、默认值或 fallback、解析器、校验器与属性。后者让调用方拿到明确的 Java 类型；key 的注册与值的合法性仍要在运行时检查，拼写错误不会自动变成编译错误。

ShardLimitValidator 的声明提供了可验证的例子：

public static final Setting<Integer> SETTING_CLUSTER_MAX_SHARDS_PER_NODE = Setting.intSetting(
    "cluster.max_shards_per_node", 1000, 1,
    Setting.Property.Dynamic, Setting.Property.NodeScope
);
Settings snapshot = Settings.builder()
    .put("cluster.max_shards_per_node", "2000").build();
int limit = SETTING_CLUSTER_MAX_SHARDS_PER_NODE.get(snapshot); // 2000

1000 是这一声明的默认值，1 是最小值。get(settings) 取原始值后解析和校验，整数解析器拒绝小于 1 的值；并非先把 0 作为有效配置发布，再交给业务纠正。实验 A 会先发送 0，再发送 2000，对照拒绝与成功路径。该配置用于限制增加开放分片的操作，不是单个节点实际分片放置的硬上限，也不会因为降低数值就删除现有分片。

Settings 的普通键值映射不可变：builder() 生成新对象，旧读者仍持有旧快照。动态更新还要通知消费者更新自己的缓存字段；旧对象不会被原地改写。安全值另由 SecureSettings 接口处理；普通设置的 Filtered 可使相关 API 输出移除敏感项，不能一概理解成显示星号。

2. 作用域与可变性要分别判断

先问“谁拥有这项配置”，再问“何时允许更新”。NodeScope 表示集群级或节点配置文件级设置，不保证每个节点都配置相同，更不保证可用集群 API 修改；只有被注册并允许动态更新的相关设置才走这个 API。IndexScope 则属于具体索引。

属性判断什么本课例子与条件
NodeScope集群 / 节点配置范围cluster.max_shards_per_node 还带 Dynamic，可通过集群 API 覆盖节点本地值
IndexScope每个索引独立的设置两个索引可以有不同副本数，更新目标由索引路径限定
Dynamic允许在运行时更新index.number_of_replicas 可在开放索引上更新；分配完成仍有自己的等待条件
Final禁止更新已存在对象的该设置index.number_of_shards 连关闭索引后也不能直接更新

Dynamic 与 Final 并不穷尽所有配置：部分非 Dynamic、非 Final 索引设置可以在关闭索引后更新，具体还受该设置与 API 的限制。Final 拒绝请求时原设置不变，已有文档不会因这次失败而失去路由；需要不同主分片布局时，可按条件 split/shrink 到新索引，或 reindex，不能据此说分片布局永远无法调整。实验 B 将分别更新主分片数与副本数，再读回确认。

源码依据：属性与索引更新条件

Setting · Property 解释作用域、Dynamic 和 Final；IndexMetadata · 主分片 / 副本声明 对照实际属性。MetadataUpdateSettingsService · 开放 / 关闭索引更新分支 选择动态更新或普通更新；两者最终都会受 AbstractScopedSettings · updateSettings 的 Final 检查约束。

3. 谁覆盖谁？null 又恢复到哪里？

对通过集群 API 管理的同名动态设置，优先级是 transient → persistent → 节点本地配置 → Setting 默认值。节点本地配置包含启动时已合成的配置，不只是一份 yml。Metadata 先放 persistent、再放 transient；节点应用时再将这份集群设置覆盖本地配置。

来源保存与观察清理的含义
persistent进入持久化集群元数据，支持完整集群重启后的恢复；推荐用于集群设置变更该层指定 key 设为 null，删除覆盖
transient参与当前集群状态，但不持久化；完整重启会丢失，滚动重启不能当作清理流程也应明确置 null，不能等重启
节点本地 / 默认没有更高覆盖时作为回退；各节点本地配置可能不同清理高层后回到仍存在的下一层，不一定是代码默认

GET /_cluster/settings 分别返回覆盖层，不是一个自动合并的“最终值”字段。include_defaults=true 增加相对于集群设置的默认 / 回退项，其中可包含处理该 REST 请求节点的本地配置，不能把 defaults 都当作硬编码默认或所有节点的运行快照。本课仅在无同名 transient、persistent、本地覆盖的单节点学习环境下预期 1000；清理 persistent 后再请求读回验证。

源码依据：合并、持久化与 defaults

Metadata.Builder · build 的覆盖合并；applySettings · 节点配置合并；Metadata · 持久化上下文只写 persistent settings；RestClusterGetSettingsAction · response / diff。persistent 的使用建议见官方 Cluster update settings API；具体优先级和存储结论已核对 v9.4.0 源码。

4. 动态更新：主节点预检，节点应用

一次 PUT /_cluster/settings 要先识别配置项、检查可变性与值，再构造新的 Metadata 和 ClusterState。SettingsUpdater.updateSettings() 还会对候选状态运行 validateUpdate()：解析并触发消费者的更新校验，但不执行消费者。失败的候选状态不会作为成功更新返回给主节点任务。

各节点收到状态后，ClusterApplierService 调用 clusterSettings.applySettings()，合并本地配置与集群覆盖，形成当前 / 前一版快照。它先把所有更新准备成 Runnable，全部准备成功才依次运行。ShardLimitValidator 在构造时读取一次限额，再注册消费者，将后续新值写入 AtomicInteger。

“先准备、后执行”只保证准备阶段失败时不会开始执行消费者。执行仍是逐个 run()，没有把所有业务字段组成一个可供任意线程原子读取的事务，也没有消费者抛异常后的通用回滚。单个 AtomicInteger 的可见性不等于多个设置一起原子切换；相关设置要靠自己的组合校验与消费者实现保护。实验读回能证明覆盖层的结果，不能测出所有线程在同一瞬间看见新值。

成功响应中的 acknowledged 反映状态更新的确认结果，不是每项业务后果已经完成的通用保证。尤其更改副本数后，是否完成分配应另外看本章索引健康；本课使用明确等待条件，不拿整个集群的颜色替代本章索引状态。

思考题

1. 限额改成 0，或降低到小于现有分片总量，会怎样？

0 违反最小值 1，更新被拒。合法降低不会删除存量分片；它约束后续会增加开放分片的相关操作。实际限额还与节点角色、开放分片数及分片组有关，不是逐节点的放置计数。本课把值调到 2000 只为观察更新，不提供容量建议。

2. 先收集 Runnable 再执行，是否保证所有线程只读到完整的新配置？

准备失败时消费者不会开始执行。准备成功后逐个 run，无法由此推出多个业务字段跨线程原子可见；执行时异常也没有通用回滚。不可变 Settings 保护的是该快照，消费者缓存与其组合一致性要分别分析。

3. persistent 设为 null 后，为什么不一定回到 1000？

null 删除指定覆盖层。仍有 transient 时它继续优先；没有集群覆盖时回退到节点本地配置，再到声明默认。只有本课无其他覆盖的前提满足时，清理后才预期 1000。defaults 也可能反映处理请求节点的本地配置。

4. Final 更新被拒后，现有文档会找不到吗？关闭索引有用吗？

请求被拒，主分片设置仍为原值，不会因该失败破坏既有路由。Final 在关闭索引后仍拒绝；满足条件的 split/shrink 或 reindex 创建目标索引，是另一套操作。

陷阱

NodeScope 不等于全集群同值它区分配置范围；是否支持 API 更新、是否必须跨节点一致，还要看属性与实际机制。
重启不能代替清理transient 不持久化，但滚动重启不是删除覆盖的承诺。用 null 删除本课指定 key，并读回；原有覆盖需要恢复原值。
defaults 不全是硬编码默认处理 REST 请求节点的本地配置也可能成为回退；先看两层集群覆盖，再查相关节点配置。
成功确认不代替分配等待副本设置可在线改，健康结果还取决于节点、分配与其他条件；只观察本章索引并设置等待超时。

速记

线索结论
快照与契约Settings 保存键值；Setting<T> 定义默认、解析、校验与属性
属性作用域与可变性分别判断；Final 禁止原对象更新，关闭索引也不绕过
覆盖transient → persistent → 节点本地 → 默认；null 只删指定层
传播主节点校验与预检 → 新集群状态 → 各节点合并、准备与执行
执行边界准备失败不执行消费者；顺序执行不等于跨线程事务或通用回滚
证据读回覆盖层、索引设置与健康；defaults 不能代表所有节点运行值

配置声明告诉你能不能改；覆盖层和消费者告诉你现在读到什么。
