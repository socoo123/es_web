配置框架

类型安全的配置系统 · 约 14 分钟 · 前置:第 3、4 课 · 8 个实验

学习目标

  • 打开一处 Setting.intSetting(...),说出它的 key、默认值、最小值和两个 Property。
  • 改一个 Dynamic 集群设置并用 _cluster/settings 对照生效值;改 Final 设置时能从报错对上 Property.Final。
  • 说出一次 Dynamic 更新的传播链:Master 写 ClusterState → 各节点 ClusterSettings → listener。

1. 心智模型:配置项是带类型的契约

传统 Java 项目读配置,拼错 key 运行时才炸、转型失败才炸、没有默认值、改完要重启。ES 把每一项写成 Setting<T>:key 是常量、类型是泛型参数、解析和校验发生在 get() 里——

public static final Setting<TimeValue> DEFAULT_SEARCH_TIMEOUT = Setting.timeSetting(
    "search.default_search_timeout",
    NO_TIMEOUT,
    Property.Dynamic,
    Property.NodeScope
);
TimeValue timeout = DEFAULT_SEARCH_TIMEOUT.get(settings);  // 拿到的是 TimeValue,不是 String

第 3 课见过启动时谁覆盖谁(进程传入 > 命令行 > yml > 代码默认)。这一课多一层:启动之后,Dynamic 项还能经 API 写进 ClusterState,盖过 yml 同名值。

2. Setting<T>:声明即契约

一个 Setting<T> 钉死四件事:key、默认值(或 fallback)、解析器/校验器、一组 Property。精读 cluster.max_shards_per_node 的声明(ShardLimitValidator):

public static final Setting<Integer> SETTING_CLUSTER_MAX_SHARDS_PER_NODE = Setting.intSetting(
    "cluster.max_shards_per_node",
    1000,   // 默认
    1,      // 最小值(不是最大值;最大走另一个重载)
    Setting.Property.Dynamic,
    Setting.Property.NodeScope
);

intSetting 把默认值编成字符串存进 Setting,真正变成 Integer 发生在 get(Settings)。最小值 1 不是注释——是解析器里的 if (value < minValue) throw …,所以 PUT 0 进不了 ClusterState,不是「先写入再被业务拒绝」。索引级的同类声明在 IndexSettings(index.max_result_window,默认 10000,Dynamic + IndexScope)。工厂还有 boolSetting/timeSetting/byteSizeSetting/simpleString 等,用到再查。插件在 getSettings() 里声明的项,启动时登记进 SettingsModule——没登记的 key,动态更新会报 not recognized。

3. 作用域与可变性:两张正交的表

作用域NodeScopeIndexScope
粒度整个节点/集群一份每个索引可以不同
写入yml 或 PUT /_cluster/settings建索引时,或 PUT /idx/_settings
例子cluster.max_shards_per_nodeindex.max_result_window
可变性DynamicFinal
运行时 API可以改,不必重启拒绝更新
关闭索引再改?可以仍然不行(Final 比「非 Dynamic」更硬)
例子index.number_of_replicasindex.number_of_shards

index.number_of_shards 显式标了 Property.Final:主分片数参与 routing 哈希,改了已有 _id 就找不回来(第 1 课思考题);副本数是 Dynamic,所以能在线加副本。集群 API 还有一层寿命:transient(重启丢失,临时排查)与 persistent(留在集群状态,长期变更);合并是 put(persistent).put(transient)——transient 盖 persistent,两者都盖 yml 里的同名 Dynamic 项。

4. Settings 容器:不可变快照

Settings 是键值袋,不是 Setting<T>:后者是「这一项怎么读」,前者是「当前这一版配置」。内部是 Collections.unmodifiableNavigableMap,没有 put;要改就 builder() 攒一份新的:

Settings settings = Settings.builder()
    .put("cluster.max_shards_per_node", "2000")
    .build();
int limit = SETTING_CLUSTER_MAX_SHARDS_PER_NODE.get(settings); // 2000

搜索、写入、管理线程会同时 get()——不可变才能不锁。动态更新的真实含义是换一份新 Settings,再通知 listener 把各自缓存的字段改掉,不是原地改旧对象。密码一类走 SecureSettings(keystore),不出现在普通输出里;Filtered 属性则让 API 输出打码。

5. 动态更新:一次 1000 → 2000 的旅行

applySettings 的 javadoc 写明:要么通知所有 consumer,要么一个都不通知。实现是先把所有 SettingUpdater.updater()(内部完成解析+校验,失败即抛,后面的 run 根本不会开始)收集成 Runnable 列表,再统一执行——一次请求同时改 low/high 水位,不会出现「只改成功一半」。

清理

思考题

1. PUT cluster.max_shards_per_node=0 会成功吗?改成 500,已有 800 个分片的集群会立刻丢分片吗?

0 进不去:最小值 1,解析在 getValue 阶段就抛,进不了 ClusterState。改成合法的 500,存量分片也不会被删——这是 shard creation time 的限额,卡的是新建分片/新开副本,存量继续活着。

2. Settings 不可变,动态更新为什么还能「立刻生效」?applySettings 先收集再执行,防的是什么?

不可变让任意线程无锁 get;生效靠「新快照 + listener 改服务自己的字段」,拿着旧 Settings 的线程也不脏。先收集再 run 是原子性:getValue 解析校验,任一失败就抛、后面的 run 不开始(all consumers or none)。若发现一个改一个,同时改两个水位可能出现 low > high 的中间态,搜索线程读到半新半旧。

3. 改 max_shards_per_node,什么时候写 yml、什么时候 persistent、什么时候 transient?

yml 适合节点本地、重启才生效的项(路径、网络绑定);集群级 Dynamic 用 API:persistent 进集群状态、滚动重启还在,适合长期策略;transient 重启丢,适合「先试试」。API 盖 yml 换来不重启、全集群一致;付出的是「yml 写了 ≠ 运行值」——排障必须看 _cluster/settings,不能只看配置文件。

陷阱

🕳 yml 里写了 ≠ 运行中就是这个值:Dynamic 项会被 transient/persistent 盖住;排障先 GET /_cluster/settings?include_defaults=true,再看配置文件。
🕳 「关掉索引就能改主分片数」:不行。Property.Final 连 closed 索引的更新也拒绝——它比「非 Dynamic」更硬,因为路由哈希的除数不能变。
🕳 transient 盖 persistent:两者都在 ClusterState 里,合并顺序是 put(persistent).put(transient)——后写的 transient 赢;重启后 transient 丢失,又回到 persistent。

速记

一句话内容
契约Setting<T> 钉死 key/类型/默认/校验/Property;Settings 是不可变快照
作用域NodeScope 集群一份;IndexScope 每索引一份
可变性Dynamic 可 API 改;Final 永远不行(number_of_shards)
传播Master 写 ClusterState → applySettings → listener 改字段
原子性先收集 Runnable 再统一 run:all or none
寿命transient 盖 persistent,重启丢;都盖 yml

心法:配置是契约不是字符串;想知道运行时的真值,问集群状态,别问 yml。
