LESSON 13 · 第三篇 · 数据写入

批量写入

bulk 协议 · 逐条路由 · 条级成败 · 约 22 分钟 · 前置:第 10、12 课 · 13 个实验

学习目标

  • 发一次混着 index/create/update/delete 和坏条目的 _bulk,逐项预测 status;并区分「NDJSON 结构坏 → 整请求 400」与「某一条在 primary 上失败 → HTTP 200 + errors: true」。
  • 对 2 主分片的索引,用 Murmur3HashFunction.hash + Math.floorMod(hash, 2) 说出 _id="1" 与 _id="3" 各落哪个 shard,并用 _search_shards?routing=… 与 _cat/shards 的 docs 列核对。
  • 打开 BulkOperation 的分组代码与 ReplicationOperation.execute 的执行顺序,说出不变量「primary 先成功,再带 seq_no 复制到 replica」,以及 items[] 为什么按原始行序对齐。

1. 心智模型:协调节点的活是「分组」,不是「写 Lucene」

生产里文档几乎不靠一条条 PUT /_doc——一次 POST /_bulk 塞几百上千条,常常跨索引、跨 shard、跨节点。这一课只盯协调节点(接到这条 HTTP 的节点)在中间干了什么:把 NDJSON 切成条目、给每条算出 shard 号、按 ShardId 分堆、并行发给各 shard 当前的 primary。primary 内部怎么写 Lucene 和 translog 是下一课的事,本课停在「一份 BulkShardRequest 交到 primary 手上」。

一句话:bulk 的协调工作是分组,不是在协调节点写 Lucene。混批的四种操作在切条目之后就没有「批」的概念了——剩下的只有「条」和「堆」。

3. NDJSON 协议:两行一组,逐条独立

入口有四条路径,但 body 格式只有一种——NDJSON,一行 JSON 加一个换行符:

// RestBulkAction.routes()
new Route(POST, "/_bulk"),  new Route(PUT, "/_bulk"),
new Route(POST, "/{index}/_bulk"),  new Route(PUT, "/{index}/_bulk")

// body:两行一组,action 行 + source 行
{"index": {"_index": "t", "_id": "1"}}     ← 奇数行:做什么、写到哪
{"title": "A"}                              ← 偶数行:文档本身
{"delete": {"_index": "t", "_id": "3"}}    ← delete 没有 source 行

四种子操作各管一段:index 无条件写(同 _id 覆盖);create 只在 _id 不存在时写(存在即 409);update 的 source 行是部分文档或 script,会被翻译成 index 或 delete;delete 单行成项。三个纪律:每一行(包括最后一行)必须以 \n 结尾;action 行此刻就被解析,不是合法 JSON 对象 → 整请求 400;source 行只按字节切片交给 IndexRequest.source(),不解析 JSON——解析推迟到 primary 上,这是「条级失败」的伏笔(第 6 节)。

💡 Content-Type:本站实验运行器对整段 JSON 发 application/json,对按行的 NDJSON(包括故意写坏、留给 ES 报错的 body)发 application/x-ndjson。两种类型 ES 的 bulk 解析都接受;curl 直发 NDJSON 时用后者。

refresh 是每请求一份的粒度。?refresh=true|false|wait_for 是 query 参数,一次 _bulk 一份策略,写进每一份 BulkShardRequest——没有「条级 refresh」。默认 false:返回时文档只在 translog/buffer。未改 refresh_interval 且分片仍在被搜索时,大约 1 秒内的自动 refresh 才会把它编进可搜视图;分片进入 search idle 后这只钟会停,下一次搜索可能自己触发 refresh(第 1 课的近实时)。wait_for 让这次写入搭「下一班自动 refresh」的车,返回即可搜,通常比 true(自己强制立刻 refresh)便宜。实验 9、10 做这个对照。

4. 逐条路由:一把哈希钥匙

分组之前,每条要先生成一个 shard 号。普通索引(IndexRouting.Unpartitioned)的公式:

// IndexRouting.java
protected int shardId(String id, @Nullable String routing) {
    return hashToShardId(effectiveRoutingToHash(routing == null ? id : routing));
}
protected final int hashToShardId(int hash) {
    return Math.floorMod(hash, numberOfShards);   // 新索引;老索引进另一分支
}
// Murmur3HashFunction.hash(String):char 按小端 UTF-16 写成字节,murmurhash3_x86_32,seed=0

有效键 = routing != null 则只用 routing,否则用 _id。三个「不要」:不要写成 hash % N——Java 的 % 对负数向零截断,而 Murmur3 经常是负数,Math.floorMod 才保证落在 [0, N);不要发明「hash('1')=1793」这类假数字——仓库测试 Murmur3HashFunctionTests.testKnownValues 钉死了输出;不要把 _id 当整数取模——键是字符串。

_id(无 routing)Murmur3HashFunction.hashfloorMod(…, 2)floorMod(…, 5)
"1"-12623559713
"2"-30392721312
"3"-115117240604
"abc"111883641914
"xyz"36597918000
"user1"44957825202

为什么是 Murmur3:非加密、CPU 便宜、分布相对均匀(减轻热点 shard)、确定性——同一有效键永远同一 shard。主分片数在创建时定死,所以 floorMod 的除数不能事后改(第 1 课:把 number_of_shards 从 2 改 3,旧文档 GET 就找错地方)。带自定义 routing 时,有效键整体换成 routing 字符串,不混入 _id:同一 routing=user1 的多篇进同一 shard(父子文档、同用户局部性的来源),代价是这把键可能把某用户做成热点;SEARCH 不带 routing 打全部 shard 仍能找到,GET by id 不带 routing 只打 hash(id) 那个 shard,经常 found: false(第 10 课的 404)。写路径不经过读侧的 OperationRouting.shardId——BulkOperation 直接 docWriteRequest.route(indexRouting),普通索引殊途同归到 Unpartitioned.shardId。核对落点用 _search_shards?routing=…(带 routing 时等价于写路径选片);不带 routing 的 _search_shards 返回全部 shard,别拿它当写路由的答案。

5. 协调节点:按 ShardId 分组

执行骨架在基类 TransportAbstractBulkAction.doExecute:先挂 indexing pressure,再 applyPipelines——有 pipeline 时先跑第 12 课的 IngestService.executeBulkRequest,跑完才进 doInternalExecute。分组发生在 ingest 之后,所以 pipeline 改 _routing 会真实改变 route() 的结果。doInternalExecute 自己不算 hash,只做「缺的目标能不能先建出来」(populateMissingTargets:index 请求在目标不存在时可自动创建;普通 delete 不会为了删一篇不存在的文档去建索引),然后把球交给 new BulkOperation(...).run()。分组的核心几行:

// BulkOperation.java(分组方法内)
IndexRouting indexRouting = concreteIndices.routing(concreteIndex);
docWriteRequest.preRoutingProcess(indexRouting);
int shardId = docWriteRequest.route(indexRouting);
docWriteRequest.postRoutingProcess(indexRouting);
List<BulkItemRequest> shardRequests = requestsByShard.computeIfAbsent(
    new ShardId(concreteIndex, shardId), shard -> new ArrayList<>());
shardRequests.add(bulkItemRequest);

route() 按操作类型进 IndexRouting 的不同入口,普通索引最终都落到同一套 Unpartitioned.shardId:

请求route() 走哪
IndexRequestindexRouting.indexShard(this)
DeleteRequestindexRouting.deleteShard(id, routing)
UpdateRequestindexRouting.updateShard(id, routing)

某一项在这里就抛了(缺 routing 且 mapping 要求、索引已关闭),addFailureAndDiscardRequest 记下失败,其它项继续进 map——「条独立」的第一层,还没到 shard。之后每个 ShardId 的列表打成一个 BulkShardRequest(带上 refresh 策略 / waitForActiveShards / timeout),client.executeLocally(TransportShardBulkAction.TYPE, …) 发出。注意:executeLocally 不是「primary 一定在本节点」——它只是在本节点启动这个 action,TransportReplicationAction 的 ReroutePhase 再按 ClusterState 把请求发到 primary 所在节点;跨节点时帧头里的 action 是 "indices:data/write/bulk[s]"(shard 子动作,与第 9、10 课 get[s] 同一套命名)。多个 ShardId 并行发出,RefCountingRunnable 等所有 shard 的 listener 都结束再拼响应——响应数组按原始条目的下标回填,不是按 shard 号排序,你看到的 items[0] 永远是 NDJSON 的第一项。把整条链连起来看:

6. 条级成败:HTTP 200 不是「全成了」

Bulk 不是数据库事务,不变量是每一项独立出结果。BulkResponse.toXContentChunked 写出的第一件事就是 "errors": hasFailures()——扫一遍 items,任何一项 isFailed() 就为 true;HTTP 状态码不是这个字段。两层失败不要混:

失败发生在哪客户端看见什么其它项
NDJSON 结构坏了:缺末尾 \n、action 行不是 JSON 对象整请求进不了 TransportBulkAction,HTTP 400没有「其它项」——请求没被切成 items
某项 source 字节原样到 primary 才解析失败(IndexRequest.source() 不解析 JSON)HTTP 200,"errors": true,该项 status 400 一类继续,201
create 撞已存在 _id(版本冲突)HTTP 200,该项 409继续,201
某 shard 整份 BulkShardRequest 失败(primary 不可用等)这份里的项都失败其它 shard 的项按自己的结果返回

这套设计的好处:一批 1000 条里 1 条 mapping 冲突,不该浪费另外 999 条已经算好路由、甚至已经写进其它 shard 的工作。风险对称:客户端必须扫 items[]——很多脚本只判断 curl 退出码或 HTTP 200,等于把失败项悄悄丢掉。

7. Primary 先成功,再复制到 replica

每份 BulkShardRequest 到了 primary 之后,顺序由 ReplicationOperation.execute 写死:

final String activeShardCountFailure = checkActiveShardCount();  // ① 先查 active 拷贝数
if (activeShardCountFailure != null) throw new UnavailableShardsException(...);
primary.perform(request, ...delegateFailureAndWrap((l, primaryResult) -> {
    handlePrimaryResult(primaryResult, l, ...);                    // ② primary 成功之后
}));                                                              //    才 performOnReplicas

handlePrimaryResult 在 primary 成功之后才取样 replication group 再 performOnReplicas——注释写明:recovery 可能在 primary 写入之后才开始,必须用写完之后的副本集合。客户端会等这些 replica RPC 结束(成功或失败)才拿到 bulk 项结果,但 replica 复制失败不会把这一项改成失败——primary 已经成功。失败的副本从 in-sync 集合摘掉(stale),节点回来后靠 Peer Recovery + translog 追赶;响应里 _shards.successful 可能小于 _shards.total。别把「等 RPC 结束」和「成功判据」混为一谈。

wait_for_active_shards 的检查发生在 primary.perform 之前,要的是「现在已经有足够多副本 active」。请求里是 ActiveShardCount.DEFAULT 时,TransportReplicationAction.resolveRequest 把它换成索引设置 index.write.wait_for_active_shards(默认 "1",只要 primary);不够数就等(超时来自请求的 timeout,bulk 常用 1m),仍不够则 UnavailableShardsException:

参数值含义
不传 / DEFAULT用索引设置,默认 1(只需 primary 已 active)
1至少 1 个 active 拷贝(通常就是 primary)
2primary + 至少 1 个 replica 已 active
all该 shard 的全部拷贝都 active
0 / NONE不等

Primary 上真正逐项执行的是 TransportShardBulkAction.performOnPrimary:while (context.hasMoreOperationsToExecute()) 逐项跑,update 先被 UpdateHelper.prepare 翻译成 index 或 delete;动态 mapping 要等 master 时这个 while 暂停,确认后从同一项重试。一项 SUCCESS 或 FAILURE 都走 markOperationAsExecuted → advance() 进下一项——一项失败不会 return 掉整份 BulkShardRequest。Replica 侧镜像「primary 已经决定的事」:performOnReplica 里,primary 失败且 seq_no == UNASSIGNED_SEQ_NO 的项 continue(没领号就不占号);已领号但失败的项用 markSeqNoAsNoop 占住序号,否则副本在该序号上出现空洞;成功项调 applyIndexOperationOnReplica(seqNo, primaryTerm, version, …)——序号来自 primary 的响应,不是 replica 自己 generateSeqNo()。

三个数记住顺序对齐这件事:

名字含义写路径上谁更新
seq_no这条操作在该 shard 上的序号primary 生成(LocalCheckpointTracker),复制时原样带给 replica
Local Checkpoint本副本已处理完的、从 0 起连续的最大序号每个副本自己推进
Global Checkpoint所有 in-sync 副本都追上的连续最大序号primary 按各副本汇报的 local checkpoint 计算

GET _doc 返回的 _seq_no/_primary_term 就是这条操作在 primary 上领到的那对值;primary_term 在一次 primary 任期内不变,重新选举后递增,replica 用 (seq_no, primary_term) 拒绝过期 primary 的旧复制。Engine 内部怎么写 Lucene/translog,是下一课。

清理

思考题

1. 单节点集群、1 主 1 副(yellow):?wait_for_active_shards=all 的 bulk 会怎样?同一批里写到另一个 green 索引的条目会跟着失败吗?

replica 从未 STARTED,凑不齐「全部拷贝 active」,这个 shard 的 BulkShardRequest 等到超时后以 UnavailableShardsException 失败。检查发生在每个 shard 自己的 ReplicationOperation.execute 开头(checkActiveShardCount),不是整份 HTTP bulk 一次。写到另一个索引的条目走另一个 ShardId 的 BulkShardRequest,不受牵连。默认(不传)只要求 1 个 active(通常即 primary),写入成功、集群仍 yellow。

2. 为什么 seq_no 只能由 primary 发号、replica 重放?拆掉这层改成「各副本自己发号」或「并行写、谁快听谁」,哪条不变量破了?

seq_no 是该 shard 操作日志的全局顺序。单点发号,副本重放同一序列,Local/Global Checkpoint 的「连续最大序号」才有含义。各副本自己发号:同一逻辑写在不同副本序号不同,checkpoint 无法比较,recovery 说不出「从 17 之后补给我」。先写 replica 再写 primary:primary 失败时副本上已有幽灵文档而协调节点把项标失败,读写永久分叉。「谁快听谁」连 version 和 mapping 以谁为准都定不下来。这就是 performOnReplica 对「失败但已领号」的项要 markSeqNoAsNoop 占号的原因——防副本序列出现空洞。

3. 客户端「任一项失败就整批重发」,会撞上什么?日志采集和转账流水谁适合这套「条级独立」?

已经 201 的项再写一遍:用 index 是覆盖(多写一次,version 涨);用 create 是 409。要么自己带幂等键,要么按 _id 只重发失败项。日志/指标采集适合条级独立:吞吐优先,失败项由采集器重试;代价是必须扫 errors 和每项 status。转账流水不适合拿 _bulk 当事务:全有或全无要靠应用层补偿。wait_for_active_shards=all 把「等所有副本 active」的延迟摊给这次写入,换「当时至少这些拷贝都在」的同步耐久——是延迟和耐久性的交换,不是正确性的魔法。

4. 为什么不能用不带 routing 的 _search_shards 推断一篇文档的写路由?_id=1 落 shard 1,是因为「数字 1」吗?

不带 routing 的 _search_shards 返回该索引全部 shard(搜索的 fan-out 集合);带 routing=x 时它等价于写路径对有效键 x 的选片。落点是 floorMod(Murmur3("1"), 2)=1——对字符串 "1" 哈希的余数,恰好等于 1 是巧合,反例是 _id="3" 余 0。同理,连续自增 id 的分布是哈希分布,不是 round-robin,3 篇写成 2:1 完全正常。

陷阱

🕳 只看 HTTP 200 / curl 退出码:200 只说明整批被受理执行,失败记在 errors:true 和各项 status 里。只盯状态码的脚本等于把失败项悄悄丢掉。
🕳 把「一条坏 JSON」当「整批 400」:坏 source 行是条级(HTTP 200 + errors:true);缺末尾 \n、action 行非法才是请求级 400。两层分不清,重试策略会放错层。
🕳 路由幻觉:_id 不是整数取模、bulk 不做均匀轮转——是字符串 Murmur3 的余数,连续 id 也会倾斜。带 routing 写入就得带 routing 读(GET 忘带经常 404);ingest 改 _routing 在分组之前生效(第 12 课)。
🌀 wait_for_active_shards 不是「复制必须成功」:它在 primary 执行之前检查「已经 active」的拷贝数(默认 1)。replica 复制失败不改变条目成败,只体现在 _shards 里;单节点 + 1 副本时 all 会一直等到超时。

速记

一句话内容
