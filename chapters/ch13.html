13.1 一个 bulk，谁负责分组，谁负责写？

本课锚定 Elasticsearch 9.4.0、Lucene 10.4.0，源码固定到 2e8528e。主线使用新建普通 standard 索引、stored source、非分区路由、无匹配模板；不展开数据流 failure store、时序路由与在线 resharding。POST /_bulk 把多个操作送入同一 HTTP 请求，减少逐条往返，但批量大小仍须按字节量、延迟和拒绝情况测量，没有固定条数能保证更快。

协调工作包括解析操作、摄取处理、解析具体写入目标、计算路由和分组。索引源文档实际由目标 primary 的分片写路径处理；“协调工作不写 Lucene”是职责边界，不能推断接收 HTTP 的机器不会写数据。单节点实验里同一机器兼任协调、ingest 与 primary；多节点时 shard action 才可能转发。

有管道的 index/create 请求先经过第 12 课的处理，再选分片，因此管道改 _index / _routing 会影响分组。普通写目标的缺失索引可能自动创建，但受设置、权限和请求条件约束；本课提前显式创建。普通内部版本 delete 不为不存在目标自动建索引，外部版本 delete 有例外。A10–A11 专门区分缺索引与缺文档。

13.2 为什么第二行坏 JSON 有时是整请求400？

NDJSON 是“一行 JSON 加换行”，不是一个 JSON 数组。index/create 后面跟完整文档，update 后面跟更新描述，delete 只有 action 行。出现 delete 后，后续 action 不再固定在奇数行；每行包括最后一行仍须换行。直发时使用 application/x-ndjson，本站运行器也会保留故意缺失的末尾换行。

{"index":{"_index":"tut-l13-items","_id":"x"}}
{"title":"A"}
{"delete":{"_index":"tut-l13-items","_id":"missing"}}
{"update":{"_index":"tut-l13-items","_id":"x"}}
{"doc":{"tag":"t1"}}

BulkRequestParser 先解析 action 元数据。对 index/create，它只切出第二行字节，普通无管道写路径随后解析文档，坏 JSON 可成为该项的 error。update 的第二行却直接调用 UpdateRequest.fromXContent，坏描述会在 bulk 解析时抛错。若配置摄取或使用其他索引模式，文档解析也可能提前；不能把“所有 source 都到 primary 才解析”当成统一规则。

入口另有增量路径。9.4.0 默认启用 rest.incremental_bulk，允许解析过程中按压力条件拆成多个执行批次；是否进入流式请求分支取决于实际 HTTP 入口。整包路径解析完才调用 bulk，增量路径可能先执行早先批次，再遇到后续坏行而返回请求级400。请求级错误不承诺整个输入完全没有副作用。本课坏 update、坏 action 与缺换行卡各只有一个项，避免用小样本推断大流式请求的回滚行为。

依据：按操作类型切行、index 与 update 第二行的不同解析、整包 / 流式入口、后续解析失败与块交接、增量默认开关、增量执行批次。

13.3 按哪把键选片，为什么结果仍保持输入次序？

本课新建普通非分区索引的有效键是 routing 非空时用 routing，否则用字符串 _id。ES 将字符串按 UTF-16 小端字节做 seed=0 的 Murmur3，再用 floorMod(hash,N) 得到分片号。Java % 对负数可能返回负余数；不能把 ID 当整数取模。两主分片时，键“1”的 hash=-126235597，余1；键“2”余1；键“3”的 hash=-1151172406，余0。

公式受索引创建版本约束：旧创建版本还使用 routingNumShards / routingFactor 分支；分区路由、其他 index.mode 与 resharding 另有处理。主分片数不能直接通过 _settings 改掉，失败更新也不会改变原索引路由；可按条件 resize 或 reindex 到新索引。不同 routing 字符串仍可能碰到同一片，所以漏带 routing 的 GET 不一定404，routing 也不是隔离权限。

BulkOperation 按完整 ShardId（索引身份和分片号）归组，保留每项的操作编号，并将 refresh、timeout、active 等待参数带入 BulkShardRequest。executeLocally 在本节点启动 shard action，复制动作框架再根据当前状态找到 primary。不同组可并发；各组结果按操作编号回填，items[0] 对应第一项操作，不是第一行或最先完成的分片。

同一具体索引、同一 ID / routing 的混合操作会进入同组，本课 index 后 update 可观察前项写入。不能据此要求跨分片全局执行顺序，其他并发请求也可能穿插。9.4.0 在显式启用受 feature flag 约束的批量优化、且组内只有 index/create 时，还能走 ShardBatchIndexer；该设置默认关闭。混合 delete/update 的组使用逐项路径，动态映射等待可能暂停并重试当前项。A 组明确 mapping，避免把映射更新时序混进实验。

依据：字符串哈希、创建版本的取模分支、非分区有效键、操作编号与分组、结果槽位与分片失败、批量优化或逐项路径、优化开关与适用条件、本地或远端 primary。

13.4 HTTP、error 和 result 分别说明什么？

bulk 不提供跨条目事务。正常返回 HTTP200 后，顶层 errors 来自 hasFailures 对各项 isFailed 的扫描。create 遇到已存在 ID 会409并带 error；存在索引内 delete 一个缺失 ID 却返回404 / result:not_found，没有 error，不单独使 errors 变 true。缺索引的普通 delete 是另一种404，带 index_not_found_exception；必须一起读 status、error 和 result。

触发条件响应范围与恢复
坏 action、坏 update 描述、未终止行请求级解析错误；大增量请求先前执行块不回滚，先核对写入状态
普通无管道 index 文档解析失败、create冲突正常 bulk响应中的条级 error；好项继续，修复输入或按业务语义重试
存在索引内 delete 缺 ID404 / not_found、无error；按删除的业务目标判断
分片写前 active不足、分片请求失败该组条目记失败；其他分片可成功，整批没有补偿回滚

“条级独立”说明结果与失败范围，不是彼此完全没有影响：同组 update 可依赖前项，批级验证、集群写阻塞或压力拒绝还可能产生请求级错误。结果的恢复规则也不同：对已成功 create 整批重发会冲突，重复 index 会再写版本，脚本 update 可能重复累加。超时或断线还可能发生在写入之后；先确认效果、使用业务幂等设计，再判断哪些项可安全重试。HTTP200、errors:false 都不是应用事务提交凭证。

依据：顶层失败扫描、isFailed 判断 error、not_found 的404、完成项后推进、全局写阻塞。

13.5 等 active 与等复制，为什么是两回事？

wait_for_active_shards 在 primary 执行前检查这份分片请求的 active 拷贝数。DEFAULT 取 index.write.wait_for_active_shards，默认1；本课也显式设1。all 要当前分片全部配置拷贝 active；0跳过这个数量检查，但仍须有可执行的 primary。它不规定复制后的成功票数，不改变副本设置，也不锁住之后的健康状态。

primary 先决定条目结果和操作序号，再重放给 replica。未分配序号的失败项跳过复制；已领序号的失败项可以 noop 占住序号；update 本身的 noop 也不需要再写一篇文档。seq_no 是分片内的操作序号，不能拿不同分片的值排序整批请求。失败项完成后继续推进，成功项的序号也不承诺从0开始。

完成响应还涉及复制及写后工作。普通 replica 故障通常记入 _shards 并通过失败处理维护副本状态；primary 条目成功可保留，successful 也可能小于 total。未分配副本不等于一次失败 RPC，单节点 yellow 的响应可为 total2 / successful1 / failed0。若失败处理发现 primary 已降级，或 primary 的 refresh / translog同步等写后工作失败，则可触发重试或分片失败；不能绝对说“副本失败永远不影响请求”。

D 组单 data 节点新建1主1副索引，先确认 yellow。一次混批指定 all：该索引的一项因副本不足超时503，0副且green目标的另一项仍成功。随后在yellow索引显式指定1，primary可写，索引仍yellow。这只验证写前门槛；本轮没有多节点复制故障实测，不用它证明故障恢复和耐久性。

依据：DEFAULT 解析、写前检查与 primary 执行、replica 的跳过与 noop、普通副本失败处理、未分配副本计入total、降级后的重试、primary 写后失败、不可用分片的503状态。

13.6 bulk返回，是否意味着全部分片都可搜？

refresh是请求级策略，传给实际触及的分片组；不能在每项 metadata 里指定不同 refresh，也不会刷新所有索引或未触及分片。false不要求刷新，但文档也可能已经被自动或外部刷新，不能宣称成功返回时“一定不可搜”。写完成、translog同步与打开搜索 reader 是不同边界；默认 realtime GET 不需要等搜索视图刷新。

true主动刷新相关分片；wait_for等待覆盖本次写入位置的刷新，可由周期或外部刷新满足，监听槽不足还可能强制刷新。两者都不修改 refresh_interval，也没有统一性能胜负。周期默认值不是可见性延迟上限；refresh=-1且无人显式刷新时，wait_for可能持续等待。C组先关闭周期，以新ID对照count0和GET命中；显式refresh后count1，再临时设1s验证wait_for并恢复-1。

依据：各分片请求的策略、三种刷新策略、refresh 与同步完成条件。

思考题

1. 坏index文档是条级错误，为什么坏update文档可以是请求级400？

index/create第二行在bulk解析阶段先切字节，本课无管道普通写路径再解析文档；update第二行要先解析成更新描述。错误范围来自实际解析位置，不能仅按“第二行”判断。增量请求后续解析失败也不撤销早先执行批次。

2. items顺序固定，是否能让跨分片的第二项依赖第一项？

不能。协调方按原操作编号回填，只保证响应对应关系；不同ShardId组可并发。A4的index/update针对同具体索引同ID，进入同组；跨分片依赖和并发写之间的一致性要另行设计。

3. HTTP200，某delete项404，顶层errors一定true吗？

不一定。存在索引里删除缺ID返回not_found而无error，通常不算failure；缺索引的普通delete404却带index_not_found_exception。顶层errors检查isFailed，不能由status≥400机械计算。

4. all失败的一项会撤销同批green索引的写入吗？

不会。门槛按分片请求检查，满足条件的其他组仍可成功。all只是写前active要求；之后副本仍可故障，也没有跨文档事务。改成1不改变配置副本数或集群yellow状态。

5. wait_for成功返回后，另一个未触及分片的旧文档是否一定可搜？

不能保证。策略覆盖本次实际触及分片上相关写入位置，不是全索引刷新。false也不代表一定不可搜；自动或外部刷新可能早已发生，旧ID还可能保留旧视图。要复现C2的0，必须恢复新鲜前提。

陷阱

只看HTTP或status：HTTP200也可能部分error；delete404/not_found也可能无error。一起核对errors、每项error和result，再按业务目标处理。
把bulk当事务：请求级400、超时和断线都不能普遍推出输入完全未写；增量已执行块没有回滚。整批重发create、脚本update会产生不同效果。
混淆等待阶段：active是写前门槛，_shards记录复制账目，refresh改变搜索视图；all不承诺后续每个副本成功。
用旧视图复现count0：refresh=-1不会清空旧reader。新ID、无外部刷新及清理后重做是实验条件；wait_for前先恢复有效的刷新来源。
角色等同物理节点：协调节点可同时承接本地primary写入；items顺序也不能代替跨分片执行顺序。

速记

边界记住什么
协议action决定行数；delete一行；update第二行立即解析；末行也须换行
增量可拆执行批次；后续解析失败不回滚先前已执行块
分组摄取在前，按完整ShardId归组；items按操作编号回填
成败HTTP200后逐项检查error/result；delete not_found不是error
等待active门槛在写前；复制和写后工作决定何时完成响应
可见性refresh只覆盖触及分片；realtimeGET与搜索reader分开

心法：一次bulk是有序输入与逐项结果的运输框架；判断写入，先辨范围，再读每项。
