LESSON 07 · 第二篇 · 请求处理

动作框架

从 REST 到内部执行 · 约 15 分钟 · 前置:第 6 课 · 9 个实验

学习目标

  • 做一次 GET 后,在 _nodes/usage 里找到它的 REST 名 document_get_action,在 _tasks 里认出 Action 名 indices:data/read/get 的样子,并说清这两个名字空间为什么互不通用。
  • 默写 TransportAction.execute 的骨架顺序——校验 → 引用计数 → 过滤器链 → 按需 fork → doExecute——并说出过滤器忘记 chain.proceed() 的后果。
  • 对三种「名字不在表里」各给对预测:未知 REST 路径的 no handler found、_tasks?actions= 配假名字的空列表、内部 execute 未登记 ActionType 的 IllegalStateException。

1. 心智模型:名字是接头

第 6 课的终点是 RestGetAction.prepareRequest 里那句 client.get(getRequest, listener)。REST 层就此交棒:它不查 Lucene、不碰 Engine,手里只有一个装着索引名和文档 id 的 GetRequest。本课回答:这之后,请求凭什么落到 TransportGetAction 头上?

答案不是 new。连接两层的是一串全局唯一的操作名:TransportGetAction.TYPE 的 name() 恰好是 indices:data/read/get。节点启动时 ActionModule.setupActions() 把「名字 → 哪个 TransportAction」登记成一张表,NodeClient 拿着这张表;client.get() 只是便捷方法,内部把 TYPE 填进统一入口 execute,按名字查表执行。

这串名字的辖区远不止查表:请求转发给持有分片的节点时用它,Security 授权用它,_tasks 过滤用它,第 9 课 Transport 帧头里的 action 字段还是它。ActionListener(onResponse / onFailure)是这条链的回调插口,本课只当「执行完了通知谁」,异步语义留给第 8 课。

3. ActionType:操作的身份证

ActionType<Response> 几乎没有行为,一个 name 字符串就是全部身份:

public class ActionType<Response extends ActionResponse> {
    private final String name;
    public String name() { return this.name; }
    @Override public boolean equals(Object o) {
        return o instanceof ActionType<?> a && name.equals(a.name);   // 相等只看名字
    }
    @Override public int hashCode() { return name.hashCode(); }
}

// TransportGetAction.java
public static final ActionType<GetResponse> TYPE = new ActionType<>("indices:data/read/get");

两个立刻用得上的事实。其一,相等看名字不看对象:查表结构是 Map<ActionType, TransportAction>,所以 new ActionType<>("indices:data/read/get") 这个新实例照样命中 TransportGetAction.TYPE 那一格——大小写不同才是另一个 key。其二,泛型 Response 运行时擦除:它存在的意义是编译期把 execute(getType, request, searchListener) 这种 listener 类型不匹配拦在编译器里,没有它,这类错会拖到运行时的 ClassCastException。

命名规范:category:scope/action

段常见取值含义
类别indices / cluster / internal索引数据、集群协调、节点内部协议
范围data/read、data/write、admin、monitor读文档、写文档、管理变更、监控
操作get、search、bulk、health…具体动词

名字不是随手起的:特权系统、审计、_tasks 过滤都按这串做前缀匹配。indices:data/read/* 和 cluster:admin/* 走的授权模型不同——依据是这串字符串,不是 Java 包名。internal: 前缀留给节点内部协议(recovery、副本复制的内部动作),第 9 课 Transport 帧里会再见到它。

常量name()一句话

声明方式有两代。主流是上面的 TYPE = new ActionType<>(name);遗留写法让 Action 自己继承 ActionType、常量叫 INSTANCE——第 5 课改过的 ClusterUpdateSettingsAction 就是这种,javadoc 明说这是 legacy、有点浪费。查表时两种都能用,ActionModule 一律 actions.register(某个 ActionType, 某个 TransportAction 类)。

4. ActionModule:启动时把名字写进表

setupActions() 里那张表是一个只在方法内存活的 ActionRegistry,按 name 字符串去重:

actions.register(TransportGetAction.TYPE, TransportGetAction.class);
// NamedRegistry.register 的去重逻辑
if (registry.putIfAbsent(name, t) != null) {
    throw new IllegalArgumentException(targetName + " for name [" + name + "] already registered");
}

所以 indices:data/read/get 在整个进程里只能有一个 handler。两个插件抢同一个名字,节点起不来(启动期 fail-fast),而不是运行时随机命中某一个。插件接在内置名单之后:ActionPlugin.getActions() 返回 ActionHandler 列表——reindex 那一组就是模块以插件身份登记的,不改内置名单。

表建好还要交货。ActionModule.configure() 用 Guice MapBinder 把每个 TransportAction 绑成 eager singleton,按 ActionType 填进 Map<ActionType, TransportAction>;节点构造尾声一句 client.initialize(actions, transportService.getTaskManager(), …) 把表交给 NodeClient。漏登记的代价不在编译期:要等有人 execute 那个名字,查表才会抛 failed to find action(第 6 节)。过滤器同源于插件:getActionFilters() 收进 ActionFilters,按 order() 从小到大排;X-Pack Security 的 SecurityActionFilter 返回 Integer.MIN_VALUE,永远排第一。

5. TransportAction:execute ≠ doExecute

TransportAction<Request, Response> 是所有内部操作的抽象基类:子类只实现 doExecute,公共骨架在基类——校验 → 引用计数 → 过滤器链 →(executor 不是 direct 才 fork)→ doExecute。注意顺序:校验和过滤器都发生在当前线程,过滤器走完、handler 是 doExecuteForking 时,才把真正的 doExecute 丢进线程池。旧版教程把它写成「先 fork 到线程池再走过滤器」,与当前仓库相反。

public final void execute(Task task, Request request, ActionListener<Response> listener) {
    handleExecution(task, request, listener,
        executor == EsExecutors.DIRECT_EXECUTOR_SERVICE ? this::doExecute : this::doExecuteForking);
}
private void doExecuteForking(Task task, Request request, ActionListener<Response> listener) {
    executor.execute(ActionRunnable.wrap(listener, l -> doExecute(task, request, listener)));
}

handleExecution 依次做三件事。第一,request.validate()——用返回值表示校验失败(返回 ActionRequestValidationException 或 null),抛异常反而算 bug(assert false + warn 再转 listener)。GetRequest.validate() 查 id 非空、version 对读合法,但 REST 的 /{index}/_doc/{id} 路由造不出空 id 请求——curl 缺 id 撞上的是第 6 课的路由层(实验 7 实测),这条校验真正拦的是内部 / Transport 调用者。第二,request.mustIncRef():请求对象在异步路径上被多处持有,注释写明「要么走到链尾执行真正的 action,要么完成 listener 短路」,两条路都用 Releasables.releaseOnce 避免双重释放。第三,总是 new RequestFilterChain 再 proceed——空 filters 数组也照走,第一次 proceed 时下标 i == 0 == filters.length,直接进 handler(「空数组就跳过 chain」是旧说法)。

public void proceed(Task task, String actionName, Request request, ActionListener<Response> listener) {
    int i = index.getAndIncrement();
    if (i < this.action.filters.length) {            // 轮到第 i 个过滤器
        this.action.filters[i].apply(task, actionName, request, listener, this);
    } else if (i == this.action.filters.length) {    // 下标用尽:真正的业务
        try (releaseRef) { handler.execute(task, request, listener); }
    } else {                                          // proceed 多调了
        listener.onFailure(new IllegalStateException("proceed was called too many times"));
    }
}

链就是一个 AtomicInteger 下标:每个 filter 必须调 chain.proceed(...) 才轮到下一个——忘了 proceed,请求挂起、listener 永不回,这是过滤器作者最容易踩的坑。对 GET 来说,doExecute 甚至不在 TransportGetAction 里:它继承 TransportSingleShardAction,基类的 doExecute 里 new AsyncSingleAction(...).start()——解析目标 shard、必要时把请求发给持有副本的节点、shardOperation 读 Engine(第 10 课)。本课的边界:过滤器放行之后,业务才开工。

6. NodeClient:查表发生在 Task 之前

// AbstractClient:便捷方法只是把 TYPE 填进统一入口
public void get(final GetRequest request, final ActionListener<GetResponse> listener) {
    execute(TransportGetAction.TYPE, request, listener);
}
// NodeClient:先查表,再登记 Task
public Task executeLocally(ActionType<Response> action, Request request, ActionListener<Response> listener) {
    return taskManager.registerAndExecute("transport", transportAction(action), request,
        localConnection, ActionListener.assertOnce(listener));
}
private TransportAction<Request, Response> transportAction(ActionType<Response> action) {
    TransportAction<Request, Response> transportAction = actions.get(action);
    if (transportAction == null) {
        throw new IllegalStateException("failed to find action [" + action + "] to execute");
    }
    return transportAction;
}

注意 registerAndExecute 的参数顺序:先 transportAction(action) 查表拿到执行体,再登记 Task。查不到就 IllegalStateException(消息里的 action 的 toString 就是名字),根本走不到 TransportAction.execute,更不会有 _tasks 记录。listener 包了 assertOnce——回调必须恰好一次,为什么、怎么保证,第 8 课。TaskManager 用 action 名登记、完成即 unregister,所以 _tasks 里看到的 action 字段和源码里的 TYPE 是同一串。

7. 过滤器与 Task:一根管子上的两个观察口

ActionFilter 能做的只有两件事:声明 order(),以及在 apply() 里二选一——自己完成 listener,或 chain.proceed(...)。ActionFilters 构造时按 order 升序排。链上最重要的是 X-Pack Security 的 SecurityActionFilter:order = Integer.MIN_VALUE,认证授权全基于 action 名字符串(经 SecurityActionMapper 可能映射成安全侧名字)——许可证过期时它按前缀拦 cluster:monitor/health* 一类监控、放行数据读写,判断依据是名字,不是 Java 类型。授权做成 filter 而不是每个 doExecute 开头复制一段,换来的是「所有执行路径(含没有 REST 入口的内部动作)共用同一条链」。

Task 是每个正在跑的 action 一份的跟踪对象。GET /_tasks 列的是 action 名不是 REST 路径,actions= 参数按前缀匹配,POST /_tasks/{task_id}/_cancel 取消。GET 通常太快抓不到——这不是 API 坏了,是完成后就 unregister;要看见它,得抓慢动作(长 search、wait_for_completion=false 的任务),或事后看 _nodes/usage 的计数——那是 REST 名字空间,下一个对照表里分清。另有 MappedActionFilter 只套某一个 Action;多数读者记住「全局链按 order 排序」即可。

清理

思考题

1. 过滤器是子类在 doExecute 里自己调用的,还是基类在 doExecute 之前走完的?空 filters 数组会不会绕过 RequestFilterChain?是先切线程池还是先校验?

基类、doExecute 之前。execute 把「executor 是否 DIRECT」折算成 handler 传给 handleExecution,但校验、mustIncRef、过滤器都在当前线程;空数组照样 new RequestFilterChain,首次 proceed 时 i == 0 == filters.length 直接进 handler。fork 只可能发生在过滤器走完之后(doExecuteForking 才碰线程池)。

2. 一个插件在 getActions() 里登记了也叫 indices:data/read/get 的 ActionHandler,节点起得来吗?运行时 new ActionType<>("indices:data/read/get")(新对象、旧名字)去查表,查得到吗?

起不来:NamedRegistry 的 putIfAbsent 命中重复,启动期就抛 already registered,节点 fail-fast,不会运行时随机命中某一个。查得到:Map<ActionType, TransportAction> 的 key 相等只看 name(equals/hashCode 委托给字符串),新实例照样命中内置 TransportGetAction。启动期按字符串去重、运行期按字符串相等——同一条不变量的两副面孔。

3. 为什么不许 RestGetAction 直接 new TransportGetAction().doExecute(...)?拆掉「名字 → 实现」这张表,哪条不变量先破?

表把名字从实现类上拆下来:插件不改 RestGetAction 也能插入新操作;Security 只认字符串,就能给所有操作(含没有 REST 入口的 internal: 动作)做授权;远程节点凭帧头里同一串名字找到 HandledTransportAction 登记的 handler。直接 new 还会绕过 ActionFilters 和 Task 登记——未授权也执行、_tasks 不可见。最先破的是「所有执行路径共用同一套过滤与登记」。

4. 认证授权为什么做成 order = Integer.MIN_VALUE 的 ActionFilter,而不是每个 doExecute 开头复制一段?换来什么,付出什么,忘了 proceed 谁收尸?

换来:所有执行路径(含 NodeClient / Transport 进来的内部请求——它们根本不经过 RestController)都过同一条链,新增 Action 不必改 Security 核心;拦的依据是名字前缀,所以许可证过期能只拦 cluster:monitor/health*、放行数据读写。付出:filter 必须 proceed——忘了请求就挂起,listener 永不回,没人收尸,Task 也 unregister 不了;多调一次则 IllegalStateException("proceed was called too many times")。Security 用 MIN_VALUE 把自己钉死在链头,order 从此成为安全不变量。

陷阱

🕳 拿 REST 名去 _tasks 找,或拿 Action 名去 usage 找:document_get_action 只在 _nodes/usage 的 rest_actions 里;indices:data/read/get 只在 _tasks、授权、跨节点帧里。两个名字空间没有交集。
🕳 「curl 打不到的路径」=「ActionType 未注册」?坏路径死在第 6 课的路由层,9.4.0 实测回 400 no handler found for uri,到不了 NodeClient;failed to find action 只有内部代码 execute 一个没登记的名字才会抛。404 属于「路由命中、文档不存在」。
🕳 ActionType.localOnly(name) 听起来像「只在本节点跑」:它与执行位置无关(且已标 forRemoval);跨节点转发是 TransportAction 子类自己用 TransportService 做的。望文生义会错。
🕳 写 ActionFilter 忘了 chain.proceed():链就断在半路,请求挂起、listener 永不回、Task 不 unregister;proceed 多调一次则是 IllegalStateException。过滤器只有「自己完成 listener」或「proceed」两条活路。
