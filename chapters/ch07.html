1. client.get 凭什么找到执行体？

第 6 课走到 RestGetAction.prepareRequest：返回的 consumer 在执行时调用 client.get(getRequest, listener)。这里的 client 是服务器内部的 NodeClient，便捷方法由 AbstractClient.get 实现，转成 execute(TransportGetAction.TYPE, request, listener)。现代 Java API Client 经 HTTP 调用，不直接拿服务器内部的 Map 查表。

TransportGetAction.TYPE 的名字是 indices:data/read/get。ActionType<Response> 的 equals / hashCode 只看 name，因此同名的新实例在 Map 中也能命中。Response 泛型帮助编译期推断监听器类型；它不参与运行时身份，也不保证随意伪造的同名对象拥有正确请求 / 响应类型。名字是动作注册范围内唯一的键，大小写不同就是不同字符串。

启动时 ActionModule.setupActions 收集内置与 ActionPlugin.getActions() 的 ActionHandler。它用 NamedRegistry 按 name 去重：重复名称使登记抛出 IllegalArgumentException，不会在运行期随机选择实现。随后 configure 用 MapBinder 将 TransportAction 绑定为 eager singleton；NodeClient.initialize 接收 Map<ActionType<?>, TransportAction<?, ?>>。

// NodeClient.executeLocally：调用参数先求值，再进入 registerAndExecute
taskManager.registerAndExecute(
    "transport", transportAction(action), request,
    localConnection, ActionListener.assertOnce(listener)
);

transportAction(action) 先查表，未登记就抛 IllegalStateException，消息含 failed to find action，此时还没有登记 Task。常用的 client.execute 路径由 NodeClient.doExecute 捕获这个异常并调用 listener.onFailure；直接调用 executeLocally 则会抛给调用者。未知 URL 或假的 tasks 过滤条件都不能复现这个内部查表失败。

2. 找到执行体之后，业务仍要等什么？

查表命中后，TaskManager.registerAndExecute 先用 action.actionName 登记 Task，再调用 TransportAction.execute。基类让不同动作共享校验、引用管理和过滤机制；子类业务在 doExecute。TaskManager 的监听器包装在成功与失败时先注销 Task，再向上游传递结果。因此一个进入 execute 后才失败的请求，与尚未查表命中的请求，有不同的跟踪边界。

校验先于过滤。request.validate() 返回 null 才继续；返回 ActionRequestValidationException 时通过 onFailure 完成。如果 validate 意外抛异常，源码另有断言、日志与失败处理。GetRequest.validate 检查 index 非 null、id 非空和读版本合法性。URL 缺 id 会先在 REST 方法匹配失败，不能把 405 当作这段内部校验的输出。

引用管理覆盖链尾与短路。校验通过后 mustIncRef() 增加请求引用，Releasables.releaseOnce 防止重复释放；一个释放点包在链尾 handler 的调用周围，另一个由 ActionListener.runBefore 包在回调前。它保护的是链阶段额外持有的引用，不能画成“整个业务期间一直持有，返回时才释放”。异步业务还要遵守自己的持有协议。

过滤器决定是否继续。ActionFilters 按 order() 升序排列，全局过滤器由插件贡献，也可加入针对指定动作的 MappedActionFilters。每个 filter 可以调用 chain.proceed，也可以主动完成 listener。空数组也创建 RequestFilterChain，首次 proceed 即到 handler；多调 proceed 会进入 proceed was called too many times 的失败分支。异步 filter 可以晚些继续；若最终既不继续也不完成，本骨架没有自动收尾的保证。

3. execute、线程池与远程 handler 的边界

execute 根据 TransportAction 基类持有的 executor 选择 handler，但不会先把校验和首次过滤丢进线程池。若是 DIRECT_EXECUTOR_SERVICE，链尾直接调 doExecute；否则 doExecuteForking 才调用 executor.execute。过滤器可异步恢复，所以“当前线程”指当次继续链的线程，不能保证仍是最初入口线程。

GET 是一个具体反例：TransportGetAction 传给 TransportSingleShardAction 的 GET 池用于分片操作；该基类给 TransportAction 的却是 DIRECT。它的 doExecute 启动 AsyncSingleAction，解析和选择分片后再按自己的 executor 安排读取。读源码要跟到真正传给基类的参数，不能从构造器里出现 GET 线程池就断定公共入口先 fork。详见 TransportSingleShardAction · 构造 / doExecute / asyncShardOperation。

本地动作 Map 与远程处理器表是不是同一张？

本地 Map 由 ActionModule 供 NodeClient 查找。远程请求名由 TransportService.registerRequestHandler 登记；HandledTransportAction 的构造器把远程 handler 接到 executeDirect，此前 Transport 分发已选择执行方式，executeDirect 不再按本图条件 fork。TransportSingleShardAction 则自行登记主动作和 name + "[s]" 分片动作。

TransportGetAction 构造时另建 TransportGetFromTranslogAction：它声明的是字符串 NAME，通过 HandledTransportAction 登记远程 handler。这一步不会自动把它加入 NodeClient 的 Map。名字相似也不能推断登记集合或全部路径的过滤行为；帧与实时读取分别留给第 9、10 课。

ActionType.localOnly(name) 已标记待移除，只是 new ActionType 的旧工厂方法。ActionType 本身不选择远程节点；需要转发时由具体 TransportAction 通过 TransportService 完成。Master、单分片、复制、广播与多节点基类分别组织不同业务，不是仅凭操作名前缀就选线程池或执行节点。

思考题

1. 同名的新 ActionType 能命中，为什么仍不该随意伪造类型？

equals/hashCode 只比较 name，所以同名 key 可命中；Response 泛型不参加 Map 的运行时身份。它提供编译期约束，不能证明你伪造的声明与已登记实现兼容。插件重名则在启动登记时被拒；调用已定义的 TYPE 可以保留源码的类型约定。

2. 为什么 actions=cluster:monitor/tasks/list 不会自动匹配 lists？

BaseTasksRequest 使用 Regex.simpleMatch；无 * 就按完整字符串相等，list 与 lists 不相等。lists 匹配父动作，lists* 才同时覆盖 lists[n] 等后缀。这个参数只筛选运行中的 Task，不执行也不检查给定动作是否登记。

3. 不调用 proceed 就一定是过滤器错误吗？

过滤器可以主动完成 listener，合法短路业务；也可以异步等待后再继续或完成。只有最终两者都不做才违反完成协议，导致请求可能停住、引用和 Task 无法经正常回调释放。多调 proceed 则有明确失败分支；不能把异步等待直接判成错误。

4. 查表失败与 validate 失败，哪一种已经建过 Task？

executeLocally 在调用 TaskManager 前先求值 transportAction(action)，查表失败未登记。validate 位于 TaskManager 已登记后调用的 TransportAction 内，失败走监听器包装并注销。因此任务可能存在得很短，事后空列表不能区分这两种失败，要结合内部异常和调用链。

5. 构造 TransportGetAction 时传了 GET 池，为什么公共 doExecute 仍可直接执行？

TransportSingleShardAction 给 TransportAction 基类传 DIRECT，自己保存 GET executor 用于分片执行。基类链尾直接调用协调 doExecute；之后的分片读取另行安排。每一层 executor 都有自己的使用点，必须跟着参数与调用点读。

陷阱

把三个观察口当作一张表usage 用 REST Handler 名，tasks 用内部动作名；前者累加、后者是运行时采样，两者都不是完整动作注册表。空 Task 列表不能证明动作未登记。
把所有过滤都写成入口线程上的同步执行首次校验和过滤在调用线程开始，filter 可异步恢复；链尾是否 fork 看基类 executor。executeDirect 与分片 executor 另有边界。
让错误 URL 代替内部查表错误未注册路径 400、缺 ID 方法不匹配 405，都尚未执行文档 GET；存在索引中的缺文档才是本组 404 + found:false。内部 failed to find action 是另一处失败。
看到 Task 就假定可取消或保留历史看 cancellable 与具体实现；完成时通常注销。任务结果存储是可选机制，不能把普通 _tasks 查询当作事后审计记录。

速记

边界一句话
身份ActionType 的相等只看 name；泛型不决定运行时 key。
登记setupActions 去重 → configure 绑定单例 → NodeClient.initialize 接表。
调用查表 → Task 登记 → validate → 引用持有 → chain → 链尾 doExecute。
线程filter 可异步继续；链尾按基类 executor 直接调用或排队，GET 分片池另看。
完成链额外引用释放一次；Task 包装在成功 / 失败回调时先注销，再通知上游。
观察usage 是 REST 累计计数；tasks 是动作运行采样，actions 无 * 时精确匹配。
