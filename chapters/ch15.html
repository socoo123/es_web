索引分片

一篇文档住哪:路由公式与分片的一生 · 约 16 分钟 · 前置:第 13、14 课(建议回顾第 5 课) · 16 个实验

学习目标

  • 对任意 _id / routing,说出三步片号演算:murmur3 哈希 → floorMod 取模 → 除数是主分片数;并用 _search_shards?routing= 亲眼核对(实验 5)。
  • 说出 index.number_of_shards 为什么是 Property.Final、number_of_replicas 为什么是 Dynamic;在单节点上演示 yellow↔green 在线往返(实验 8-9)。
  • 打开 IndexShard:指出构造函数只把状态置成 CREATED(Engine 还是 null),createEngine 发生在 RECOVERING 阶段的 innerOpenEngineAndTranslog;GET 被 readAllowed() 拦在 Engine.get 之前。

1. 心智模型:索引是名字,分片才是家

写入篇走到收官:第 13 课看请求怎么按分片切开,第 14 课进了一片里的 InternalEngine。中间缺的一环是——凭什么切给这一片?这一片又是个什么东西?答案的前半句是路由公式,后半句是:分片自己就是一个完整的 Lucene 索引。所谓「索引」,只是元数据里的一个名字(映射 + 设置);数据从来不住在索引这层,而住在它的每个主分片里——各有一套 segments、各有一份 translog、各做各的 merge,互不通气。副本不是「半份数据」,是把某一主分片整份复制到另一台机器。

3. 路由公式:一篇文档只属于一个主分片

ES 里没有「文档漂移」:一篇文档从写入那一刻起就钉死在一个主分片上,之后的每次读写都用同一个式子重新算出同一片——

shard = Math.floorMod( murmur3(_routing), number_of_primary_shards )

精读 OperationRouting.generateShardId,整个决定只有三步:

// server/src/main/java/org/elasticsearch/cluster/routing/OperationRouting.java
public static int generateShardId(IndexMetadata indexMetadata, @Nullable String id, @Nullable String routing) {
    final String effectiveRouting = routing == null ? id : routing;  // ① 钥匙:不传 routing 就用 _id
    ...
    return calculateScaledShardId(indexMetadata, effectiveRouting, hashOffset);
}

private static int calculateScaledShardId(IndexMetadata indexMetadata, String effectiveRouting, int hashOffset) {
    final int hash = Murmur3HashFunction.hash(effectiveRouting);     // ② murmur3:字符串 → 32 位有符号整数
    return Math.floorMod(hash, indexMetadata.getNumberOfShards());   // ③ 除数 = 主分片数,结果即片号
}

三个参与者各有讲究。钥匙:写、GET、搜索都要带同一把;不传 routing 时用 _id,而自动生成的 _id 是随机串,散列后近似均匀地铺满各片——这就是默认写入大致均衡的原因。哈希:选 murmur3 而不是 String.hashCode,要的是跨版本、跨客户端都稳定——片号绝不能依赖某个 JDK 的内部实现;"brown" 的哈希是 741580288,在你机器上、在 9.4.0 上、在十年后都一样。取模:用的是 Math.floorMod 而不是 %,因为 murmur3 返回有符号整数,可能为负——比如 "brown-1" 的哈希是 -616020358,% 3 会得到 -1(不存在 -1 号分片),floorMod 保证结果永远落在 [0, N)。

动画演的是「过程」:钥匙 → 哈希 → 取模 → 查表 → 挑副本。第 13 课的图 2 画过双钥匙路由的静态结构,这里补上它每一格真正发生的事。想把演算结果变成能敲的门,用 _search_shards:不带参数返回全部片(搜索要广播),带 routing= 只返回那一片(实验 4、5)。

💡 routing 的正确打开方式:按租户/用户固定钥匙(如 routing=user-42),让这个用户的全部文档聚在同一片——GET 和带钥匙的搜索都只打一片,省掉 fan-out。代价有二:高基数才均匀(一个巨租户会压出热点片);以及钥匙成了合同——忘带就敲错门(实验 7 亲眼看你扑空)。

4. 除数为什么钉死:Final 的机制本体

第 1 课的思考题问过「主分片数为什么改不得」,第 5 课撞过那道墙:PUT /idx/_settings {"index.number_of_shards": 5} 直接 400 final index setting [index.number_of_shards], not updateable。现在机制能说全了:主分片数是取模的除数。N 一变,所有存量钥匙的 floorMod 结果全部改写——文档并没有被删,但按新除数再也算不到它住的那片,等于就地蒸发。ES 没有在线重散列,与其提供一个必然弄丢数据的开关,不如用 Property.Final 干脆拒绝。想要不同的分片数,正道是建新索引 + _reindex。对照之下 number_of_replicas 只是「每片要几份拷贝」,不进公式,所以是 Dynamic,0↔1 随时在线改(实验 8-10)。

5. 从片号到节点:查路由表,自适应挑副本

片号只是编号,请求最终要落到「某台机器上的某份拷贝」。这一步不算,查表:cluster state 的路由表按索引组织(IndexRoutingTable → 每片一个 IndexShardRoutingTable),里面列着这一片的主分片和各副本分别在哪台节点、什么状态。OperationRouting.shards() 拿片号取到这一组,迭代器交给上层。

一组里选谁?搜索和 GET 是只读,读谁都拿到同一份数据,所以没有 preference 时走自适应副本选择(ARS,设置 cluster.routing.use_adaptive_replica_selection,默认 true、Dynamic):按各节点近期的响应时间与队列长度估计「谁最快」,而不是简单轮询——主副一视同仁。写路径是唯一例外:必须先写主分片,再由主复制给在位的副本,那是第 13 课的复制链。单节点是最直观的对照组:replica 无处放,路由表里这组只剩 primary 一个可选项,集群因此 yellow(第 1 课的结构性黄)——病根不在分片层,在拓扑。

6. 分片的一生:构造时还没有 Engine

路由表告诉你打哪一片;那一片在节点上是个 IndexShard 对象。它封装这一份拷贝的 Store 与 Engine,但注意时序:对象先存在,Engine 后出生。IndexService.createShard 里只做三件事——拿 ShardLock、建 Store(Lucene 目录的封套)、new IndexShard(...);构造函数末尾把状态置成 CREATED,currentEngine 那个 AtomicReference 还是空的。原因在于 IndexWriter 需要一份「已经合法」的 Lucene 目录,而 CREATED 这一刻目录可能是空的(新索引 EMPTY_STORE)、可能是半份别人拷来的文件(PEER)、也可能是上次崩溃留下的旧 commit(EXISTING_STORE)——构造函数无从判断文件是否就绪,Engine 只能等恢复阶段把目录摆好再建:

// server/src/main/java/org/elasticsearch/index/shard/IndexShard.java — innerOpenEngineAndTranslog
if (state != IndexShardState.RECOVERING) {
    throw new IndexShardNotRecoveringException(shardId, state);   // CREATED 直接调用?不行
}
synchronized (engineMutex) {
    assert currentEngine.get() == null : "engine is running";
    final Engine newEngine = createEngine(config);   // → engineFactory.newReadWriteEngine(第 14 课的 InternalEngine)
    getAndSetCurrentEngine(newEngine);
}

空索引也照样走恢复:EMPTY_STORE 先 markAsRecovering,「空目录」也是一种就绪,然后 createEngine,再 recoverFromTranslog(空 translog 也要走一遍)。本地重启是 EXISTING_STORE:先开 Engine,再把没 commit 的 translog 重放到这个已存在的 Engine 上——和第 14 课写入路径同一个不变量:Lucene 目录先能打开,translog 才有地方 replay。Peer 恢复(PEER)是文件和 operations 先落盘,再 openEngineAndSkipTranslogRecovery。三路殊途同归:Engine 诞生时,状态仍是 RECOVERING;变 STARTED 要等后续 updateShardState 看到 routing 已 active——「Engine 能用了」和「cluster 认为这片可服务」不是同一时刻。

于是有了两套名字都叫 STARTED 的枚举,别对着 _cat 找 CREATED:_cat/shards 的 state 列来自 ShardRouting.state()(RestShardsAction 里一行 table.addCell(shard.state())),那是 cluster state 视角的分配状态;IndexShardState 才是这个 JVM 里那个对象的生命周期,空索引上 CREATED→STARTED 只有几十毫秒,curl 抓不住,要看它只能去读源码:

_cat/shards 的 state(ShardRoutingState)本节点上的 IndexShardState
UNASSIGNED没有这个对象(不是 CLOSED;本节点根本没为这份拷贝 new IndexShard)
INITIALIZINGCREATED → RECOVERING → POST_RECOVERY

7. 读闸门:GET 在什么情况下到不了 Engine.get

第 10、14 课的实时 GET 故事(VersionMap、translog 直查)都默认一件事:这片允许读。IndexShard.get 进门第一行不是 engine.get,是闸门——

// server/src/main/java/org/elasticsearch/index/shard/IndexShard.java
private static final EnumSet<IndexShardState> readAllowedStates = EnumSet.of(IndexShardState.STARTED, IndexShardState.POST_RECOVERY);

private Engine.GetResult innerGet(Engine.Get get, ...) {
    readAllowed();   // 闸门在 Engine.get 之前:状态不在允许集,直接抛
    ...
    return withEngine(engine -> engine.get(get, ...));
}

允许集只有 {POST_RECOVERY, STARTED}——不含 CREATED、不含 RECOVERING、不含 CLOSED。带上 POST_RECOVERY 是故意的:盖住「Engine 已开、master 还没把 routing 标 active」的那扇窗,免得明明能返回 _source 的请求被判非法。状态不合法时抛 IllegalIndexShardStateException,消息形如 CurrentState[CLOSED] operations only allowed when shard state is one of [POST_RECOVERY, STARTED],其 status() 映射 404——失败发生在分片生命周期,VersionMap 根本没被摸到。

别把三条「closed」混成一条。本地 POST /idx/_close 之后再 GET,得到的是 cluster block:FORBIDDEN/4/index closed、HTTP 403(定义在 MetadataIndexStateService.INDEX_CLOSED_BLOCK),协调节点就拦住了,根本到不了分片层;「GET 打到已 CLOSED 的分片对象」那个 404 通常出现在卸分片的竞态里,本地难以稳定复现,以源码为准;恢复/refresh 路径上的 IndexShardClosedException(operation only allowed when not closed)又是第三条,那是 verifyNotClosed,GET 主路径不走它。

你撞上的报什么 / 状态码谁抛的
索引 _close 后读写blocked by: [FORBIDDEN/4/index closed],403cluster block(到不了 IndexShard)
GET 打到 CLOSED 的分片对象CurrentState[CLOSED] operations only allowed when…,404readAllowed() → IllegalIndexShardStateException
恢复/refresh 撞上已关的分片operation only allowed when not closedverifyNotClosed → IndexShardClosedException

close() 本身的顺序也值得记一笔:先把状态打成 CLOSED(此后闸门立刻拒新请求),马上 getAndSetCurrentEngine(null) 摘掉引用,然后才在 executor 上可选地 flushAndClose()——第 14 课的 flush:commit + 裁 translog。Store 不在这段里关,由 IndexService.closeShard 另行放文件锁、关目录。三层管理(IndicesService → IndexService → IndexShard)不必画墙纸,记住两张 volatile 不可变 Map、copy-on-write 更新、读路径无锁就够了。

清理

思考题

1. 3 片索引,把某租户的 10 万篇文档全部用 routing=tenant-7 写入,docs 会怎么分布?好处和代价各是什么?

全落 1 片:片号由钥匙决定,不由文档决定——同一把钥匙永远同一片。好处:这个租户的 GET 和带钥匙的搜索都只打一片,省掉两片的开销。代价:热点(这一片的 CPU/磁盘/merge 独重,其余两片闲着);以及钥匙从「约定」变「合同」,GET/搜索忘带就扑空。routing 只有在高基数钥匙下才换来均衡。

2. 为什么 ES 不用一致性哈希,让「加片」在线生效?

取模换的是简单与可推演:任何客户端拿同一个公式就能算出文档在哪,不需要维护哈希环/虚拟槽的状态。一致性哈希把复杂度搬进集群状态,而且照样要搬数据——改 N 时旧文档全部错位这一点两种方案都逃不掉。ES 的选择是把「换除数」显式化:Final 拒绝在线改,要改就 reindex 到新索引,数据怎么搬、什么时候搬都由你说了算。

3. 一份正在 RECOVERING、还没 createEngine 的分片收到 GET,会发生什么?会抛 Lucene 的 AlreadyClosedException 吗?

readAllowed() 在 withEngine 之前抛 IllegalIndexShardStateException,消息是 CurrentState[RECOVERING] operations only allowed when shard state is one of [POST_RECOVERY, STARTED](404)。连 engine 引用都没碰——AlreadyClosedException 是另一条路:Engine 引用被摘掉后有人绕过闸门去 getEngine()。协调节点侧更常见的失败其实是这份拷贝还在 INITIALIZING、不进可路由集合,TransportSingleShardAction 换下一份或收成 NoShardAvailableActionException——失败发生在选片,不在 innerGet。

4. Engine 为什么不能在 IndexShard 构造函数里就 new 出来?三条恢复路径里哪条的不变量先破?

IndexWriter 要的是一份「已经合法」的 Lucene 目录,构造函数看不见目录的最终形态:EMPTY_STORE 此时还是空目录;PEER 可能正在收半份 segment,中途打开 IndexWriter 会看见残缺索引;EXISTING_STORE 要先选定 safe commit。而且恢复代码假定自己可以往 Store 写文件——prepareForIndexRecovery 里 assert currentEngine.get() == null 保护的正是「拷文件时不和已打开的 IndexWriter 抢同一份 Directory」。所以 createEngine 被钉死在 RECOVERING 且文件就绪之后。

陷阱

🕳 「_cat/shards 的 state 列就是分片的全部状态」:那是 ShardRoutingState,只有 4 个词;CREATED/RECOVERING/POST_RECOVERY 是 JVM 里的 IndexShardState,空索引上只有几十毫秒。replica 显示 UNASSIGNED 不是 CLOSED——本节点根本没有那个对象。
🕳 「routing 只是可选的性能提示」:写的时候带了 routing,读不带就是另一把钥匙:GET 算到别的片、found:false,搜索也会漏掉这篇。钥匙是合同不是建议;拿不准就别用,或者像实验 12 那样用 _routing.required 把合同显式化。
🕳 「索引 _close 后的报错 = 分片 CLOSED 的报错」:本地 _close 挡你的是 cluster block:403 FORBIDDEN/4/index closed,协调节点就拦住了;「GET 打到 CLOSED 分片对象」的 404(IllegalIndexShardStateException)是卸分片竞态里才会出现的另一条。都叫 close,不是同一个异常。
