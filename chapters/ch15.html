一篇文档住在哪个分片，分片又何时能服务请求？先用路由策略确定逻辑片号，再从集群路由表选择节点上的拷贝；这份拷贝的 IndexShard 还要经过恢复与状态闸门。本课把这三个问题逐一对照。

学习目标

  • 按本课索引条件算出 brown 的片号，用 _search_shards 对照；区分“不同键同片”与确定跨片的 GET 结果。
  • 对照无 routing 搜索、普通 GET 与写入，指出分片范围、拷贝选择和主副职责的区别；修改副本数并验证 Final 拒绝后原文档仍可读。
  • 从固定源码指出 Engine 在 RECOVERING 中打开、读闸门允许的两态；用 close/open 实验区分索引关闭、分片对象状态与删除。

15.1 文档、逻辑片与节点拷贝是三个层次

第 13 课把批量操作按片分组，第 14 课进入片内引擎。现在追问：为什么选这一片？索引保存映射、设置等逻辑元数据；主分片把文档空间分成若干部分，每个分片的本地拷贝拥有自己的 Store、Engine 与 Lucene 文件。普通可写拷贝独立管理 segment、translog 和合并。副本保存同一逻辑片的数据，可在故障后承担主分片职责；复制的是操作与数据一致性协议，不能推断主副 segment 文件永远逐字节相同。

逻辑片号不等于节点地址。例如片 0 可以从节点 A 迁到 B，也可以有 A 上的 primary 与 B 上的 replica。路由先决定是哪一组，集群路由表再告诉请求哪些拷贝在哪里、处于什么分配状态。协调是节点当前承担的职责，也可以与数据分片共处一台节点。单节点实验只能观察本地路径和未分配副本，不能替代多节点复制与故障转移验证。

15.2 一个取模公式，要先写出适用条件

本课显式新建 ES 9.4.0 的 standard 索引、3 个主分片，routing_partition_size=1，无 routing_path、无 resharding；文档显式给 ID。普通写入和 GET 有 routing 就用它，缺省才用 ID。这个条件下可以用：

key   = routing != null ? routing : id
hash  = Murmur3_x86_32(UTF-16LE(key), seed=0)
shard = Math.floorMod(hash, 3)

真正入口是 IndexRouting，旧网页贴出的 OperationRouting.generateShardId 伪源码并不对应本版本。Unpartitioned.shardId 选择钥匙，hashToShardId 按索引创建版本分支：达到 MOD_ROUTING_FUNCTION 的创建版本使用主片数取模；较旧索引使用 floorMod(hash, routingNumShards) / routingFactor。分区路由还引入 ID 的 offset，一把 routing 可覆盖多个片；带 routing_path 的策略也不同。运行节点升级到 9.4.0，不会自动把既有索引都变成本课路由策略。

策略选择 ↗；创建版本与公式 ↗；普通与分区策略 ↗。

哈希不是只写“murmur3”就能复现：ES 的字符串重载先把 Java char 按小端双字节排列，再调用种子 0 的 x86_32。旧动画套用 UTF-8 结果，错误地写成 hash(brown)=741580288。正确离线值是 998382972，3 片时落片 0；hash(brown-1)=-2007555306 也落片 0。不同字符串同片很常见；不能宣称错误键必然找不到，更不能把 String.hashCode 的规范结果说成随 JDK 版本任意变化。

字符串编码与哈希 ↗。本轮离线实现通过官方 7 个测试向量复核，A7/A8/A12 的两轮真实 API 返回与上述值一致。floorMod 保证负哈希得到非负片号；例如 tenant-7 的 -1321139497 % 3 = -1，而 floorMod(...,3)=2。

七步演算：从钥匙到节点上的拷贝

播放器逐步解释钥匙、编码、取模、查表和请求类别。两节点表是概念示例，最后一帧才回到实验的单节点条件。数字属于固定条件下的离线演算，不把动画当 ES 返回或远程复制证据。系统减少动态效果时保留手动步进。

15.3 GET 找一个片，普通搜索先选范围

GET 没有 routing 时按 ID 计算一个目标片。A4 把 brown-1 用 brown 写到片 0；A9 省略 routing，ID 自己也算到片 0，因而仍能命中。为看清跨片后果，A11 再把 route-0 用 brown 写到片 0；route-0 的缺省片是 2，A13 才稳定得到 404 found:false。A14 带回 brown 即可读到。routing 保存为元数据，但普通片内 ID 查找不会再校验请求 routing 字符串与存储值必须相等。

普通搜索不带 routing 会选择全部片，不会因为忘带而自动漏掉这篇。本例 A15 搜到两篇，候选范围为 3 片；A16 带 routing=route-0 缩到片 2，才得到 200 与零命中。_search_shards 展示候选组，本身不执行查询。非分区本例一把键选一个逻辑片，多把键可能重复同片。routing 只缩小片范围，片内还可能有其他租户，业务过滤与访问控制仍需另行表达。

有无 routing 的搜索范围 ↗。普通搜索默认开启 ARS，有响应、队列等排名输入时排序；无统计或并列也不承诺总选到最快拷贝。普通 GET 的调用传入空 collector / nodeCounts，保留随机化后的候选顺序，不能套用搜索的 ARS 结论。GET 与搜索输入 ↗；排名条件 ↗。

只读请求选择一份可用拷贝，写入先到 primary 再复制，职责不同。复制一致性不等于所有 reader 瞬时相同：搜索可见性还受各份刷新视图影响。副本未分配不是这次复制失败；在单节点、active=1 的本例，A4 可以成功，_shards.total=2 仍含配置要求的拷贝，而 successful=1, failed=0。这些字段要连同请求条件解释，不能从写成功反推存在另一份已同步副本。

15.4 Final 拒绝更新，原路由仍然有效

number_of_shards 为 Final，直接更新被拒；B4 实测 400 illegal_argument_exception，开放索引的入口文案包含 non dynamic setting(s) [[index.number_of_shards]]，并指出创建后不能修改；不是旧卡写死的 Final 检查文案。B5 检查仍为 3，B6 再读回原文档。假设随意改布局，部分键会改片，存量数据必须有对应搬迁与路由协议；不能说“所有键必变”“被拒后文档蒸发”。默认参数之外还有分区、创建版本与新布局条件；不同布局可按 split/shrink 的适用条件或 reindex 到目标索引，本课不演这些路径。

number_of_replicas 为 Dynamic，不参与本例的逻辑片计算；调整的是需要多少份拷贝。单数据节点不能把同片 primary 与 replica 都放自身：3 主片正常分配、要求 1 副本时本索引 yellow；B1 改 0 后 B2 等到 green；B7/B8 再恢复 1 并检查 yellow。分配与健康收敛异步，设置 acknowledged 不承诺同一瞬间所有观测已改变，其他索引也可让全局健康仍 yellow。

Final 与 Dynamic ↗；拒绝更新 ↗；同节点分配约束 ↗。

15.5 IndexShard 已存在，不等于 Engine 已打开

本地 IndexService.createShard 获取 ShardLock、准备 Store、构造 IndexShard；初始状态 CREATED，Engine 引用尚空。随后 markAsRecovering 进入 RECOVERING。普通路径的 innerOpenEngineAndTranslog 要求正处 RECOVERING，并检查尚无当前引擎，才创建与安装 Engine。这里解释一次普通创建过程，不把这条断言泛化成“整个对象一生绝不会替换引擎”。

EMPTY_STORE 先建立空索引文件与日志，EXISTING_STORE 准备可打开的本地提交；两者开 Engine 后再重放需要的日志。Peer 的文件型恢复先准备目标文件，再 prepareForTranslogOperations 打开目标 Engine，随后 phase2 发送历史操作；操作型 peer 恢复可以复用已有文件。旧文案把“文件和 operations 全先落盘，再开 Engine”写反了。恢复操作需要已有引擎应用，不能等全部应用完才创建它。

本地恢复顺序 ↗；peer 打开目标 Engine ↗；准备完成后 phase2 ↗。postRecovery 刷新并完成回调后进入 POST_RECOVERY；应用路由 active 时才转 STARTED。恢复后状态 ↗；路由激活 ↗。

集群 ShardRoutingState（CAT）与本地 IndexShard 的关系
UNASSIGNED没有分配给节点的该份拷贝；不是一个本地 CLOSED 状态
INITIALIZING通常经历 CREATED / RECOVERING / POST_RECOVERY
STARTED本地在应用 active 路由后进入 STARTED，不能视为跨层瞬时原子对照
RELOCATING源端通常仍服务；目标是另一份正在初始化的本地对象

CAT 的 state 来自 shard.state()。恢复 API 的 type 与 stage 又是恢复过程的枚举；三套状态不可互换。不承诺 CREATED 到 STARTED 只需几十毫秒。D6 看恢复类型与结果，不能从一次 CAT 采样证明 JVM 每次中间转移。

15.6 读闸门、索引关闭与删除分别发生什么？

innerGet 先调用 readAllowed，允许集为 POST_RECOVERY / STARTED；其他状态抛 IllegalIndexShardStateException，它的 HTTP 映射是 404。在协调路由层通常先选可用候选，可能换拷贝或在不可用时失败，所以不能用普通 REST GET 稳定触发某个 RECOVERING 本地对象。恢复重放与副本复制有独立写条件，也不能把“未 STARTED”一概说成任何写操作都不允许。

close 先设置 CLOSED，再摘掉 Engine 引用，随后在 executor 清理引擎与监听器；是否 flush 由调用条件决定。状态门控制新入口，不能推断所有已开始操作此刻都完成。IndexService 另行关闭 Store 与管理引用/锁。索引 _close 保留数据与元数据；实测 D2 的普通 GET 返回 400 index_closed_exception、reason=closed：SingleShardRequest 禁止闭合索引，具体索引解析在检查索引级 block 之前就拒绝。关闭 block 本身映射 403，但不能据此推断这个 GET 的实际错误。

D3/D4 重开与等待，D5 应能读回原文档：恢复创建新的本地服务对象，不是把原 CLOSED 对象直接退回 CREATED。最后点名 DELETE 才删除两索引的数据和设置。400 的索引关闭解析、404 的文档查无、404 的本地状态异常要同时按 reason、found 与触发层次辨认，不能只记数字。

思考题

1. brown 与 brown-1 不同，为什么缺省 GET 还能读到？

ES以UTF-16LE计算的两个哈希都对3取模为0。routing先选片，普通片内查找使用ID，不再要求请求routing与原元数据字符串相等。不同键同片可命中；route-0缺省去片2才构成确定404对照。

2. routing=tenant-7 就能隔离租户数据吗？

不能。普通非分区索引中它缩小搜索片范围，但其他键可以落同片；无routing搜索查全部片。同租户固定键可减少扇出，负载是否均衡还看键分布和单键体量。用业务字段过滤与实际权限机制表达隔离。

3. Final 更新被拒，为什么还要查设置和 GET？

验证400只拒绝本次请求，number_of_shards仍3、存量路由仍有效。随意换布局需要数据搬迁，但不是每个键都改片；split/shrink与reindex的条件和目标索引另行判断。

4. RECOVERING 能有 Engine 吗？能应用恢复操作吗？

能。文件准备后就在RECOVERING内打开引擎，本地随后重放日志，peer目标开Engine后接收phase2。readAllowed不接受RECOVERING，但恢复写按来源有独立检查；不能把读闸门泛化为禁止所有恢复写。

5. close 后 GET 的400，证明本地 readAllowed 执行了吗？

不能。本例具体索引解析抛index_closed_exception，早于索引级block检查和innerGet。关闭block的403、本地非法状态异常的404是不同层的错误；CAT四态、恢复stage、JVM五态分别观测。close保留数据，open恢复后可读回，DELETE才删除本课资源。

陷阱

🕳 只写 murmur3 就复制数字：编码、算法变体、种子和索引路由策略都要一致。本课字符串是UTF-16LE，不是UTF-8；负数用floorMod。运行版本也不能替代创建版本。
🕳 忘 routing 一概404或漏搜：GET键可同片；无routing普通搜索查全部片。required只拒缺失的文档请求，不校验键内容、不禁止无routing搜索，也不表达租户权限。
🕳 搜索ARS套到所有读取：普通GET未传排名统计；单节点只有primary不证明远程排名或副本读取视图一致。写入的primary职责另行判断。
🕳 CAT STARTED就是全部生命周期：CAT来自路由四态，本地五态与恢复stage另看。Engine在RECOVERING中已可创建，恢复操作可应用；关闭分支可提前发生。
