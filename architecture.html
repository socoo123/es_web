全景图:一次请求的旅程

从客户端进来,先过第二篇的入口层,然后按目的分流:写一篇文档走左路(第三篇),搜一次走右路(第四篇);两条路都汇到 Lucene 的 segment 上。集群平面(第五篇)在底下托着;地基(第一篇)与横切能力(第六篇)各占一行。

四条走读路线

不必按课号线性读。挑一条你想回答的问题,顺着箭头走;每一站就是一课。

路线 A · 写一篇文档,它经历了什么?

L06 REST 入口 → L07 动作框架 → L08 write 线程池 → L13 bulk 按条分组 → L15 选目标分片 → L12 摄取管道改 JSON → L11 映射定型 → L14 进 buffer + translog → L10 立刻 GET 验证

为什么这样排:bulk 在协调端就按 routing 把每条文档分好组(L13→L15);真正的预处理与映射定型发生在目标节点(L12、L11);写进引擎后 GET 立刻可读,但要等 refresh 才可搜(L10 收尾正好验证这件事)。跨节点转发才走传输层(L09)。

路线 B · 搜一次 _search,发生了什么?

L06 REST 入口 → L07 TransportSearchAction → L08 search 线程池 → L16 Query Then Fetch 两阶段 → L17 搜索上下文 → L18 DSL → token 查询 → L20 BM25 打分 → L19 聚合归并 → L27 换一门语言:ES|QL

名次在 Query 阶段就定死了(L20),Fetch 只是搬正文;聚合走「本地先算一层,协调端再归并」(L19);读到的永远是已 refresh 的 EXTERNAL 快照——与路线 A 的结尾呼应。

路线 C · 一个节点挂了,集群怎么自愈?

L21 集群状态快照 → L22 重新选主 → L23 重算分片分配 → L24 副本恢复/快照找回 → L25 期间别把集群打爆:熔断

真理之源只有一份集群状态(L21);谁能写它由选举决定(L22);分片去哪儿由 decider 链投票(L23);数据搬家靠 peer recovery,对账能 reuse 的 segment、只补缺失的 ops(L24)。

路线 D · 这个系统怎么搭起来的?

L03 节点启动 → L04 插件体系 → L05 配置框架 → L09 传输层 → L26 脚本引擎 → L29 安全机制 → L30 全链回放收官

从 main() 到 ready(L03),一切都是插件(L04)、一切都有类型安全的配置(L05);之后按需补横切能力。L30 把 29 课串到一次 POST _search 上,是全站的收官动画。

💡 用法建议:先 bash docker/start.sh 把本地 9.4.0 跑起来,再挑一条路线开走;每课的实验都能在控制台直接执行,预测→操作→对照。读完任何一条路线,回课程总览看下一组。
